## 比較表は暗記ではなく判断の順番に使う

似た機能は、文法の違いだけを並べても選べません。まず「どんな状態を表したいか」「誰が更新するか」「どんな操作が必要か」を決めます。たとえばListが便利だから全てListにするのではなく、位置で読むのか、IDで探すのか、重複をなくすのかを先に考えます。

ここでは各レッスンを横断して選び方を整理します。最初から全てを暗記する必要はありません。一つを選んだ理由と、選ばなかったものが今回の目的と違う理由を説明できるようにします。

## class・struct・record

classは参照型の定義、structは値型の定義です。recordは値に基づく等値性などを提供する宣言の仕組みで、`record`は通常record class、`record struct`は値型です。recordを第三のメモリ分類と考えないことが重要です。

| 選択肢 | 代入や比較の中心 | 選ぶ例 | 特に確認すること |
|---|---|---|---|
| class | 参照をコピー。既定の等値性は参照の同一性 | 状態を持ち操作で変化する在庫 | 更新可能な入口と共有範囲 |
| struct | 値をコピー | 小さな値のまとまり | 大きな値のコピー、内部の参照、既定値 |
| record class | 参照型。値に基づく等値性を生成 | 入力データ、変更前後を別の値として扱うモデル | withは深いコピーではない |
| record struct | 値型。値に基づく等値性を生成 | 値の組で等値比較やコピーを使いたい場面 | 参照メンバーの共有は残る |

```csharp
var first = new Position(2, 3);
var moved = first with { X = 5 };
Console.WriteLine($"{first.X},{first.Y}");
Console.WriteLine($"{moved.X},{moved.Y}");
Console.WriteLine(first == new Position(2, 3));
readonly record struct Position(int X, int Y);
```

期待される出力は`2,3`、`5,3`、Trueです。firstの値を元にXだけを変えた別の値を作っています。この例のメンバーはintなので内部の変更可能な実体の共有はありません。Listをメンバーへ追加すると、同じ結論をそのまま適用できません。

## 配列・List・Dictionary・HashSet

| 欲しい操作 | 候補 | 例 | 不向きな選び方 |
|---|---|---|---|
| 件数固定で位置を指定 | 配列 | 12か月分の値 | 頻繁な追加のたびに手作業で拡張 |
| 順序付きで追加・削除 | List<T> | APIから取得した商品の一覧 | ID検索を必ず高速にできると思う |
| キーから値を参照 | Dictionary<TKey,TValue> | 商品IDから商品を取得 | 同じキーを複数登録する前提 |
| 要素の存在や重複排除 | HashSet<T> | 処理済みIDの集合 | 順序や添字の保証を期待する |

```csharp
var names = new Dictionary<int, string>();
names.Add(10, "ノート");
names.Add(20, "ペン");
if (names.TryGetValue(20, out string? name))
{
    Console.WriteLine(name);
}
var processed = new HashSet<int>();
Console.WriteLine(processed.Add(20));
Console.WriteLine(processed.Add(20));
```

期待される出力はペン、True、Falseです。Dictionaryは20というキーから値を取り出します。HashSetは最初の20を追加し、二回目は既にあるので追加しません。順序を付けて全件表示することと、識別子で検索することを別の要件として考えます。

## IEnumerable・ICollection・List

IEnumerableは順に取り出す契約、ICollectionは件数や追加・削除なども表す契約、Listは具体的な実装です。呼び出し側へ不要な操作を見せないため、必要な契約だけを引数にすることがあります。ただしインターフェイスの型に変えただけで、実体の不変性や計算量を保証できるわけではありません。

| 型 | 利用側が想定する操作 | 選ぶ目安 | 注意 |
|---|---|---|---|
| IEnumerable<T> | 順に読む | 一回列挙する表示や集計 | 遅延計算、繰り返し列挙の費用 |
| ICollection<T> | 件数や追加・削除など | コレクションとして操作する契約が必要 | 変更可能かは実装とIsReadOnly等の契約も確認 |
| IReadOnlyList<T> | 件数と添字で読む | 読み取り用の一覧を渡す | 元の実体まで不変になるわけではない |
| List<T> | 添字、追加、削除など | 具体的な可変一覧を所有する | 外部へ渡すと意図せぬ更新を許し得る |

同じIEnumerableを二度列挙すると、遅延処理なら二度計算する場合があります。結果を固定したいときはToListなどで具象化しますが、メモリ使用量と、どの時点の結果を保存するかも判断します。「何でもToList」とするのではなく、必要な境界で行います。

## abstract classとinterface

abstract classは共通の状態や実装を持てる基底クラスです。interfaceは利用する側に必要な契約を表します。現代のinterfaceには既定実装などの機能もありますが、初学段階では「呼び出し側が必要な操作を、具体的な部品から分ける」目的を先に理解します。

| 判断 | abstract class | interface |
|---|---|---|
| 共通の状態を持つ基底が必要 | 選択肢になる | 通常のインスタンスフィールドを持つ基底としては使わない |
| 無関係な型に同じ操作を要求 | 継承の関係を慎重に検討 | 操作の契約として使いやすい |
| 複数の役割を同時に表す | クラスの基底は一つ | 複数の契約を実装できる |
| テストで差し替える | 仮想メソッドなどを利用する場合もある | 通知や時計などの境界を分ける候補 |

通知先の差し替えならINotifierという契約を考えます。在庫に名称や数量の共通実装が必要だからといって、無関係な通知処理まで同じ基底へ入れません。部品を必要とする関係は継承でなく、別の部品を受け取る組み合わせでも表せます。

## const・readonly・init・required

| 機能 | 主に何を制限・要求するか | 選ぶ例 | 保証しないこと |
|---|---|---|---|
| const | コンパイル時に確定する定数 | 固定された数学的な値など | 配置先で変わる設定の読み込み |
| readonlyフィールド | 許された初期化時など以外の再代入 | 生成時に受け取った依存部品を保持 | 参照先のList内部の変更禁止 |
| init | 初期化段階での設定 | 作成後は値を付け替えないデータ | 参照先を含めた完全な不変性 |
| required | 作成時に指定が必要なメンバー | 必要項目の設定忘れを減らす | 空白や負数などの業務的妥当性 |

`required string Name`へ空文字を指定しても、空白名禁止という業務規則までは自動で満たされません。`readonly List<int>`にもAddできる場合があります。記号が保証する範囲を、期待する業務条件より広く解釈しないようにします。

## 通常の値渡し・ref・out・in

C#の通常の引数渡しは値渡しです。参照型でも通常は参照の値をコピーします。refは変数そのものを参照で渡し、outは呼び出し先が値を設定する契約、inは呼び出し先から読み取り専用の参照として扱う契約です。

| 指定 | 呼び出し前の初期化 | メソッド側からの代入 | 選ぶ例 |
|---|---|---|---|
| 通常 | 入力値が必要 | パラメーターへの代入は呼び出し元変数を付け替えない | 通常の計算の入力 |
| ref | 必要 | 呼び出し元の変数へ反映 | 明確な理由がある変数の更新 |
| out | 事前の値は不要 | 正常に戻る前に設定が必要 | TryParseの変換結果 |
| in | 入力値を使う | パラメーター経由の再代入を制限 | 大きな値型を渡す設計の選択肢 |

```csharp
int value = 3;
Replace(ref value);
Console.WriteLine(value);
static void Replace(ref int target)
{
    target = 8;
}
```

期待される出力は8です。targetへの代入が、呼び出し元のvalueへ反映されます。通常の計算なら戻り値で新しい値を返す方が読みやすい場合もあります。inを付ければ必ず高速という保証はなく、必要なコピーや最適化を含め実測で判断します。また参照型をinで渡しても、参照先の内部状態が自動的に不変になるわけではありません。

## Task・Thread・同期・非同期

| 言葉 | 表すもの | 選ぶときの問い |
|---|---|---|
| Thread | 命令を進める実行の流れ | 実行主体を直接管理する必要が本当にあるか |
| Task | 完了、失敗、中止、結果を表す処理 | 誰が完了を待ち、例外を受け取るか |
| 同期 | 呼び出しが戻るまで次へ進まない形 | 処理が短く、待ちで問題が起きないか |
| 非同期 | 完了を後で受け取れる形 | 外部I/Oの待ち時間があるか |
| 並列 | 複数処理を同時に実行 | CPU計算を独立して分割できるか |

Taskを作った数だけ専用Threadが増えるとは限りません。asyncを付けてもCPU計算が自動で速くなるわけではありません。HTTP・DB・ファイルなどのI/Oでは、まずライブラリの非同期APIを利用します。詳しい進行は[非同期の時間軸](async-timeline.html)で追います。

## HTTPメソッドは状態への意図で選ぶ

| メソッド | 主な意図 | 例 | 繰り返しへの基本的な観点 |
|---|---|---|---|
| GET | 表現を取得 | 一覧や一件を読む | 取得が業務更新にならないようにする |
| POST | 対象へ処理を依頼 | 新規作成 | 同じ要求で二重作成になり得る |
| PUT | 対象の表現を指定して作成・置換 | 完了状態リソースを指定値にする | 同じ指定による意図する効果を一定にする |
| PATCH | 変更内容を適用 | 一部項目の更新 | 変更の形式によって冪等性が異なる |
| DELETE | 対象との関連を削除 | 一件を削除 | 二回目のコードが違っても削除後の状態は同じにできる |

HTTPの契約上の冪等性は「応答本文やステータスが毎回全く同じ」という意味ではありません。既に削除したものへの二回目のDELETEが404でも、意図する対象の状態は削除済みです。PATCHも「+1」と「値を5にする」では再適用の効果が違います。通信失敗時の再送を考え、操作と状態の関係を決めます。

## 選択を説明する練習

商品IDで名前を探し、二重処理したIDを記録し、画面に渡す一覧を作る場合を考えます。解答の一例は、ID検索にDictionary、処理済み確認にHashSet、表示する順序付き結果にListです。一つの構造だけで全てを済ませる必要はありません。

同様に「注文時刻をテストで固定したい」なら、時計の部品を外から渡す設計を検討します。その契約がinterfaceである必要があるか、単純な値の引数で十分かを規模に合わせて判断します。比較表の結論をそのまま当てはめず、責務・共有・変更・テストの要件を一つずつ説明します。
