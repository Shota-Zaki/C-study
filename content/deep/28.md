## HTTPは相手へ要求を送り、応答を受ける約束

HTTPは、クライアントが要求を送り、サーバーが応答を返すための通信の約束です。クライアントは要求する側、サーバーは要求を受けて機能を提供する側です。Web APIはHTTPなどを通して、他のプログラムからデータや機能を使えるようにする窓口です。

リクエストには、どこへ送るかというURL、何をしたいかというメソッド、追加情報のヘッダー、必要に応じた本文があります。レスポンスには結果を示すステータスコード、ヘッダー、本文があります。JSONは本文を表現する形式の一つで、HTTPそのものと同じではありません。

```flow
クライアント | URL・メソッド・ヘッダー・本文を組み立てる
通信 | DNS解決や接続、必要ならTLSで暗号化
サーバー | 経路を選び、入力を検証し処理する
レスポンス | ステータス・ヘッダー・本文を返す
クライアント | 成功判定、本文の変換、業務利用
```

DNSは名前から通信先のアドレスを調べる仕組み、TLSは通信を暗号化し相手を確認するための仕組みです。HTTPSはTLSで保護されたHTTPです。本番の秘密情報を平文のHTTPで送らないこと、証明書検証を無効にしてエラーを回避しないことが基本です。

## URLとHTTPメソッドを読む

`https://example.invalid/items/3?include=detail`という例では、httpsが方式、example.invalidがホスト名、/items/3がパス、include=detailがクエリです。example.invalidは説明用で、接続できるサービスとして使いません。フラグメントの#以降は通常HTTPリクエストの対象情報としてサーバーへ送られません。

| メソッド | 主な意味 | 選ぶ例 | 繰り返しの注意 |
|---|---|---|---|
| GET | 表現を取得 | 商品一覧を読む | 状態変更を目的にしない |
| POST | 資源に処理を依頼 | 新しい注文を作る | 再送で重複し得る |
| PUT | 指定先の表現を置換 | ID指定で全項目を更新 | 同じ要求の意図は冪等 |
| PATCH | 部分的な変更を適用 | 完了状態だけ変更 | 内容次第で冪等とは限らない |
| DELETE | 対象を削除 | 指定IDを削除 | 意図は冪等だが応答は変わり得る |

冪等とは、同じ操作を何度行っても、意図した最終状態への効果が一回と同じになる性質です。毎回同じステータスを返すという意味ではありません。再試行を設計するとき、通信失敗でも相手では処理済みの可能性があるため、この性質が重要になります。

## 最小例：通信処理を差し替えて順序を学ぶ

外部サイトへ依存せず、HttpClientが送った要求と返ってきた応答を学ぶ例です。HttpMessageHandlerはHttpClientの送信を受け持つ部品です。ここでは本物のネットワークの代わりに決まった応答を返します。実際のDNS・TLS・相手サーバーを検証する例ではありません。

```csharp
using System.Net;
using System.Net.Http.Json;
using System.Text;

using var client = new HttpClient(new DemoHandler());
using HttpResponseMessage response = await client.GetAsync("https://example.invalid/items/3");
Console.WriteLine((int)response.StatusCode);
response.EnsureSuccessStatusCode();
Item? item = await response.Content.ReadFromJsonAsync<Item>();
Console.WriteLine(item?.Name ?? "データなし");

public record Item(int Id, string Name);

public sealed class DemoHandler : HttpMessageHandler
{
    protected override Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken cancellationToken)
    {
        Console.WriteLine($"要求:{request.Method} {request.RequestUri?.AbsolutePath}");
        var response = new HttpResponseMessage(HttpStatusCode.OK)
        {
            Content = new StringContent("{\"id\":3,\"name\":\"Note\"}", Encoding.UTF8, "application/json")
        };
        return Task.FromResult(response);
    }
}
```

期待出力は要求:GET /items/3、200、Noteです。GetAsyncはTask<HttpResponseMessage>を返し、awaitで応答を受け取ります。StatusCodeはHTTPの結果、ReadFromJsonAsyncはJSONを型へ変換する処理です。usingで応答を解放します。Contentは応答の本文を表す部品です。

## 成功の段階を四つに分ける

| 段階 | 成功したこと | まだ保証しないこと |
|---|---|---|
| 接続・応答を受信 | 相手から応答を受け取れた | HTTPが成功状態とは限らない |
| HTTP 2xx | HTTP上の成功として返った | 本文が期待するJSONとは限らない |
| JSON変換 | 対象型へ変換できた | 名前や数量が業務上有効とは限らない |
| 業務検証 | 利用条件を満たした | 次の保存などの成功まで保証しない |

EnsureSuccessStatusCodeは2xx以外で例外を投げる補助です。404などを通常の分岐として扱うAPIでは、先にStatusCodeを見て意味を判断する方法が向いています。全ての失敗を同じ「通信できません」にまとめると、相手の正常な404とネットワーク障害を区別できません。

## 間違い：404の本文を成功DTOへ読む

DTOは、通信などの境界で受け渡すデータの形をまとめた型です。サーバーがエラー時に別形式のJSONやHTMLを返すことがあります。成功用のDTOへ無条件に逆シリアル化すると、JsonExceptionが発生したり、空のプロパティを持つ値ができたりします。

```csharp-error
using System.Net;
using System.Net.Http.Json;
using System.Text;

using var response = new HttpResponseMessage(HttpStatusCode.NotFound)
{
    Content = new StringContent("not found", Encoding.UTF8, "text/plain")
};
Item? item = await response.Content.ReadFromJsonAsync<Item>();
Console.WriteLine(item?.Name);

public record Item(int Id, string Name);
```

この本文は成功用JSONではありません。確認するのはJSONの型だけではなく、StatusCode、Content-Type、実際の本文です。修正では404を先に分岐します。

```csharp
using System.Net;
using System.Net.Http.Json;
using System.Text;

using var response = new HttpResponseMessage(HttpStatusCode.NotFound)
{
    Content = new StringContent("not found", Encoding.UTF8, "text/plain")
};
if (response.StatusCode == HttpStatusCode.NotFound)
{
    Console.WriteLine("対象がありません");
}
else
{
    response.EnsureSuccessStatusCode();
    Item? item = await response.Content.ReadFromJsonAsync<Item>();
    Console.WriteLine(item?.Name ?? "データなし");
}

public record Item(int Id, string Name);
```

期待出力は対象がありませんです。失敗本文に秘密情報が含まれる場合があるため、無制限にそのまま利用者へ表示したりログへ残したりしないようにします。

## HttpClientを毎回使い捨てにしない

HttpClientの背後には接続を再利用するプールがあります。短い要求のたびに生成・破棄すると、接続資源の消費や効率低下につながる場合があります。長く使うクライアントに接続寿命を設定する方法や、IHttpClientFactoryを利用してハンドラーを管理する方法を選びます。

上の自己完結したコンソール例では、アプリ全体で一回使って終了するためusingで所有を明示しています。Webサーバーの各リクエスト処理で同じようにnew HttpClientして使い捨てる設計へ、そのまま拡大しないでください。第31レッスンのDIと組み合わせると、クライアントの設定・寿命・用途をまとめられます。

## 実際のHTTP呼び出しで加えるもの

タイムアウトは一定時間以上かかった処理を打ち切るための制限、キャンセルは利用者や呼び出し元からの中止要求です。HttpClientへTokenを渡し、必要な時間制限も設けます。大量の応答を読む場合はサイズやストリームの扱いを設計します。外部入力から任意のURLへアクセスさせる機能は、内部ネットワークへの意図しないアクセスにつながるため、許可する送信先を管理します。

失敗した要求を再試行するとき、POSTの注文が相手で既に作成されているかもしれません。再試行回数だけでなく、重複を防ぐキーなどAPI側の契約を確認します。GETだから常に無条件再試行、というより、時間・回数・相手の制限を含めて設計します。

## 3段階の練習

**基礎**：DemoHandlerの返すnameをPenへ変え、期待表示がPenになる理由を説明します。変えるのはJSON本文です。URLのパスを変えただけでハンドラーの固定データが自動で変わるわけではありません。

**標準**：404なら「対象なし」、200なら名前を表示する分岐を作ります。StatusCodeの確認をJSON変換より前に置きます。本文がJSONとして壊れている200も別の失敗ケースとして考えます。

**応用**：キャンセルTokenを受け取る取得メソッドを作り、GetAsyncとReadFromJsonAsyncへ伝えます。通信相手が応答しない、404、JSON不正、業務データ不正をそれぞれどこで区別するか説明します。ページ上の下書きでは動作は確認されないため、手元のSDKとテスト用ハンドラーで確認します。
