## 処理そのものを受け渡す理由

メソッドの引数へ数値や文字列を渡すことは既に学びました。今度は「どの計算をするか」も渡します。デリゲートは、引数と戻り値の形が一致するメソッドを呼び出すための型です。ボタンが押された後の処理、データを残す条件、並べ替えの比較など、共通の手順に差し替え可能な処理を組み込むために使います。

ラムダ式はその場で小さな関数を記述する構文です。イベントは、出来事が発生したことを通知し、登録された処理を呼ぶ仕組みです。この三つは同義語ではありません。「どんな処理を渡せるか」がデリゲート、「処理をどう書くか」がラムダ式、「誰が通知を発生させてよいか」を管理するのがイベントです。

## 最小例：名前のあるメソッドから始める

```csharp
Func<int, int> operation = Double;
int result = operation(4);
Console.WriteLine(result);

static int Double(int value)
{
    return value * 2;
}
```

期待出力は8です。Func<int, int>の最後の型引数は戻り値、それより前は引数です。この場合「intを一つ受け取り、intを返す処理」です。Doubleの後ろに()を付けずに代入している点が重要です。ここではDoubleを実行せず、後から呼べるものとして渡しています。operation(4)で初めて4を渡して呼び出します。

```flow
① operationを初期化 | Doubleを呼び出せるデリゲートを保持
② operation(4) | Doubleのvalueに4を渡す
③ return value * 2 | 8を返す
④ resultに受け取る | Consoleへ8を表示
```

Double(4)の戻り値8をデリゲートへ代入することはできません。処理と処理結果は別の種類の値です。

## ラムダ式へ置き換える

```csharp
Func<int, int> operation = value => value * 2;
Console.WriteLine(operation(4));

Func<int, int, int> add = (left, right) => left + right;
Console.WriteLine(add(3, 5));

Action<string> report = message => Console.WriteLine(message);
report("集計完了");
```

期待出力は8、8、集計完了です。=>の左は受け取る引数、右は計算する式です。引数が二つなら括弧で囲みます。Action<string>はstringを受け取って値を返さない処理です。「戻り値がない」ことを表すvoidは、結果を使わず表示などの作業を行うメソッドに使います。

複数の文が必要な場合は`value => { int doubled = value * 2; return doubled; }`のように波括弧とreturnを書きます。短く書くこと自体が目的ではありません。処理が長くなったら、目的が分かる名前のメソッドへ分けるほうが読みやすくなります。

| 書き方 | 引数 | 戻り値 | 選ぶ場面 |
|---|---|---|---|
| Action | なし | なし | 完了後の通知処理 |
| Action<string> | 文字列 | なし | メッセージを表示・記録 |
| Func<int, bool> | 整数 | 真偽値 | 数値を残す条件 |
| Func<int, string> | 整数 | 文字列 | 数値を表示用文字列へ変換 |

## 実用例：ループの手順と条件を分ける

```csharp
int[] scores = { 40, 70, 85 };
Console.WriteLine(CountMatching(scores, score => score >= 60));
Console.WriteLine(CountMatching(scores, score => score >= 80));

static int CountMatching(int[] values, Func<int, bool> condition)
{
    int count = 0;
    foreach (int value in values)
    {
        if (condition(value))
        {
            count++;
        }
    }
    return count;
}
```

期待出力は2、1です。CountMatchingは「配列を順に見て、条件がtrueなら数える」という共通の手順だけを持ちます。60以上か80以上かは呼び出す側が決めます。condition(value)はラムダ式へ各得点を渡す呼び出しです。次のレッスンのWhereも、各要素を残すかどうかを判定する処理を受け取ります。

| 1回目の要素 | conditionの結果 | countの前→後 |
|---:|---|---|
| 40 | false | 0→0 |
| 70 | true | 0→1 |
| 85 | true | 1→2 |

## 外側の変数を使うと何が保存されるか

クロージャーとは、関数が外側の変数を後からも使える仕組みです。単に「作った時点の値を必ずコピーする」と覚えてはいけません。次の例では同じlimit変数を参照するため、呼び出す時点の値が使われます。

```csharp
int limit = 60;
Func<int, bool> isPassing = score => score >= limit;
Console.WriteLine(isPassing(70));
limit = 80;
Console.WriteLine(isPassing(70));
```

期待出力はTrue、Falseです。最初は70>=60、次は70>=80です。コンパイラーは必要に応じて、外側の変数を後から参照できる保持用のオブジェクトなどを生成します。具体的な生成形状は実装に依存します。重要なのは、元のメソッドの呼び出しが終わっても、デリゲートから使われる変数の寿命が延びる場合があることです。

## 間違い：forの変数をそのまま覚えさせる

次は構文エラーではありませんが、0、1、2を表示する目的には合いません。

```csharp
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
{
    actions.Add(() => Console.WriteLine(i));
}
foreach (Action action in actions)
{
    action();
}
```

期待される観察結果は3、3、3です。ループ中に表示しているのではなく、同じi変数を参照する処理を三つ保存しています。呼び出す頃にはiが3です。確認する場所はラムダ式の作成位置と、実際に呼び出す位置です。各回の値を残すなら、その回ごとの変数を作ります。

```csharp
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
{
    int captured = i;
    actions.Add(() => Console.WriteLine(captured));
}
foreach (Action action in actions)
{
    action();
}
```

修正後の期待出力は0、1、2です。capturedはループ本体に入るたびに別の変数になります。問題はラムダ式が遅いことではなく、何を共有しているかです。

## イベント：通知する側と受け取る側を分ける

```csharp
var stock = new Stock();
Action<int> handler = remaining => Console.WriteLine($"残り:{remaining}");
stock.Changed += handler;
stock.TakeOne();
stock.Changed -= handler;
stock.TakeOne();
Console.WriteLine($"最終:{stock.Count}");

public sealed class Stock
{
    public int Count { get; private set; } = 3;
    public event Action<int>? Changed;

    public void TakeOne()
    {
        if (Count == 0) return;
        Count--;
        Changed?.Invoke(Count);
    }
}
```

期待出力は残り:2、最終:1です。+=は購読、つまり通知を受ける処理の登録です。-=は登録解除です。Changed?.Invokeは購読者がいれば呼び出し、いなければ呼び出しません。eventを宣言した型の外からは、通常そのイベントへ直接値を代入したり通知を発生させたりできません。Stockが状態を変更した後だけ通知する、という管理ができます。

通常のデリゲート呼び出しは呼び出し元のスレッドで同期的に行われます。スレッドとはCPU上で処理を進める実行の流れです。eventを付けても自動で別のスレッドにはなりません。登録された処理が例外を投げると、そのまま呼び出し元へ伝わり、後続の処理が呼ばれないことがあります。「通知は必ず安全」という前提を置かないでください。

## 間違い：解除するとき別のラムダ式を書く

`stock.Changed += n => Console.WriteLine(n);`の後に見た目が同じラムダ式で-=しても、同じデリゲートとして解除できるとは限りません。上の完成例のようにhandler変数へ保持して同じ登録を解除します。長期間存在する通知元が購読先を保持し続けると、不要になった画面などがGCで回収されない原因になります。

現段階では「通知元は購読処理への参照を持つ」「必要がなくなったら購読を解除する」を理解すれば十分です。イベントを非同期にする設計や複数スレッド間の通知は、Taskとキャンセルを学んでから扱います。

## 3段階の練習と読み直す場所

**基礎**：Func<int, int>で3倍にする処理を作り、入力4に対して12を表示してください。ヒントは`n => n * 3`です。名前付きメソッドを代入する別解も同じ結果になります。戻り値12をデリゲートへ代入する間違いに注意します。

**標準**：CountMatchingを使って{2,5,8,11}の偶数を数えてください。条件は`n => n % 2 == 0`、期待結果は2です。%は割った余りです。条件の中でcountを更新せず、true/falseだけを返すと役割が明確になります。

**応用**：Stockへ2個以下になったときだけ警告する購読者を追加してください。通知元は全ての変更を通知し、購読者で`if (remaining <= 2)`を判断する解答が考えられます。通知元に画面表示を直接書かないことで、後から記録用の購読者を追加できます。購読解除後に警告が出ないことも、手元のSDKで確かめます。
