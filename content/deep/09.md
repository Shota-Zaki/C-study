## クラスは「関連する状態と操作を、一つの型へまとめる」

商品の名前、価格、在庫を別々の変数で管理すると、二つ目の商品を追加するときに組み合わせを間違えやすくなります。クラスは、関連する値と操作を一つの型として定義します。型は値の種類と利用可能な操作の規則です。商品型なら、商品ごとに保持する状態と、その状態をどう変更できるかをまとめます。

クラスの宣言は型の定義であって、個々の商品のデータではありません。`new Product(...)`で実行中に作られた具体的な一つをインスタンス、またはオブジェクトと呼びます。同じProductクラスから、ノートの実体とペンの実体を別々に作れます。クラスを「設計図」と説明することはありますが、C#では実際に型情報や利用できるメンバーを定義している、と結び付けて理解します。

メンバーは型の構成要素です。フィールドは状態を保存する場所、プロパティは値の読み書きを公開する窓口、メソッドは名前の付いた操作です。コンストラクターは生成時に初期状態を整える処理です。プロパティの内部的な仕組みは次のLesson 10で扱い、ここでは`get`だけなら外から値を読み取れる、と読みます。

## 最小例：二つの実体を作る

```csharp
var notebook = new Product("ノート", 200);
var pen = new Product("ペン", 100);
Console.WriteLine($"{notebook.Name}: {notebook.Price}");
Console.WriteLine($"{pen.Name}: {pen.Price}");

public class Product
{
    public string Name { get; }
    public int Price { get; }

    public Product(string name, int price)
    {
        Name = name;
        Price = price;
    }
}
```

期待される出力：

```text
ノート: 200
ペン: 100
```

`new`はここではクラスの新しい実体を作る式です。`Product(...)`はクラス名と同じ名前のコンストラクターへ引数を渡します。コンストラクターには戻り値の型を書きません。`public`は外から利用できることを示すアクセス修飾子です。`Name`と`Price`は各インスタンスが別々の値を持ちます。

```flow
Productの型定義 | 名前・価格・初期化の規則
new Product("ノート", 200) | 実体Aを作り初期化
notebook | 実体Aへの参照を受け取る
new Product("ペン", 100) | 実体Bを作り初期化
pen | 実体Bへの参照を受け取る
```

| 処理の位置 | notebook | pen | 完了している初期化 |
|---|---|---|---|
| 開始前 | 未宣言 | 未宣言 | なし |
| 最初のnew後 | Aを参照 | 未宣言 | A: ノート、200 |
| 二つ目のnew後 | Aを参照 | Bを参照 | B: ペン、100 |
| 表示後 | Aを参照 | Bを参照 | 状態は変わらない |

notebook変数の中にクラスの全コードがコピーされるわけではありません。クラスは参照型なので、変数は実体への参照を保持します。参照とは実体をたどるための値です。同じ参照をコピーすると実体を共有し、newを二回使えば別々の実体を作ります。

## 生成時の内部で起きること

通常のクラス生成では、インスタンスの保存領域が用意され、フィールドは既定値で初期化され、フィールド初期化子やコンストラクターによって初期状態が整えられます。`int`の既定値は0、参照型の既定値はnullです。ローカル変数を未代入のまま読めない規則と、フィールドの既定値は混同しません。

継承がある場合には基底側のコンストラクターとの連鎖も関わります。基底・派生のフィールド初期化子の順番と、コンストラクター本体が走る順番は単純な一つの「上から下」ではありません。いまは継承のないクラスで観察し、Lesson 11で基底コンストラクター本体が先に完了する流れを扱います。初期化途中で上書き可能なメソッドを呼ぶ設計は避けます。

GCは、使われなくなったマネージドオブジェクトのメモリを再利用可能にする仕組みです。オブジェクトは一般にマネージドヒープ上で管理されますが、JITが配置や割り当てを最適化する場合もあります。クラスを理解する中心は物理的な箱の場所ではなく、実体の同一性と参照共有です。newしたらファイルなどの外部資源もGCがすぐ解放する、とは考えません。

## コンストラクターで有効な状態を作る

初期値が不足したオブジェクトを作り、後から必要な値を順番に設定する設計では、途中の不完全な状態が利用される恐れがあります。必須情報をコンストラクターで受け取り、条件に合わないなら作成を拒否すると、生成に成功した実体の前提を明確にできます。

```csharp
var product = new Product("ノート", 200);
Console.WriteLine(product.Name);

public class Product
{
    public string Name { get; }
    public int Price { get; }

    public Product(string name, int price)
    {
        if (string.IsNullOrWhiteSpace(name))
            throw new ArgumentException("商品名が必要です", nameof(name));
        if (price < 0)
            throw new ArgumentOutOfRangeException(nameof(price));
        Name = name.Trim();
        Price = price;
    }
}
```

期待出力は`ノート`です。例外は処理を通常どおり進められないことを通知する仕組みです。`throw`は例外を発生させ、`ArgumentException`は引数の問題を表します。`nameof(name)`はコード上の名前`name`を文字列として取得し、名前変更時の修正漏れを減らします。例外の受け取りはLesson 16で扱います。

価格-1や空白だけの名前は、この仕様では生成を拒否します。nullableの型注釈だけでは空白や負数を検証できません。メソッドの契約として必要な範囲・状態は、コードで検証する必要があります。実務の業務モデルも「フィールドをまとめるだけ」でなく、不正な状態が入り込む経路を減らす役割を持ちます。

## インスタンスとstaticを分ける

インスタンスメンバーは個々の実体に属します。staticメンバーは型に属し、特定の実体を指定せず利用します。staticフィールドはその型で共有されるため、各商品の価格をstaticへすると、商品ごとの価格を表せなくなります。

```csharp
var first = new Counter();
var second = new Counter();
first.Increment();
first.Increment();
second.Increment();
Console.WriteLine($"first={first.Value}, second={second.Value}");
Console.WriteLine($"全体={Counter.TotalIncrements}");

public class Counter
{
    public int Value { get; private set; }
    public static int TotalIncrements { get; private set; }

    public void Increment()
    {
        Value++;
        TotalIncrements++;
    }
}
```

期待出力は`first=2, second=1`、`全体=3`です。`private set`は外から値を直接設定させず、クラス内部の操作で更新する指定です。firstとsecondは別のValueを持ちますが、TotalIncrementsは共有されます。この例は単一の処理の流れを前提とし、複数スレッドからの同時更新へそのまま使えるものではありません。スレッドは処理を実行する経路で、同時実行の問題は非同期・Webの章で扱います。

## 間違い：インスタンスの値を型から読む

```csharp-error
Console.WriteLine(Product.Name);
public class Product
{
    public string Name { get; } = "ノート";
}
```

`Name`は特定の商品の状態ですが、Productという型名だけではどの実体か決まりません。インスタンスを必要とするメンバーを型から使おうとしてコンパイルエラーになります。修正位置は利用側で、実体を作って参照します。

```csharp
var product = new Product();
Console.WriteLine(product.Name);
public class Product
{
    public string Name { get; } = "ノート";
}
```

期待出力はノートです。エラーを消すためにNameをstaticへ変えると、個々の商品名を持つという設計を壊す可能性があります。「その値は個別か共有か」を先に判断し、それに合う呼び出し方へ直します。

## 間違い：自分自身へ代入する

```csharp
var person = new Person("Aoi");
Console.WriteLine($"[{person.Name}]");
public class Person
{
    private string name = "未設定";
    public string Name => name;
    public Person(string name)
    {
        name = name;
    }
}
```

この誤った例の期待出力は`[未設定]`です。パラメーターnameがフィールドnameを隠しており、右も左も同じパラメーターです。コンパイラーは同じ変数への代入を警告することがあります。`this`は現在のインスタンスを表すので、`this.name = name;`とすると左はフィールド、右はパラメーターになります。

```csharp
var person = new Person("Aoi");
Console.WriteLine(person.Name);
public class Person
{
    private string name;
    public string Name => name;
    public Person(string name)
    {
        this.name = name;
    }
}
```

修正後の期待出力はAoiです。別解はフィールドを`_name`のように区別する命名です。命名規約を統一することは見た目の問題だけでなく、値がどこへ保存されるかを明確にする実務上の意味があります。

## 選択基準と練習

| 選択 | 適する状態・役割 | 例 |
|---|---|---|
| インスタンスフィールド・プロパティ | 実体ごとに異なる状態 | 商品名、ユーザーの設定 |
| staticメソッド | 特定の実体を必要としない処理 | 入力だけで決まる計算 |
| staticフィールド | 型で共有する状態が本当に必要 | 共有状態には寿命・同時更新の検討が必要 |
| コンストラクター引数 | 生成に必須の情報 | 商品名、初期価格 |

基礎は、別々の名前を持つPersonを二つ作り、順に表示する課題です。標準は、価格が負なら生成を拒否するProductを作り、0と1は受け付けることを境界値で説明します。応用はCounterのIncrementを合計5回呼ぶコードを書き、各実体のValueの合計とTotalIncrementsが等しくなる理由を説明します。

CounterのValueをstaticへ変えた場合、すべてのCounterから同じValueが見えるため、「各実体ごとの回数」を失います。これはstatic/instanceの混同を観察する実験です。次のLesson 10では、内部状態を誰でも直接書き換えられる設計を避け、操作を通じて有効な状態を保つ方法へ進みます。
