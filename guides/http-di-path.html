コード検証の読み方

出力はコードから説明した想定結果です。この制作環境では.NET SDKを利用できず、C#のビルド・実行は未検証です。コード下書きはブラウザーで動作しません。手元で確かめる手順は教材の使い方と検証にあります。

「APIを呼ぶ」と「メソッドを呼ぶ」の間にあるもの

メソッドを直接呼ぶ場合、同じプログラムの中で型に合った値を渡します。HTTP APIでは、別のプログラムからメソッド・URL・ヘッダー・本文という形で要求が届きます。ASP.NET Coreが要求を受け、対応する処理を選び、入力をC#の型へ対応付けた後で、業務のメソッドを呼びます。

HTTPは要求と応答の通信規則、APIは他のプログラムから利用するための機能の入口です。JSONは本文に使えるデータ形式であり、HTTPそのものでもC#のオブジェクトそのものでもありません。DTOは受け渡すデータの項目を定義する型です。これらを別の層として読むと、失敗した場所を絞れます。

図の認証は概念上の位置づけです。教材のローカル用サンプルに認証が自動的に実装されるという意味ではありません。実際のミドルウェアの順序は構成によって重要になるため、必要な機能を登録した上で、公式の順序と実動作を確認します。

一つの作成要求を状態表で読む

開始時の保存データが空、次のIDが1とします。{"title":"C#を学ぶ"}という本文を受け取ると、JSONのTitleを読み、空白だけではないかを確認します。正常ならID1のTodoを保存し、201とLocationを返します。次のIDは2になります。

段階 入力・ローカル 保存済みデータ 次ID
要求前 まだ入力なし 空 1
JSONを読む Title="C#を学ぶ" 空 1
条件確認 使用するtitleを確定 空 1
保存 Todo(1,title,false) ID1の一件 2
応答 201、Location=/todos/1 ID1の一件 2
続くGET ID1を探す ID1の一件 2

空白だけのタイトルなら検証段階で400を返し、保存と採番へ進ませません。「不正な入力のときにエラーを返した」という確認だけでなく、在庫や件数などの状態が変わっていないことまで検査します。

DTOと保存用モデルを分ける理由

外から受け取るタイトルと、サーバーが決めるIDは責任が違います。利用者がIDや所有者など内部で決める項目を自由に指定できると、意図しない上書きや権限の問題につながります。小さな学習アプリでも、何を入力として許すかを型で分けると契約が明確になります。

C# · 独立したコード例
var input = new CreateInput("  学習  ");
string? title = input.Title?.Trim();
if (string.IsNullOrWhiteSpace(title))
{
    Console.WriteLine("入力不正");
    return;
}
var saved = new Todo(1, title, false);
Console.WriteLine($"{saved.Id}:{saved.Title}:{saved.Done}");

record CreateInput(string? Title);
record Todo(int Id, string Title, bool Done);

これは通信を行わないコンソール例です。期待される出力は1:学習:Falseです。入力の空白を除去し、欠損や空白だけを拒否してから保存用の値を作っています。実際のID生成や永続保存はこの例では行っておらず、HTTP全経路を検証したことにもなりません。完成した学習用APIはLesson 32の詳細で扱います。

DIはまず「外から渡す」と理解する

依存関係とは、ある部品が働くために別の部品を必要とする関係です。DIは必要な部品を利用する側の外から渡すことです。DIコンテナーは、登録した規則に基づいて部品を作り、必要な場所へ渡す仕組みです。DIとコンテナーは同じ意味ではなく、手でコンストラクターへ渡すだけでも依存を注入できます。

C# · 独立したコード例
var service = new GreetingService(new FixedNameSource());
Console.WriteLine(service.Create());

interface INameSource
{
    string GetName();
}
class FixedNameSource : INameSource
{
    public string GetName() => "学習者";
}
class GreetingService
{
    private readonly INameSource _source;
    public GreetingService(INameSource source) { _source = source; }
    public string Create() => $"こんにちは、{_source.GetName()}";
}

期待される出力はこんにちは、学習者です。GreetingServiceは具体的な取得元をnewしていません。①外側でFixedNameSourceを作る、②GreetingServiceへ渡す、③Createが契約のGetNameを呼ぶ、④文字列を返す、となります。テストでは同じ契約の別実装を渡せるため、実際の通信や時刻に依存せずに振る舞いを調べられます。

DIの寿命は「共有する範囲」

寿命 基本の再利用範囲 Webでの例 誤解すると起きること
Singleton コンテナー全体で一つ スレッド安全に設計した共有サービス 利用者の状態が要求間で混ざる
Scoped 同じスコープの中 通常は同じHTTP要求内 終了した要求の部品を後で使う
Transient 解決するごと 独立した短い処理部品 同じ状態を共有していると勘違いする

Webの通常の要求はスコープを持ち、終了時にその範囲の管理対象の解放が行われます。ScopedをSingletonへ保持すると、短い寿命のものを長く使う不適切な依存になり得ます。検査で検出される構成もありますが、何でも実行基盤が安全に変換してくれるわけではありません。

教材の共有TodoStoreがSingletonなら、複数要求が同じDictionaryを操作します。採番、保存、取得の各操作は共有状態です。lockなどで必要な範囲を守り、一覧のコピーも保護内で作ることで、列挙中に更新される問題を避けます。プロセス間で共有されるわけではないので、複数サーバーや再起動をまたぐ保存はDBなど別の基盤が必要です。

HTTPの失敗を原因の層で分ける

状況 見る層 教材の基本的な応答・扱い
端末名が見つからない DNSなど接続前 HTTPコード自体を受け取れない場合がある
相手へ接続できない ネットワーク・待ち受け 通信例外や期限切れを調べる
/todos/abcがint制約に不一致 ルーティング 対応ルートがなければ通常404
JSONが壊れている 本文の読み取り・対応付け 基本的に400の入力失敗
タイトルが空白 入力・業務検証 400と修正できる情報
指定IDがない 保存データの検索 404
重複するコードがある 現在の保存状態との衝突 契約に応じて409
予期しない例外 サーバー内部 内部情報を漏らさない500などとログ

同じ400でも、JSONを読めなかった場合と独自検証で拒否した場合では本文の形が同一とは限りません。利用するフレームワークの設定を確認し、統一したいならエラー契約を実装して検査します。nullable注釈だけでHTTP入力の全てが検証されると考えません。

ミドルウェアは行きと帰りのある流れ

ミドルウェアは次の処理を呼ぶ前後に共通の処理を置いたり、途中で応答を完了したりする部品です。AがBを呼び、Bがエンドポイントを呼ぶなら、後処理はエンドポイントからB、Aへ戻る順になります。この形で例外処理や計測などを共通化できます。

途中で応答を返して次を呼ばなければ、後ろの処理は通りません。この性質は認証やエラー応答などで重要です。認証は本人確認、認可はその操作の権限確認です。ログインしているだけで全てのデータを編集できてよいわけではありません。教材の範囲を外部へ公開するときは、この二つを別々に設計します。

単体・統合・実ネットワークの検査を分ける

純粋な在庫計算を直接呼べば、入力と出力、状態変化を小さく検査できます。しかしその検査だけでは、URLが正しい処理へ届くかやJSONが引数へ変わるかは確認できません。HTTP統合テストでは、複数の部品を通してステータスと本文の契約を検査します。

テスト用ホストを使うHTTP統合テストも、実際のDNS・TLS・公開サーバーのファイアウォールまで自動的に検証するものではありません。偽HttpMessageHandlerはさらに範囲が狭く、クライアントへ固定応答を渡す検査です。何を通したかを記録すると、確認済みの範囲を過大に報告せずに済みます。

作成から削除までの確認課題

目的は一連のAPI契約と状態を確かめることです。最初に一覧GETで200と空配列を確認し、正常なPOSTで201とID、Locationを受け取ります。そのLocationをGETして同じ値を確かめ、完了状態を指定して更新し、もう一度同じ指定を送って結果が崩れないことを確かめます。最後にDELETEして204、その後の個別GETで404を確認します。

別の入力として空白タイトルを送ります。期待するのは400と、件数が増えていないことです。不正JSON、欠損、存在しないID、繰り返し更新、サーバー再起動も別々のケースにします。メモリ上の保存なら再起動で失われることを、バグではなく現在の保存契約として明記します。この経路を説明できれば、Web APIを単なるMapGetの文法としてではなく、入力・型・サービス・状態・応答の接続として理解できます。
