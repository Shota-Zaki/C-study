非同期処理の時間軸と状態

開始・未完了・再開・成功・失敗・中止を、スレッドとTaskを混同せずに追う。

.NET 10 / C# 14

何が終わるのを待っているのか

非同期処理は、処理の完了を後から受け取れるようにする仕組みです。たとえばHTTP取得では、要求を送った後に相手が応答を返すまで時間がかかります。その間ずっとCPUで新しい計算をし続けるわけではありません。適切な非同期APIなら、未完了の待ち時間にスレッドを塞ぎ続けず、完了後の処理へつなげられます。

スレッドは命令を実行する流れ、Taskは処理の完了・失敗・中止を表す対象です。Task<int>なら完了したときの整数の結果も表します。Taskは専用スレッドの別名ではありません。すぐに結果があるTaskも、外部I/Oを待つTaskも、CPU処理を表すTaskもあり得ます。

asyncとawaitの担当範囲

asyncはawaitなどを使った非同期メソッドの記述を可能にします。awaitは対象の処理が完了していればその結果を受け取り、未完了なら続きを後へ回せるようにします。asyncが付いたメソッドも、呼び出すと最初の未完了なawaitへ達するまでは通常の呼び出しとして進みます。全ての行が最初から別スレッドに飛ぶわけではありません。

この図は実行順の概念です。再開する具体的なスレッドや実行時刻を固定していません。実行環境や待つ対象により、同期コンテキストやスケジューラーなど、続きをどこで進めるかの規則が関わります。最初は「元のスレッドへ必ず戻る」「awaitのたびに必ず切り替わる」という断定をしないことが大切です。

タイマーではなく明示的な合図で追う

TaskCompletionSource<T>は、完了させる時点と結果を別のコードから指定できる部品です。テストや、他の完了通知をTaskへつなぐ場合などに使います。通常のファイルやHTTP操作で、自分で毎回作る必要はありません。ここでは進行の順序を読みやすくするために使います。

C# · 独立したコード例
var signal = new TaskCompletionSource<int>();
Console.WriteLine("1:呼び出し前");
Task work = ObserveAsync(signal.Task);
Console.WriteLine("3:まだ合図していない");
signal.SetResult(7);
await work;
Console.WriteLine("5:観察が完了");

static async Task ObserveAsync(Task<int> source)
{
    Console.WriteLine("2:待機の直前");
    int value = await source;
    Console.WriteLine($"4:結果は{value}");
}

期待される出力は1、2、3、4、5の番号順です。2までは呼び出しの冒頭で進みます。sourceは未完了なのでObserveAsyncの続きは保留され、呼び出し元が3を表示します。SetResultで7を渡すと続きが進めるようになり、workの完了を待ってから5を表示します。4がSetResultの呼び出し中に進むか後で進むかは、ここでは固定しません。await workが4より後に5を表示する関係を作っています。

時点 signal.Task work valueの扱い
生成直後 未完了 まだ呼んでいない 未宣言
sourceをawait 未完了 未完了 結果をまだ受け取れない
SetResult(7) 成功の結果7を持つ 続きが進行可能 再開時に7を受け取る
ObserveAsync終了 成功 成功 4の表示に使われた
呼び出し元のawait後 成功 成功 5へ進める

中断してもローカル値が使える理由

コンパイラーは、awaitの後で続きに戻れるように、実行位置と必要な値を保持する状態機械へ変換します。状態機械とは「今どこまで進んだか」と「次に必要な値」を保持して処理を切り替える仕組みです。ソースの上ではローカル変数に見えても、必要に応じてその値が続きのために保持されます。

これを「ローカルは必ずスタックにあり、メソッドが一度戻ったら全て消える」と覚えていると矛盾します。型と値の意味、必要な寿命、実際の物理配置は別に考えます。asyncがどのようなILへ変わるかを最初から暗記する必要はありません。中断前の値と、中断中に他の場所から変わる共有状態を区別できれば十分です。

一つずつ待つ場合と、先に二つ始める場合

独立した処理を一つずつawaitすると、一つ目の完了後に二つ目を始める構成になります。先に二つのTaskを取得してからWhenAllをawaitすると、両方が進行中である時間を重ねられます。ただし、それぞれの処理が実際に非同期で進められることと、互いに独立していることが前提です。

C# · 独立したコード例
var first = new TaskCompletionSource<int>();
var second = new TaskCompletionSource<int>();
Task<int[]> all = Task.WhenAll(first.Task, second.Task);
second.SetResult(20);
Console.WriteLine(all.IsCompleted);
first.SetResult(10);
int[] result = await all;
Console.WriteLine(string.Join(",", result));

期待される出力はFalse、10,20です。二つ目が先に終わっても、最初が未完了なのでallは完了しません。結果の配列は、ここではWhenAllに渡したTaskの順で並びます。完了した時刻の順へ自動的に並び替えるものではありません。

「前の結果を使って次の要求を作る」処理は独立ではありません。利用者IDを取得してからその利用者の注文を取得するなら、最初の結果を受け取る必要があります。速くするためだけに全てをWhenAllへ入れると、必要な前提や資源の上限を壊す場合があります。

失敗はどこで受け取るか

Taskが失敗すると、通常はそのTaskをawaitする場所で例外を受け取れます。メソッドを呼んだだけでTaskを放置すると、結果だけでなく失敗も適切に処理できません。try/catchは、待つ操作も含めた範囲へ置きます。

C# · 独立したコード例
try
{
    await FailAsync();
}
catch (InvalidOperationException)
{
    Console.WriteLine("処理の失敗を受け取りました");
}

static async Task FailAsync()
{
    await Task.Yield();
    throw new InvalidOperationException("学習用の失敗");
}

期待される出力は処理の失敗を受け取りました、です。Task.Yieldはここでいったん非同期的な続きへ回すために使っています。一定時間待つ機能ではありません。例外をcatchしたから業務が成功したことにはならず、失敗の表示・再入力・呼び出し元への伝播などを決めます。

WhenAllは一つが失敗しても他を自動中止しません。全体の完了を表すTaskに複数の失敗が記録される場合があります。通常のawaitで表に出た一つの例外だけで全失敗を見たとは限らないため、必要に応じて全体TaskのExceptionなども調べます。Lesson 24に具体例があります。

中止要求は強制終了ではない

CancellationTokenは「もう不要なので止めてほしい」という要求を伝えます。対応したAPIへ渡したり、処理中に確認したりすることで協調的に停止します。トークンを作って変数に置くだけでは、その存在を知らない処理は止まりません。

C# · 独立したコード例
using var source = new CancellationTokenSource();
source.Cancel();
try
{
    await Task.Delay(1000, source.Token);
}
catch (OperationCanceledException)
{
    Console.WriteLine("中止されました");
}

期待される出力は中止されました、です。中止済みのトークンをDelayへ渡しているので、完了待ちを成功として扱いません。ここでは指定時間の実測を検証していません。呼び出し元が中止した場合と、タイムアウトによる期限切れをどのように利用者へ伝えるかは、アプリの契約として整理します。

共有状態を安全に変える

awaitがあることと、共有するListやDictionaryが安全であることは別です。複数の要求が同じ期間に進み、読み取りと更新の間に割り込むと結果が変わる問題を競合状態と呼びます。「在庫が1あることを確認する」と「1減らす」を別々に行えば、二つの要求が両方成功と考える可能性があります。

CPU上の短い共有操作をlockで保護する設計や、非同期の同時実行数をSemaphoreSlimで制限する設計などがあります。lockのブロック内ではawaitを使えません。非同期の前後まで同じ保護を必要とするなら、設計と同期方式を見直します。またセマフォの取得に失敗した場合まで無条件にReleaseすると上限を壊すので、取得後のtry/finallyとして整理します。

自分で追う練習

上の二つのTaskの例で、firstだけを完了させた直後のall.IsCompletedは何か説明してください。答えはFalseです。secondが未完了なので「全て」の条件を満たしていません。続いてsecondを完了させると結果を受け取れます。

応用として、失敗したTaskと成功したTaskをWhenAllへ渡した場合を考えます。両方が終わること、全体は失敗になること、成功側が自動で取り消されるわけではないことを説明します。結果を保存する前に全体の扱いを決める必要がある理由が分かれば、Lesson 28のHTTPへ進めます。
