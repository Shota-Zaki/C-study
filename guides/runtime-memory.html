コンパイル・呼び出し・メモリのつながり

C#の文章が動くまでと、値・参照・寿命の違いを、一つの実行の流れから理解する。

.NET 10 / C# 14

ソースと実行中の状態を分ける

Program.csはディスクに保存された文章です。実行中の変数の値は、プログラムが起動した後の状態です。同じソースでも、入力が異なれば変数の値は変わります。コードの文字を読むことと、その時点の状態を読むことを分けると、デバッグがしやすくなります。

C#は型や構文の規則、.NET SDKはビルドなどの道具、Runtimeは実行する基盤です。通常の.NETアプリでは、コンパイラーがILという中間命令と型の情報を含むアセンブリを作り、実行時のCLRがそれを扱います。JITは必要な機械語への変換を担い、GCは管理対象のメモリ回収を担います。一つの道具が全て同じタイミングで行うわけではありません。

この図は学習用の通常のビルドと実行です。配布前に機械語を作るNative AOTや各種最適化もあるため、「必ず起動時に全コードを一度だけ変換する」とは説明しません。初めはIL命令の暗記ではなく、ビルド時のエラーと起動後の失敗を区別できることが重要です。

メソッドへ渡るのは何か

メソッドは名前を付けた処理です。呼び出し側が渡す値を引数、受け取る側の型と名前をパラメーター、返す結果を戻り値といいます。次の例では、呼び出し側のtotalと、Addのaは別の変数です。

C# · 独立したコード例
int total = 10;
int result = Add(total, 5);
Console.WriteLine(total);
Console.WriteLine(result);

static int Add(int a, int b)
{
    a += b;
    return a;
}

期待される出力は10、15です。①totalに10を保存、②Addへ10と5を渡す、③aとbが受け取る、④aを15へ変える、⑤returnで15を返す、⑥resultへ15を保存、⑦二つを表示、の順です。aへの代入は呼び出し側totalへ代入したことにはなりません。

時点 total Add内のa Add内のb result
呼び出し前 10 まだない まだない まだない
引数を受け取る 10 10 5 まだない
aへ加算 10 15 5 まだない
戻る 10 この呼び出しは終了 この呼び出しは終了 15

この呼び出しの積み重なりを追うために、呼び出しスタックという見方を使います。最適化によるインライン化などがあるため、ソースのメソッド呼び出し全てが実際の機械語上で同じ形の領域を必ず作る、とまでは断定しません。

値型と参照型は「コピーされるもの」で区別する

値型は代入時に値がコピーされます。参照型は通常、実体へアクセスするための参照の値がコピーされます。値型は必ずスタック、参照型の変数は必ずヒープという暗記は不正確です。 値型のフィールドはオブジェクトや配列の一部にもなり、ローカル値は最適化でレジスターに置かれることもあります。分類が決める中心は、代入や引数での意味です。

C# · 独立したコード例
int first = 3;
int second = first;
second = 9;

var a = new List<int> { 3 };
var b = a;
b.Add(9);
Console.WriteLine($"{first}/{second}");
Console.WriteLine(string.Join(",", a));

期待される出力は3/9と3,9です。secondはfirstの値3を受け取った別の変数なので、secondだけを9にしてもfirstは3です。一方、aとbが参照するListの実体は一つです。b経由で要素を増やすと、aから見ても増えています。

参照図の矢印はアクセス先の関係です。参照を、生のメモリアドレスとして自由に計算できる数値だとは扱いません。また、変数b自体をnew List<int>()で別の実体へ付け替えることと、bの現在の参照先を更新することは別です。

structにも参照は含まれる

structは値型ですが、フィールドやプロパティにListなどの参照型を持つことがあります。この場合、structをコピーすると、そのメンバーに含まれる参照の値もコピーされます。内部のList全体が自動的に複製されるわけではありません。

C# · 独立したコード例
var original = new Basket(new List<string> { "本" });
var copied = original;
copied.Items.Add("ペン");
Console.WriteLine(string.Join(",", original.Items));

readonly record struct Basket(List<string> Items);

期待される出力は本,ペンです。Basketの値は二つありますが、それぞれのItemsは同じListを参照しています。readonlyという語があっても、そのListへAddすることまでは禁止しません。「外側が値型」「外側の再代入を制限」「内部が不変」の三つを分けます。

独立したListが必要なら、new List<string>(original.Items)で要素をコピーしたListを作り、それを新しいBasketへ渡します。ただし要素が変更可能なclassなら、その要素の実体はさらに共有されます。独立させたい境界を決め、必要な深さだけ明示的に複製します。

originalをcopiedへ代入した後、copied.Items.Add("ペン")を実行した状態です。

外側がreadonly record structでも、ListへのAddまで禁止するわけではありません。値のコピー、参照先の共有、内側の可変性を分けます。

GCが追うのは到達できる実体

GCは、生きている実行やstaticの参照などを起点として、参照を辿れる管理対象オブジェクトを調べます。辿れないものは回収対象になり得ます。単に変数名が見えなくなった瞬間に、その実体のメモリが必ず解放されるわけではありません。回収の時点は実行基盤が判断します。

オブジェクト同士が循環して参照していても、起点からどちらにも到達できなければ回収可能です。反対に、使うつもりのないオブジェクトでも長寿命の集合やイベントから参照され続けると、GCにとっては到達可能な対象です。GCがあることと、不要な参照を持ち続けてよいことは同じではありません。

学習段階ではGC.Collect()で無理に回収を起こす習慣を付けません。まず、誰がその実体を保持しているか、保持する期間は適切かを考えます。性能問題は測定してから調べ、図から正確なメモリ使用量を推測しないようにします。

画面を閉じても、長寿命の発行側にイベント登録が残る場合を考えます。

不要な参照が残ると、もう使わないつもりの実体にも到達できる場合があります。購読の解除などで保持期間を管理します。実際の回収時刻をこの図で保証するものではありません。

DisposeとGCは別の責任

メモリが将来回収されることと、開いたファイルなどの利用を今終えることは別です。IDisposableは使い終えた資源を解放する契約で、usingは終了時にDisposeを呼ぶ構文です。usingという名前は、名前空間を指定する宣言にも使われますが、役割は異なります。

C# · 独立したコード例
using System.IO;
using (var reader = new StringReader("一行目\n二行目"))
{
    Console.WriteLine(reader.ReadLine());
    Console.WriteLine(reader.ReadLine());
}
Console.WriteLine("読み取り終了");

期待される出力は一行目、二行目、読み取り終了です。usingのブロックを抜けるときにreaderをDisposeします。途中で例外が伝わる場合にも、通常のスタック巻き戻しで解放処理が行われます。ただしプロセスの強制終了など全ての状況で必ず最後まで動くという保証ではありません。

自分で説明する練習

次の問いは、図を描いて説明してからLesson 13とLesson 16で確認します。aとbが同じListを参照するとき、①b.Add(1)、②bを別のListへ代入、③aをnullにする、の各操作が、実体と参照に何をするか説明してください。

解答の要点は、①現在の共有実体を更新、②bの参照先だけを変更、③aの参照だけを切る、です。③で他に参照が残っていれば実体はまだ到達可能です。どの場合も、「変数名の数＝実体の数」「null代入＝即座にGC」のようには結び付けません。
