23 asyncとawait — 詳細解説

開始・待機・再開の順序。

.NET 10 / C# 14
本文・演習詳細解説
重要awaitは未完了のTaskを待つ間、呼び出し元へ制御を返せます。新しいスレッドを必ず作る命令ではありません。

読み込みが終わる前と後で、実行できる行が変わります。一つの非同期処理を使い、呼び出した直後に得るTaskと、await後に得る結果を分けて追います。

待ち時間と計算時間を区別する

ファイル、ネットワーク、データベースなどの処理では、CPUがずっと計算する時間だけでなく、外部の処理が完了するのを待つ時間があります。I/Oは入力・出力のことで、ファイルの読み書きや通信が代表例です。非同期処理は、こうした完了待ちを表現し、待っている間に呼び出し側へ制御を戻せるようにします。

Taskは、処理の完了・失敗・キャンセルなどを表すオブジェクトです。Task<T>は成功時にT型の結果も持ちます。Threadはコードを実行する流れです。Taskが一つあるから専用のThreadが一つ生まれる、という関係ではありません。非同期I/Oでは待っている間に専用スレッドを占有しない実装もあります。

用語 何を表すか 混同しないこと
同期 呼び出しの完了までその流れで待つ 常に悪いわけではない
非同期 完了を後から受け取れる 自動的に並列計算になるわけではない
並行 複数の処理が進行中である 同じ瞬間にCPUで実行とは限らない
並列 複数の処理を同時に実行 CPU資源や安全な共有が必要
Task 完了状態と結果を表す スレッドそのものではない
Thread 処理を実行する流れ Taskと一対一ではない

最小例：awaitで完了後へつなぐ

C# · 独立したコード例
Console.WriteLine("開始");
string result = await GetMessageAsync();
Console.WriteLine(result);
Console.WriteLine("終了");

static async Task<string> GetMessageAsync()
{
    await Task.Delay(10);
    return "受信完了";
}

期待出力は開始、受信完了、終了です。Task.Delayは指定した時間以上の待機を表すTaskを返します。正確に10ミリ秒で再開する保証ではありません。ここでは外部待ちを簡単に表す練習として使っています。

asyncは、そのメソッド内でawaitを使える非同期メソッドの形を指定します。awaitは対象が既に完了していれば結果をすぐに受け取り、未完了なら後続の処理を続きとして保存して、呼び出し側へ戻ります。Task<string>をawaitした結果の型はstringです。

処理の開始と完了待ちは別

次は完了する時点を明示的に制御し、タイミングに左右されず順序を追う例です。TaskCompletionSource<T>は、Taskの完了を外側から知らせるための型です。通常のAPI呼び出しではAPIがTaskを返すので毎回自作する必要はありません。ここでは観察用の信号として使います。

C# · 独立したコード例
var signal = new TaskCompletionSource<bool>(
    TaskCreationOptions.RunContinuationsAsynchronously);
Console.WriteLine("1:呼び出す前");
Task<string> work = ReadAfterSignalAsync(signal.Task);
Console.WriteLine("3:呼び出し元へ戻った");
signal.SetResult(true);
Console.WriteLine(await work);

static async Task<string> ReadAfterSignalAsync(Task signal)
{
    Console.WriteLine("2:最初のawaitより前");
    await signal;
    return "4:信号の後に完了";
}

期待出力は1、2、3、4の番号順です。ReadAfterSignalAsyncを呼び出した直後は、最初の未完了awaitに到達するまで通常どおり処理を進めます。signalはまだ未完了なので、workというTaskを呼び出し元が受け取れます。SetResultで信号を完了させると、待っていた処理が続行可能になります。RunContinuationsAsynchronouslyは、完了通知した呼び出しの中で続きの処理をそのまま同期実行させないための指定です。この例の順序の中心は、SetResultより前に3を表示していることです。

本文の実例との対応：開始・待機・再開の順序

次の図は本文の実例「データ取得の完了を待つ」を使った補助例です。この節のコードとは変数や入力値が異なるため、処理の対応に注目します。

コンパイラーが支える「続き」の保存

awaitの前後で使うローカル変数や、どのawaitの続きかという状態を保持できる形へ、コンパイラーが変換します。この仕組みを状態機械と呼びます。元の呼び出しスタックをそのまま止めて専用スレッドごと保持する、という理解ではありません。

続きがどのスレッドで動くかは、実行環境や同期コンテキストなどによります。同期コンテキストは、続きの処理を特定の実行場所へ戻すための仕組みです。画面を持つアプリでは画面用の流れへ戻す必要がある場合があります。コンソールやASP.NET Coreでは、同じスレッドへ戻ることを前提にしません。今は「await後に同じローカル変数を使えるが、同じThreadとは限らない」を理解します。

未完了の処理をawaitするとき、メソッドは必要な状態と続きの位置を保ちます。

この図は状態遷移の概念図です。完了済みならそのまま続けられる場合があり、どのスレッドで再開するかも環境や文脈で異なります。

間違い：Taskを取得しただけで完了したと思う

C# · 失敗を学ぶ例（そのまま起動しない）
SaveAsync();
Console.WriteLine("保存できました");

static async Task SaveAsync()
{
    await Task.Delay(100);
    Console.WriteLine("実際の保存処理が完了");
}

CS4014の警告対象となる形です。待たずに「保存できました」を表示し、コンソールのメイン処理が先に終わると、保存の続きが完了する前にプロセスが終了する可能性があります。出力順や完了の有無を固定して期待してはいけません。確認する場所は呼び出し行のawaitと、返されたTaskを誰が監視しているかです。

C# · 独立したコード例
await SaveAsync();
Console.WriteLine("保存できました");

static async Task SaveAsync()
{
    await Task.Delay(10);
    Console.WriteLine("実際の保存処理が完了");
}

修正後は実際の保存処理が完了、保存できましたの順です。名前をAsyncで終える慣習は非同期メソッドと気づく助けになりますが、名前だけで待機を自動挿入するわけではありません。

失敗はawaitする側で扱う

C# · 独立したコード例
try
{
    int result = await LoadAsync();
    Console.WriteLine(result);
}
catch (InvalidOperationException ex)
{
    Console.WriteLine($"読み込み失敗:{ex.Message}");
}

static async Task<int> LoadAsync()
{
    await Task.Delay(1);
    throw new InvalidOperationException("形式が不正です");
}

期待出力は読み込み失敗:形式が不正ですです。非同期メソッドの失敗は返されたTaskへ保持され、await時に例外として観察できます。Taskを放置すると成功・失敗のどちらも呼び出し側が扱えなくなります。

async voidはTaskを返さないため、呼び出し元がawaitできません。主にイベントハンドラーなど戻り値voidが要求される場面に限定し、通常の業務処理ではTaskまたはTask<T>を返します。イベントの入り口がasync voidでも、実際の処理はTaskを返すメソッドへ分けると検証しやすくなります。

境界値・比較

境界・比較例：完了済みTaskの場合

Task.FromResultは完了済みのTaskを返します。awaitがあるという理由だけで、必ず一度中断すると判断しないでください。

C# · Program.cs
Console.WriteLine("A");
int value = await Task.FromResult(42);
Console.WriteLine(value);
Console.WriteLine("B");

想定出力

A
42
B

.Resultや.Waitで待つこととの違い

.Resultや.Waitは、呼び出し元のスレッドを止めて待つ同期的な待機です。画面アプリなどでは、止めたスレッドに続きの処理が戻ろうとして互いに進めなくなるデッドロックの原因になる場合があります。デッドロックとは、互いに相手を待つなどして進行できなくなる状態です。

全ての.Resultが必ずデッドロックするわけではありませんが、画面の応答停止やサーバーのスレッド不足も問題になります。通常はTaskを返す呼び出し関係を上までつなぎ、awaitを使います。ASP.NET Coreで古い画面アプリと全く同じ同期コンテキストがある、と説明しないことも重要です。

結果が未完了のTaskを待つ場合を比べます。

ResultやWaitで同期的に待つと、呼び出したスレッドを止めます。環境によってはデッドロックや処理能力の低下につながるため、非同期の経路ではawaitでつなぐことを基本にします。

I/OとCPU処理で方法を選ぶ

ファイルやHTTP APIにAsync版が用意されているなら、まずその非同期APIを使います。同期の通信を無条件にTask.Runで囲んでも、待機のためのスレッドを消せるわけではありません。Task.Runは主にCPUを使う計算などをスレッドプールへ送るときに検討します。スレッドプールは複数の処理のために実行用スレッドを共有・管理する仕組みです。

サーバーではCPU処理をTask.Runへ移すだけで処理能力が増えるわけではありません。処理の種類と呼び出し環境を見て判断します。重い計算を別の実行場所へ移すことと、I/Oの待機を効率化することを分けます。

ネットワークからの応答待ちと、大量の計算は異なる負荷です。

asyncというキーワードだけで計算が軽くなるわけではありません。I/Oでは非同期APIを使い、CPU処理を別スレッドへ移すかは応答性や負荷を見て判断します。

3段階の練習

基礎：Task<int>を返し、待機後に7を返すメソッドを書き、awaitして表示します。解答の形はstatic async Task<int> GetAsync() { await Task.Delay(1); return 7; }です。受け取るintと、待つ前のTask<int>を区別します。

標準：保存後に一覧を読み直す二つの非同期処理を順番に呼びます。await SaveAsync(); await ReloadAsync();が中心です。保存結果に依存しているので、無条件に同時開始しないことが重要です。

応用：非同期処理が失敗した場合だけエラーを表示し、成功時だけ完了メッセージを出してください。try内でawaitしてから成功表示を置き、catchへ失敗表示を分けます。finallyは成功でも失敗でも通るため、そこへ「成功」と書かないでください。
