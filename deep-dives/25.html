コード以外に何が必要か

C#のソースファイルには処理を書きます。しかし、どの.NET向けに作るか、どのライブラリを使うか、実行するアプリなのか他から参照される部品なのか、といった情報も必要です。それらをまとめる単位がプロジェクトです。通常、設定は拡張子.csprojのファイルに記述します。

ライブラリは、他のプログラムから使えるようにまとめたコードなどの部品です。NuGetは.NETのパッケージを配布・取得・依存関係として管理する仕組みです。パッケージはライブラリ本体だけでなく、関連する設定や資源を含むこともあります。usingを書くこと、プロジェクト参照を追加すること、NuGetパッケージを追加することは別の操作です。

最小構成の.csprojを読む

次はコンソールの独立したサンプルプロジェクトに使う設定です。XMLは、タグで項目と値を囲んで構造を表す記述形式です。

xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>
部分 意味 変える場面
Project Sdk ビルドに使う共通の規則 WebならMicrosoft.NET.Sdk.Webなど
OutputType=Exe 実行するアプリとして出力 部品用プロジェクトはライブラリ
TargetFramework=net10.0 .NET 10のAPIを対象にする 対応環境を変えるとき
ImplicitUsings よく使う名前空間を自動的に取り込む usingを全て明示したい場合
Nullable nullに関する注釈と解析を有効にする 基本は有効のまま設計する

TargetFrameworkはTFMとも呼ばれます。TFMは対象フレームワークを示す短い識別子です。.NET SDKのインストール済みバージョン、対象フレームワーク、C#言語バージョンは関連しますが同一の番号ではありません。対象をnet10.0にするだけで未インストールのSDKが自動的に手に入るわけではありません。

SDK・コンパイラー・ランタイムの関係を確認する

SDKは開発に必要な道具一式、コンパイラーはC#をビルド可能な形へ変換する道具、ランタイムはアプリを実行する仕組みです。通常の.NET 10プロジェクトは既定でC# 14を使います。この教材はその組み合わせを対象にします。不要にLangVersionをpreviewへ変更せず、基礎として安定した機能を使います。

ターミナルで入力するコマンド
dotnet --info
dotnet --list-sdks
dotnet --list-runtimes

出力は端末のインストール状況によって変わります。SDK一覧が空なら、ランタイムだけを入れている可能性があります。エディターで色が付くことと、正しいSDKでビルドできることは別です。エラー時は実際のコマンド出力を確認します。

ビルドの流れを分解する

通常、dotnet buildやdotnet runは必要なrestoreを暗黙に行います。restore成功はコードのコンパイル成功を意味せず、build成功は実際の入力に対して正しい動作を意味しません。手順ごとに何を確かめたかを区別します。

ターミナルで入力するコマンド
dotnet new console -n ProjectPractice -f net10.0
cd ProjectPractice
dotnet restore
dotnet build
dotnet run

ProjectPracticeが既にある場所では、別の練習用フォルダー名を使います。各コマンドが作る・変更するものを把握し、既存の作業へ無条件に上書きしないようにします。

ファイルを分けても同じプロジェクトの一部

Program.csには入口、PriceCalculator.csには計算用の型を置く例です。下の二つは別ファイルとして同じプロジェクトへ保存します。コード片を一つのトップレベル文ファイルへ無理に混ぜる必要はありません。

Program.cs：

C# · 既存コードへの差分 / 部分例
Console.WriteLine(PriceCalculator.Total(120, 3));

PriceCalculator.cs：

C# · 既存コードへの差分 / 部分例
public static class PriceCalculator
{
    public static int Total(int unitPrice, int quantity)
    {
        return checked(unitPrice * quantity);
    }
}

期待出力は360です。SDK形式のプロジェクトは通常、対象フォルダー以下の.csファイルを既定の規則でコンパイル対象に含めます。ファイルを分けることと、別プロジェクトにすることは異なります。フォルダーへ古いProgram.csのコピーを残すと、意図せずコンパイル対象になる場合があります。

間違い：同じ型や入口のコピーを置く

C# · 失敗を学ぶ例（そのまま起動しない）
Console.WriteLine("開始");

public class Product { }
public class Product { }

同じ名前空間に同名の型を重複宣言した形で、コンパイルエラーになります。また、複数のファイルにトップレベル文を置く場合も入口が重複する問題があります。確認する場所は「今開いているファイル」だけでなく、プロジェクトへ含まれる全ての.csファイルです。

修正は重複した型や古い入口を除き、独立した例は別のプロジェクトへ置くことです。

C# · 独立したコード例
Console.WriteLine("開始");

public class Product { }

この教材の各サンプルが独立したフォルダーを持つのは、同じ名前の型や入口が互いに衝突しないためでもあります。

プロジェクト参照とNuGetを区別する

操作 対象 何ができるようになるか
using 既に利用可能な名前空間 型名を短く書ける
ProjectReference 手元の別プロジェクト その出力ライブラリを参照
PackageReference NuGetパッケージ 外部の配布部品へ依存
FrameworkReference 共有フレームワーク 対象の共通機能を参照

アプリから自作の計算ライブラリを使うならプロジェクト参照、外部の検証済みパッケージを使うならPackageReferenceなどを選びます。名前空間が見つからないというエラーに対して、usingだけを何度も追加しても、参照自体が存在しなければ直りません。

依存関係には直接指定するものと、その部品がさらに使う間接的なものがあります。ライブラリAを追加すると、Aが必要とするBも解決される場合があります。依存の全体を把握して更新します。

実務では「その日に取れたもの」だけに依存しない

パッケージにはバージョンがあります。新しい版が必ず既存コードと完全互換とは限りません。利用目的、対応TFM、ライセンス、保守状況、公開元、セキュリティ警告を確認し、検証した版をプロジェクトに記録します。ここでは確認していない具体的な最新パッケージ番号を固定しません。

復元した依存関係を固定して再現性を高めるために、packages.lock.jsonとロックモードを使う運用もあります。ロックファイルは「実際に解決した依存関係の記録」です。チームで使うSDKはglobal.jsonで選択規則を揃える方法があります。global.jsonはSDKそのものを同梱するものではなく、端末側に対応SDKが必要です。

restore失敗はコードの文法エラーではない

症状 主な確認対象 先に避けること
dotnetが見つからない SDKの導入、PATH、端末の再起動 コードを無意味に書き換える
対象フレームワークに対応しない 使用中SDK、global.json LangVersionだけを変更する
パッケージ取得失敗 接続、復元元、認証、指定版 不明な配布元へ無条件変更
型が見つからない 参照、名前空間、アクセス範囲 public化だけで解決しようとする
ビルド成功なのに結果が古い 対象プロジェクト、保存、実行パス 手元の表示だけを信じる

この成果物の作成環境では.NET SDKを利用できず、取得先にも接続できなかったため、実ビルド・実行は未検証です。ソース上の確認と実ビルドは別の検証として記録しています。手元では同梱の検証手順に沿って確認してください。

3段階の練習

基礎：上の.csprojについて、対象フレームワークと実行可能アプリかどうかを説明します。答えはnet10.0、Exeです。SDK番号とTFMを同じものと答えないようにします。

標準：計算用の型を別の.csファイルへ分け、Program.csから呼びます。期待結果360は変わりません。ファイル名を変えただけでは型の名前空間まで自動で変わるとは限らない点を確認します。

応用：同じソースを別端末で再現するために必要なものを整理します。ソース、.csproj、依存の版、SDK選択、設定の用意方法、ビルド手順を残すのが中心です。bin/objをコピーするだけでは開発手順の再現になりません。秘密情報は設定例と分けます。
