20 enum・タプル・拡張メソッド — 詳細解説

注文状態を名前付きの値で表す。

.NET 10 / C# 14
本文・演習詳細解説
重要enumの名前付き定数だけで、外部から来た値が必ず有効になるわけではありません。

この単元では、異なる三つの困りごとを扱います。状態の数字に名前を付けるenum、複数の結果を返すタプル、既存の型を読みやすく使う拡張メソッドを、役割ごとに分けます。

名前のない数値や複数の戻り値を整理する

enumは関連する定数へ名前を付けた型、タプルは複数の値を一時的にまとめる型、拡張メソッドは既存の型に対してメソッド風に呼べる処理を追加する仕組みです。それぞれ「状態の選択肢」「小さな結果の組」「処理の置き場所」という異なる問題を解決します。

業務コードに0、1、2だけが並ぶと、どれが未着手でどれが完了か読み取りにくくなります。enumを使うと、意味を型と名前で表現できます。ただし、enumを使えば外部入力が自動で正しい値になるわけではありません。

enumの最小例と状態の変化

C# · 独立したコード例
WorkStatus status = WorkStatus.Todo;
Console.WriteLine(status);
status = WorkStatus.Doing;
Console.WriteLine(status);
status = WorkStatus.Done;
Console.WriteLine((int)status);

public enum WorkStatus
{
    Todo = 0,
    Doing = 1,
    Done = 2
}

期待出力はTodo、Doing、2です。enumの基になる整数型は指定しなければintです。(int)statusは名前ではなく対応する数値を取り出します。初期状態TodoからDoing、Doneへ代入で変化しています。enum自身が順序や遷移の可否を判断しているのではありません。

状態 値 この教材での意味 次に許可する状態の例
Todo 0 まだ開始していない Doing
Doing 1 作業中 Done / Todo
Done 2 完了 業務ルール次第

状態遷移とは、現在の状態から別の状態へ移ることです。DoneからTodoへ戻せるかはenum宣言ではなく業務の処理で決めます。

間違い：整数から変換できれば定義済みだと思う

C# · 独立したコード例
WorkStatus status = (WorkStatus)99;
Console.WriteLine(status);
Console.WriteLine(Enum.IsDefined(status));

public enum WorkStatus { Todo, Doing, Done }

観察結果は99、Falseです。定義されていない整数もenum型の値にできるため、外から受け取った値は検証します。Enum.IsDefinedは、その値が宣言されているかを確認します。TryParseで変換が成功した場合でも、数値文字列によって未定義の値になる場合があります。

C# · 独立したコード例
string input = "99";
if (Enum.TryParse<WorkStatus>(input, ignoreCase: true, out var status)
    && Enum.IsDefined(status))
{
    Console.WriteLine(status);
}
else
{
    Console.WriteLine("状態を確認してください");
}

public enum WorkStatus { Todo, Doing, Done }

期待出力は状態を確認してくださいです。入力をDoneへ変えるとDoneになります。Flags属性を使う組み合わせ型では、単一の定義に一致するかとは別の検証が必要です。属性は宣言へ追加情報を付ける構文です。権限の組み合わせなどを学ぶときに、許可するビットの範囲を別途設計します。現段階では単一選択のenumを確実に検証します。

外部入力をenumに変換した後、未定義の数値を後続へ渡さないための判断です。

この図は通常の名前付き状態を想定します。Flags属性による組み合わせを許すenumでは、許可するビットの組み合わせを別に設計します。

タプル：複数の結果を返す

C# · 独立したコード例
var result = Calculate(new[] { 10, 20, 30 });
Console.WriteLine($"件数:{result.Count}, 合計:{result.Total}");
(int count, int total) = Calculate(new[] { 4, 5 });
Console.WriteLine($"件数:{count}, 合計:{total}");

static (int Count, int Total) Calculate(int[] values)
{
    int total = 0;
    foreach (int value in values)
    {
        total += value;
    }
    return (values.Length, total);
}

期待出力は件数:3, 合計:60、件数:2, 合計:9です。戻り値の型(int Count, int Total)は二つのintをまとめ、各要素へ名前を付けています。return (values.Length, total)で一組の値を返します。二つ目の呼び出しでは分解し、countとtotalという別の変数へ受け取っています。

タプル構文で一般に使うSystem.ValueTupleは値型です。代入ではタプルの値がコピーされますが、内部の要素が参照型なら参照がコピーされます。要素名は読みやすさを助けますが、別の業務型として厳密に区別するものではありません。長期間使う公開データや複雑な制約には、専用のclassやrecordのほうが意図を表しやすい場合があります。

間違い：同じ型の要素を逆順に返す

C# · 独立したコード例
var result = Calculate();
Console.WriteLine($"件数:{result.Count}, 合計:{result.Total}");

static (int Count, int Total) Calculate()
{
    int count = 3;
    int total = 60;
    return (total, count);
}

観察結果は件数:60, 合計:3です。両方intなので、型の検査だけでは入れ替えを検出できません。修正する場所はreturnの並びです。

C# · 独立したコード例
var result = Calculate();
Console.WriteLine($"件数:{result.Count}, 合計:{result.Total}");

static (int Count, int Total) Calculate()
{
    int count = 3;
    int total = 60;
    return (Count: count, Total: total);
}

修正後は件数:3, 合計:60です。要素名を明示し、値の意味が合うか確認します。テストでも件数だけでなく合計も検証します。分解先の変数名を変えるだけでは、返す値の入れ替わりは直りません。

(int Count, int Total)へ(30, 2)を返してしまった場合を考えます。

どちらもintなので、順序が逆でも型検査だけでは意図を判定できません。入力10と20からCount=2、Total=30になるテストが取り違えを見つけます。

拡張メソッド：型を変更せず便利な操作を置く

C# · 独立したコード例
string text = "  C#  ";
Console.WriteLine(text.NormalizeLabel());
Console.WriteLine(LabelExtensions.NormalizeLabel(text));

public static class LabelExtensions
{
    public static string NormalizeLabel(this string value)
    {
        ArgumentNullException.ThrowIfNull(value);
        return value.Trim();
    }
}

期待出力はC#、C#です。二つの呼び出しはこの例では同じ静的メソッドを呼びます。static classはインスタンスを作らず使う型です。従来形式の拡張メソッドではstaticメソッドの最初の引数にthisを付け、どの型を受け手として使うかを示します。text.NormalizeLabel()ではtextがvalueへ渡ります。

拡張メソッドはstringの実装そのものを書き換えたり、stringへ新しいフィールドを追加したりしません。呼び出し候補の解決はコンパイル時の型などに基づきます。通常の適用可能なインスタンスメソッドがあればそちらが優先されます。見た目だけでvirtualのような実行時の差し替えと同じだと思わないでください。

.NET 10 / C# 14ではextensionブロックによる拡張メンバーの記述も利用できます。従来のthis引数形式も利用できます。新しい構文へ移っても、元の型のprivateな状態を自由に触れる仕組みに変わるわけではありません。

本文の実例との対応：注文状態を名前付きの値で表す

境界値・比較

境界・比較例：TryParseだけでは足りないenum検証

数値の文字列はenumへ変換できても、その値に対応する定義済みメンバーがあるとは限りません。

C# · Program.cs
string input = "99";
bool parsed = Enum.TryParse(input, out OrderStatus status);
Console.WriteLine(parsed);
Console.WriteLine(Enum.IsDefined(status));
enum OrderStatus { Pending, Paid, Shipped }

True
False

拡張メソッドとLINQがつながる

WhereやSelectが配列やListからメソッドのように呼べるのは、Enumerableが提供する拡張メソッドだからです。必要な名前空間System.Linqがスコープ内にあると候補になります。名前空間をusingすることと、外部パッケージを追加することは別です。

enum・タプル・拡張メソッドの選択基準

やりたいこと 候補 理由
状態を有限の名前で表す enum 意味のある選択肢を表せる
メソッドから小さな結果を二つ返す 名前付きタプル 一時的な組を簡単に表せる
検証や振る舞いを持つ業務データ class / record 名前と責務を独立させる
型を変更せず自然な補助操作を置く 拡張メソッド 共通処理の呼び出しを整理
実行時に実装を差し替える interface / virtual 拡張メソッドとは役割が違う

一つの処理に全てを使う必要はありません。何を表したいのかで選びます。

長期間やり取りする複雑なデータや、常に守りたいルールが増えるなら、専用の型を定義する選択もあります。記述が短くなることだけで選ばないでください。

3段階の練習

基礎：PriorityをLow=0、Normal=1、High=2で宣言し、入力Highを変換・検証してください。Enum.TryParseとEnum.IsDefinedを両方確認します。未定義整数の入力でも成功扱いにしないのが目的です。

標準：{2,4,6}の件数と合計を名前付きタプルで返してください。解答は(Count:3, Total:12)です。空の配列なら(0,0)と定義すると、呼び出し側で結果の意味を統一できます。

応用：stringに対する補助処理として、Trimした結果が空なら「未入力」を返すNormalizeLabelを作ってください。string trimmed = value.Trim(); return trimmed.Length == 0 ? "未入力" : trimmed;が中心です。三項演算子の条件 ? 真の値 : 偽の値はifで書く別解もあります。nullを許可するなら引数をstring?へ変え、先にnullの扱いを定義してください。

役割
少数の値を一つの値のまとまりとして受け渡す。
なぜ必要か
合計と件数など、局所的な複数結果を返す。
具体例
(int Count, int Total) result = (3, 120);

混同しやすい点：要素名だけで業務型の違いを強く区別できるとは限らない。

拡張メソッド静的メソッドを対象.Method()の形で呼ぶ仕組みで、従来の構文はstaticクラスの第一引数にthisを付けます。元の型の実装は変えず、privateへの特別な権限も得ません。

既存型を変更せず、その型に対する操作を呼びやすくする。
なぜ必要か
共通処理を整理し、既存のメンバーとの解決規則を理解する。
具体例
public static string Clean(this string? value) => value?.Trim() ?? "";

混同しやすい点：インスタンスメンバーのoverrideではない。C#14には拡張ブロックもある。
