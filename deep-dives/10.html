カプセル化は「変更してよい道筋を決めること」

カプセル化は、内部状態を隠すだけでなく、外部がどの操作を通して状態を利用・変更できるかを設計することです。在庫数をpublicフィールドで公開すると、どこからでも-100を代入できます。「在庫は負にならない」という規則を守るには、変更を一つの入口へ集める必要があります。

不変条件とは、正常なオブジェクトがいつも満たすべき条件です。残高が負でない、名前が空でない、といった条件です。すべての呼び出し側へ毎回同じ注意を要求するより、オブジェクト自身が許された変更だけを公開すると、チームで機能を追加しても規則を維持しやすくなります。

プロパティはフィールドのような見た目でアクセスできるメンバーですが、読み取りや書き込みはアクセサーという処理で実装します。getは読む処理、setは書く処理です。自動実装プロパティではコンパイラーが保存用のフィールドとアクセサーを生成します。プロパティが必ず一つの値を保存しているとは限らず、読むたびに計算するものもあります。

最小例：保存する値と計算する値

C# · 独立したコード例
var item = new LineItem(120, 3);
Console.WriteLine(item.UnitPrice);
Console.WriteLine(item.Quantity);
Console.WriteLine(item.Total);

public class LineItem
{
    public int UnitPrice { get; }
    public int Quantity { get; }
    public int Total => UnitPrice * Quantity;

    public LineItem(int unitPrice, int quantity)
    {
        UnitPrice = unitPrice;
        Quantity = quantity;
    }
}

期待出力は120、3、360です。UnitPriceとQuantityは生成時に設定する自動実装プロパティです。Totalは読み取り時に計算するプロパティで、別のtotalフィールドへ360を保存していません。=>は一つの式の結果を返す記法です。

計算結果まで重複して保存すると、数量だけ変えた後でtotalを更新し忘れる可能性があります。軽い計算なら元の値から求めることで不整合を減らせます。ただし、プロパティを読むだけで重い通信やファイル書き込みが起こると利用者が予測しにくくなるため、そのような処理は意図の分かるメソッドにします。

get・set・init・requiredの違い

記法 読み取り 設定できる主なタイミング 選択場面
{ get; set; } 外部から可能 外部から随時 自由な編集が本当に許されるデータ
{ get; private set; } 外部から可能 型の内部から 更新を操作メソッドへ集める
{ get; } 外部から可能 自動実装なら宣言やコンストラクターなど 生成後に固定する値
{ get; init; } 外部から可能 オブジェクト初期化段階など 作成時の設定を許し、後の再代入を制限
required 設定を要求する追加指定 宣言に応じる 呼び出し側の設定忘れを検出

requiredは値の品質検証ではありません。空文字や不正な範囲を防ぐものでもなく、非null注釈と組み合わせても実行時の完全な保証にはなりません。initも、参照先の可変オブジェクトを深く不変にする機能ではありません。initのListプロパティがあっても、そのListのAddまで自動禁止されません。

実用例：在庫を操作で減らす

C# · 独立したコード例
var stock = new Stock(5);
Console.WriteLine(stock.TryTake(2));
Console.WriteLine(stock.Quantity);
Console.WriteLine(stock.TryTake(10));
Console.WriteLine(stock.Quantity);

public class Stock
{
    public int Quantity { get; private set; }

    public Stock(int quantity)
    {
        if (quantity < 0)
            throw new ArgumentOutOfRangeException(nameof(quantity));
        Quantity = quantity;
    }

    public bool TryTake(int amount)
    {
        if (amount <= 0 || amount > Quantity)
            return false;
        Quantity -= amount;
        return true;
    }
}

期待出力はTrue、3、False、3です。TryTakeは「指定数を引き出せたか」をboolで返します。要求数が正か、在庫以内かを先に検証し、失敗なら状態を変えません。成功した場合だけ減らします。例外は初期値が不正な呼び出しを拒否するために使い、通常に起こり得る在庫不足はfalseで表しています。

呼び出し前 要求 判定 呼び出し後 戻り値
5 2 0より大きく、在庫以下 3 true
3 10 在庫を超える 3 false
3 0 正の数量ではない 3 false
3 -1 負の数量 3 false

「先に減らしてから負なら戻す」設計よりも、検証後に一度だけ更新する方が失敗時の状態を追いやすくなります。この例は単一の呼び出しの流れを想定しています。Web APIなどで同時にTryTakeを呼ぶ場合は、判定と更新を一体として守る同期やデータベース側の制約が必要で、private setだけでは同時更新の問題を防げません。

明示的なフィールドとsetアクセサー

C# · 独立したコード例
var person = new Person();
person.Name = "  Aoi  ";
Console.WriteLine(person.Name);

public class Person
{
    private string _name = "未設定";

    public string Name
    {
        get { return _name; }
        set
        {
            if (string.IsNullOrWhiteSpace(value))
                throw new ArgumentException("名前が必要です");
            _name = value.Trim();
        }
    }
}

期待出力はAoiです。set内のvalueは代入された右側の値を受け取る特別な名前です。person.Name = " Aoi ";でsetが呼ばれ、検証し、空白を除いた結果を_nameへ保存します。Nameを読むとgetが_nameを返します。privateフィールドへ外から直接触らせず、加工・検証の道筋を一つへまとめています。

C# 14ではfieldキーワードを使ってコンパイラー生成の保存フィールドにアクセスするプロパティも書けます。ただし、この教材の基礎例は明示的なフィールドで保存先を見えるようにしています。短い新構文へ置き換える前に、getとsetが何をしているかを説明できることを重視します。

間違い：プロパティから自分自身を呼ぶ

C# · 失敗を学ぶ例（そのまま起動しない）
var person = new Person();
Console.WriteLine(person.Name);
public class Person
{
    public string Name => Name;
}

Nameを読むとget相当の処理へ入り、その中で再びNameを読むため、終わらず自分自身を呼び続けます。これを再帰呼び出しといいます。再帰は問題を小さくしながら解く場合には役立ちますが、この例は終了条件がなく、StackOverflowExceptionなどによってプロセスが停止する原因になります。通常のcatchで安全に回復できる前提にしません。

修正位置はアクセサー内の保存先です。

C# · 独立したコード例
var person = new Person();
Console.WriteLine(person.Name);
public class Person
{
    private string _name = "Aoi";
    public string Name => _name;
}

期待出力はAoiです。プロパティと保存用フィールドを別の名前にします。setでName = value;と書いて自分自身を呼ぶ場合も同じ問題です。アクセサー内で何へアクセスしているか、メンバーの種類まで確認します。

間違い：privateのエラーをpublic化で回避する

C# · 失敗を学ぶ例（そのまま起動しない）
var stock = new Stock();
stock.Quantity = -10;
public class Stock
{
    public int Quantity { get; private set; } = 5;
}

外部からprivate setへ代入できないためコンパイルエラーになります。これは保護したい設計が機能している状態です。修正はsetをpublicへ変えることではなく、実用例のTryTakeのように意味のある操作を用意し、許された変更を依頼することです。

アクセス修飾子は暗号化や利用者の認証ではありません。C#コードのどこからメンバーを利用できるかという境界です。public APIをインターネットへ公開してよいかというセキュリティ判断とは別です。Lesson 30以降のHTTP入力検証や認可を、privateだけで代替することはできません。

コレクションを公開するときの注意

読み取り専用プロパティでも、返しているオブジェクトが可変なら外から内部を変更できることがあります。public List<int> Scores { get; }はプロパティ自体の再代入を禁止しているだけで、Scores.Add(100)は可能です。Listは要素を追加・削除できるコレクションで、Lesson 15で学びます。

読み取り専用インターフェイスやコピーを返す設計を検討しますが、インターフェイス越しの操作制限と、実体が絶対に変更されないことは別です。誰が所有し、誰が更新するのかを明確にする必要があります。ここでは「getだけならすべて不変」と一般化しないことを覚えます。

段階別の練習

基礎はLineItemのQuantityを4で生成しTotalの480を説明することです。標準はStockへ補充メソッドを追加し、0以下を拒否して正の値だけ加えます。入力は在庫3と補充2、期待は在庫5です。上限を決めないままintの加算を繰り返すと範囲超過の可能性があるので、実務では上限やcheckedを検討します。

応用は、引き出しに失敗したときの状態が変わらないことを確認する課題です。在庫3へ10・0・-1を順に要求しても3を維持する、最後に3を要求すると0になる、という順序付きのケースを作ります。各メソッドが単独で動くだけでなく、操作の連続でも不変条件を保てるかを考えます。

クラスの外側へ何を公開し、内側へ何を隠すかを決めることで、変更箇所を限れます。次のLesson 11では複数の型で共通の振る舞いを持つ方法を学びます。継承を使っても、基底型が守るべき条件を派生型が壊さないことが重要になります。
