インターフェイスは「利用側が必要な操作の契約」

インターフェイスは、型が提供する操作などの契約を定義する仕組みです。通知を利用する処理にとって重要なのは「指定した文字列を通知できること」であり、毎回具体的な出力先の内部を知る必要はありません。利用側が契約だけを受け取れば、実際の部品を差し替えられます。

実装とは、契約で要求された操作を具体的なコードで提供することです。INotifierにSend(string message)があれば、それを実装するクラスは対応する操作を提供します。名前の先頭のIはインターフェイスを識別しやすくする慣習で、文法上の必須条件ではありません。

契約は「どんなメンバーが存在するか」だけではありません。何を受け取り、何を行い、失敗をどう知らせるかも、設計上の約束です。同じSendでも、一方は空文字を無視し、もう一方は例外を投げるなら、利用側はその違いを理解する必要があります。シグネチャとは名前・パラメーターなどメンバーを識別する構造で、振る舞いの契約すべてを表すものではありません。

最小例：共通の型で実装を呼ぶ

C# · 独立したコード例
INotifier notifier = new ConsoleNotifier();
notifier.Send("保存しました");

public interface INotifier
{
    void Send(string message);
}
public class ConsoleNotifier : INotifier
{
    public void Send(string message)
    {
        Console.WriteLine($"通知: {message}");
    }
}

期待出力は通知: 保存しましたです。interfaceで契約を宣言し、クラス名の後の: INotifierで実装することを示します。通常の暗黙的実装では要求されるメンバーをpublicとして提供します。voidは戻り値を返さない指定です。

notifier変数の宣言型はINotifier、実体はConsoleNotifierです。コンパイラーは契約を通して使える操作を確認し、実行時はその実体の実装へ呼び出しをつなぎます。interfaceという独立した送信機械が裏側で生成されるわけではありません。

依存関係をコンストラクターで受け取る

依存関係とは、ある処理が動くために必要とする別の部品です。ReportServiceが通知部品を必要とするなら、通知部品への依存があります。依存性の注入、DIは、その部品を内部で固定してnewするのではなく外から渡す設計です。特定のフレームワークがなくても、コンストラクターで手渡せばDIになります。

C# · 独立したコード例
var service = new ReportService(new ConsoleNotifier());
service.Complete("売上集計");

public interface INotifier
{
    void Send(string message);
}
public class ConsoleNotifier : INotifier
{
    public void Send(string message)
    {
        Console.WriteLine($"通知: {message}");
    }
}
public class ReportService
{
    private readonly INotifier _notifier;

    public ReportService(INotifier notifier)
    {
        _notifier = notifier;
    }

    public void Complete(string reportName)
    {
        _notifier.Send($"{reportName}が完了しました");
    }
}

期待出力は通知: 売上集計が完了しましたです。まず通知部品を作り、その参照をReportServiceへ渡します。コンストラクターで_notifierへ保存し、Completeで利用します。readonlyはこのフィールドを後から別の参照へ差し替える箇所を制限します。参照先の部品の内部状態まで変更不能になるわけではありません。

時点 生成・処理 保持する関係
① ConsoleNotifierを生成 通知実体A
② ReportServiceを生成 サービスBがAを参照
③ Completeを呼ぶ 通知文を組み立てる
④ _notifier.Sendを呼ぶ Aが表示処理を行う

ASP.NET CoreではDIコンテナーという「登録に基づき部品を生成・供給する仕組み」を使えますが、その前にこの手渡しの関係を理解します。Lesson 31の登録・解決・寿命も、魔法ではなくこのオブジェクトのつながりの管理です。

実用例：出力せず記録する部品へ差し替える

検証では、画面や外部サービスへ本当に通知せず、どんな内容が渡されたかを調べたいことがあります。この例は最後のメッセージを保持する実装に差し替えます。

C# · 独立したコード例
var recorder = new RecordingNotifier();
var service = new ReportService(recorder);
service.Complete("在庫集計");
Console.WriteLine(recorder.LastMessage);

public interface INotifier
{
    void Send(string message);
}
public class RecordingNotifier : INotifier
{
    public string? LastMessage { get; private set; }
    public void Send(string message)
    {
        LastMessage = message;
    }
}
public class ReportService
{
    private readonly INotifier _notifier;
    public ReportService(INotifier notifier)
    {
        _notifier = notifier;
    }
    public void Complete(string reportName)
    {
        _notifier.Send($"{reportName}が完了しました");
    }
}

期待出力は在庫集計が完了しましたです。通知の呼び出し前はLastMessage=null、呼び出し後は組み立てられた文字列です。ReportServiceのコードは通知先の変更を知る必要がありません。記録する実装を利用して、正しいメッセージが渡されたかを検証できます。これがLesson 26の単体テストへつながります。

この小さな実装は最後の一件だけを記録します。呼び出し回数やすべての通知内容を検証するなら、Listなどで履歴を持つ設計へ広げます。何を検証したいかによってテスト用の部品の状態も決めます。

間違い：インターフェイスをnewする

C# · 失敗を学ぶ例（そのまま起動しない）
INotifier notifier = new INotifier();
public interface INotifier
{
    void Send(string message);
}

インターフェイスは通常の具体的な実体を直接生成する型ではないため、コンパイルエラーになります。契約だけでは、通知の具体的な処理とインスタンスの作り方が決まっていません。

修正位置はnewの型です。最小例のようにnew ConsoleNotifier()を生成し、INotifier型の変数で受け取ります。DIコンテナーを使う場合も、裏側では登録した具体的な実装を選んで生成します。登録なしでも名前だけで都合のよい実装が見つかる、とは考えません。

間違い：実装のアクセス範囲が合わない

C# · 失敗を学ぶ例（そのまま起動しない）
public interface INotifier
{
    void Send(string message);
}
public class ConsoleNotifier : INotifier
{
    private void Send(string message)
    {
        Console.WriteLine(message);
    }
}

この例は通常の暗黙的実装として契約を満たしません。外から呼べる契約なのに、対応するメソッドをprivateにしています。修正位置は実装のアクセス修飾子です。public void Sendへ変えます。

明示的インターフェイス実装という別の書き方もあります。

C# · 独立したコード例
INotifier notifier = new ConsoleNotifier();
notifier.Send("確認");

public interface INotifier
{
    void Send(string message);
}
public class ConsoleNotifier : INotifier
{
    void INotifier.Send(string message)
    {
        Console.WriteLine(message);
    }
}

期待出力は確認です。void INotifier.Sendはインターフェイス経由で利用する明示的な実装です。このメソッドへ通常のpublic/privateを付ける書き方ではありません。具体型からそのままnew ConsoleNotifier().Send(...)とは呼べない点も、暗黙的実装と異なります。

abstract classとの比較

観点 抽象クラス インターフェイス 判断の目安
主な目的 共通の土台と状態・実装をまとめる 必要な能力・操作の契約を定める 共有したいのは実装か、契約か
クラスからの利用 直接の基底クラスは一つ 複数を実装できる 別系統の型にも契約を付けたいか
インスタンス状態 フィールドやコンストラクターを持てる 通常のインスタンスフィールドは持たない 共通の保存状態が必要か
実装 一部を共通化できる 既定実装を持てる機能もある 機能があることと乱用することは別

現行C#のインターフェイスは「すべて本体なしのメソッドだけ」とは限りません。既定実装やstatic関連のメンバーもあります。ただし、この段階ではインスタンス操作の契約と、別のクラスによる実装という基本に集中します。複雑な機能を知っていても、利用側に不要な操作を大量に要求する契約は避けます。

インターフェイスを全クラスへ機械的に一つずつ作る必要もありません。差し替え、テスト、複数実装、外部部品との境界など、実際の変更理由を考えます。小さな内部計算だけに一対一の契約を増やすと、追うファイルが増えるだけの場合があります。

段階別の練習

基礎課題は、接頭辞記録:を付けて画面へ表示する別のINotifier実装を作ることです。ReportServiceを変更せず、生成箇所だけ差し替えて結果を確かめます。

標準課題はRecordingNotifierへ呼び出し回数Countを追加します。Completeを二回呼ぶ入力に対してCount=2、LastMessageは二回目の通知です。増分処理はSend内に置き、ReportService側が記録用の型を知らなくても状態が更新されるようにします。

応用課題はReportServiceのコンストラクターでnullを拒否することです。_notifier = notifier ?? throw new ArgumentNullException(nameof(notifier));が解答例です。null合体で、値があれば保存し、なければ例外で生成を拒否します。非null注釈だけに依存せず、部品を受け取る境界を明確にします。
