実行中の値を次回へ残す

変数やListに入れたデータは、アプリケーションが終了すると通常そのままでは次回へ引き継がれません。ファイルへ保存し、次の起動時に読み込むことで、実行中の状態と保存済みの状態をつなぎます。こうしてデータを終了後も残すことを永続化と呼びます。

JSONは、名前と値、配列、数値、文字列、true/false、nullなどをテキストで表すデータ形式です。オブジェクトをJSONへ変換することをシリアル化、JSONから型に沿った値を作ることを逆シリアル化と呼びます。ファイルへ書く処理とJSONへ変換する処理は別です。JSONは文字列として通信へ使うこともできます。

最小例：JSONはまず文字列として扱える

C# · 独立したコード例
using System.Text.Json;

var item = new Item("Note", 3);
string json = JsonSerializer.Serialize(item);
Console.WriteLine(json);
Item? loaded = JsonSerializer.Deserialize<Item>(json);
if (loaded is null)
{
    Console.WriteLine("データなし");
}
else
{
    Console.WriteLine($"{loaded.Name}:{loaded.Quantity}");
}

public record Item(string Name, int Quantity);

通常の設定で期待されるJSONは{"Name":"Note","Quantity":3}、続く表示はNote:3です。JSONのプロパティ順序を業務の意味として依存しないようにします。Deserialize<Item>の型引数は「どんな型へ戻したいか」を指定しています。文字列の中にJSONのnullがあると、参照型の逆シリアル化結果がnullになる可能性があるため、Item?で受けています。

JSONを読むことは、既存のitemをそのまま取り戻すことではありません。この例では同じような値を持つ別のオブジェクトが作られます。参照の同一性ではなく、保存したデータの内容を確認します。

パスは「どこを基準にするか」が重要

パスはファイルやフォルダーの位置を表すものです。絶対パスは基準からの全体の位置、相対パスは現在の基準からの位置です。"data/items.json"のような相対パスは通常、現在の作業ディレクトリを基準に解決されます。作業ディレクトリはコマンドを起動した場所などにより変わります。

C# · 独立したコード例
Console.WriteLine($"作業場所:{Environment.CurrentDirectory}");
Console.WriteLine($"アプリ基準:{AppContext.BaseDirectory}");
string path = Path.Combine(Environment.CurrentDirectory, "data", "items.json");
Console.WriteLine($"保存先:{Path.GetFullPath(path)}");

出力の具体的なパスは環境ごとに変わります。Environment.CurrentDirectoryとAppContext.BaseDirectoryは同じとは限りません。後者はアプリケーションの基準ディレクトリです。インストール先への書き込みは権限の問題があるため、本番では利用者のデータ保存先などを設計します。この教材のファイル例は練習用フォルダーで試します。

Path.Combineは区切りをOSに合わせて組み立てる補助です。ただし、利用者が自由入力したパスを安全な保存先へ自動的に制限する機能ではありません。外部入力で任意のパスを作らせないことが基本です。

実用例：一覧の保存と読み込み

次の例は現在の作業フォルダー内にpractice-data/items.jsonを作成・上書きします。既存の大切なデータがない練習用の場所で扱います。

C# · ファイル操作を伴う例
using System.Text.Json;

string directory = Path.Combine(Environment.CurrentDirectory, "practice-data");
Directory.CreateDirectory(directory);
string path = Path.Combine(directory, "items.json");
var items = new List<Item>
{
    new Item("Note", 3),
    new Item("Pen", 2)
};
var options = new JsonSerializerOptions { WriteIndented = true };
string json = JsonSerializer.Serialize(items, options);
File.WriteAllText(path, json);

string saved = File.ReadAllText(path);
List<Item>? loaded = JsonSerializer.Deserialize<List<Item>>(saved);
if (loaded is null)
{
    Console.WriteLine("一覧がnullです");
    return;
}
foreach (Item item in loaded)
{
    Console.WriteLine($"{item.Name}:{item.Quantity}");
}

public record Item(string Name, int Quantity);

期待出力はNote:3、Pen:2です。CreateDirectoryはフォルダーが既に存在する場合にも使えます。WriteIndentedはJSONを人間が読みやすい改行・字下げ付きにします。WriteAllTextは既存ファイルを上書きします。これらのAPIは短い全体読み書きに便利ですが、巨大なファイルを全て文字列へ読み込むとメモリ使用量も増えます。

時点 メモリ上のitems ファイル loaded
List作成後 2件 まだ今回の保存なし 未宣言
Serialize後 同じ2件 まだ書いていない 未宣言
WriteAllText後 同じ2件 JSONが保存済み 未宣言
Deserialize後 同じ2件 同じJSON 別のListと要素を生成

ストリームと資源の寿命

ストリームは、データを順番に読み書きする通り道です。ファイル全体を一つの文字列へ読み込まず、必要な範囲から処理する設計にも使います。FileStreamなどはOSのファイル資源を使うので、所有する側がusingで確実に解放します。GCによるオブジェクトの回収と、ファイルを閉じる時点を同じものと考えないでください。

同期APIでは呼び出し側が完了まで待ちます。非同期の読み書きでは待機中に呼び出し側へ制御を戻せる場合があります。第23レッスンでawaitを学んでからReadAllTextAsyncやSerializeAsyncへ進みます。

間違い：JSONとして読めれば有効な業務データだと思う

C# · 独立したコード例
using System.Text.Json;

string json = "{\"Name\":\"\",\"Quantity\":-5}";
Item? item = JsonSerializer.Deserialize<Item>(json);
Console.WriteLine(item?.Quantity);

public record Item(string Name, int Quantity);

観察結果は-5です。このJSONは構文として正しく、intへも変換できますが、空の商品名と負の数量が業務上正しいかは別です。nullable参照型の注釈だけで、全ての入力制約が実行時に検証されるわけではありません。修正では外部データを受ける型と利用前の検証を明示します。

C# · 独立したコード例
using System.Text.Json;

string json = "{\"Name\":\"\",\"Quantity\":-5}";
ItemInput? item = JsonSerializer.Deserialize<ItemInput>(json);
if (item is null || string.IsNullOrWhiteSpace(item.Name) || item.Quantity <= 0)
{
    Console.WriteLine("名前と数量を確認してください");
    return;
}
Console.WriteLine($"{item.Name.Trim()}:{item.Quantity}");

public sealed class ItemInput
{
    public string? Name { get; set; }
    public int Quantity { get; set; }
}

期待出力は名前と数量を確認してくださいです。Quantityが省略されたとき0でよいのか、省略と明示的な0を区別する必要があるのかも設計します。区別が必要ならint?などで受けます。

名前の大文字・小文字と既定値を確認する

通常のJsonSerializerを既定設定で直接使う場合、プロパティ名の照合は大文字・小文字を区別します。Web向けの既定設定とは違いがあるので、単体のコンソール例とWeb APIを混同しません。

C# · 独立したコード例
using System.Text.Json;

string json = "{\"name\":\"Note\"}";
var exact = JsonSerializer.Deserialize<NameInput>(json);
var flexible = JsonSerializer.Deserialize<NameInput>(json,
    new JsonSerializerOptions { PropertyNameCaseInsensitive = true });
Console.WriteLine(exact?.Name ?? "未設定");
Console.WriteLine(flexible?.Name ?? "未設定");

public sealed class NameInput
{
    public string? Name { get; set; }
}

期待出力は未設定、Noteです。Nameとnameが一致していないことが原因です。見当違いの「ファイルの読み込み失敗」と決めつけず、JSONの実際の内容と型、オプションを確認します。

失敗を層ごとに分ける

失敗 確認場所 回復方針の例
ファイルがない 絶対パス、初回起動か 初期データで開始、または場所を案内
書けない 保存先、権限、読み取り専用 保存失敗を通知し元データを維持
JSONの構文が壊れている JsonExceptionの位置、実ファイル 勝手に空で上書きしない
型が合わない 数値と文字列、配列と単一値 入力形式を修正
名前や数量が不正 逆シリアル化後の値 業務ルールで拒否

途中で保存に失敗しても既存ファイルを壊しにくくするには、一時ファイルに書いてから置き換えるなどの設計を検討します。ただし、原子的な置き換えや停電時の永続性はOS・ファイルシステム・APIに依存します。「一時ファイルを使えば絶対安全」とはしません。複数の処理が同時に書く場合の競合も別問題です。

3段階の練習

基礎：Item("Book",2)をJSONへ変換し、読み戻してBook:2を表示します。入力と出力の間にファイルは不要です。まず変換だけを確認すると、パスの問題と分離できます。

標準：保存例へ3件目を追加し、再読み込み後の件数が3であることを表示してください。loaded.Countで確認できます。元のitems.Countだけを表示しても、保存・読み込みが正しいことは確かめられません。

応用：保存済みJSONが壊れているとき、エラーを表示して終了し、ファイルを空の一覧で上書きしない流れを設計してください。Read→Deserialize→Validateに成功してから編集・保存へ進むのが解答の中心です。catchで無条件に空Listを返すと、破損と本当に空の一覧が区別できなくなります。

自分でコードを書く

本文の小さな実験を終えたら、本編の下書き欄へ進みます。解答を写す前に、入力・必要な状態・出力を自分の言葉で整理してください。
