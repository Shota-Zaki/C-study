16 例外処理とusing — 詳細解説

例外が発生したときの資源の解放。

.NET 10 / C# 14
本文・演習詳細解説
重要usingによるDisposeと、GCによるメモリ回収は異なる役割です。

失敗した行の次へそのまま進むとは限りません。例外が起きたときの経路を確認した後で、正常終了でも失敗でも後始末が必要な資源をusingで管理します。

例外は通常の戻り値とは別の経路で失敗を伝える

メソッドは戻り値を返して呼び出し側へ戻ります。しかし、ファイルが読めない、必要な状態が壊れているなど、通常の結果を作れない場合があります。例外はその異常をオブジェクトとして通知し、通常の次の文ではなく対応する例外処理へ移る仕組みです。

例外オブジェクトには型、メッセージ、呼び出し経路を示すスタックトレースなどがあります。スタックトレースは、どのメソッドからどのメソッドを呼んで問題に至ったかを追う手掛かりです。エラー文の日本語だけを読まず、例外型・発生行・入力・呼び出し経路を合わせて調べます。

すべての失敗を例外にする必要はありません。ユーザーが数字でない文字を入力することが普通に想定されるなら、TryParseのような成功/失敗の戻り値が分かりやすくなります。一方、内部的に保証していた前提が壊れて正常な値を返せないなら、例外が適する場合があります。

try・catch・finallyの処理順

C# · 独立したコード例
Console.WriteLine("開始");
try
{
    Console.WriteLine("変換前");
    int value = int.Parse("abc");
    Console.WriteLine(value);
}
catch (FormatException)
{
    Console.WriteLine("整数の形式ではありません");
}
finally
{
    Console.WriteLine("後片付け");
}
Console.WriteLine("終了");

期待される出力：

想定される出力 / データ
開始
変換前
整数の形式ではありません
後片付け
終了

tryは例外が起こり得る処理の範囲です。catchは対応する型の例外を受け取ります。finallyは通常の終了・例外の伝播・returnなどで対象の範囲を抜ける際の後片付けに使います。プロセスの強制終了やOS障害など、どんな状況でも必ず動くという保証ではありません。

段階 処理 次へ進まない文
① 開始、変換前を表示 なし
② ParseがFormatExceptionを発生 Console.WriteLine(value)
③ 対応するcatchへ移動 tryの途中へ戻らない
④ finallyを実行 なし
⑤ catchで処理できたので続行 終了を表示

catchで処理した後に、失敗したParseの次へ自動的に戻るわけではありません。やり直しが必要なら、再試行の回数と条件を自分で設計します。無条件に繰り返すと、解決しない失敗を延々と繰り返します。

通常の例外処理の範囲で、finallyを含む二つの経路を比べます。

finallyは後始末を置く場所で、失敗した処理をやり直す場所ではありません。強制的なプロセス終了などまで含めて必ず動くと一般化しないでください。

どこでcatchするか

呼び出し先で対応できるcatchがないと、例外は呼び出し元へ伝わります。各層で何でもcatchする必要はありません。「入力を求め直せる」「代替結果を返せる」「要求をエラー応答へ変換できる」など、適切な対応ができる境界で受け取ります。

C# · 独立したコード例
try
{
    Console.WriteLine(ReadQuantity("abc"));
}
catch (FormatException)
{
    Console.WriteLine("数量を入力し直してください");
}

static int ReadQuantity(string input)
{
    return int.Parse(input);
}

期待出力は数量を入力し直してくださいです。ReadQuantity内の例外が呼び出し側のcatchへ届きます。これは伝播を理解する教材例で、ユーザー入力の実装ではTryParseも検討します。下位メソッドで勝手に画面表示するより、利用側がどう知らせるかを決めやすくなります。

catchを複数書く場合は、具体的な型を先、広い基底型を後へ置きます。Exceptionを先に受け取ると、派生する多くの例外を先に捕まえてしまいます。コンパイラーが到達不能なcatchを指摘する場合もあります。

IDisposableとusingの目的

GCは不要なマネージドメモリを回収対象にします。しかし、ファイル、ネットワーク接続、OSのハンドルなどは、必要な時点で利用を終える必要があります。ハンドルはOSが管理する資源を識別・操作するための値です。資源を閉じる処理をDisposeとして提供する契約がIDisposableです。

using文・using宣言は、対象を使う範囲を抜けるときにDisposeを呼ぶための構文です。名前空間を取り込むusing System;とは別の役割です。usingを付けてもオブジェクトのメモリがその瞬間に必ず回収されるわけではありません。

C# · 独立したコード例
Console.WriteLine("外側の開始");
using (var resource = new TraceResource())
{
    Console.WriteLine("利用中");
}
Console.WriteLine("外側の続き");

public sealed class TraceResource : IDisposable
{
    public TraceResource() { Console.WriteLine("生成"); }
    public void Dispose() { Console.WriteLine("解放処理"); }
}

期待出力は外側の開始、生成、利用中、解放処理、外側の続きです。このTraceResourceは順序を観察するための教材用クラスで、実際のOS資源を保持していません。Disposeのタイミングが、実体を使う範囲の終わりへ結び付いていることを確認します。

概念的には、生成後の利用をtryで囲み、finallyでDisposeを行う形に近いものです。ただし、対象の型や構文に応じた言語上の規則があるため、生成コードの細部を完全に同一とは扱いません。生成そのものが失敗した場合は、まだ受け取れていない実体に対してDisposeする流れにはなりません。

using宣言と早期return

C# · 独立したコード例
Process();

static void Process()
{
    using var resource = new TraceResource();
    Console.WriteLine("処理");
    return;
}

public sealed class TraceResource : IDisposable
{
    public TraceResource() { Console.WriteLine("生成"); }
    public void Dispose() { Console.WriteLine("解放処理"); }
}

期待出力は生成、処理、解放処理です。using宣言はその宣言を含むスコープの終わりでDisposeします。必要な範囲より広いメソッドの先頭へ置くと、資源を長く保持してしまう場合があります。狭い範囲で閉じたいならusing文のブロックを使います。

非同期で解放処理を待つIAsyncDisposableとawait usingもあります。非同期とは待ち時間に実行スレッドを占有し続けない形で処理を組み立てることで、Lesson 23以降で扱います。今はDisposeとGCを分け、usingのスコープが寿命を決めることを理解します。

本文の実例との対応：例外が発生したときの資源の解放

次の図は本文の実例「一行ずつ読み、読み取りを終了する」を使った補助例です。この節のコードとは変数や入力値が異なるため、処理の対応に注目します。

using宣言を持つスコープの途中でreturnする場合も、正常なスコープ離脱の処理としてDisposeが行われます。

returnの後にDisposeを書くだけでは、その行へ到達できません。usingで範囲を表せば、早期returnや通常の例外伝播での離脱にも対応できます。

境界値・比較

境界・比較例：例外時も呼ばれるDispose

例外で通常の処理を中断しても、usingの範囲を抜けるときにDisposeが呼ばれ、その後でcatchへ移ります。

C# · Program.cs
try
{
    using var resource = new DemoResource();
    throw new InvalidOperationException();
}
catch (InvalidOperationException) { Console.WriteLine("catch"); }
class DemoResource : IDisposable
{
    public void Dispose() => Console.WriteLine("Dispose");
}

Dispose
catch

実用例：文字列を一行ずつ読む

C# · 独立したコード例
using var reader = new StringReader("C#\n.NET\nWeb API");
string? line;
int lineNumber = 0;
while ((line = reader.ReadLine()) is not null)
{
    lineNumber++;
    Console.WriteLine($"{lineNumber}: {line}");
}

期待出力は1: C#、2: .NET、3: Web APIです。StringReaderは文字列を読み取り元として扱う部品です。\nはコード上で改行文字を表すエスケープです。通常の引用符付き文字列へ、意図せずソースの実改行をそのまま入れると別の構文エラーになるため注意します。

条件式のかっこ内でReadLineの結果をlineへ代入し、それがnullでない間だけ本体を実行します。最後の行の後はnullになり、ループを抜けます。各回でReadLineが進むので、状態が変わらない無限ループではありません。using宣言により、スコープを終えるとreaderのDisposeが呼ばれます。StringReaderはOSのファイルハンドルを持つ例ではありませんが、同じ利用パターンを安全に学べます。

間違い：例外を握りつぶす

C# · 独立したコード例
int quantity = 0;
try
{
    quantity = int.Parse("abc");
}
catch (Exception)
{
}
Console.WriteLine($"数量={quantity}");

この問題例の期待出力は数量=0です。変換に失敗したのに、正常に0を入力したかのように続いてしまいます。空のcatchは原因の情報を失わせ、不正な状態を成功に見せることがあります。catchした事実と、回復できたことは同じではありません。

修正位置は例外の扱いと続行条件です。入力ならTryParseへ変えて失敗を明示する方法があります。

C# · 独立したコード例
if (!int.TryParse("abc", out int quantity))
{
    Console.WriteLine("数量の変換に失敗しました");
    return;
}
Console.WriteLine($"数量={quantity}");

期待出力は数量の変換に失敗しましたです。内部処理で回復不能なら例外を上へ伝えます。catch内から同じ例外を再送出するときは通常throw;を使い、throw ex;で元の発生位置の情報を損なわないようにします。例外へ文脈を追加する場合は、元例外をinner exceptionとして保持する設計もあります。

間違い：使い終わる前にDisposeする

C# · 失敗を学ぶ例（そのまま起動しない）
var reader = new StringReader("C#");
reader.Dispose();
Console.WriteLine(reader.ReadLine());

解放後のreaderを利用しようとして、ObjectDisposedExceptionが起こります。nullとは異なり、参照は存在しても利用が終わった状態です。修正はDisposeをなくして永久に保持することではなく、利用を終えた後へ寿命を合わせることです。

C# · 独立したコード例
using var reader = new StringReader("C#");
Console.WriteLine(reader.ReadLine());

期待出力はC#です。誰が生成し、誰が所有し、どこで利用を終えるかを決めます。DIから渡された部品を利用側が勝手にDisposeすると、他の利用側が壊れる場合もあります。所有権と寿命はLesson 31で再登場します。

資源を返す側でusingを終えてしまうと、受け取った側がすでに破棄済みの資源を使うことがあります。

どの処理が資源を所有し、いつDisposeするかを明確にします。他から借りた資源を勝手に破棄してよいとは限りません。

選択基準と段階別の練習

仕組み 解決すること 解決しないこと
Try系API 想定される失敗を結果で分ける すべての予期しない障害の回復
try/catch 対応できる例外を受け取る 不正な状態を自動で元に戻す
finally スコープを抜ける際の後片付け プロセス強制終了時の完全保証
using / Dispose 所有する資源の利用終了 メモリをその瞬間に必ず回収
GC 到達不能なマネージドメモリの回収 外部資源を必要時刻に必ず閉じる

基礎課題はtryのParseを"12"へ変え、どの表示がなくなるかを説明することです。catchは実行されず、finallyは実行されます。標準課題はTraceResourceのusing本体で例外を投げ、外側でcatchし、Disposeがcatchの前に行われる流れを追うことです。

応用課題は処理の各段階をログへ残す場合、同じ例外をすべての層で重複記録しない方針を考えることです。利用者向けの短い説明と、開発者向けの原因・発生位置は役割を分けます。認証情報や個人情報を例外ログへ無条件に書かない配慮も必要です。次の章では処理自体を値として渡すラムダ・デリゲートを学びます。
