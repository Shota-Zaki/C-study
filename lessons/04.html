文字列と入力の変換

文字列を数量として受け付ける条件。

.NET 10 / C# 14
本文・演習詳細解説
重要TryParseの成功と、業務上有効な値であることは別々に確認します。

図解：文字列を数量として受け付ける条件

要点

  • 文字列補間と書式を使う
  • 失敗を想定して数値へ変換する
重要

TryParseは変換の成否と変換後の値を分けて扱えます。string同士の==は文字列内容の等値性を判定します。

C#
string message = $"合計: {total}";

概念・構文

外から来るデータは、正しい値になる前はただの文字列です。「数字として読める」「許された範囲に入る」「画面にどう表示するか」を別の工程として扱います。C#の文字列の等値性と比較ルールもここで確認します。

文字列を組み立てる

C#では$"名前は{name}"と書くと、波括弧内の式が文字列へ埋め込まれます。stringは不変なので、TrimやReplaceなどの結果は新しい文字列です。元の変数を更新したい場合は戻り値を代入します。長さはLengthプロパティで取得し、length()メソッドではありません。

文字列の==は内容を比較する

両辺がstring型なら==は文字列の内容を比較します。一方、objectとして扱った場合やユーザー定義型では演算子の意味が異なることがあります。大文字小文字を無視する識別子比較などではStringComparison.OrdinalIgnoreCaseのように比較ルールを明示します。

入力失敗は通常の分岐で扱う

Console.ReadLine()など外部入力は、不正な形式やnullを含み得ます。int.TryParse(input, out int value)は成功したかをboolで返し、変換した値をout引数へ格納します。数字でない入力や範囲外を分岐で処理できるため、入力ミスのたびに例外を使う必要はありません。変換成功後も、年齢なら0以上など業務上の条件を別に確認します。

文字列を数値として読む前の三段階

Console.ReadLine()は入力が終わるとnullを返す可能性があり、値が必ずあるとは限りません。文字列があっても"abc"は整数として解釈できません。整数として読めても、年齢として-5や人数として0が許されるかは別問題です。nullや空欄の判定、形式の解析、業務上の範囲確認を分けると、ユーザーへ理由を返しやすくなります。

TryParseは成功をboolで返し、out引数へ変換結果を設定します。失敗時の結果値だけを見て判断してはいけません。int.TryParse("abc", out int value)はfalseでvalueは0になりますが、"0"の変換は成功してvalueが0になります。同じ0でも成功・失敗は異なるので、戻り値と値をセットで扱います。

短絡評価は安全な処理順を作る

int.TryParse(input, out int value) && value >= 1という式では、左辺がfalseなら右辺を評価しません。この短絡評価を使うと、変換成功後にだけ範囲判定を行えます。条件を読みやすく分割し、「形式が不正」と「範囲が不正」のメッセージを分けてもよいでしょう。短く書くことより、失敗理由を設計に反映できることが重要です。

ユーザー入力の誤りが通常の操作として発生するなら、ParseしてFormatExceptionを繰り返し捕捉するより、TryParseの成功・失敗として表す方が意図が明確です。ただしこの方針は例外を一切使わないという意味ではありません。ファイル読込失敗や想定外の障害と、利用者が数字を打ち間違えるケースを分けます。

stringは参照型だが、通常の==は内容を比較する

C#のstring同士の==は文字列の内容を比較します。ただしobject型として比較した場合や演算子が定義された独自型では話が変わるため、「C#の==はすべて内容比較」と一般化しないでください。

大文字小文字を無視して識別子を比較するなら、string.Equals(a,b,StringComparison.OrdinalIgnoreCase)のように方針を明示します。ユーザー向けの自然言語の並べ替えと、内部コードやキーの比較は同じ要件ではありません。文字列を全部ToLowerしてから比較する方法は、新しい文字列を作り、カルチャーにも左右されるため、比較用APIがある場面ではそれを使います。

不変性・エスケープ・文字数の注意

stringは変更不能です。TrimやReplaceは元の文字列の内容をその場で書き換えるのではなく、結果の文字列を返します。raw.Trim();だけではrawの参照は置き換わりません。raw = raw.Trim();または別の変数へ受け取る必要があります。大量に連結する場面ではStringBuilderを検討しますが、数回の補間に一律で使う必要はありません。

通常の文字列では改行を\n、バックスラッシュを\\のように表現します。パスでは@"C:\work"のような逐語的文字列も使えます。さらにstring.Lengthが数えるのはUTF-16のコード単位です。絵文字などは見た目の一文字がLength=1とは限らないため、入力制限で「文字数」を使う場合は何を数える仕様かを明確にします。

仕組みの補足

文字列と数値の違い

画面で見える120は文字の並びとして表現されます。string text = "120";は文字列、int number = 120;は整数です。文字列の+は結合、整数の+は加算なので、"12" + "3"は"123"、12 + 3は15になります。入力を計算へ使うには、文字列の意味を読み取って数値へ変換する必要があります。この読み取りを解析、英語でparseと呼びます。

文字列はstring型の値です。C#のstringは内容をその場で変更できない性質を持ちます。この性質を不変と呼びます。TrimやReplaceは元の文字列の内容を書き換えるのではなく、結果となる文字列を返します。変数へ別の文字列を再代入することはできます。内容が不変であることと、変数へ再代入できないことは別です。

C# · 独立したコード例
string text = "  C#  ";
string cleaned = text.Trim();
Console.WriteLine($"[{text}]");
Console.WriteLine($"[{cleaned}]");
Console.WriteLine(text.Length);
Console.WriteLine(cleaned.Length);

想定される出力 / データ

6
2

Trim()は前後の空白を除いた結果を返します。[]を付けるのは、目に見えにくい空白の違いを観察するためです。Lengthは文字列の長さを読むプロパティで、UTF-16コード単位の数です。UTF-16は文字を数値単位で表現する方式で、絵文字などは見た目の一文字が複数単位になる場合があります。人が見た一文字を数えたい場合は単純なLengthと要件が一致するか検討します。

入力の三つの状態

Console.ReadLine()は通常、一行の入力を文字列で返します。何も入力せずにEnterを押すと空文字列""になります。入力の終わりを受け取った場合はnullを返し得ます。nullは文字列の内容ではなく「参照する値がない」ことを表す特別な値です。空文字、空白だけの文字列、nullは別々に考えます。

値 意味 数値へ変換できるか

"" 長さ0の文字列 数字がなく失敗
" " 空白だけの文字列 数字がなく失敗

null 入力終端などで文字列自体がない TryParseは失敗として扱える

この段階では、string?の?はnullの可能性を表す注釈、と理解してください。詳しいコンパイラーの検査はLesson 08で扱います。どんな入力も必ず数値になると仮定せず、成功と失敗の二つの流れを設計することが重要です。

よくある間違い

TryParse成功は「業務上も正しい値」の保証ではありません。-10もintへの変換は成功します。数値範囲や空欄を受け付けるかは別途検証します。

Trimを呼んだのに空白が残る

修正後の確認

  • 出力が[C#]になる
  • raw自体の内容は変わっていない
  • 空白だけの入力なら[]になる

実例：購入数量の入力検証

実務例：コマンド名など機械的な識別では、カルチャー依存を避ける比較方式を明示する。

確認問題

Q1. string a = "hi"; string b = new string(new[] {'h', 'i'}); a == b は？
解説：string同士の==は内容で比較します。

string同士の==は内容を比較する規則を持ちます。newで別の実体を作ったことだけからFalseと判断するのは参照同一性との混同です。

解説：どちらも有効なstringです。

char配列からstringを作るコンストラクターがあり、どちらの変数もstringです。異なる作り方であることは構文エラーの理由になりません。

正解：文字列の内容が一致しています。

どちらもhとiが同じ順に並ぶためTrueです。同じオブジェクトかまで確認したい場合にはReferenceEqualsという別の問いになります。

解説：この説明は通常のclassの参照比較とは区別します。

文字列は通常のclassで既定の参照比較をする場合とは異なります。==の意味は使う型により変わることを確認します。

Q2. int.TryParse("-5", out int n) の結果は？
解説：-5はintとして正しい形式です。

負号を含む-5はintの範囲内の整数です。数量として許せない場合でも、解析が失敗したことにはなりません。

解説：この入力では例外を投げません。

TryParseはこの有効な入力では成功を返します。入力ミスを例外で受けるParseと、成否をboolで受けるTryParseの役割も区別します。

解説：失敗ではありません。

0になるのはこの例の解析結果ではありません。負数を業務上拒否したいなら、変換成功の後にn>0などの条件を別に確認します。

正解：変換できることと、業務上許可することは別です。

trueで数値として読めたことを示し、outのnへ-5が入ります。形式の検証と業務上の範囲検証を二段階で行います。

Q3. int.TryParse("abc", out int x)でxが0でした。何から失敗を判断しますか？
解説：入力"0"も変換結果が0なので、成功と失敗を区別できません。

"0"を読むと成功して0、"abc"を読むと失敗して0です。同じout値になるので、xだけから成功・失敗を逆算できません。

解説：出力の呼び出しは解析結果の成否を定義しません。

Console.WriteLineは値を表示するだけです。表示の仕方ではなく、TryParseが返したboolをifで調べることで制御を分けます。

正解：falseが変換失敗を表し、out値とは別に判定します。

boolがtrueなら解析できた値、falseなら失敗という契約です。out値は別の出力なので、先に成否を判断してから業務処理へ進みます。

解説：同じ文字数でも数値として有効な入力と無効な入力があります。

"123"と"abc"はどちらも3文字です。文字数の条件だけでは数字の構成やintの範囲を判断できません。

Q4. string a="C#"; string b=new string(new[]{'C','#'}); a==bは？
解説：有効な文字列同士の比較なので、この条件で例外にはなりません。

nullの逆参照や範囲外操作を行っているわけではありません。内容の比較という有効な操作なので、例外を想定する根拠がありません。

解説：等値比較の意味は言語と型の規則で決まっています。

==は型に定められた規則で評価します。同じ入力と同じ比較条件なら、コンパイラーが気まぐれで結果を変えるものではありません。

解説：string同士の==は、参照が別でも文字列内容が同じならTrueになります。

参照が別であることはReferenceEqualsでは重要ですが、string同士の==では文字内容が判断基準です。比較対象の型を先に見ます。

正解：C#のstringの==は文字列内容が一致するかを比較します。

両方ともCと#が同じ順に並んでいます。大文字・小文字や空白が変われば内容が違うため、このTrueの根拠は具体的な文字列です。

Q5. raw.Trim();だけを実行した場合、rawは？
解説：実行中にローカル変数の静的な型が変化することはありません。

Trimの戻り値もstringです。変数の型を別の型へ置き換える操作ではなく、整えた文字列を受け取る必要があります。

解説：Trimは戻り値を返すため、rawを更新するには代入が必要です。

`raw = raw.Trim();`なら変数を新しい結果へ付け替えられます。呼び出しただけの形では戻り値を捨てています。

正解：戻り値を捨てているので、変数の参照は置き換わりません。

stringは内容を直接書き換えない型です。Trimは必要な結果を返し、元のraw変数への代入は呼び出し側で明示します。

解説：Trimが呼び出し元の変数へnullを代入することはありません。

raw自体がnullなら呼び出しが失敗しますが、Trimがrawをnullへ更新するわけではありません。前提のnullと操作の戻り値を分けます。
