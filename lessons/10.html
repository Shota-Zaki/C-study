Lesson 10 · Chapter 3

プロパティとカプセル化

在庫を変更する入口。

.NET 10 / C# 14
本文・演習詳細解説
重要状態の変更をメソッドへ集めると、検証を通らずに不正な値へ変わることを防げます。

図解：在庫を変更する入口

要点

  • get・private set・initを使い分ける
  • 勝手に変更させない状態を設計する
重要

プロパティは値の読み書きに契約を持たせる構文です。get、private set、init、requiredなどを、変更できる時期と責任に合わせて選びます。

C#
public int Count { get; private set; }

概念・構文

C#のプロパティはフィールドを短く書くためだけの機能ではありません。値の読み取りと更新の入口を制御し、外側に公開する契約を作ります。public set、private set、init、getのみの違いを、残高や在庫のルールと結び付けて学びます。

フィールドとプロパティは違う

public int Count { get; private set; }はプロパティです。外部はCountを読めますが、設定できるのは型の内部です。自動実装プロパティではコンパイラーが裏側の保存領域を用意します。単に全フィールドをpublicにするより、後から検証や計算を加えやすくなります。

状態の変更を操作として表す

在庫ならCount = -100を外から許可するのではなく、AddやRemoveで条件を検証して変更します。プロパティを公開しただけでカプセル化できたとは限りません。get/setが何でも許す状態なら、不正なデータが入り込む点はpublicフィールドと変わりません。

initとrequiredの役割

initは主にオブジェクトの初期化時に設定し、その後の代入を制限します。requiredは呼び出し側に初期化を要求するコンパイル時の仕組みです。ただし空文字や不正な範囲まで自動検証するわけではありません。参照先のListをinitで持っても、リストの中身まで不変にはなりません。

プロパティはget/setを持つメンバー

public int Count { get; set; }は自動実装プロパティで、コンパイラーが格納用フィールドを生成します。外側のinventory.Countという記法はフィールドに似ていますが、getやsetというアクセサーを介します。必要に応じて検証や計算を実装でき、公開する名前を保ちながら内部の表現を変更できます。

一方、プロパティのgetterへ時間のかかる通信や状態を破壊する処理を隠すと、単なる値の参照に見えるコードから予想外の副作用が起こります。Total => Price * Quantityのような軽い計算は自然ですが、DB検索や通知はメソッドとして目的を示した方がよい場合があります。構文上可能なことと利用者に理解しやすいAPIは別です。

残高の変更を意味のある操作へ限定する

Balanceにpublic setを付けると、外側から-100の代入や根拠のない上書きができます。private setにしてDepositやTryWithdrawへ操作を絞れば、入金は正の金額、引き出しは残高以内というルールを更新の入口で守れます。単にsetをprivateにしただけで安全になるのではなく、公開メソッドの検証も必要です。

Balance += amountは現在値の読み取りと新しい値の設定です。将来、入金記録や上限検証を加える場合にもDepositという意味のある入口があれば、利用側の呼び出し方を保ちながら変更できます。ただし将来の全機能を予測して過剰な抽象化を加える必要はありません。現在守るべき状態と操作を明確にします。

getのみ・private set・initの時間軸

getのみの自動実装プロパティは、コンストラクターなどで値を設定し、外側からの代入を許しません。private setは型の中の処理から更新できます。initは通常、オブジェクト初期化などの初期化フェーズで設定でき、生成後の通常の代入を制限します。誰がいつ変更できるかという二軸で比べると区別できます。

initだから参照先の中身まで不変というわけではありません。public List<string> Tags { get; init; }なら生成後のTagsの再代入は制限されてもTags.Addは可能です。コレクションを外へ返す場合は、その実体を変更してよいか、読み取り専用の見せ方で十分か、コピーが必要かを別に判断します。

requiredとC# 14のfieldを過信しない

requiredはオブジェクトを作る側にそのメンバーの初期化を要求する機能です。空文字や負数まで自動的に拒否する業務検証ではありません。required string Title { get; init; }へTitle=""を渡すことは、初期化という要求自体は満たします。注釈・初期化要求・業務条件の検証を三つに分けます。

C# 14のfieldを使うと、アクセサー内からコンパイラー生成の格納用フィールドを参照できます。手書きの_nameなどを省けますが、検証の設計が自動化されるわけではありません。明示的なフィールドやprivate setでも、検証とアクセス制御を実装できます。

仕組みの補足

カプセル化と変更経路の制限

カプセル化は、内部状態を隠すだけでなく、外部がどの操作を通して状態を利用・変更できるかを設計することです。在庫数をpublicフィールドで公開すると、どこからでも-100を代入できます。「在庫は負にならない」という規則を守るには、変更を一つの入口へ集める必要があります。

不変条件とは、正常なオブジェクトがいつも満たすべき条件です。残高が負でない、名前が空でない、といった条件です。すべての呼び出し側へ毎回同じ注意を要求するより、オブジェクト自身が許された変更だけを公開すると、チームで機能を追加しても規則を維持しやすくなります。

プロパティはフィールドのような見た目でアクセスできるメンバーですが、読み取りや書き込みはアクセサーという処理で実装します。getは読む処理、setは書く処理です。自動実装プロパティではコンパイラーが保存用のフィールドとアクセサーを生成します。プロパティが必ず一つの値を保存しているとは限らず、読むたびに計算するものもあります。

最小例：保存する値と計算する値

C# · 独立したコード例
var item = new LineItem(120, 3);
Console.WriteLine(item.UnitPrice);
Console.WriteLine(item.Quantity);
Console.WriteLine(item.Total);

public class LineItem
{
    public int UnitPrice { get; }
    public int Quantity { get; }
    public int Total => UnitPrice * Quantity;

    public LineItem(int unitPrice, int quantity)
    {
        UnitPrice = unitPrice;
        Quantity = quantity;
    }
}

期待出力は120、3、360です。UnitPriceとQuantityは生成時に設定する自動実装プロパティです。Totalは読み取り時に計算するプロパティで、別のtotalフィールドへ360を保存していません。=>は一つの式の結果を返す記法です。

計算結果まで重複して保存すると、数量だけ変えた後でtotalを更新し忘れる可能性があります。軽い計算なら元の値から求めることで不整合を減らせます。ただし、プロパティを読むだけで重い通信やファイル書き込みが起こると利用者が予測しにくくなるため、そのような処理は意図の分かるメソッドにします。

public class Stock
{
    public int Count { get; private set; }
    public void Add(int amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount));
        Count = checked(Count + amount);
    }
    public bool TryTake(int amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount));
        if (amount > Count) return false;
        Count -= amount;
        return true;

よくある間違い

public List<T> Items { get; }としても呼び出し側がItems.Addできます。getだけで「深い不変性」が得られるわけではありません。

外部代入で残高が負数になる

修正箇所: Wallet.Balanceの公開setter

修正前

csharp
var wallet = new Wallet();
wallet.Balance = -100;
public class Wallet { public decimal Balance { get; set; } }

修正後

csharp
var wallet = new Wallet();
wallet.Deposit(100m);
Console.WriteLine(wallet.Balance);
public class Wallet
{
    public decimal Balance { get; private set; }
    public void Deposit(decimal amount)
    {
        if (amount <= 0) throw new ArgumentOutOfRangeException(nameof(amount));
        Balance += amount;
    }
}
変更理由

直接代入を非公開にし、正数だけ受け付けるDepositへ変更を集約します。型の不変条件「残高を不正な方法で減らさない」を、公開APIから破りにくくします。

修正後の確認

  • 100の入金で残高100
  • 負数のDepositは例外
  • 外部からBalanceへ代入するコードはコンパイル不可
実コード例

実例：在庫数を負数にしない設計

発送数量を検証し、在庫不足なら状態を変更しません。

C# · Program.cs
var stock = new Stock(5);
Console.WriteLine(stock.TryShip(3));
Console.WriteLine(stock.TryShip(9));
Console.WriteLine(stock.Quantity);
class Stock
{
    public int Quantity { get; private set; }
    public Stock(int quantity)
    {
        if (quantity < 0) throw new ArgumentOutOfRangeException(nameof(quantity));
        Quantity = quantity;
    }
    public bool TryShip(int amount)
    {
        if (amount <= 0 || amount > Quantity) return false;
        Quantity -= amount;
        return true;
    }
}

True
False

処理と値の変化

  1. 3個を発送5個から3個減り2個になる
  2. 9個を発送在庫不足なのでfalseを返す
  3. 失敗後の状態減算していないため2個のまま
条件を変えた場合

0個と-1個の発送もfalseになり、在庫は変わりません。

確認問題

Q1. public int Count { get; private set; }で外部からできることは？
解説：setがprivateなので外部からは設定できません。

Countを読むアクセスとsetterへ書くアクセスを分けています。外部でCount=3とすると、private setterへアクセスできずエラーになります。

解説：getはpublicです。

getは公開されているため読み取りは可能です。privateが付いているのはsetだけなので、どのアクセサーを制限しているか確認します。

正解：外部から読むことは可能です。変更は型の内部に限定されます。

外部はstock.Countで状態を確認し、変更はTryTakeなど型が公開する適切な操作を通します。単なる読み取り専用値とは異なり内部では更新できます。

解説：プロパティ自体はpublicです。

プロパティ全体がprivateなのではありません。publicとアクセサーごとのprivateを分けて読み、見える情報と変更できる操作を判断します。

Q2. required string Title { get; init; }は空文字を自動拒否する？
解説：requiredは初期化の要求であり、入力内容の検証ではありません。

requiredは初期化を要求する仕組みです。Title=""という指定も初期化にはなるため、空文字の拒否を別に設計します。

解説：空白検証は自分で設計します。

空白は有効なstringの内容です。string.IsNullOrWhiteSpaceなどの検証を自分の業務ルールとして追加しなければ、空白だけの値も入り得ます。

解説：文字数の制約は付いていません。

上限100という数値は宣言のどこにもありません。名前や修飾子から業務の範囲制約まで推測せず、検証コードを確認します。

正解：初期化されていても、不適切な文字列は入り得ます。

requiredとinitは「初期化の要求」と「設定できる時期」を表します。値が利用目的に合うかはコンストラクターや作成処理などで守ります。

Q3. required string Title {get;init;}へTitle=""を指定した場合は？
解説：空文字からnullへ自動変換する機能ではありません。

空文字は長さ0のstringでありnullとは別です。requiredは空文字を欠損へ変換する機能ではないので、指定した値の意味はそのままです。

解説：空文字の設定自体は初期化として可能です。

Titleへ値を指定しているため、初期化要求の観点では成立します。コンパイルできても業務データとして正しいとは限らない例です。

解説：requiredは値の業務上の妥当性を自動判定しません。

requiredの役割を内容検証と取り違えています。空文字・空白・長すぎる文字列などは、それぞれ別の入力条件として扱います。

正解：値を設定したことと、内容が有効であることは別です。

宣言を満たしたことと有効なタイトルであることを二段階で判断します。Titleの検証を追加し、初期化後に無効状態を作れないよう設計します。

Q4. TotalがPrice*Quantityで決まるとき、軽い計算プロパティにする利点は？
解説：計算プロパティに保存の副作用を入れる必要はありません。

プロパティは読み取り時に計算できますが、DB保存を伴う必要はありません。軽い状態参照へ予期しない外部I/Oを隠すと利用側が困ります。

解説：プロパティの型は宣言した戻り値によって決まります。

PriceとQuantityからintやdecimalなど宣言した型の値を返します。計算したという理由だけで値型が参照型になるわけではありません。

正解：元データから求めるので重複状態の不整合を避けられます。

PriceやQuantityが変わるたびに別のTotalを更新する必要がなくなります。二重に持つ同じ情報がずれる問題を、元から計算することで減らします。

解説：getterを評価すれば式の計算は行われます。

Totalを読むとgetterのPrice*Quantityを評価します。式を保存しただけで永久に同じ結果を返すわけではないため、計算コストも考えます。

Q5. get; private set;のプロパティは？
解説：型の内部ではsetterへアクセスできます。

型の内部のメソッドはprivate setterを呼べます。外から直接変更できないことと、生成後に一切変わらないことは違います。

解説：privateは外部に変更を許可する意味ではありません。

privateはアクセスを狭める指定です。外部だけに変更を許す仕組みではなく、状態変更を型が管理できるようにします。

解説：生成後も型内部のメソッドから更新できます。initとは異なります。

initなら初期化時期の制限ですが、private setは呼び出せる場所の制限です。型内部の通常メソッドなら生成後にも値を更新できます。

正解：公開する読み取りと、制限する変更を分けた指定です。

読み取りは公開し、状態変更の入口をメソッドなどへ絞れます。たとえば在庫が負にならないよう、更新前の検証を必ず通せます。

理解チェックと公式資料

  • フィールドとプロパティを区別できる
  • 状態更新を意味のあるメソッドへ集約できる
  • requiredと入力検証を混同しない
  • initやprivate setの変更範囲を説明できる
