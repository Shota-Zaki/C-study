概念と内部の仕組み

C#のdecimal、var、const、readonlyは、それぞれ「値の種類」「型の決まり方」「変更を許す範囲」に関係します。ここでは「格納できる値」「式を評価する型」「変更を許す範囲」の三つを分けます。計算結果の変数だけをdoubleにしても整数除算を修正できない理由まで追います。

varは型をなくさない

int・long・double・boolは用途ごとに値の種類と範囲が異なります。C#のstringはSystem.Stringの別名です。var count = 3;なら、コンパイラーがcountをintと判断します。後から文字列を代入できる「何でも入る箱」ではありません。型を文脈から読み取れる場所でvarを使い、読み手が迷う場所では型名を明示しましょう。

整数と小数を混ぜる前に

int同士の7 / 2は3です。計算後にdoubleへ代入しても小数部分は戻りません。7 / 2.0のように演算時点で小数にします。金額など10進数の精度を重視する場面ではdecimalを検討し、800mのようにmを付けます。decimalでも丸め方や有効桁数の設計は必要です。

constとreadonlyは別物

constはコンパイル時に確定する定数です。readonlyフィールドは宣言時またはコンストラクターで設定できます。参照先がListの場合、readonlyでもAddによる中身の変更は可能です。参照そのものの再代入と、参照先オブジェクトの変更は別の制約です。

変数の型と式の型は別々に決まる

intは32ビットの符号付き整数、longはより広い範囲の整数です。doubleは浮動小数点数、decimalは10進小数の精度を重視する場面で検討する型です。C#のintはSystem.Int32の別名で、List<int>のように値型をジェネリック型引数にも直接指定できます。

7 / 2は両辺がintなので整数除算として評価され、結果は3です。double answer = 7 / 2;でも、まず3が計算されてから3.0として代入されます。小数の商が必要なら7 / 2.0や(double)7 / 2のように、計算前のオペランドを変えます。これは表示形式を変える問題ではなく、演算自体の型の問題です。

decimalと丸め規則を別々に設計する

小数リテラルにmを付けるとdecimalです。0.1mと0.1は異なる型で、decimalとdoubleを混ぜる演算には明示的な変換が必要になる場合があります。金額の例でdecimalを使うのは、十進小数を扱う意図を型に表すためです。ただしdecimalでも表現できる桁数と範囲には限界があり、無限精度ではありません。

「金額にdecimalを使えば正しい」は不十分です。税を明細ごとに丸めるか合計後に丸めるか、小数点以下を切り捨てるか四捨五入するかを決める必要があります。Math.Roundは指定によって丸め方が変わります。教材では計算と丸めのルールを明示し、ToStringの表示桁を変えるだけで業務計算を丸めたつもりにならないようにします。

varは型推論であって、型の省略ではない

var count = 3;のcountはコンパイル時にintと決まります。その後count = "3";とは書けません。右辺の型が明らかなnew List<string>()などではvarが重複を減らします。一方、メソッド名だけでは戻り値が想像しにくい場合は型を明示すると読みやすくなります。短ければ常によいという判断ではありません。

varは初期化式が必要です。var x = null;では具体的な型を推論できません。nullを扱いたければstring? x = null;などの型情報を与えます。varを使うこととnull許容かどうかは別問題です。動的なメンバー解決を行うdynamicは異なる機能なので、型推論を説明するためにdynamicという言葉を使わないようにしましょう。

const・readonly・オーバーフロー

constはコンパイル時に確定する値に使います。readonlyフィールドは宣言時や対応するコンストラクターなど、許された場所での代入に制限します。readonly List<int>でもListの中身の追加は可能で、参照の再代入制限と内容の不変性は別です。

整数には範囲があり、範囲を越える演算にはcheckedで例外検出を指定できます。暗黙の変換が許される拡大変換でも、たとえば大きなlongからdoubleへの変換では精度をすべて保持できるとは限りません。範囲と精度を分けて考え、金額・件数・識別子で必要な型とエラー時の扱いを決めます。

概念をもう一段掘り下げる

型があると何を防げるのか

型は値の種類と許される操作を定める規則です。「年齢」と「名前」をどちらも曖昧な箱として扱うと、名前へ1を加えるような処理が紛れ込みます。int age = 20;、string name = "Aoi";と宣言すれば、コンパイラーは操作の組み合わせを検査できます。型は値の保存形式だけでなく、プログラムを書く人へ意図を伝える役割も持ちます。

変数宣言は名前と型を決め、初期化は最初の値を与えます。int score;のように宣言だけをしたローカル変数は、値を代入する前に読み取れません。「メモリの中に何かあるはずだから読める」とは扱わず、すべての実行経路で値が決まるかをコンパイラーが検査します。フィールドや配列要素の既定値とは規則が異なります。

整数には範囲があります。intは符号付き32ビット整数で、-2,147,483,648から2,147,483,647までを表せます。longはより広い範囲の符号付き64ビット整数です。範囲を超える可能性がある件数や合計は、業務上の最大値を考えて選びます。型が大きければすべて解決するわけではなく、必要な範囲・精度・単位を先に定めます。

構文と式の評価

C# · 独立したコード例
int quantity = 3;
int unitPrice = 120;
int total = quantity * unitPrice;
Console.WriteLine(total);

期待出力は360です。intは型、quantityは名前、=は代入、3は初期値、;は文の終わりです。quantity * unitPriceは値を計算する式です。この式にも型があり、この例では二つのintからintの結果を作ります。

順序 式が読む値 計算・保存 状態
① 3 quantityを初期化 quantity=3
② 120 unitPriceを初期化 quantity=3, unitPrice=120
③ 3と120 360をtotalへ保存 total=360
④ totalの360 文字へ変換して表示 変数の値は変わらない

型情報はコンパイル時の検査に使われ、生成物にも型・メンバーの情報が含まれます。実行時のメモリ配置はCLRやJITの最適化にも関係します。「intなので必ずStackにある」と断定する必要はありません。まずintの代入では値がコピーされるという言語の意味を理解します。メモリの詳細はLesson 13と補助教材で扱います。

文法・実例・処理順

csharp
var count = 3;
const decimal unitPrice = 800m;
decimal total = unitPrice * count;
Console.WriteLine(total);
Console.WriteLine(7 / 2);
Console.WriteLine(7 / 2.0);

想定出力

2400 3 3.5

処理順

  1. countはintに決まり、unitPriceはdecimalの定数になる。
  2. 掛け算ではintからdecimalへ暗黙変換でき、2400になる。
  3. 整数除算は3、小数を含む除算は3.5になる。

値・状態の変化を追う

代入先が小数型でも整数除算は終わっている

csharp
using System.Globalization;
int total = 7;
int count = 2;
double lost = total / count;
double exact = (double)total / count;
decimal price = 125m;
decimal taxIncluded = price * 1.10m;
Console.WriteLine(lost.ToString("F1", CultureInfo.InvariantCulture));
Console.WriteLine(exact.ToString("F1", CultureInfo.InvariantCulture));
Console.WriteLine(taxIncluded.ToString("F2", CultureInfo.InvariantCulture));

出力

3.0 3.5 137.50
段階値・状態読み解き
lostの右辺int / int → intの3代入先を見て3.5へ計算し直すことはない
lostへの代入3をdoubleへ変換失った0.5は復元されない
exactの右辺7をdoubleに変換してから割るdouble / int → doubleの3.5
税込計算125m * 1.10m = 137.50mdecimal同士で計算する
ToStringF1とF2で表示桁を指定カルチャーを固定して小数点を一定にする

よくある間違いと修正

よくある間違い

byteはC#では0〜255です。数値型は名前だけでなく範囲と精度を確認してください。またdecimalとdoubleの混在は暗黙変換できません。

平均の小数部分が消える

修正箇所: 平均値を求める式

修正前

csharp
int sum = 5;
int count = 2;
double average = sum / count;
Console.WriteLine(average);

修正後

csharp
int sum = 5;
int count = 2;
double average = (double)sum / count;
Console.WriteLine(average.ToString("0.0", System.Globalization.CultureInfo.InvariantCulture));
変更理由

修正位置は代入先の型ではなく割り算の前です。sumをdoubleへ変換して小数を含む演算にすることで2.5を保持します。countが0になり得る処理では、別途「平均を定義できない場合」の分岐が必要です。

修正後の確認

  • 5/2が2.5になる
  • 6/2が3.0になる
  • 件数0の仕様を決めずに実データへ流用しない

処理と結果の読み解き

小計は3600、倍率は1.10、合計は3960。decimalのmを付け、整数個数と金額の意味を分ける。表示書式0はこの端数なしの条件に合わせている。

よくある別解と選び方

小計を別の変数へ分けてもよい。実務では端数が出る場合の丸め規則を追加し、表示形式だけで計算規則を決めない。

よくある間違いと確認箇所

10%を10として掛けると倍率が11になる。単価・数量・税率の単位を記録して確認する。

実務へのつながり：金額では型の選択だけでなく、端数をいつどう丸めるかを仕様で決める。

標準：割合を百分率へ変える

全80問中63問正解した正答率を小数第2位まで「78.75%」と表示します。整数除算にしないでください。

  • 正答数か問題数を計算前に小数型へ変える
  • 割合を100倍して百分率にする
  • InvariantCultureで小数点表記を固定する
開始コード
csharp
// 標準：割合を百分率へ変える
// 課題とテストケースを読んで、自分で実装してください。

入力例・前提条件

correct=63、total=80。出力は小数2桁の百分率。

考え方のヒント

(decimal)correctを割り算の前に置き、最後に100を掛ける。

入力するとlocalStorageへ保存実行・自動採点は行いません
解答例と確認ポイント
csharp
using System.Globalization;
int correct = 63;
int total = 80;
decimal percent = (decimal)correct / total * 100m;
Console.WriteLine($"{percent.ToString("F2", CultureInfo.InvariantCulture)}%");

想定出力

78.75%
  • 63/80をintで計算すると0なので、最初にdecimalへ変換する。
  • 計算結果0.7875を100倍して78.75にする。
  • 分母0はこの固定例にはない。一般化するときは総問題数0の表示仕様を先に決める。
入力 / 条件期待結果
63/8078.75%
80/80100.00%
0/800.00%

処理と結果の読み解き

63÷80は0.7875、百分率へすると78.75。F2で小数2桁の表示を選び、InvariantCultureで小数点表現を固定して%を付ける。

よくある別解と選び方

比率をdecimal変数へ保存してから百分率を求めても同じ。途中の比率をテストしやすくなる。

よくある間違いと確認箇所

int同士で先に割ると0になり、後からdecimalへ変えても失われた小数は戻らない。変換位置を確認する。

実務へのつながり：進捗率や達成率では、分母が0の条件も実際の要件として検討する。

応用

応用：丸める位置の違いを観察する

税込137.5円の明細が2件あります。各明細を0桁へAwayFromZeroで丸めた合計と、合計後に丸めた金額を表示し、差が生じる理由を説明します。

  • Math.Roundに桁数0を渡す
  • MidpointRounding.AwayFromZeroを明示する
  • 各件で丸める計算と合計で丸める計算を別の変数へ保存する
開始コード
csharp
// 応用：丸める位置の違いを観察する
// 課題とテストケースを読んで、自分で実装してください。

入力例・前提条件

各明細137.5mが2件。0桁、AwayFromZeroで丸める。

考え方のヒント

各明細を138にしてから足す場合と、275を先に作る場合を別々に計算する。

入力するとlocalStorageへ保存実行・自動採点は行いません
解答例と確認ポイント
csharp
decimal line = 137.5m;
decimal perLine = Math.Round(line, 0, MidpointRounding.AwayFromZero) * 2m;
decimal afterTotal = Math.Round(line * 2m, 0, MidpointRounding.AwayFromZero);
Console.WriteLine(perLine);
Console.WriteLine(afterTotal);

想定出力

276 275
  • 明細ごとでは137.5が138になり、138*2=276になる。
  • 合計後では137.5*2=275.0のため275になる。
  • 型が同じでも処理順序で結果は変わる。正しい業務仕様を先に決める必要がある。
入力 / 条件期待結果
137.5円×2件276 / 275
100円×2件200 / 200
137.4円×2件274 / 275

処理と結果の読み解き

明細ごとなら138×2=276。合計後なら137.5×2=275で既に整数。四捨五入のような丸めは計算の順序を変えると同じ結果になるとは限らない。

よくある別解と選び方

明細を配列にして一件ずつ丸める構成は後のコレクション学習で扱える。今は二つの式の中間結果を比較する。

よくある間違いと確認箇所

合計が違うことをdecimalの誤差と決めつけない。丸めを適用した時点が異なることが、この例の差の原因。

実務へのつながり：請求書などでは明細単位か合計単位かを契約で明示し、テストへ固定する。

確認問題

Q1. var count = 3; の後に count = "3"; を書くと？
正解：countはintに推論済みです。stringは代入できません。

初期値3はintなのでcountの型もintに決まります。"3"はstringであり、代入前に必要な変換を明示しなければ規則に合いません。

解説：varは動的な型変更を許しません。

varは型名をコンパイラーに推論させる記法です。初期化後に何でも入れられる変数になる、という認識が間違っています。

解説：型の不一致はコンパイル時に検出されます。

代入の右辺と左辺の型はコンパイル時に分かります。この種類の不一致は、アプリが起動してから初めて分かるものではありません。

解説：文字列を数値にするにはParseやTryParseなどを使います。

数値に見える文字列でも、自動で解析してくれるわけではありません。int.TryParseで成功を確認してから整数値を代入する方法を使います。

Q2. double result = 7 / 2; のresultは？
解説：先に整数同士で計算されるため、小数部分は失われます。

右辺の7と2はどちらもintです。保存先がdoubleでも、整数除算で既に失われた0.5が後から復元されることはありません。

正解：intの3がdoubleに変換されます。表示が3でも型はdoubleです。

まず7/2がintの3になり、その3をdoubleの3へ変換します。小数を得るには7.0/2や(double)7/2のように計算前の型を変えます。

解説：四捨五入ではありません。整数除算はゼロ方向に切り捨てます。

整数除算は最も近い整数へ四捨五入する操作ではありません。正の7/2は3、負の-7/2は-3となる方向で端数を捨てます。

解説：intからdoubleへの代入はできます。

intからdoubleへの暗黙の数値変換があるため代入はできます。コンパイル可能なことと、小数を含む期待値が得られることは別です。

Q3. double result = 9 / 4;のresultが保持する数値は？
正解：整数除算の2をdoubleへ変換して保持します。

9/4を先に整数として計算すると2です。その後のdoubleへの変換で保持型は変わりますが、計算済みの値は2のままです。

解説：四捨五入が行われる式ではありません。

9を4で割った実数値も2.25であり、2.5ではありません。ここではそもそもint同士の除算なので小数を保持しない点を先に確認します。

解説：intからdoubleへの変換は可能なのでコンパイルできます。

混在しているのは右辺計算後のintと保存先doubleです。その変換は認められるため、計算の意味の違いをコンパイルエラーと混同しません。

解説：右辺がint同士なので、小数部分は代入前に失われます。

小数を得たいなら9.0/4などとします。(double)(9/4)では括弧内の整数除算が先なので2.25にはなりません。

Q4. var amount = 100m;の後でamount = 200.5;とすると？
解説：暗黙に丸めて型を合わせる処理ではありません。

型が合わない代入を、暗黙の丸めで解決する規則ではありません。decimalの値を意図するなら200.5mと接尾辞を揃えます。

解説：varで決まったdecimal型は後から変わりません。

100mから推論されたamountはdecimalのままです。後の代入で変数の宣言型がdoubleへ置き換わることはありません。

解説：初期化式100mからコンパイル時にdecimalへ推論されます。

mはdecimalリテラルを表すので、この宣言ではビルド時に型を決められます。実行するまで未定の箱ではありません。

正解：200.5はdoubleリテラルです。200.5mにするなど型を揃えます。

接尾辞のない200.5はdoubleです。小数を表す型同士でも暗黙に何でも相互変換されるわけではなく、精度や意味を考えて型を揃えます。

Q5. readonly List<int>のフィールドについて正しい説明は？
解説：要素へconstが伝播する仕組みではありません。

readonlyはそのフィールドへ別の値を代入する場所を制限します。参照先にある各要素の宣言へconstを付ける作用はありません。

解説：readonlyはListの公開メソッドまで禁止する機能ではありません。

Listへの参照を付け替えることと、List.Addで内容を増やすことは別です。読み取り専用フィールドでも参照先の公開操作は呼べます。

正解：参照をどこで代入できるかと、参照先の変更可能性は異なります。

たとえば通常のメソッドでfield=new List<int>()は制限されても、field.Add(1)は別の操作です。深い不変性が必要なら型の設計から考えます。

解説：共有データの同時更新には別の同期設計が必要です。

二つの処理が同じListへ同時に追加する問題は残ります。readonlyという修飾子はロックや安全な同時更新の代わりにはなりません。

理解チェックと公式資料

  • 式を評価する前と代入する時の型変換を区別できる
  • decimalでも丸め規則が必要な理由を説明できる
  • varの推論型を右辺から読める
  • readonlyが深い不変性を保証しないと説明できる
