責務の分離と入力検証

入力から結果までの責務。

.NET 10 / C# 14
本文・演習詳細解説
重要入力の整形、値の検証、計算、表示を分けると、変更の影響を小さくできます。

入力を読み、検証し、計算し、表示する処理を一つに詰めると、どこを変更すればよいか分かりにくくなります。まず計算と表示を分け、値が境界を通る順序を確認します。

要点

  • メソッドやクラスの責務を分ける
  • 外部入力と内部の前提条件を区別する
重要

入力の解釈、業務ルール、永続化や表示などの副作用を分けると、変更とテストの範囲を限定できます。必要な境界から小さく責務を分離します。

C#
decimal total = OrderCalculator.Total(price, quantity);

入力・計算・表示を分ける

責務分離の目的はファイルやinterfaceを増やすことではありません。入力の読み取り、業務ルール、保存、表示が互いに混ざって変更しにくくなるのを防ぎます。小さな関数から始め、実際の変更理由に合わせて境界を作ります。

1つの変更理由を意識する

入力を読み、計算し、JSONを保存し、画面表示まで行うメソッドは、いろいろな理由で変更されます。まず入力受付、業務ルール、保存、表示に分けて考えます。ただし小さな計算に最初から多数の層やinterfaceを作る必要はありません。変更やテストの境界として役立つ最小限から始めます。

入力境界・業務処理・出力の三段階

Console.ReadLineやHTTPのJSONは外部入力です。文字列を数値へ変換し、許される範囲かを確認した後、計算や状態変更へ渡します。表示やHTTPステータスへの変換は最後の境界で行います。同じ計算をCLIとAPIで使いたいなら、計算の中へConsole.WriteLineやResults.BadRequestを入れないことが出発点です。

「入力の解釈」と「業務的に許す値」は別です。-100はdecimalへ変換できても商品価格としては不正かもしれません。逆に"abc"は数値として解釈できません。理由を分けておくとエラーメッセージやテストが具体的になり、後からWebへ移すときも計算を流用できます。

純粋な関数がテストしやすい理由

同じ入力から同じ戻り値を計算し、外部状態を変えない関数は、日時、ファイル、DB、ネットワークの準備なしに確認できます。税率を固定の隠れた設定にせず引数へ渡せば、複数の率や境界を簡単に試せます。丸め方法もルールとして明示すれば、表示環境に依存しない検査ができます。

すべてを純粋関数だけで実装できるわけではありません。保存や送信には副作用が必要です。重要なのは、計算や判定を可能な範囲で純粋にし、副作用を少数の分かりやすい場所へ集めることです。メソッドが返す結果と、変更する状態の両方を契約として読み取れるようにします。

計算と表示を分離する理由

一つのメソッドへ全てを詰め込むと何が困るか

入力を読む、数値へ変換する、値の範囲を確認する、在庫を変える、画面へ表示する、という処理を一つへ集めると、画面を変えたいだけでも業務ルールへ触れやすくなります。責務とは、その部品が担当する仕事と判断の範囲です。責務を分ける目的はファイル数を増やすことではなく、変更する理由を分かりやすくすることです。

入力検証にも種類があります。「整数に変換できるか」は形式の検証、「数量は正か」は値の検証、「在庫以内か」は現在の状態を含む業務上の検証です。表面だけで全てを検証しても、別の入口から呼ばれたときに業務状態が壊れるなら不十分です。

最小例：計算と表示を分ける

C# · 独立したコード例
int total = CalculateTotal(120, 3);
Console.WriteLine($"合計:{total}");

static int CalculateTotal(int unitPrice, int quantity)
{
    if (unitPrice < 0) throw new ArgumentOutOfRangeException(nameof(unitPrice));
    if (quantity <= 0) throw new ArgumentOutOfRangeException(nameof(quantity));
    return checked(unitPrice * quantity);
}

期待出力は合計:360です。CalculateTotalはConsoleへ表示せず、値を返します。画面、ファイル、Web APIのどこから呼んでも同じ計算を利用できます。nameofは変数やメンバーの名前を文字列として得る構文です。引数名を直接文字列で重複記述するより、名前変更に追随しやすくなります。

このメソッドはプログラム内部から不適切な引数を渡された場合を例外で示します。利用者が何度も入力を間違える通常の流れでは、入口でTryParseしたり、成功・失敗を結果として返したりする設計も適しています。例外と結果型を目的で使い分けます。

計算の部品と入力の処理を分ける

public static class OrderCalculator
{
    public static decimal Total(decimal price, int quantity)
    {

この例は入力"3"を数量へ変換し、単価500の合計を求めます。

計算の部品へConsoleの入力や表示を混ぜないことで、例えば数量3の合計が1500になることを、画面操作なしでも確認できます。

想定出力

合計: 1500

処理順

  1. 文字列の変換とユーザー向けエラー表示を入口で行う。
  2. 計算クラスは価格と個数を受け取り、自分の前提条件を守る。
  3. 戻った計算結果を表示側で文字列にする。
実コード例

実例：入力検証付きの商品合計

文字列入力から金額計算までを、Try形式のメソッドへまとめます。

C# · Program.cs
if (TryCalculate(" 3 ", 120m, out decimal total))
    Console.WriteLine($"合計: {total:0}円");
else
    Console.WriteLine("数量が不正です");
static bool TryCalculate(string input, decimal price, out decimal total)
{
    total = 0m;
    if (price < 0m || !int.TryParse(input, out int quantity) || quantity < 1)
        return false;
    total = price * quantity;
    return true;
}

想定出力

処理と値の変化

  1. 初期値失敗経路でもout引数を確定させる
  2. 検証価格・変換・数量の条件を先に調べる
  3. 計算有効な条件でのみ合計を求める
条件を変えた場合

入力を"0"や"abc"へ変えても、不正な数量で計算する処理へは進みません。

サンプル一式 Program.cs

不正な値で状態を変更しない

入力エラーと内部不正

外部の文字列は変換と範囲確認をしてから業務処理へ渡します。内部メソッドでも重要な前提条件はガードします。たとえば「購入数は正」というルールは、画面側のチェックだけに依存しません。APIやバッチが追加されても同じ不正値を拒否できる場所に置きます。

失敗の返し方を選ぶ

日常的に起きる入力エラーはboolとエラー内容や結果型で返すと扱いやすい場合があります。契約違反には例外を使うこともあります。どちらにしても呼び出し側が「成功か」「何が問題か」を区別できることが重要です。曖昧な-1やnullを何通りもの意味に使い回さないようにします。

失敗を表す型と不変条件

よくある入力ミスをTry系のboolや結果型で返すと、呼び出し側で通常の分岐として扱えます。一方、呼び出し契約に反する値を内部APIへ渡した場合や予期しない障害は例外を使う選択肢があります。falseが「入力が不正」「DBへ接続できない」「重複」の全部を表すと理由を失うので、必要ならエラーの種類を持つ結果型を設計します。

更新の前にすべての条件を確認し、成功したときだけ状態を変えます。残高を先に引いてから不足を検査するような順番では、不正な操作で状態を壊します。DBなど複数の更新先をまとめる場合はトランザクションが必要になり、メソッドを分割しただけでは整合性を保証できません。

画面の入力だけで検証しても、別の呼び出し元から計算の部品を使うときに不正な値が届く可能性があります。

入口では直し方が分かる案内をし、内部の部品も自分の前提を守ります。二つの検証が同じ目的とは限らないことを確認します。

分割の基準は変更理由と依存方向

業務ルールが変わる、表示形式が変わる、保存先が変わるという異なる変更を別々に扱えると、修正範囲を限定できます。最初はProgramから純粋な計算メソッドを取り出すだけでも改善します。保存先を差し替える必要が生じたらRepositoryやinterfaceを検討し、実際のテスト境界に合わせて導入します。

まだ存在しない要件のために多数の抽象クラスや汎用フレームワークを作ると、学習も保守も難しくなります。小さく始め、変更点が現れたときに分けやすい形を残すことが重要です。共通化は名前が似ているだけで行わず、同じルールとして同時に変わるものかを確認します。

残高や在庫のように値を変更する処理では、途中で失敗した後に状態だけ変わることを避けます。

検証と更新を一つの操作として扱う必要がある場合は、その範囲まで設計します。同時実行時には、チェック直後に他の処理が値を変える可能性も考えます。

static TitleResult ValidateTitle(string? input)
{
    string value = input?.Trim() ?? "";
    if (value.Length == 0) return new(false, null, "タイトル必須");
    if (value.Length > 10) return new(false, null, "10文字以内");
    return new(true, value, null);
}
public record TitleResult(bool Success, string? Value, string? Error);

成否と理由をoutで返す方法もあるが、関連情報をrecordへまとめると利用側の契約を読み取りやすい。

よくある間違いと確認箇所

Trim前の長さだけを検査すると、空白だけの入力や不要な拒否が起こる。正規化後の値を一貫して使う。

実務例：API入力を内部の業務モデルへ渡す前に、使用する形へ整えて検証する。

確認問題

Q1. 計算メソッドへ渡す前にUI側で検証したら、内部の前提条件は不要？
正解：UI以外の呼び出しでも不正状態を防げます。

画面の検証は利用者に早く伝える役割、内部の検証は不正状態を作らない役割です。別のAPIやテストから直接呼ばれても在庫や金額の重要な条件を維持します。

解説：将来の入口やテストから呼ばれる可能性があります。

入口が一つという前提は将来変わります。内部メソッドの契約として必要な条件を守ることで、呼び出し元が増えても安全性を維持できます。

解説：言語は価格や個数の業務ルールを知りません。

intは整数かどうかなどを扱いますが、注文数が1以上で在庫以下かは業務の規則です。型に任せる部分と、自分で検証する条件を分けます。

解説：APIの追加だけでは検証は増えません。

HTTPの入口を増やしても在庫数の規則は自動追加されません。変換・入力検証・業務検証の各段階で何を保証するかを明示します。

Q2. 小さな学習アプリの設計で適切な方針は？
解説：抽象化そのものが目的ではありません。

interfaceは呼び出し側が具体的な実装に依存しないようにする道具です。差し替えの必要がない全クラスへ作ること自体を目標にしません。

正解：可読性と変更容易性に効くところを選びます。

表示文言、入力変換、在庫更新は変更される理由が異なります。理解やテストが楽になる境界から分け、必要が生まれた部分だけ拡張します。

解説：短さだけで保守性は決まりません。

一行に詰めると、どの条件で値が変わるかが読みにくくなります。行数よりも責務、名前、処理順が追えることを優先します。

解説：失敗を見えなくする設計は危険です。

失敗を無視すると、呼び出し側が成功と誤認して処理を続けます。想定する失敗を結果で返すか例外として扱うかを契約で決めます。

Q3. 純粋な計算関数の特徴は？
正解：テストしやすさの基本となる性質です。

例えばAddTax(price,rate)が同じ値から同じ結果を返し、保存や表示をしない形です。時間や共有変数に依存しないため、固定条件で検証しやすくなります。

解説：staticメソッドでも外部状態を読む・変更することはできます。

staticメソッドでもDateTime.Nowを読んだりファイルを更新したりできます。呼び出し方法ではなく、外部状態との関係で純粋性を判断します。

解説：ファイル保存は副作用です。

ファイルへの保存は外部の状態を変える副作用です。計算結果を返す部分と、それを保存する部分を分けると検証の対象が明確になります。

解説：表示は計算結果の外部への作用です。

画面表示も外部へ働きかける処理です。純粋な計算は戻り値を返すだけにし、呼び出し元が必要に応じて表示できます。

Q4. 在庫不足の要求を受けたときの基本順序は？
解説：在庫の正しい値を失います。

在庫が3で5個の要求を受けた場合、正しい在庫は3のままです。失敗を理由に0へ変えると、存在する在庫の情報を壊してしまいます。

解説：不正要求で状態を壊す可能性があります。

3から5を先に引くと-2となり、その後の例外でも状態が残る恐れがあります。成功条件を確定させてから一度だけ更新します。

解説：呼び出し側が誤った成功として扱います。

不足を成功として返すと、出荷や支払いなど次の処理が進む可能性があります。成功・失敗と実際の状態変更を一致させます。

正解：失敗した操作で不変条件を壊さないようにします。

個数が正で在庫以下と確認できてから減算します。共有状態なら、確認と更新の間に別の処理が割り込まない設計も必要です。

Q5. 責務分離を進める適切な基準は？
正解：変更の影響を限定し、テストと再利用をしやすくします。

表示方法を変えても在庫計算を触らなくてよい構成が一例です。分割は、変更の影響やテスト時の依存を小さくするために行います。

解説：数を増やすことが目的ではありません。

クラスを増やすだけでは処理の移動が多くなり、全体を理解しにくくなることがあります。意味のある責務が分かれているかを確認します。

解説：不確かな抽象化が不要な複雑さを生む場合があります。

まだ存在しない全機能へ対応しようとすると、使わない抽象化が増えます。現在の要件と確認できた変更点に基づいて設計を選びます。

解説：過剰な分割で理解と管理の負担が増えます。

別プロジェクト化には参照や公開範囲の管理も必要です。単なるファイル分割で十分な段階と、独立した配布・依存境界が必要な段階を区別します。
