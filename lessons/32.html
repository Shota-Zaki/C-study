APIの検証と統合

APIの操作と状態を連続して検証する。

.NET 10 / C# 14
本文・演習詳細解説
重要単体テストの成功だけでは、HTTP経路・入力変換・状態変化まで正しいとは限りません。

図解：APIの操作と状態を連続して検証する

要点

  • 単体・統合・E2Eテストの範囲を区別する
  • 完成条件から制作課題を進める
重要

APIは正常系だけでなく、入力不正、対象なし、状態変化、再試行などの契約を検証します。制作課題では実装条件と制約を説明できる状態まで仕上げます。

C#
// HTTPステータス、JSON、入力境界をセットで確認する

概念・構文

APIの検証では、HTTPメソッド・ステータスコード・応答形式・状態の変化を確認します。単体テスト・統合テスト・E2Eテストでは、確認できる範囲が異なります。

テストの範囲を選ぶ

単体テストは計算や検証など小さな単位、統合テストは複数の部品がつながる範囲を確かめます。ASP.NET CoreではWebApplicationFactoryを使ってテスト用アプリを立ち上げ、HTTPとして確認できます。E2Eはユーザー操作の入口から結果までの流れを確認します。テスト名だけで範囲が自動的に決まるわけではなく、どこを本物にしてどこを差し替えるかを明記します。

HTTPとして契約を確認する

下のAPIへ正常なIDと存在しないIDを送って、200/404とJSONの項目を確認します。Windows PowerShellならInvoke-RestMethod、応答コードを含めるならInvoke-WebRequestなどで呼べます。POSTにはJSONとContent-Typeが必要です。本文を受け取るメソッドだけ単体テストしても、ルートやJSONバインドの誤りは見つからない場合があります。

作品の完成条件を先に決める

制作課題は、支出集計CLI、JSON保存付きタスク管理CLI、タスク管理APIの3つです。入力不正を拒否する、再実行で結果を確認する、保存できる範囲と消える範囲を説明する、までを完成条件にします。次の学習候補はEF CoreとSQL、認証・認可、ASP.NET Coreのテスト、デプロイです。全部を一度に加えず、今の作品の不足から選びます。

ステータス・ヘッダー・本文・状態変化を確認する

APIの成功確認は本文だけでなく、HTTPステータス、Content-Type、Location、更新後にGETした結果まで含みます。POSTで201が返っても、その後のGETが404なら作成契約は成立していません。入力が不正だった場合は400が返るだけでなく、保存データが増えていないことも確認します。

テストケースには入力・前提状態・操作・期待結果を残します。順番に依存するケースでは「新規起動したメモリ状態」「作成直後」などを明示し、再実行時に以前のデータで結果が変わる問題を避けます。ランダムGUIDは値そのものを固定比較せず、型・形式とLocationから取得した対象との一致を確認します。

単体・統合・E2Eの範囲を区別する

単体テストは計算関数やサービスなどの小さい単位を検証します。HTTPハンドラー関数を直接呼ぶだけなら、ルーティングやJSONバインドまで通したとは言えません。WebApplicationFactoryなどを使う統合テストは、アプリのパイプラインをテストサーバー上で動かして要求と応答を確認できます。

E2Eは利用者の操作から複数の構成要素を通す範囲のテストです。ブラウザ、API、実際のテスト用DBまで含むかなど、どこまで通したかを報告します。偽ハンドラーの成功を実通信の成功と呼ばず、テストサーバーの成功を本番のTLSやネットワークの確認と呼ばないことが重要です。

curlと自動化で同じ契約を繰り返す

Windows PowerShellではcurlという名前の解決が環境によって異なるため、ここではcurl.exeを明示します。-iでレスポンスヘッダーを含め、-Xでメソッド、-HでContent-Type、--data-binary @request.jsonでファイルの本文を送れます。日本語や引用符を含むJSONはUTF-8ファイルへ保存するとシェルの引用符問題を切り分けやすくなります。

手順をスクリプトへ移すときは終了コードやステータスを比較し、違えば失敗として終了させます。404の本文が表示されたことを「コマンドが動いたから合格」としないでください。

統合テストへの移行と公開前の境界

WebApplicationFactory<Program>を使う構成では、テストプロジェクトからWebプロジェクトを参照し、対象.NET系統に合うMicrosoft.AspNetCore.Mvc.Testingを追加します。トップレベル文のProgramをテストから参照するためpublic partial class Program { }を追加する方法があります。実DBの代わりを注入する場合も、何を差し替えたか明示してテストを分離します。

ローカル学習APIには、認証・所有権の検査、HTTPS、永続化、同時更新、リクエスト上限、秘密管理、バックアップ、監視などの本番条件が残ります。これらを実装していない状態でインターネットへ公開しないでください。「学習課題の完了条件を満たした」と「本番公開してよい」は別の判定です。

C#仕様の整理

観点C#での扱い読み方・設計上の要点
関数のテストxUnit等で対象呼び出しHTTPパイプラインは通らない
HTTP統合WebApplicationFactory等ルート・バインド・応答を通す
手動HTTPcurl.exe等シェルの引用符とHTTP失敗を分ける
公開品質同様に別の設計と検証が必要サンプル完了と本番完成を分ける

仕組みの補足

APIの要求・処理・応答

最終レッスンでは、型、分岐、メソッド、オブジェクト、コレクション、LINQ、HTTP、DIを一つの処理経路として読みます。目標は大きな完成コードを暗記することではなく、「入力がどこから来て、どこで検証され、どの状態が変わり、何が返るか」を自分の言葉で説明できることです。

ここではローカル学習用のタスク一覧APIを題材にします。追加・一覧・個別取得・完了状態の更新・削除を持ちます。保存先はメモリで、再起動すると消えます。認証・認可・本番公開・永続データベースは別の設計課題として境界を明確にします。静的教材を開いてもこのAPIが裏で動くわけではありません。

APIの契約を先に決める

メソッドと経路 入力 成功 主な失敗
GET /todos なし 200と配列 予期しない失敗は500
GET /todos/{id:int} 整数ID 200と対象 対象なし404
POST /todos title 201、Location、作成対象 空白・長さ不正400
PUT /todos/{id:int}/completion done 200と更新対象 対象なし404、done欠落400
DELETE /todos/{id:int} 整数ID 204 対象なし404

完了状態を独立した資源の表現としてPUTする契約です。タスク全体のPUTへtitleを省略する曖昧さを避けています。同じdone=trueを繰り返しても、最終的に完了状態はtrueです。入力doneはbool?で受け、省略と明示的なfalseを区別します。

文法・実例・処理順

csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
app.MapGet("/lessons/{id:int}", GetLesson);
app.Run("http://127.0.0.1:5080");

static IResult GetLesson(int id)
{
    if (id is < 1 or > 32)
        return Results.NotFound(new { error = "レッスンがありません" });
    return Results.Ok(new { id, title = $"Lesson {id}" });
}

想定出力

GET /lessons/1 → 200 GET /lessons/32 → 200 GET /lessons/33 → 404 GET /lessons/abc → 404（ルート制約不一致）

処理順

  1. 整数として解釈できるパスだけがハンドラーへ渡される。
  2. 業務上の範囲1〜32を検証する。
  3. 正常と対象なしで異なるHTTP応答を返す。

よくある間違いと修正

よくある間違い

制作課題のAPIはローカル学習用で、認証や永続DBを備えた公開サービスではありません。インターネットへそのまま公開しないでください。

存在しない対象でも200で返す

修正箇所: APIの不在時の応答

修正前

csharp
app.MapGet("/levels/{id:int}", (int id) =>
    Results.Ok(new { found = id is >= 1 and <= 3 }));

修正後

csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
app.MapGet("/levels/{id:int}", (int id) =>
    id is >= 1 and <= 3 ? Results.Ok(new { id }) : Results.NotFound());
app.Run("http://127.0.0.1:5080");
変更理由

個別リソースの取得という今回の契約では、対象不在を404で表します。本文のfoundだけで判定する独自の成功形式から、HTTPクライアントがステータスで判断できる形へ変更します。検索結果0件を200の空配列で返すケースとは別です。

修正後の確認

  • id1→200
  • id0→404
  • id4→404

標準：一覧の空と個別の不在を分ける

  • 個別対象は未登録

応用

応用：更新の前後をHTTP契約で検証する

POST /toggleで完了状態を反転し204を返し、GET /stateで確認します。初期false→POST→true→POST→falseを検査します。並行変更はlockで保護します。

  • 204は本文を返さない
  • 一つの操作として状態反転を保護
  • GETも同じ保護の下で読む
開始コード
csharp
// 応用：更新の前後をHTTP契約で検証する
// 課題とテストケースを読んで、自分で実装してください。
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
// ここにエンドポイントを実装
app.Run("http://127.0.0.1:5080");

入力例・前提条件

初期Done=false。POST /toggleを二回送り、各回の後にGET /stateする。

考え方のヒント

反転をlockで保護し、応答204には本文を付けない。

入力するとlocalStorageへ保存
解答例と確認ポイント
csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
object sync = new();
bool done = false;
app.MapGet("/state", () => { lock (sync) return Results.Ok(new { done }); });
app.MapPost("/toggle", () =>
{
    lock (sync) done = !done;
    return Results.NoContent();
});
app.Run("http://127.0.0.1:5080");

想定出力

GET /state → 200 {"done":false} POST /toggle → 204（本文なし） GET /state → 200 {"done":true} POST /toggle → 204（本文なし） GET /state → 200 {"done":false}
  • 更新の応答だけでなく後続GETで実際の状態を確認する。
  • toggleは同じ要求を再送すると元へ戻るため冪等ではない。自動再試行へ安易に組み込まない。
  • これは共有状態の学習例で、利用者ごとの分離も永続化もない。状態を指定するPUTへの変更は次の設計課題にできる。
入力 / 条件期待結果
初期起動false
POST1回true
POST2回false

処理と結果の読み解き

一回目でtrue、二回目でfalseへ戻る。排他制御しても再送による二度の反転は防げず、並行安全性と冪等性は別の性質。

よくある別解と選び方

本番の更新契約ならDone=trueのような目標状態を指定する設計が候補。詳細解説の統合APIで比較する。

よくある間違いと確認箇所

通信失敗の再送を常に安全と考えない。最初の処理が済んで応答だけ失われた場合、二回目で元へ戻る。

実務例：公開前に再試行・状態更新・競合の契約を考え、テストで意図する効果を確認する。

確認問題

Q1. HTTP統合テストで、計算メソッドの単体テストだけより確認しやすいものは？
解説：命名はレビューなどで確認します。

変数名の意味が読みやすいかは人によるレビューや静的解析の領域です。HTTP要求を送るテストだけから、命名の適切さを自動判定することはできません。

解説：アプリのテスト対象ではありません。

アプリの統合テストはプログラムやサービスの接続を確認します。利用するCPUの製造そのものを検査するテストではありません。

正解：部品間のつながりを含めて確認できます。

URLが目的の処理へ届くか、応答コードと本文が契約どおりかを一緒に検査できます。計算メソッドの正しさだけでは見つからない接続の不具合を対象にします。

解説：テストの範囲外の問題は残ります。

確認した入力、設定、実行環境の範囲に限った結果です。実ネットワーク、権限、負荷、運用設定など別の検証が必要な条件を残します。

Q2. ローカル制作課題のAPIを本番公開する前に必要なことは？
解説：公開範囲を広げるだけでは安全性や運用は整いません。

外から到達できるようにするだけでは、誰が何を操作できるかやデータ保護は実装されません。公開範囲を広げる前に運用要件を満たす必要があります。

解説：調査不能になるだけで問題は解消しません。

利用者へ内部の詳細を漏らさないことは重要ですが、運用側が原因を調べる情報は必要です。安全な応答と適切なログ・監視を両立させます。

解説：見た目とAPI運用は別です。

画面の見た目を変えても、APIの認証や保存の問題は解決しません。サーバー側の契約、セキュリティ、バックアップを独立して確認します。

正解：教材で未実装の運用要件を満たす必要があります。

教材のインメモリ保存は再起動で消え、認証なども別の設計です。学習用として動作することと、外部利用者のデータを安全に扱えることを区別します。

Q3. ハンドラー関数を直接呼ぶ単体テストだけでは確認できないものは？
解説：外部依存のない計算は単体で確認しやすい対象です。

固定入力を受け取って計算結果を返す関数は、直接呼び出して期待値と比較できます。HTTPを通さないことが単体テストの対象を小さくする利点です。

正解：HTTPパイプラインを通していないため統合テストが別途必要です。

ルートの選択、JSONから引数への変換、ミドルウェアなどは直接呼び出しで通りません。HTTP経路を通す検査を追加して接続を確認します。

解説：入力を渡して条件分岐を試せます。

境界値を引数として渡せば、関数内の分岐の挙動を検証できます。ただしHTTP入力がその引数へ正しく変換されるかは別の検査です。

解説：直接呼び出しで確認できます。

戻り値は直接受け取って比較できます。その値が実際のHTTP応答へどう変換されるかまで知りたい場合に、統合テストが必要になります。

Q4. 一覧GETの結果が0件なら自然な応答の一例は？
正解：問い合わせは成功し、結果集合が空であると表せます。

一覧というリソースへの問い合わせ自体は成功しているため、200と[]で結果がないことを表せます。個別IDが存在しない404とは意味が異なります。

解説：0件だけでサーバー故障とはしません。

データが0件なのは正常に起こり得る状態です。サーバーの故障とすると、利用者や監視が不要な障害対応を行ってしまいます。

解説：一覧取得の成功と個別の不在は別です。

一覧が存在するが要素がない場合と、指定した一件が存在しない場合を分けます。常に404にすると、一覧取得の契約が曖昧になります。

解説：新しいリソースを作ったわけではありません。

GET一覧では新しいリソースを作っていません。201やLocationは新規作成の契約で使うため、この成功結果には通常200を選びます。

Q5. toggle操作を通信失敗時に無条件で再送すると？
解説：再試行と認証の実装は無関係です。

再送は同じ処理をもう一度要求するだけで、本人確認の仕組みを追加しません。再試行の安全性と認証・認可は別に設計します。

解説：HTTPメソッドは自動的に置き換わりません。

通信エラーを理由にHTTPメソッドが勝手にGETへ変換されるわけではありません。どの要求を再送するかはクライアントの実装と契約によります。

解説：状態反転は通常冪等ではありません。

toggleは現在値に対して反転するため、同じ操作を二回行うと結果が変わります。done=trueのような目標状態の指定と区別します。

正解：最初の要求が処理済みで応答だけ失われた場合に問題になります。

一回目の更新が完了して応答だけ失われると、再送で再び反転します。目標状態を指定する操作や重複識別など、再試行しても意図が崩れない契約を検討します。
