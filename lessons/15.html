ジェネリックとコレクション

データの形とコレクション。

.NET 10 / C# 14
本文・演習詳細解説
重要Listは順序付きの列、Dictionaryはキーから値の検索、HashSetは重複しない集合に使います。

図解：データの形とコレクション

要点

  • 目的に合うコレクションを選ぶ
  • ジェネリックで型の安全性を確保する
重要

List<T>、Dictionary<TKey,TValue>、HashSet<T>は用途が異なります。型引数と各APIの失敗時契約まで含めて選びます。

C#
var scores = new Dictionary<string, int>();

概念・構文

コレクションを選ぶ基準は「使い慣れているか」ではなく、順番・重複・検索キー・更新方法です。List、Dictionary、HashSetを同じデータで比べ、ジェネリックが型の安全性をどこで保証するかを確認します。

Listは順序、Dictionaryはキー

List<T>は要素を順番に並べ、追加・削除できます。Dictionary<TKey,TValue>はキーから値を探す用途です。HashSet<T>は重複を避けたい集合に使います。何でもListに入れて毎回先頭から探すのではなく、アクセス方法から選びます。Listの件数はCountで、配列のLengthと異なります。

ジェネリックは型を引数にする

List<int>のintは「どの型の値を扱うか」を指定します。要素をobjectで持って取り出すたびにキャストする設計より、型の間違いをコンパイル時に検出しやすくなります。自分でもTを受け取る型やメソッドを作れます。必要に応じてwhere T : ...で制約を付けます。

存在しないキーを考える

辞書のdict[key]はキーがないと例外です。存在しないことが通常ケースならTryGetValueで分岐します。文字列キーを大文字小文字の区別なしで扱う場合は、作成時にStringComparer.OrdinalIgnoreCaseなど比較方法を指定します。DictionaryやListを複数スレッドから同時更新する場合は別途同期が必要です。

List・Dictionary・HashSetの目的

List<T>は順序を持つ可変長の並びです。添字で位置を指定でき、同じ値を複数回含められます。Dictionary<TKey,TValue>はキーから値を引く対応表です。HashSet<T>は重複のない集合で、存在するかを扱う用途に適しています。辞書や集合の列挙順を業務上の順序として頼らず、表示に順序が必要なら明示的に並べ替えます。

会員番号から会員を探すならDictionary、入力されたタグから重複を除くならHashSet、学習ログを順番に保持するならListが候補です。どの操作を頻繁に行うかも考えます。ハッシュ構造の検索は平均的に効率がよい一方で、ハッシュ衝突や比較の実装などにも影響されるため、すべての状況で一定時間と断言しません。

ジェネリックは型の関係を保持する

List<int>はintを要素として扱い、文字列をAddしようとすればコンパイルで拒否されます。List<object>に何でも入れる設計では、取り出し側で型を確認しなければなりません。型引数は単に括弧が増える記法ではなく、入力と出力の関係を保つための情報です。

T First<T>(T[] values)なら、int[]を渡すと戻り値はint、string[]ならstringとして扱えます。メソッドの中ではTが備えると保証されていないメンバーを勝手に呼べません。where T : IComparable<T>などの制約は、その操作を使える根拠を型として示すものです。必要になった段階で制約、共変・反変などC#のジェネリック仕様を段階的に学びます。

辞書の追加・上書き・未登録を分ける

dictionary.Add(key,value)は同じキーがあれば例外になります。dictionary[key]=valueは未登録なら追加、存在すれば上書きします。TryAddは追加できたかをboolで返します。データの重複をエラーにするのか、最新値で上書きするのかを仕様として決め、その意図に合うAPIを選びます。

読み取りのdictionary[key]は未登録のキーで例外になります。未登録が通常あり得るならTryGetValueで存在と値をまとめて確認します。値型の場合、失敗時のout値が既定値になることがありますが、0という値が登録されているケースと区別するため、boolの戻り値を使います。ContainsKeyの後に添字で読むより意図を一度で表せます。

比較方法と公開するコレクションの契約

"C#"と"c#"を同じキーとみなすなら、DictionaryやHashSetの作成時にStringComparer.OrdinalIgnoreCaseを指定できます。後から各呼び出しでToLowerして整える方式では、処理漏れや比較方針の不統一が生まれやすくなります。識別子の比較と、人向けの自然言語の比較は要件を分けます。

メソッドが並びを読み取るだけならIEnumerable<T>、件数と添字も必要ならIReadOnlyList<T>など、必要な操作を契約にする選択肢があります。ただし読み取り専用インターフェイスで返しても実体が絶対に不変になったわけではありません。別の参照から変更される可能性や、要素自身の変更可能性は残ります。

C#仕様の整理

観点C#での扱い読み方・設計上の要点
並びList<int>など値型を型引数へ直接指定できる
対応表Dictionary<TKey,TValue>追加・上書き・検索失敗のAPIを区別
集合HashSet<T>重複の意味を比較方法で決める
制約where T : ...汎用メソッドの内部で使える操作を保証

仕組みの補足

コレクションを選ぶ前に、必要な操作を決める

コレクションは複数の要素をまとめて扱う部品です。配列は長さが固定、Listは順序付きで追加・削除ができ、Dictionaryはキーから値を探すことに向いています。「複数だから何でもList」と決めるのではなく、順序・重複・検索方法・更新方法を先に考えます。

ジェネリックは、扱う型を引数として受け取れる型やメソッドの仕組みです。List<int>はintを要素とするList、List<string>はstringを要素とするListです。Tはその型のための仮の名前です。要素の型を保てるため、取り出すたびにobjectから変換したり、違う型を入れた誤りを実行時まで持ち越したりしにくくなります。

Listの状態を一操作ずつ追う

C# · 独立したコード例
var numbers = new List<int> { 1, 2, 3 };
numbers.Add(4);
numbers.Remove(2);
numbers[0] = 10;
Console.WriteLine(string.Join(",", numbers));
Console.WriteLine(numbers.Count);

期待出力は10,3,4、3です。Addは末尾へ追加、Removeは一致する最初の要素を削除、[0]は先頭要素へのアクセスです。Countは現在入っている要素数です。

操作 前の状態 後の状態 Count
初期化 なし [1,2,3] 3
Add(4) [1,2,3] [1,2,3,4] 4
Remove(2) [1,2,3,4] [1,3,4] 3
[0]=10 [1,3,4] [10,3,4] 3

Listは通常、内部の配列に要素を保存します。Capacityは内部で確保している要素の収納能力、Countは現在入っている要素数です。Capacityを100にしても、要素が100個あるとは限りません。追加時に容量が足りなければ、より大きな領域へ要素をコピーする場合があります。具体的な容量増加の数値へ依存したコードは書きません。

末尾追加は通常効率的ですが、途中のInsertやRemoveAtでは後ろの要素をずらす処理が必要です。要素が少なければ読みやすさを優先し、非常に大量のデータでは操作回数や計算量を測ります。計算量とは要素数に応じて必要な処理がどう増えるかという見方です。

文法・実例・処理順

csharp
var scores = new Dictionary<string, int>
{
    ["C#"] = 80,
    ["SQL"] = 90
};
if (scores.TryGetValue("C#", out int score))
    Console.WriteLine(score);

var tags = new HashSet<string> { "C#", "SQL", "C#" };
Console.WriteLine(tags.Count);
Console.WriteLine(First(new[] { 10, 20 }));

static T First<T>(T[] values)
{
    if (values.Length == 0) throw new ArgumentException("要素が必要です");
    return values[0];
}

想定出力

80 2 10

処理順

  1. C#というキーが存在し、scoreへ80が入る。
  2. HashSetでは重複したC#が1つとして扱われる。
  3. First<T>のTはintに推論され、先頭の10を返す。

値・状態の変化を追う

大文字小文字を無視してタグを数える

csharp
string[] inputs = { "C#", "SQL", "c#", "Python", "sql" };
var counts = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase);
foreach (string input in inputs)
{
    counts.TryGetValue(input, out int current);
    counts[input] = current + 1;
}
foreach (string key in counts.Keys.OrderBy(x => x, StringComparer.Ordinal))
    Console.WriteLine($"{key}: {counts[key]}");

C#: 2 Python: 1 SQL: 2

SQL同様に1別キー

よくある間違いと修正

よくある間違い

列挙中に同じListへAdd/Removeすると通常は例外になります。削除対象を別に集める、RemoveAllを使うなど、処理方法を決めてください。

未登録のキーを添字で読んで例外になる

修正箇所: 辞書の読み取り

修正前

csharp
var scores = new Dictionary<string, int>();
Console.WriteLine(scores["C#"]);

修正後

csharp
var scores = new Dictionary<string, int>();
if (scores.TryGetValue("C#", out int score))
    Console.WriteLine(score);
else
    Console.WriteLine("未登録");
変更理由

未登録が正常に起こり得る仕様なので、TryGetValueで存在と値を受け取ります。score==0では未登録と0点を区別できないため、戻り値で分岐します。

修正後の確認

  • 未登録なら未登録
  • C#=0を登録すると0
  • C#=80を登録すると80

確認問題

Q1. キーから値を探す用途に最も直接対応するのは？
正解：キーと値の対応を管理します。

IDから商品、名前から設定値のような対応を型で表せます。キーの比較方法と、キーが存在しない場合の扱いも合わせて決めます。

解説：配列でも実装はできますが、キー検索を直接表す型ではありません。

配列を順に検索する実装も可能ですが、キーによる対応管理という目的が型から読み取りにくくなります。添字と業務キーを同一視しません。

解説：文字列の組み立て用です。

StringBuilderは文字列を段階的に組み立てる可変の部品です。キーと任意の値の対応を検索するデータ構造ではありません。

解説：非同期処理の結果を表す型です。

Task<T>は完了後にTを得られる処理を表します。複数データをキーで保持するコレクションとして選ぶ型ではありません。

Q2. C#で整数のリストを作る型は？
解説：そのような標準型はありません。C#ではList<T>のTへ要素型を指定します。

List<T>という汎用型へintを指定します。数値用に別々の専用型名を覚えるのではなく、型引数で要素の型を表します。

正解：値型intを型引数にできます。

Tにintを渡した構築型なので、通常のAddではintとして扱える値を受け取ります。取り出すときもintとして読め、毎回objectから変換する必要がありません。

解説：そのような構文ではありません。

ジェネリック型は型名の後の山括弧で引数を指定します。intにListというプロパティがあるような記述ではありません。

解説：一般的なジェネリックリストはList<T>です。

List<object>は混在する値を持てますが、整数だけという制約が弱くなります。目的が整数の一覧ならList<int>の方が型で意図を守れます。

Q3. Dictionaryのdict[key]=valueの意味は？
正解：インデクサー代入は追加と上書きを行います。

そのキーがなければ対応を追加し、既にあれば値を入れ替えます。キー重複をエラーとして検出したい場合はAddやTryAddを検討します。

解説：既存キーで例外になるAddとは異なります。

Addは重複キーで失敗しますが、インデクサーへの代入は上書きを許します。よく似た追加操作でも、重複時の契約を確認します。

解説：辞書はキーによる対応を更新するもので、末尾指定ではありません。

辞書の添字は業務キーを表し、Listの末尾位置の意味ではありません。dict["name"]のように指定したキーの対応を更新します。

解説：変更する操作であり読み取り専用化ではありません。

実際にデータを変更する操作です。readonlyフィールドや読み取り専用の公開型とは別であり、ここに変更禁止の指定はありません。

Q4. 型パラメーターTでCompareToを使うための制約の例は？
解説：constはジェネリック制約の構文ではありません。

constはコンパイル時の定数を宣言する修飾子です。任意の型Tに比較メソッドがあることを要求するジェネリック制約にはなりません。

解説：usingで操作可能性の契約を保証することはできません。

usingは名前の解決などを助ける指定です。型Tがどんな操作を持つかを保証するには、where句で契約を要求します。

解説：varは型パラメーターの制約として指定する型ではありません。

varはローカル変数などの型推論に使う文法であり、実装すべきインターフェイスではありません。制約の型として指定できません。

正解：比較操作の契約をTに要求し、メソッドを安全に利用できます。

TがIComparable<T>を実装するという条件を付けるので、CompareToを型の規則に従って呼べます。全ての型が比較可能と仮定しない設計です。

Q5. HashSet<string>で"C#"と"c#"を同じものとして扱う指定は？
解説：objectへ変換しても望む比較方針は自動設定されません。

objectへ変えることは、大文字・小文字を無視する比較を指定することではありません。集合へ比較器を渡して、追加と検索の規則を揃えます。

解説：件数計算だけを変えても重複判定の仕様は変わりません。

件数を調整しても、ContainsやAddの重複判定は変わりません。保存データの意味を後から件数だけで補正する方法ではありません。

解説：削除は任意の重複の意味を正しく表現しません。

末尾を消しても、どの文字列が等しいかを定義できません。任意の追加順でも一貫する比較規則をコレクション作成時に決めます。

正解：集合全体で一貫した比較方法を適用できます。

OrdinalIgnoreCaseは大文字・小文字を無視した序数的な比較です。識別用のキーなどに使い、自然言語の並べ替え規則とは目的を分けます。
