概念と内部の仕組み

recordは「変更できないclass」の別名ではありません。データとしての等値性、表示、コピーなどのコードをコンパイラーが補ってくれる型の書き方です。どの値を同じとみなすか、withで何がコピーされるかを理解し、通常のclassとの使い分けを考えます。

等しい、には複数の意味がある

普通のclassでは、演算子を独自定義しなければ==は参照の同一性を比較します。record classはデータ向けの型で、型と構成要素に基づく等値性が生成されます。同じ氏名・点数の2つの記録を同じ値として比較したい場合に役立ちます。ユーザーIDが同じなら同一人物など、業務上の同一性は別途設計が必要です。

短く書けるが魔法ではない

public record Result(string Subject, int Score);と書くと、位置パラメーターに対応するプロパティなどが生成されます。recordとだけ書いた場合は参照型です。record structは値型です。record classだから全て不変、というわけでもありません。明示的なsetプロパティや可変の子オブジェクトを持てます。

withは一部を変えたコピー

result with { Score = 90 }は、元を残して一部の値を変更した新しいレコードを作ります。ただし参照型メンバーの参照先まで複製する深いコピーではありません。Listをメンバーに持つ場合、リストの内容比較や独立したコピーが必要なら自分で設計します。

同一性と等値性を分ける

同一性は同じ実体を指しているか、等値性は定義した意味で同じ値かを表します。二つのResult("C#",80)は別々にnewしてもrecordの値ベースの等値比較では等しくなります。一方ReferenceEqualsは同じ参照先かを調べるためfalseです。同じ内容の別オブジェクトを重複データとして扱いたい場面で役立ちます。

普通のclassにもEqualsや==を独自実装できますが、recordはデータ用の基本コードを生成します。何をもって同じとするかが重要なので、データベースのIDで同一視するエンティティを、全フィールド一致のrecordへ機械的に置き換えるのは避けます。値そのものを表すデータか、更新し続ける同一の存在かを考えます。

record classとrecord struct

recordとだけ書くとrecord classで参照型です。record structは値型になります。どちらもデータ向けの等値性などを提供しますが、代入の意味はclassとstructの分類に従います。recordという単語だけで値型だと判断しないでください。

位置指定のrecord classで宣言したプロパティは通常initアクセサーを持ちます。record structの位置指定プロパティは通常変更可能で、readonly record structを選べば別の性質になります。構文を短く書ける分、どのメンバーが生成されるかを確認することが大切です。公開契約に使うなら、データの検証とシリアル化の要件も合わせて検討します。

withはコピー後の一部を変更する

var revised = original with { Score=90 };は、元を残したまま一部を変更したコピーを作ります。操作後もoriginal.Scoreは元の値です。変更前後の値を比較したいUIや履歴データで読みやすい表現になります。ただしrecord classのwithによるコピーは通常浅いコピーです。

内部にListがあれば、コピーした二つのrecordが同じListを共有することがあります。initはプロパティの再代入時期を制限するだけで、List.Addまで止めません。履歴として独立性が必要ならListも複製する、不変コレクションを使う、要素自体も不変にするなど、要件に合う段階まで設計します。

コレクションの等値性と辞書のキー

record内の各メンバーはその型の等値性に従います。Listや配列が入っている場合、別々のListに同じ要素が並んでいても、自動的に要素ごとのシーケンス比較になるわけではありません。SequenceEqualのような比較が必要か、型の契約として内容比較を定義するかを考えます。

DictionaryやHashSetのキーに使うデータの等値性に関係する値を、登録後に変更すると検索の前提を壊す可能性があります。recordでも変更可能なメンバーを持たせれば安全とは限りません。キーは不変な値を使うのが基本です。便利な自動生成とデータモデルの正しさを混同しないようにします。

概念をもう一段掘り下げる

「同じ実体」と「同じ内容」は違う問い

同一性は、同じオブジェクトそのものかという問いです。等値性は、決めた規則で値が等しいかという問いです。同じ名前と価格を持つ二つの商品オブジェクトを別々にnewした場合、実体は別です。しかし注文の値を比較したい処理では、内容が等しいと扱いたいことがあります。

C#の==は型によって意味が異なり、演算子として定義を変えられる型もあります。Equalsも型によって実装が異なります。ReferenceEqualsは参照の同一性を問うものです。「==は必ず参照比較」「Equalsは必ず内容比較」と一律に暗記しないことが重要です。

最小例：通常のclassとrecord

C# · 独立したコード例
var first = new ProductClass("Pen", 100);
var second = new ProductClass("Pen", 100);
Console.WriteLine(first == second);
Console.WriteLine(first.Equals(second));

var one = new ProductRecord("Pen", 100);
var two = new ProductRecord("Pen", 100);
Console.WriteLine(one == two);
Console.WriteLine(ReferenceEquals(one, two));

public class ProductClass
{
    public string Name { get; }
    public int Price { get; }
    public ProductClass(string name, int price)
    {
        Name = name;
        Price = price;
    }
}
public record ProductRecord(string Name, int Price);

期待出力はFalse、False、True、Falseです。このProductClassは等値性をカスタマイズしていないので、別の実体は等しくありません。record classには値に基づく等値性のためのメンバーが生成されるので、同じ実行時のrecord型で対応する値が等しい二つは等しいと扱われます。ただし実体は別です。

recordは、データを中心とする型で等値性・表示・コピーなどの定型的な実装をコンパイラーに生成させる機能です。recordだけならrecord class、record structなら値型です。recordを使えばデータベース上の同じ行か自動で判断されるわけではありません。何を同じ値とするかは設計の問題です。

文法・実例・処理順

csharp
var first = new Result("C#", 80);
var second = new Result("C#", 80);
var improved = first with { Score = 95 };
Console.WriteLine(first == second);
Console.WriteLine(ReferenceEquals(first, second));
Console.WriteLine($"{first.Score} → {improved.Score}");

public record Result(string Subject, int Score);

想定出力

True False 80 → 95

処理順

  1. firstとsecondは別インスタンスだが、レコードの値は等しい。
  2. ReferenceEqualsは同じインスタンスかを調べるのでFalse。
  3. withは新しいレコードを作り、first.Scoreは80のまま残る。

値・状態の変化を追う

Console.WriteLine(original == improved);

よくある間違いと修正

よくある間違い

recordのListメンバーは、自動で全要素を内容比較するとは限りません。コレクションの比較にはSequenceEqualなど、要件に合う比較が必要です。

withした履歴のタグまで変わる

修正箇所: recordの参照型メンバーのコピー

修正前

csharp
var original = new Note(new List<string> { "基礎" });
var copy = original with { };
copy.Tags.Add("復習");
public record Note(List<string> Tags);

修正後

csharp
var original = new Note(new List<string> { "基礎" });
var copy = original with { Tags = new List<string>(original.Tags) };
copy.Tags.Add("復習");
Console.WriteLine(string.Join(",", original.Tags));
Console.WriteLine(string.Join(",", copy.Tags));
public record Note(List<string> Tags);
変更理由

withで外側をコピーするだけではListを共有します。今回はタグが不変なstringなので、新しいListへ要素をコピーすることで必要な独立性が得られます。タグが可変クラスならその深さも検討します。

修正後の確認

  • 元は基礎のみ
  • コピーは基礎,復習
  • ReferenceEquals(original.Tags,copy.Tags)はfalse

Console.WriteLine(first.Values.SequenceEqual(second.Values));
public record Batch(int[] Values);

想定出力

False True
  • 外側がrecordでも、配列の等値性が自動的に要素単位へ置き換わるわけではない。
  • 別々に作った配列は参照が違うためrecord比較はfalseとなる。
  • SequenceEqualは順に対応する要素を比較するので、この内容ではtrueになる。
入力 / 条件期待結果
同じ並び1,2False / True
順番2,1False / False
同じ配列を共有True / True

処理と結果の読み解き

Batch同士の比較では配列メンバーの既定の比較が使われ、別配列なのでfalse。SequenceEqualでは列の要素を順に比較し、1と2が一致してtrue。

よくある別解と選び方

要素列を値として比較する独自の等値性を定義する設計もあるが、ハッシュコードとの整合性まで必要になる。

よくある間違いと確認箇所

withやrecordという名前だけで深いコピー・深い比較が保証されると考えない。メンバーの型の比較規則まで確認する。

実務へのつながり：APIモデルの差分検出で、外側のrecordと内部のコレクションの性質を分けて扱う。

確認問題

Q1. record Person(string Name); のPersonは何型？
解説：値型はrecord structと書きます。

値の内容で比較しやすいことと、値型であることは別です。record単独の宣言は参照型であり、値型を選ぶにはrecord structと書きます。

解説：record単独は参照型です。値型にする場合はrecord structと書きます。

recordという名前から「必ず値型」と推測しないでください。classかstructかという分類と、等値比較を生成する機能を別々に考えます。

正解：record単独はrecord classです。

この宣言はrecord class Personと同じ型分類です。変数同士の通常代入では、別のPerson全体ではなく参照値をコピーします。

解説：独立したユーザー定義型です。

Nameがstringというメンバーを持つ新しいPerson型です。stringへの別名ならusingの別名指定などであり、record宣言とは異なります。

Q2. recordのwithによるコピーは？
解説：子オブジェクト全体を再生成するわけではありません。

withは参照型メンバーの実体まで再帰的に複製しません。Listを持つrecordならコピー前後で同じListを指すことがあり、変更が伝わります。

解説：元は残して別のレコードを作ります。

式は新しいコピーを結果として返します。元のrecord変数へその結果を代入しない限り、変数自体は元の実体を指したままです。

解説：シリアル化ではありません。

JSON変換にはJsonSerializerなどを使います。withはメモリ上の値をコピーして指定メンバーを変える構文で、テキスト化ではありません。

正解：可変の子オブジェクトを持つときに注意が必要です。

たとえばTitleだけをwithで変えても、Listプロパティは同じ参照のままになり得ます。独立させたい子だけを明示的にコピーする設計が必要です。

Q3. record Result(string Name,int Score);は？
解説：内部の参照や変更可能メンバーまで自動的に不変にはなりません。

位置指定recordの生成プロパティはinitになりますが、record全般が深い不変性を自動保証するわけではありません。追加メンバーや可変な参照先も確認します。

正解：recordだけの宣言はrecord classを表します。

Resultの変数は実体への参照を保持します。一方で、生成される等値比較はメンバーの値を使うため、参照型かどうかと比較の意味を分けます。

解説：データ用の型宣言であり契約だけのinterfaceではありません。

interfaceは実装が提供すべき操作などの契約を示します。この宣言はインスタンスを作れるrecord型であり、役割が違います。

解説：record structと書いた場合とは異なります。

値型にする構文はrecord struct Result(...)です。recordだけの短い宣言から、structのコピー規則を適用しないでください。

Q4. recordのwithについて正しい説明は？
解説：record classでも利用できる構文です。

record classはwithの代表的な対象です。参照型であることはコピー式を使えない理由ではなく、コピーで共有される範囲に影響します。

解説：子オブジェクトを再帰的に複製する処理ではありません。

Listの参照値をコピーするので、要素を独立させるにはnew List<T>(...)などが必要です。その場合でも要素が参照型ならさらに深さを検討します。

解説：式の結果としてコピーを返し、元の値を残します。

withの結果を別の変数へ受ければ元のrecordは残ります。ただし、共有した可変な子を変更すると両方から見えるという別の注意点があります。

正解：参照型メンバーは参照が共有される場合があります。

元のメンバーをコピーし、withの指定部分へ新しい値を設定した結果を作ります。「非破壊的な外側のコピー」と「子の独立性」は別です。

Q5. recordのメンバーが別々の同内容Listだったとき、通常のrecord比較は？
解説：recordがListの比較規則をシーケンス比較へ自動変更することはありません。

List<T>の通常の等値性は要素列の同一内容を自動比較するものではありません。recordが各メンバーに使う比較の意味まで確認します。

解説：Listをメンバーに持つrecord自体は有効です。

Listをプロパティに持つrecordを宣言・比較することはできます。問題は文法ではなく、生成された比較が要件に合うかどうかです。

解説：件数だけの特別な比較が生成されるわけではありません。

同じ件数のListでも、異なる要素を持ち得ます。recordが特別にCountだけを見る規則はなく、メンバーの等値比較へ従います。

正解：コレクションの内容を比べる要件なら別に表現する必要があります。

同内容かつ同順序なら等しいという要件にはSequenceEqualなどを明示します。文字列の比較方針や、順序を無視するかも別途決めます。
