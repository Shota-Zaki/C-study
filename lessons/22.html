日時とカルチャー

同じ瞬間の異なる表示。

.NET 10 / C# 14
本文・演習詳細解説
重要時刻の値、UTCからの差、表示形式は別々の情報です。

図解：同じ瞬間の異なる表示

要点

  • DateOnly・DateTimeOffset・TimeSpanを選ぶ
  • 保存用と表示用の書式を分ける
重要

DateOnly、DateTimeOffset、TimeSpan、CultureInfoは扱う時間情報が異なります。保存用の値と利用者向け表示を分けて設計します。

C#
// DateOnly / DateTimeOffset / TimeSpan

概念・構文

日時の不具合は、計算より「何を表す値か」の取り違えから起きます。日付だけ、時刻だけ、世界のある瞬間、経過時間を別の型として扱い、表示形式と保存形式を分けます。

何を表したいかで型を選ぶ

誕生日や締切日など時刻のない日付にはDateOnly、15時30分のような時刻にはTimeOnly、経過時間にはTimeSpanを使えます。ある瞬間をUTCとのずれ付きで記録するならDateTimeOffsetが候補です。DateTimeにも用途はありますが、KindがUTC/Local/Unspecifiedのどれかを確認します。

オフセットは地域そのものではない

+09:00はUTCから9時間進んでいることを表します。同じオフセットの地域は複数あり、DateTimeOffsetだけでAsia/TokyoなどのタイムゾーンIDや夏時間規則を保持するわけではありません。将来の「現地の毎朝9時」を扱う予定表では、地域のタイムゾーン規則も必要です。

表示と保存を分ける

日付や小数のToStringはカルチャーの影響を受けます。人向け表示は対象地域に合わせ、機械向けの文字列ではISO 8601形式やInvariantCultureなどを明示します。日本語の文字列をそのまま日時として再解析する設計より、JSONの日時表現など一貫した形式を選ぶ方が保守しやすくなります。

日付・瞬間・期間を違う型で表す

DateOnlyは誕生日や営業日など日付そのもの、TimeOnlyは開店時刻など時刻そのものを表す候補です。DateTimeOffsetは日時とUTCからのオフセットを持ち、ある瞬間を表す用途に向いています。TimeSpanは二つの時点の差などの期間を表します。日付しか必要ない値へ適当な午前0時とタイムゾーンを付けると、変換時に日付がずれる原因になります。

DateTimeにはKindによるUtc・Local・Unspecifiedの違いがあります。Unspecifiedだから自動的に日本時間になるわけではありません。外部仕様と型の意味を合わせ、ログやAPIで時点を交換するときはUTCまたは明示されたオフセットを持つ形式を検討します。

オフセットはタイムゾーンの全ルールではない

2026-09-14T09:00:00+09:00と2026-09-14T00:00:00+00:00は同じ瞬間です。DateTimeOffsetをUTCへ変換するとこの対応を確認できます。ただし+09:00はUTCとの差であり、地域名や夏時間を含むタイムゾーンのすべての規則を表しているわけではありません。

「毎日その地域の9時に実行」のような将来の予定では、地域のタイムゾーンと日付の規則を持つ必要があります。TimeZoneInfoなどで変換するときは、存在しないローカル時刻や二通りに解釈できる時刻がある地域も考えます。今回の固定オフセットの例を、そのまま全世界の予定管理へ拡張できると考えないでください。

人に見せる形式と機械へ保存する形式

表示では利用者の文化に応じた日付や数値の表記が役立ちます。一方、保存・API・テストで文化が変わると困る値はInvariantCultureと明示的な形式を使います。DateTimeOffsetのO形式はオフセットを含むラウンドトリップ用表現です。DateOnlyならyyyy-MM-ddなど、日付という意味に合う書式を決めます。

01/02/2026のような表記は月日順の解釈が文化によって変わります。外部から固定形式を受け取るならTryParseExactとCultureInfoを指定し、曖昧な入力を推測で受け入れない方が検証しやすくなります。表示文字列を業務計算の内部値として保存し続けることは避けます。

経過時間の合計と部品を区別する

TimeSpan.Minutesは分の成分であり、期間全体を分へ換算した値ではありません。90分ならHoursは1、Minutesは30、TotalMinutesは90です。処理時間や学習時間の合計を表示するときは、必要な単位に合うTotal系プロパティを確認します。

実行時間の計測にはStopwatchを使い、時計の表示時刻の差だけに頼らない設計を検討します。現在時刻を直接取得するコードはテストごとに結果が変わりやすいので、固定値を渡す、時刻取得を抽象化する、TimeProviderを利用するなどの方法があります。テストで日付を固定することと、本番の現在日付を固定してしまうことは別です。

仕組みの補足

日付・時刻・瞬間の違い

誕生日、会議の開始時刻、注文が確定した瞬間、処理にかかった時間は、全て数字で時を表しますが意味は異なります。必要な意味を型で区別しないと、表示する地域が変わっただけで日付がずれたり、同じ瞬間を別のものとして比較したりします。

UTCは世界の時刻を扱う基準です。オフセットはUTCとの差を表します。タイムゾーンは地域ごとの時刻の規則であり、夏時間などによる過去・将来の差も含むため、単なる+09:00のような差とは同じではありません。カルチャーは数値や日時の表示・解析に使う地域的な書式などの設定です。

表したいもの 主な候補 選ぶ理由
誕生日・締め日 DateOnly 時刻や地域換算を持たせない
毎日の開店時刻 TimeOnly 特定の日付とは切り離す
発生した瞬間とUTCとの差 DateTimeOffset 一つの瞬間を明確に扱いやすい
UTC / Localなどの区分を持つ日時 DateTime 既存APIなどとの連携。Kindに注意
所要時間・間隔 TimeSpan 日付ではなく長さ
実際の経過時間の測定 Stopwatch 時計合わせの影響を避けやすい計測

DateOnlyは日付そのものを表す

C# · 独立したコード例
using System.Globalization;

var deadline = new DateOnly(2026, 9, 30);
DateOnly next = deadline.AddDays(1);
Console.WriteLine(deadline.ToString("yyyy-MM-dd", CultureInfo.InvariantCulture));
Console.WriteLine(next.ToString("yyyy-MM-dd", CultureInfo.InvariantCulture));

期待出力は2026-09-30、2026-10-01です。AddDaysは元の値を書き換えず、新しい日付を返します。DateOnlyは値型なので、変数deadlineとnextはそれぞれの値を保持します。月末から翌月へ移る計算を、日だけ手動で31に増やすのではなくAPIへ任せています。

yyyy-MM-ddでは年、月、日を指定し、MMは月です。mmは分なので、大文字と小文字の違いが意味を持ちます。InvariantCultureは利用者の地域設定に左右されない書式処理に使うカルチャーです。データ交換の安定した文字列表現に適しています。

文法・実例・処理順

csharp
using System.Globalization;

var started = new DateTimeOffset(2026, 9, 14, 9, 0, 0, TimeSpan.FromHours(9));
var ended = started.AddMinutes(45);
TimeSpan duration = ended - started;
Console.WriteLine(started.ToUniversalTime().ToString("yyyy-MM-dd HH:mm 'UTC'", CultureInfo.InvariantCulture));
Console.WriteLine($"{duration.TotalMinutes}分");
Console.WriteLine(1234.5m.ToString("F2", CultureInfo.InvariantCulture));

想定出力

2026-09-14 00:00 UTC 45分 1234.50

処理順

  1. 9時の+09:00はUTCでは同日の0時を表す。
  2. 日時の差はTimeSpanとなり、TotalMinutesで45を得る。
  3. 固定カルチャーとF2で小数点以下2桁を明示する。

よくある間違いと修正

よくある間違い

日付だけの予定を「UTCの午前0時」に変換して保存すると、地域によって日付がずれる原因になります。日付だけなら日付だけの型を使います。

90分の学習が30分と表示される

修正箇所: TimeSpanから合計分を取得する箇所

修正前

csharp
var study = TimeSpan.FromMinutes(90);
Console.WriteLine(study.Minutes);

修正後

csharp
using System.Globalization;
var study = TimeSpan.FromMinutes(90);
Console.WriteLine(study.TotalMinutes.ToString("0.##", CultureInfo.InvariantCulture));
変更理由

Minutesは時間を除いた分の成分です。期間全体を分へ換算するTotalMinutesへ変更し、90分を90として扱います。

修正後の確認

  • 30分→30
  • 60分→60
  • 90分→90
実コード例

実例：UTCの記録を+09:00で表示する

固定の入力を使い、実行した日時や端末の地域設定に依存しない例です。

C# · Program.cs
using System.Globalization;
var utc = new DateTimeOffset(2026, 1, 1, 0, 0, 0, TimeSpan.Zero);
var local = utc.ToOffset(TimeSpan.FromHours(9));
Console.WriteLine(utc.ToString("yyyy-MM-dd HH:mm zzz", CultureInfo.InvariantCulture));
Console.WriteLine(local.ToString("yyyy-MM-dd HH:mm zzz", CultureInfo.InvariantCulture));
Console.WriteLine(utc == local);

想定出力

2026-01-01 00:00 +00:00
2026-01-01 09:00 +09:00
True

処理と値の変化

  1. utcオフセット0で値を生成する
  2. ToOffset同じ瞬間を別のオフセットで表現する
  3. ==表記は違っても同じ瞬間なのでTrue
条件を変えた場合

ToOffsetは単に9時間後の別の瞬間を作る操作ではありません。時間を進めるAddHoursとの違いを確認します。

確認問題

Q1. 時刻のない誕生日を表す候補として最も直接的なのは？
解説：非同期処理を表します。

Taskは完了や結果を表す非同期の型です。日付そのものを保持したい目的とは種類が異なるため、名前の時間的な印象だけで選びません。

解説：TimeSpanは経過時間などの期間を表すため、誕生日の日付そのものには適しません。

TimeSpanは90分や3日間など長さを表します。誕生日の2026年9月14日という暦上の一点とは意味が違います。

正解：年月日を表すための型です。

DateOnlyは年月日を持ち、不要な時刻やUTC換算を持ち込みません。時刻を含まない業務データの意味を直接表せます。

解説：キャンセル通知用です。

CancellationTokenは中止要求を伝える値です。誕生日の保存や日時の形式変換には使いません。

Q2. DateTimeOffsetの+09:00が保証するのは？
解説：同じオフセットの地域は複数あります。

同じUTC差を持つ地域は複数あり、その場所で本当に発生した証拠にもなりません。オフセットを地理情報として過剰に解釈しないでください。

解説：地域のタイムゾーン規則そのものではありません。

+09:00はその値の差であり、地域の過去・将来の切り替え規則は持ちません。必要ならタイムゾーンの識別情報を別に保持します。

解説：時計の正確さまでは保証しません。

端末が間違った時刻を作っても型へ保存できます。型が表せる情報と、入力された時計が正確かという品質は別の問題です。

正解：オフセットの意味を地域名と区別します。

UTC表示へ換算する差が9時間であることを表します。同じ瞬間を別のオフセットで表示しても、時計の数字が変わるだけの場合があります。

Q3. TimeSpan.FromMinutes(90).Minutesは？
解説：合計分を得るのはTotalMinutesです。

Minutesは時間を除いた分の成分です。90分という全体の長さを分で読むならTotalMinutesを使います。

解説：TotalSecondsなら5400です。

5400は90分を秒へ換算した合計です。成分のMinutes、合計のTotalMinutes、合計秒のTotalSecondsを別々に読みます。

正解：1時間30分のうち分の成分を返します。

90分は1時間30分なので、分の成分は30です。部品と全体の単位換算を混同しないよう、プロパティ名のTotalを確認します。

解説：TotalHoursの値と混同しています。

1.5は全体を時間で表したTotalHoursです。Minutesは合計時間を別単位に変換するプロパティではありません。

Q4. DateTimeOffsetの+09:00だけで地域の夏時間ルールまで分かる？
解説：同じオフセットを使う地域は一つとは限りません。

オフセットだけではどの地域の規則かを一意に決められません。将来の予約などで地域を使うなら、地域IDも管理します。

正解：予定管理では必要に応じて地域情報も保持します。

固定のUTC差と地域の規則は別です。夏時間の変更や曖昧な現地時刻を扱う場面では、タイムゾーンを含む設計が必要です。

解説：固定の差だけでは地域と将来のルールを特定できません。

一つの時点の差から、地域や将来の切り替えを復元することはできません。データに含まれていない情報を型から推測しないでください。

解説：UTCとの差があるので同じ瞬間のUTCへ変換できます。

UTCとの差は分かるので、そのDateTimeOffsetが表す瞬間をUTCへ変換できます。変換可能性と地域規則の保持は別の性質です。

Q5. 日付依存の単体テストを安定させる方法は？
解説：本質的な依存を解消していません。

実行日に合わせて期待値を書き換えると再現性が落ちます。判定に使う基準日を固定して、仕様が正しいかを同じ入力で比較します。

正解：時間という外部依存を固定でき、境界値を再現できます。

基準日を引数にする、または時計のinterfaceを渡す方法があります。月末・年末・境界時刻を任意に再現でき、テストの目的が明確になります。

解説：検証対象のルールを失ってしまいます。

比較を消すと、本来検証したい期限や範囲の仕様も確かめられません。環境依存を分離し、判断のロジックは残します。

解説：テスト実行日や境界時刻に依存します。

テストが日付や実行時刻で変わる原因を内部へ残しています。必要な現在日時の取得は境界に寄せ、判断へ値として渡すと安定します。
