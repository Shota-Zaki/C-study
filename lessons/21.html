Lesson 21 · Chapter 6

ファイルとJSON

オブジェクトとJSONの変換。

.NET 10 / C# 14
本文・演習詳細解説
重要JSON文字列とC#オブジェクトは異なる表現です。保存・復元には変換と入力の検証が必要です。

アプリの変数とディスク上のファイルは別物です。まず値をJSON文字列へ変換し、その後で保存場所、読み込み、復元後の検証へ進みます。

要点

  • JSONへ変換して復元する
  • ファイル不存在と破損を区別する
重要

System.Text.Jsonで直列化・逆直列化しても、復元後の値が業務上妥当とは限りません。ファイルI/O、型変換、値検証を段階に分けます。

C#
string json = JsonSerializer.Serialize(value);

C#の値とJSON文字列を行き来する

ファイル保存では、文字列をJSONへ変換できることだけでなく、どこへ保存するか、読み出したデータが有効か、破損時にどうするかまでが一つの処理です。ファイル操作と業務データの検証を分離し、データを黙って失わない設計を学びます。

メモリと保存先を区別する

Listへ追加したデータは、通常アプリの終了で失われます。再起動後も必要ならファイルやデータベースへ保存します。ファイルI/Oは存在しないパス、アクセス権、容量不足などで失敗します。File.Existsを先に確認しても、その直後に状態が変わる可能性があるため、I/O自体の例外処理も考えます。

JSONはデータの交換形式

System.Text.JsonのJsonSerializer.Serializeでオブジェクトを文字列へ変換し、Deserialize<T>で復元します。既定の設定では主にpublicプロパティを扱います。文字列の見た目を手で連結してJSONを作ると、引用符や改行のエスケープで壊れるため、シリアライザーを使います。

シリアル化は構造を変換する処理

JsonSerializer.SerializeはオブジェクトからJSON文字列を作り、Deserialize<T>はJSONから指定した型のデータを復元します。プロパティ名、大文字小文字、命名規則、フィールドを含める設定などに規則があります。コンソールでの既定設定とWebで用いられる設定が同じとは限らないため、データ交換の契約を明示します。

この単元ではDTOをrecordなどで定義し、保存形式とアプリ内部の操作を分けます。JSONはオブジェクトの振る舞いやメソッドの処理まで保存するものではありません。参照の循環や多態的な型をそのまま保存したい場合は追加設計が必要なので、最初は単純なデータの形を保ちます。

オブジェクトをJSONにして復元する

csharp
using System.Text.Json;

var session = new StudyLog("CSharp", 30);
string json = JsonSerializer.Serialize(session);
Console.WriteLine(json);
var restored = JsonSerializer.Deserialize<StudyLog>(json)
    ?? throw new InvalidOperationException("データがありません");
Console.WriteLine(restored.Minutes);

public record StudyLog(string Subject, int Minutes);

この最小例は、メモリ上のオブジェクトとJSON文字列を相互に変換します。Serializeだけでディスクへ保存されるわけではありません。

ファイルへの書き込みは、この変換とは別にFile.WriteAllTextなどで行います。まず変換の入出力を確認すると、ファイルの場所の問題と混同せずに調べられます。

想定出力

{"Subject":"CSharp","Minutes":30} 30

処理順

  1. レコードをJSON文字列へ変換する。
  2. Deserializeは指定した型へ読み込む。
  3. nullの結果を拒否してからMinutesへアクセスする。

メモリ上の値と保存する文字列

ファイルとJSONによるデータ保存

変数やListに入れたデータは、アプリケーションが終了すると通常そのままでは次回へ引き継がれません。ファイルへ保存し、次の起動時に読み込むことで、実行中の状態と保存済みの状態をつなぎます。こうしてデータを終了後も残すことを永続化と呼びます。

JSONは、名前と値、配列、数値、文字列、true/false、nullなどをテキストで表すデータ形式です。オブジェクトをJSONへ変換することをシリアル化、JSONから型に沿った値を作ることを逆シリアル化と呼びます。ファイルへ書く処理とJSONへ変換する処理は別です。JSONは文字列として通信へ使うこともできます。

最小例：JSONはまず文字列として扱える

C# · 独立したコード例
using System.Text.Json;

var item = new Item("Note", 3);
string json = JsonSerializer.Serialize(item);
Console.WriteLine(json);
Item? loaded = JsonSerializer.Deserialize<Item>(json);
if (loaded is null)
{
    Console.WriteLine("データなし");
}
else
{
    Console.WriteLine($"{loaded.Name}:{loaded.Quantity}");
}

public record Item(string Name, int Quantity);

通常の設定で期待されるJSONは{"Name":"Note","Quantity":3}、続く表示はNote:3です。JSONのプロパティ順序を業務の意味として依存しないようにします。Deserialize<Item>の型引数は「どんな型へ戻したいか」を指定しています。文字列の中にJSONのnullがあると、参照型の逆シリアル化結果がnullになる可能性があるため、Item?で受けています。

JSONを読むことは、既存のitemをそのまま取り戻すことではありません。この例では同じような値を持つ別のオブジェクトが作られます。参照の同一性ではなく、保存したデータの内容を確認します。

続き：処理順・状態変化・修正例を読む →

書き込むファイルの場所を決める

相対パス・作業ディレクトリ・文字コード

File.WriteAllText("data.json",json)の相対パスは、ソースファイルがある場所ではなく、実行プロセスの現在の作業ディレクトリを基準に解決されます。IDE、ターミナル、サービスで起動方法を変えると保存先が変わる原因になります。Environment.CurrentDirectoryやPath.GetFullPathで実際の場所を確認します。

Path.Combineでパスを組み立て、存在しない保存フォルダーは必要に応じてDirectory.CreateDirectoryで用意します。文字列からバイト列への変換には文字コードが関係します。外部と交換するファイルではUTF-8などの取り決めを明示します。利用者が入力した任意のパスをそのまま結合して書き込む設計は、許可した領域の外へアクセスしない検証も必要です。

"logs.json"のような相対パスでは、どのフォルダーを基準にするかが必要です。

相対パスは通常、実行時のカレントディレクトリを基準に解釈されます。Program.csのある場所や実行ファイルの場所と必ず一致するわけではありません。

JSONを読み、欠損と値の範囲を検証する

csharp
using System.Text.Json;
foreach (string json in new[] { "{\"Title\":\"C#\",\"Count\":2}", "null", "{\"Title\":\"\",\"Count\":-1}" })
{
    BookData? book = JsonSerializer.Deserialize<BookData>(json);
    if (book is null || string.IsNullOrWhiteSpace(book.Title) || book.Count < 0)
    {
        Console.WriteLine("データ不正");
        continue;
    }
    Console.WriteLine($"{book.Title}: {book.Count}");
}
public record BookData(string? Title, int Count);

出力

C#: 2 データ不正 データ不正
段階値・状態読み解き
構文を読む最初のJSONはBookDataへ変換変換と検証は別
最初の値Title=C#、Count=2必要条件を満たす
JSON null復元結果がnullプロパティへ触れる前に拒否
空タイトル・負の件数オブジェクトとしては復元可能業務検証で拒否
実コード例

実例：タスクをJSONへ変換して復元する

ブラウザ内実行にも適した、ディスクを使わない変換だけの例です。

C# · Program.cs
using System.Text.Json;
var task = new TaskItem(1, "Review", false);
string json = JsonSerializer.Serialize(task);
Console.WriteLine(json);
TaskItem? restored = JsonSerializer.Deserialize<TaskItem>(json);
Console.WriteLine(restored?.Title ?? "復元なし");
record TaskItem(int Id, string Title, bool Done);

このコードの図解：オブジェクトとJSONの変換

想定出力

{"Id":1,"Title":"Review","Done":false}
Review

処理と値の変化

  1. Serializeプロパティの値をJSONへ変換する
  2. string jsonこの時点では単なる文字列として保持する
  3. Deserialize指定したTaskItem型へ復元する
条件を変えた場合

jsonを"null"にすると、restoredはnullになります。後続処理でnullを考慮する必要があります。

サンプル一式 Program.cs

読み込み失敗と不正データから守る

復元と検証は別

JSONとして読めても業務上正しいとは限りません。必須値・範囲・重複IDなどを検証します。ファイルがない初回起動と、ファイルが壊れた異常をどちらも空データとして扱うと、元データを上書きして失う恐れがあります。制作課題では読み込み失敗時は中断し、勝手に初期化しません。

構文が正しいJSONでも業務データとして不正な場合

JSONのnullをDeserializeすると、参照型の結果がnullになることがあります。必要なプロパティが欠けていても設定や型によって既定値が入る場合があります。stringを非nullableで宣言しただけで、外部データのすべての欠損や不正値が自動的に拒否されると考えてはいけません。

読み出し後にタイトルの空白、負の件数、重複ID、対応していない保存形式のバージョンなどを検査します。「JSONとして読める」「必要項目がある」「業務ルールを満たす」を順に確認すると、失敗理由を分けて表示できます。ブラウザから来るDTOも同じ考え方です。

ファイルを読み込んで復元する処理には、異なる失敗の段階があります。

たとえばMinutesが負でも、型に収まる数値ならJSONから復元できる場合があります。復元後に業務ルールを検証し、不正な状態をそのまま採用しないようにします。

読めないデータを空データで上書きしない

初回でファイルが存在しないことと、既存ファイルが壊れて読めないことは別です。catchですべて空Listへ置き換えてから保存すると、復旧できたはずのデータを失うおそれがあります。破損やアクセス権限の問題は利用者へ伝え、元ファイルを保持したまま復旧方法を選びます。

保存途中で停止すると、直接上書き中のファイルが中途半端になる可能性があります。同じ保存先領域の一時ファイルへ書いてから置き換える、バックアップを保持する、DBのトランザクションへ移すなどの選択肢があります。ただしファイルの置き換えだけで全OS・全ファイルシステムのクラッシュ耐性や同時書き込みが保証されるわけではありません。学習用の単一プロセス保存と本番の永続化を区別します。

よくある間違いと修正

よくある間違い

JSONを暗号化された形式だと思わないでください。パスワード、トークン、個人情報をそのまま保存しない設計が必要です。

復元結果のnullを無視してアクセスする

修正箇所: Deserialize直後の境界

修正前

csharp
using System.Text.Json;
var data = JsonSerializer.Deserialize<Item>("null");
Console.WriteLine(data!.Name);
public record Item(string Name);

修正後

csharp
using System.Text.Json;
var data = JsonSerializer.Deserialize<Item>("null");
if (data is null || string.IsNullOrWhiteSpace(data.Name))
{
    Console.WriteLine("有効なデータがありません");
    return;
}
Console.WriteLine(data.Name);
public record Item(string? Name);
変更理由

!は実行時のnullを解消しません。復元の境界で結果と必須値を検証してから、後続へ有効なデータだけを渡します。この例は構文として有効なJSONを扱い、壊れたJSONのJsonExceptionは別の失敗経路です。

修正後の確認

  • null→説明を表示
  • Nameが空→説明を表示
  • 正常なName→表示

応用

応用：一時フォルダーで保存と復元を試す

他のファイルを上書きしない専用の一時フォルダーを作り、学習時間30をJSON保存して読み直します。最後に今回作ったフォルダーだけを削除します。

解答例と確認ポイント
csharp
using System.Text.Json;
string directory = Path.Combine(Path.GetTempPath(), "csharp-lab-" + Guid.NewGuid().ToString("N"));
Directory.CreateDirectory(directory);
try
{
    string path = Path.Combine(directory, "study.json");
    File.WriteAllText(path, JsonSerializer.Serialize(new Study(30)));
    var data = JsonSerializer.Deserialize<Study>(File.ReadAllText(path));
    if (data is null || data.Minutes < 0) throw new InvalidDataException("学習時間が不正です");
    Console.WriteLine($"復元: {data.Minutes}分");
}
finally
{
    Directory.Delete(directory, recursive: true);
}

よくある間違いと確認箇所

Path.GetTempPathが返す共有の一時領域そのものを再帰削除しない。今回作った子フォルダーだけを扱う。

実務例：ファイル操作は副作用があるため、保存先・上書き・失敗時・後片付けを一組で考える。

確認問題

Q1. Serializeの結果が得られた時点で、通常すでに完了しているのは？
正解：文字列を作る操作です。保存は別途必要です。

Serializeはオブジェクトの値をJSONとして表す文字列を作ります。その文字列を保存するか通信するかは、呼び出し側が別の操作で決めます。

解説：ファイル書き込みは自動では行いません。

File.WriteAllTextなどの書き込みを呼んでいなければ、終了後に残る保存は行われません。メモリ上の文字列と永続化を別の段階として確認します。

解説：ネットワーク通信は含みません。

通信先や送信APIの指定がなければクラウドへは送られません。データ形式の変換とネットワークへの送信は別です。

解説：範囲や必須などの検証は別です。

負の数量でもintとしてシリアル化できます。JSONへ変換できることから、業務上許せる値だと判断しないでください。

Q2. 壊れた保存ファイルを読み込めない場合、最も避けたい対応は？
解説：調査と復旧のために必要な対応です。

どのファイルをどの理由で読めなかったかを知らせると復旧につながります。秘密情報を露出しない範囲で、原因の切り分けに必要な情報を残します。

正解：元のデータを失う危険があります。

壊れたデータを空の一覧と同じ扱いにすると、次の保存で元データを消してしまいます。初回でファイルがない場合と、破損して読めない場合を分けます。

解説：復旧の可能性を残します。

元ファイルを保持しておけば、形式の修正やバックアップとの比較ができます。読み込めなかった時点で無条件に書き換えないことが重要です。

解説：書き換えを止めて安全に失敗する選択肢です。

編集や保存へ進めず、安全に失敗を返すことは適切な選択肢です。継続する場合も、元データを破壊しない別のモードとして設計します。

Q3. 相対パスdata.jsonの基準は？
解説：SDKのインストール先を基準にはしません。

SDKは開発ツールの置き場所です。アプリの相対パスは、そのインストール先へ自動的に向くものではありません。

解説：保存先を明示しない限りデスクトップとは限りません。

デスクトップへ保存したいなら、その場所を適切に取得して指定する必要があります。ファイル名だけで利用者の特定フォルダーが選ばれるわけではありません。

解説：ソースの配置と起動時の作業場所は別です。

ビルド後のアプリはソースの場所とは別の場所で起動できます。Program.csと同じフォルダーにあるはず、という前提だけでファイルを探しません。

正解：Environment.CurrentDirectory等で確認できます。

Environment.CurrentDirectoryとPath.GetFullPathで実際の解決先を表示すると切り分けられます。起動方法を変えた場合に同じ基準か確認します。

Q4. Deserializeが成功したデータについて正しいのは？
解説：型がintというだけでは負数を禁止しません。

intは負数を表せる型です。Quantity=-1を型へ変換できても、数量は1以上という業務ルールは別に検証します。

解説：コンパイル時の解析と外部入力の検証を混同できません。

nullable解析はC#のソース上の安全性を助けます。外部JSONから入る値の欠落や業務制約を、注釈だけで全て保証するとは考えません。

解説：構文の変換と業務上の正しさは別です。

構文が正しく対象型へ変換できた段階です。タイトル空白、日付の前後関係、IDの存在などは追加の利用条件として確認します。

正解：外部データの境界で必要な条件を検証します。

入力DTOで欠落を表し、null・空白・範囲・組み合わせを確認してから業務処理へ渡します。変換の成功と利用の許可を分けるのが重要です。

Q5. 既存ファイルが壊れていたとき最も避けたい対応は？
解説：破損と初回未作成を区別します。

破損の種類や取得できるバックアップを調べることは適切です。初回のファイル未作成と、既存ファイルを読めない事象を同じ処理にしません。

解説：復旧可能性を残す対応です。

誤った保存で復旧可能性を消さず、何が起きたかを利用者へ伝えます。読み取り失敗時に変更系の処理へ進まない方針を明示します。

正解：元データを失い、破損を発見しにくくします。

元の一覧が本当は空でなかった場合、次回から破損の痕跡も失われます。成功に見せて上書きするのではなく、保存を止めて復旧へ進みます。

解説：保存済みバックアップが復旧に役立つ場合があります。

バックアップの内容と時点を確認して戻す方法が考えられます。ただしバックアップが存在し正常であるかは、実際に確認が必要です。
