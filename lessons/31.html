概念と内部の仕組み

DIはnewを禁止する規則ではなく、アプリが依存オブジェクトをどこで作り、どの範囲で共有し、いつ破棄するかを管理する仕組みです。設定とログも境界を決め、秘密情報と要求ごとの状態を安全に扱います。

サービスを登録して受け取る

builder.Servicesへ登録したサービスを、エンドポイントの引数などから受け取れます。Transientは解決のたび、Scopedはスコープごと、Singletonはコンテナーの生存期間で共有します。WebアプリのScopedは通常1リクエストのスコープです。Singletonにはリクエストごとの可変状態を不用意に置かず、共有データは同時実行への対策が必要です。

設定値と秘密を分ける

appsettings.jsonや環境変数を通じて設定値を受け取れます。接続先など環境ごとに変わる値をコードへ固定しない設計にします。開発中の秘密情報にはUser Secretsなどを使えますが、User Secretsも暗号化保管ではありません。本番用の秘密管理とは分けて考えます。

ログは調査のための記録

ILoggerのテンプレートへ値を渡す構造化ログにすると、項目ごとに検索しやすくなります。パスワードやトークン、入力本文を無条件に出力してはいけません。正常終了だけでなく、入力不正、依存先の障害、処理時間など、運用で必要な情報と保存量を考えます。

登録・解決・利用を分ける

builder.Services.AddSingleton<IMessageService,MessageService>()は対応と寿命を登録します。ハンドラーの引数やコンストラクターでIMessageServiceを要求すると、コンテナーが必要な依存を組み立てます。利用側はnewの詳細ではなく契約へ依存し、テストでは別の実装を渡せます。

何でもIServiceProviderを渡して内部でGetServiceする形は、必要な依存が型の引数から見えにくくなるService Locatorの問題を招きます。基本は必要な依存をコンストラクターやハンドラー引数で明示します。登録漏れ、循環依存、寿命の不整合はDI導入時に新しく確認すべき失敗です。

Transient・Scoped・Singletonの寿命

Transientは解決ごと、Scopedは同じスコープ内、Singletonはコンテナー全体で基本的に一つを共有します。Webでは通常要求ごとにスコープが作られます。要求内で同じ業務状態を共有する必要があるならScopedが候補で、すべての要求で共有するSingletonへ利用者ごとの情報を置くとデータ混入の原因になります。

SingletonがScopedの依存を保持すると、本来の要求の寿命を超えて参照し続ける問題になります。DbContextなど要求範囲の依存をSingletonへ直接注入しないことが基本です。Singletonは共有されるため、変更可能な状態があれば並行アクセスを設計します。登録をSingletonにしただけでスレッドセーフにはなりません。

設定は外へ出すが、読み取るだけで安全とは限らない

IConfigurationからappsettings.json、環境変数などの設定を読み取れます。複数の設定供給元には優先順位があり、同じキーが上書きされることがあります。設定を型へまとめてOptionsとして扱うと、関連項目を一つの契約として検証しやすくなります。必須設定や範囲を起動時に検証しておけば、不正設定のまま要求を受けにくくできます。

接続文字列やAPIキーを公開リポジトリへ直接保存しないでください。開発用のUser Secretsはソースへ埋め込まないための仕組みですが、それ自体を本番の暗号化された秘密管理と同じものとは扱いません。環境変数にも漏えい経路はあり、本番では利用環境に合う秘密管理と権限を設計します。

構造化ログはイベントと値を分ける

logger.LogInformation("Item {ItemId} loaded",id)のようにメッセージテンプレートと値を分けると、ItemIdを検索や集計へ使いやすくなります。文字列補間で全部を一つの文字列へ潰すより、構造を保てます。Trace/Debug/Information/Warning/Errorなどは重要度と運用時の量に合わせて使います。

ログへ認証トークン、パスワード、個人情報を無制限に出さないようにします。要求本文を丸ごと出すより、必要なIDや結果、相関IDを限定して記録します。同じ例外を各層で重複して記録すると一つの障害が何件もあるように見えるため、責任を持って記録する境界も決めます。

概念をもう一段掘り下げる

依存を「使う側の中で作る」から分ける

依存とは、ある処理が仕事をするために必要とする別の部品です。通知処理がメール送信部品を使う、APIがデータ保存部品を使う、といった関係です。DIはDependency Injectionの略で、必要な部品を外から渡す設計です。第12レッスンでコンストラクターへinterfaceの実装を渡したことが、その基本です。

DIコンテナーは、どの型にどの実装を渡すか、いつ作るか、いつまで使うかを登録から管理する仕組みです。DIはフレームワークの機能名だけではありません。手動でnewして渡す設計もDIです。コンテナーは組み立てや寿命の管理を助けます。

最小例：手動で依存を渡す

C# · 独立したコード例
var service = new GreetingService(new FixedClock());
Console.WriteLine(service.Create());

public interface IClock
{
    DateTimeOffset UtcNow { get; }
}
public sealed class FixedClock : IClock
{
    public DateTimeOffset UtcNow => new(2026, 9, 14, 0, 0, 0, TimeSpan.Zero);
}
public sealed class GreetingService
{
    private readonly IClock _clock;
    public GreetingService(IClock clock)
    {
        _clock = clock ?? throw new ArgumentNullException(nameof(clock));
    }
    public string Create() => $"UTC年:{_clock.UtcNow.Year}";
}

期待出力はUTC年:2026です。GreetingServiceは時計を自分でnewせず、外から受け取ります。実際の現在時刻を返す時計と、テスト用の固定時計を差し替えられます。業務処理が時刻の取得方法へ直接結び付かないことが利点です。

続き：処理順・状態変化・修正例を読む →

文法・実例・処理順

csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSingleton<VisitCounter>();
var app = builder.Build();
app.MapGet("/visits", (VisitCounter counter, ILogger<VisitCounter> logger) =>
{
    int count = counter.Next();
    logger.LogInformation("Visit count: {Count}", count);
    return Results.Ok(new { count });
});
app.Run("http://127.0.0.1:5080");

public class VisitCounter
{
    private int count;
    public int Next() => Interlocked.Increment(ref count);
}

想定出力

GET /visits → {"count":1} もう一度GET /visits → {"count":2} 再起動するとカウンターは初期化される

処理順

  1. VisitCounterを共有サービスとして登録する。
  2. 各リクエストで同じカウンターを受け取る。
  3. Interlockedで同時実行時の加算競合を避け、値をログとJSONへ返す。

値・状態の変化を追う

同じ要求内と別要求でScopedのIDを比較する

csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddScoped<RequestStamp>();
builder.Services.AddSingleton<AppStamp>();
var app = builder.Build();
app.MapGet("/lifetime", (RequestStamp first, RequestStamp second, AppStamp shared) =>
    Results.Ok(new { sameRequestInstance = ReferenceEquals(first, second), requestId = first.Id, appId = shared.Id }));
app.Run("http://127.0.0.1:5080");
public class RequestStamp { public Guid Id { get; } = Guid.NewGuid(); }
public class AppStamp { public Guid Id { get; } = Guid.NewGuid(); }

出力

GET /lifetimeを2回実行します。 各応答のsameRequestInstanceはtrueです。 requestIdは要求ごとに異なり、appIdは同じアプリ起動中は同じ値です。 ※GUIDの具体値は固定ではありません。
段階値・状態読み解き
起動二つの寿命を登録登録しただけでは全利用者向けデータが生まれるわけではない
要求1ScopedのRequestStampを解決firstとsecondは同じ要求スコープ
SingletonAppStampを全体共有要求ごとの情報を入れない
要求2新しいScopedが生成appIdは共有のまま
再起動コンテナーを作り直すappIdも変わる

よくある間違いと修正

よくある間違い

ScopedサービスをSingletonへそのまま保持させると寿命が合わず問題になります。長く生きるサービスに、リクエスト専用の状態を取り込まないようにします。

Singletonの共有カウンターで更新が失われる

修正箇所: 共有サービス内の読み取りと加算

修正前

csharp
public class Counter
{
    public int Value { get; private set; }
    public int Next() => ++Value;
}

修正後

csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSingleton<Counter>();
var app = builder.Build();
app.MapPost("/counter", (Counter counter) => Results.Ok(new { value = counter.Next() }));
app.Run("http://127.0.0.1:5080");
public class Counter
{
    private int _value;
    public int Next() => Interlocked.Increment(ref _value);
}
変更理由

複数要求からの読み取り・加算・書き戻しの競合を、この単一整数操作ではInterlockedでまとめます。複数の関連値を一括更新する処理やDBを含む更新が自動的に安全になるわけではありません。

修正後の確認

  • 連続POSTで1,2,3
  • 並行要求でもこの整数加算は原子的
  • 再起動で0に戻る。永続IDとして使わない

基礎・標準・応用演習

基礎

基礎演習

GET /greetingで設定項目Greetingを返してください。設定がなければHelloを返し、秘密情報は扱いません。

開始コード
csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
// IConfigurationを使って/greetingを実装する。
app.Run("http://127.0.0.1:5080");

入力例・前提条件

設定キーGreetingがある場合と、ない場合を使う。

考え方のヒント

builder.Configurationなどから値を読み、nullの場合だけHelloを選ぶ。

入力するとlocalStorageへ保存実行・自動採点は行いません
解答例と確認ポイント
csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
app.MapGet("/greeting", (IConfiguration config) =>
    Results.Ok(new { message = config["Greeting"] ?? "Hello" }));
app.Run("http://127.0.0.1:5080");
解答で確認する条件確認方法
設定なしではmessage=Helloを返す。コードと想定結果を照合
appsettings.jsonのGreetingを変えて再起動すると反映される。コードと想定結果を照合

処理と結果の読み解き

設定なしでは既定値、設定ありでは指定値を返す。設定ファイルを作ったことと、そのプロバイダーが読み込まれたことを区別する。

よくある別解と選び方

環境変数で同じ設定を上書きする確認もできる。構成の優先順と秘密をログへ出さない方針を守る。

よくある間違いと確認箇所

設定全体をJSONで応答へ返さない。必要なGreetingという一項目だけを公開する。

実務へのつながり：コードを書き換えず配置先で動作を変える際、公開する設定を限定する。

標準

標準：設定を起動時に検証する

Greetingが未設定ならHello、設定されていればTrim後1〜40文字を要求します。不正なら起動時に例外とし、正常時はGET /greetingで返します。

  • Build前に設定を読む
  • 未設定と空文字を別に扱う
  • 秘密でない項目だけ返す
開始コード
csharp

var app = builder.Build();

考え方のヒント

未設定と不正な設定を分け、起動時に条件を確定する。

入力するとlocalStorageへ保存実行・自動採点は行いません
解答例と確認ポイント
csharp
var builder = WebApplication.CreateBuilder(args);
string message = (builder.Configuration["Greeting"] ?? "Hello").Trim();
if (message.Length is < 1 or > 40) throw new InvalidOperationException("Greetingは1〜40文字にしてください");
builder.Services.AddSingleton(new GreetingOptions(message));
var app = builder.Build();
app.MapGet("/greeting", (GreetingOptions options) => Results.Ok(new { message = options.Message }));
app.Run("http://127.0.0.1:5080");
public record GreetingOptions(string Message);

想定出力

設定なし: GET /greeting → 200 {"message":"Hello"} Greetingに空白だけを設定: 起動時に失敗 GreetingにHiを設定: GET /greeting → 200 {"message":"Hi"}
  • 設定の不正を最初の利用時まで遅らせず起動境界で検知する。
  • 不変なrecordを一つ共有する今回の用途ではSingletonの共有状態問題が少ない。
  • これはOptionsの考え方を手動で示す例で、IOptionsやValidateOnStartを使う仕組みとは区別する。

処理と結果の読み解き

未設定は仕様どおり補い、空白だけや長すぎる値は不正として起動を止める。要求を受けるたびに曖昧な設定を使わず、早く原因を示す。

よくある別解と選び方

OptionsのValidateOnStartで型付き設定へまとめる方法がある。検証時点が起動時であることを確認する。

よくある間違いと確認箇所

不正な設定を全てHelloに隠すと配置ミスに気づけない。既定値を使う条件を明示する。

実務へのつながり：設定の形式と業務条件を開始時に検査し、運用中の不明な失敗を減らす。

  • テンプレートの{ItemId}等へ値を渡す

確認問題

Q1. Singletonのカウンターへ複数リクエストが同時アクセスするとき必要な観点は？
正解：複合操作や更新の競合を設計する必要があります。

一つのインスタンスを複数の要求が共有するため、読み取りと更新の組み合わせが競合します。単純なcount++でも、読み取り・計算・保存を一体として保護する観点が必要です。

解説：DIの寿命は永続化とは別です。

Singletonは生成したサービスをコンテナー内で共有する寿命の指定です。プロセスを終了するとメモリ上の状態は失われ、DB保存は別の処理です。

解説：null安全性と同時実行安全性は別です。

nullableの注釈は値が存在しない可能性を扱います。同じ値へ同時にアクセスしたときの順序や排他制御を保証するものではありません。

解説：staticでも共有状態の競合は残ります。

staticでも複数スレッドから同じ変数へ到達します。共有範囲を広げることと競合を防ぐことは別で、必要ならlockなどの方法で操作を保護します。

Q2. 開発用User Secretsについて正しい説明は？
解説：開発時の仕組みです。

User Secretsはローカル開発で秘密をプロジェクト外へ分離する仕組みです。暗号化された本番向けの秘密管理サービスと同じ安全性を期待しません。

正解：本番の秘密管理とは区別します。

リポジトリへ秘密を書かない助けになりますが、保存先へのアクセス権にも注意します。本番では配備環境に適した秘密管理を選びます。

解説：ソース管理に秘密を含めないために利用します。

目的は秘密をソース管理から分けることであり、Gitへ追加することではありません。appsettings.jsonに秘密を戻してしまわない運用も必要です。

解説：保管先や権限への注意は必要です。

平文で保存され得る情報だからこそ、利用端末やファイルの権限が重要です。開発用の便利な機能が端末のセキュリティまで代替するわけではありません。

Q3. ScopedのWebサービスは通常どの範囲で共有される？
解説：それはSingletonの共有範囲に近い説明です。

アプリ内で同じものを再利用するのはSingletonの説明です。Scopedは明示されたスコープごとにインスタンスを共有します。

解説：DIコンテナーは分散状態を自動共有しません。

DIコンテナーは通常プロセス内の仕組みです。複数サーバー間で状態を共有するにはDBや共有キャッシュなど別の基盤が必要です。

正解：要求ごとに作られるスコープで共有します。

通常のWeb要求では要求ごとにスコープが作られ、その中で同じScopedサービスを利用できます。要求が終わった後へ参照を持ち出す寿命の誤りに注意します。

解説：Transientの説明に近くなります。

解決のたびに生成するのは基本的にTransientの考え方です。Scopedは同一スコープ内で再利用されるので、毎回別インスタンスとは限りません。

Q4. Singletonへ利用者ごとの変更可能な情報を保存すると？
解説：Singletonは基本的にコンテナー全体で共有です。

Singletonのインスタンスはユーザーごとに自動複製されません。CurrentUserなどを変更可能なフィールドに保存すると、別の要求が上書きする恐れがあります。

解説：DIは永続化機能ではありません。

寿命設定だけでは永続化先は作られません。加えて、利用者情報の共有範囲を誤った問題はDB保存の有無とは別に残ります。

解説：共有状態の並行アクセスは別の設計が必要です。

長寿命の共有オブジェクトへ情報を集めることは安全性を自動的に高めません。利用者や要求ごとのデータは適切な範囲に置き、同時実行も検討します。

正解：寿命と共有範囲を誤るとデータ混入につながります。

要求Aの利用者情報を要求Bが読み取るような混入が起こり得ます。サービスの寿命と、保持するデータが有効な期間を一致させます。

Q5. 構造化ログの基本形は？
正解：テンプレートと値を分けて記録できます。

メッセージの型となるテンプレートとItemIdという値を分離できます。ログの出力先によっては、項目を使った検索や集計へつなげられます。

解説：秘密情報の漏えいになります。

ログは多くの人や外部基盤から閲覧される可能性があります。調査に必要な識別子と秘密情報を区別し、パスワードやトークンを記録しません。

解説：表示はできますが値を一つの文字列にまとめます。

文字列補間は表示用の一つの文字列を先に作ります。構造化した項目として残したい場合はテンプレート引数を使い、補間しか使えないと考えません。

解説：同じ障害が重複して見え、調査を妨げる場合があります。

同じ例外を複数層で記録すると、別々の障害のように見える場合があります。どの境界で記録・変換・通知するかを決め、役に立つ文脈を一度付けます。
