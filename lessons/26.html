概念と内部の仕組み

テストは「成功と表示された」ことではなく、実際の出力と期待値を比較して不一致を検知できる仕組みです。デバッガーで原因を観察し、境界を自動テストへ残して、同じ不具合を繰り返さない流れを作ります。

思い込みより実際の値を見る

VS CodeのC#デバッグでは、止めたい行にブレークポイントを置き、変数・呼び出し履歴・ステップ実行で流れを追います。まず例外メッセージと発生行を読み、そこへ来た入力を確認します。Console.WriteLineだけで追う方法も有効ですが、ログを大量に残す前に、観察する値と仮説を決めます。

テストは期待する仕様をコードにする

Arrangeで入力を準備し、Actで対象を呼び、Assertで期待値と比べます。計算をメソッドへ分けると、画面やDBなしで検証できます。正常値だけでなく、0件、最小値、境界の直前・一致・直後、失敗を検証します。外部通信に毎回依存するテストは遅く不安定になりやすいため、差し替えられる境界を作ります。

テストの仕組みを段階的に学ぶ

下の例は追加パッケージ不要の簡易アサーションです。テストフレームワークの代替として大規模運用するものではありません。次の段階ではdotnet new xunit -n Learning.Testsでテストプロジェクトを作り、テスト対象への参照を追加し、dotnet testで実行します。xUnitのFactは1つのテスト、Theoryは複数入力の検証に使えます。

デバッガーは仮説を確かめる道具

ブレークポイントで処理を止め、入力、ローカル変数、呼び出し履歴を確認します。ステップ実行でどの分岐へ進むかを追い、期待した値と最初にずれる地点を見つけます。最終結果だけを何度も表示するより、原因が発生する境界へ観測点を置く方が効率的です。

例外が起きた行だけが原因とは限りません。前の行で不正な値を入れた、呼び出し側が契約を破ったなどの可能性もあります。ウォッチ式でメソッドを呼ぶと副作用が生じることがあるため、観察自体が状態を変えないかも注意します。変数の推測ではなく、実際の値とコールスタックから仮説を絞ります。

Arrange・Act・Assertを分ける

Arrangeでは入力と依存を準備し、Actでは対象操作を実行し、Assertでは期待値と実際の値を比較します。送料なら小計3000を用意し、Shippingを呼び、戻り値が0かを確認します。結果を表示して人が毎回目視するだけでは、自動的に不具合を検知できません。

テストの期待値を実装と同じ式で計算すると、同じ間違いを二か所へ複製することがあります。期待値は仕様から独立に決めます。一つのテスト名には「どの条件で何になるか」を表し、失敗時に入力・期待値・実際の値を出すと原因を追いやすくなります。

境界・同値クラス・回帰テスト

小計3000以上で無料なら2999、3000、3001を試すことで>と>=の取り違えを発見できます。正常入力を多数ランダムに試す前に、空、0、負数、上限、null、重複など、処理の分かれ目を整理します。すべての入力を列挙できなくても、同じ規則で処理される集合から代表値を選べます。

不具合を修正するときは、修正前に失敗し、修正後に成功するテストを作ります。最初から成功するテストだけでは、問題を捕まえているか不明です。回帰テストとして残すことで、将来の変更が同じ条件を壊したときに検知できます。原因となった入力値をテスト名や失敗メッセージに残します。

単体テストとテストフレームワーク

この教材の簡易Checkは比較の仕組みを理解するためのものです。実務ではxUnitなどのフレームワークでテストを発見・実行し、失敗件数や診断を得ます。Factは一つの事実、TheoryとInlineDataは複数の入力で同じ規則を検証する書き方の例です。テストプロジェクトは対象プロジェクトへの参照を持ちます。

dotnet new xunit -n Study.Tests -f net10.0で作ったテンプレートのパッケージ設定を確認し、dotnet add ... reference ...で対象を参照してdotnet testで実行します。フレームワークや実行基盤のバージョンはテンプレートと公式資料へ合わせます。コンソールのCheckが成功したことを、xUnitやHTTP統合テストが実施済みという報告に置き換えてはいけません。

概念をもう一段掘り下げる

動くことと正しいことを分ける

コンパイルに成功したコードでも、境界値で計算を間違えたり、エラー時に状態を壊したりします。デバッグは動作を観察して原因を調べる作業、テストは期待する結果と実際の結果を比較して仕様を確かめる作業です。どちらも「エラーが出ないから大丈夫」という判断を具体的な根拠へ変えるために使います。

単体テストは、狭い範囲の処理を他の大きな仕組みからなるべく切り離して確かめるものです。結合テストは、複数の部品が連携したときの動作を確かめます。APIをHTTP経由で確かめる場合は、経路や変換も含めた結合テストになります。

最小例：期待値を固定して比べる

次はテストフレームワークを導入する前に、比較の本質を理解するコンソール例です。このページ上でコードを実行しているわけではありません。

C# · 独立したコード例
int actual = ShippingFee(5000);
int expected = 0;
if (actual != expected)
{
    throw new InvalidOperationException($"期待:{expected} 実際:{actual}");
}
Console.WriteLine("境界5000の比較が一致");

static int ShippingFee(int subtotal)
{
    return subtotal >= 5000 ? 0 : 500;
}

期待出力は境界5000の比較が一致です。「5000以上なら送料0」という仕様をexpected=0で表し、メソッドを呼んだ結果と比較しています。結果を見てから期待値を書き換えると、間違いを正当化するだけになってしまいます。期待値は仕様から決めます。

文法・実例・処理順

csharp
AssertEqual(false, IsPassed(59), "59点");
AssertEqual(true, IsPassed(60), "60点");
AssertEqual(true, IsPassed(61), "61点");

static bool IsPassed(int score) => score >= 60;
static void AssertEqual<T>(T expected, T actual, string caseName)
{
    if (!EqualityComparer<T>.Default.Equals(expected, actual))
        throw new InvalidOperationException($"{caseName}: 期待={expected}, 実際={actual}");
}

想定出力

3件の検証に成功

処理順

  1. 閾値60に対し、59/60/61という境界を選ぶ。
  2. IsPassedを実行し、期待値と実値を比較する。
  3. 不一致なら例外で止まるため、成功表示に到達すれば3件一致している。

よくある間違いと修正

よくある間違い

テストが通ったことは「検証した条件で一致した」という意味です。未検証の入力、OS差、同時実行、安全性まで保証するわけではありません。

テストが間違った実装でも成功する

修正箇所: 期待値と実際の値を比較する箇所

修正前

csharp
int actual = Shipping(3000);
Console.WriteLine("テスト成功");
static int Shipping(int subtotal) => subtotal > 3000 ? 0 : 300;

修正後

csharp
int expected = 0;
int actual = Shipping(3000);
if (expected != actual) throw new InvalidOperationException($"期待={expected}, 実際={actual}");
Console.WriteLine("テスト成功");
static int Shipping(int subtotal) => subtotal >= 3000 ? 0 : 300;
変更理由

まず比較を追加した状態で旧実装の>が失敗することを確かめ、その後>=へ修正します。成功ラベルの表示だけでは検査にならず、テストが不具合を検出することも確認する必要があります。

修正後の確認

  • 旧>で3000は失敗
  • 修正>=で3000は成功
  • 2999と3001も追加

標準：範囲の外と両端を検証する

0〜100を有効とするIsScoreを作り、-1,0,100,101を期待値と比較してください。

  • 下限と上限を両方確認
  • 期待値はfalse,true,true,false
  • 失敗時は入力を含む例外

入力例・前提条件

順序が乱れた元配列をSortedCopyへ渡す。

考え方のヒント

結果の並びと、元配列が変わっていないことを二つの検査にする。

入力するとlocalStorageへ保存実行・自動採点は行いません
解答例と確認ポイント
csharp
int[] source = { 3, 1, 2 };
int[] sorted = SortedCopy(source);
if (!sorted.SequenceEqual(new[] { 1, 2, 3 })) throw new InvalidOperationException("結果の順序が不正");
if (!source.SequenceEqual(new[] { 3, 1, 2 })) throw new InvalidOperationException("入力を変更した");
Console.WriteLine("結果と非破壊性を確認");
static int[] SortedCopy(int[] values) => values.OrderBy(x => x).ToArray();

想定出力

結果と非破壊性を確認
  • 戻り値が正しいことだけでなく、入力を変更しない契約を検査する。
  • Array.Sort(values)へ置き換えると元配列の検査が失敗する。
  • 副作用の有無もAPIの契約であり、テスト対象になる。
入力 / 条件期待結果
3,1,2結果1,2,3、元3,1,2
空両方空
2,2,1結果1,2,2、重複保持

処理と結果の読み解き

新しい配列を作って並べ替えるため、戻り値は昇順、元は元の順序のまま。目的がコピーである以上、出力だけ合っていても元を変えたら失敗。

よくある別解と選び方

OrderBy().ToArray()とClone後のArray.Sortなどが候補。元の保持という契約を同じテストで確認する。

よくある間違いと確認箇所

Array.Sort(source)だけで元を更新してしまわない。関数名と契約が求める副作用の有無を検査する。

実務へのつながり：変更のないはずの入力を保護するテストは、部品の安全な再利用につながる。

確認問題

Q1. 合格基準が60点以上なら、境界確認に有効な組み合わせは？
解説：境界付近の誤りを見つけにくい組み合わせです。

すべて不合格側なので、60を含むかどうかのミスを見逃します。テスト件数ではなく、比較演算子が切り替わる場所を選ぶことが重要です。

解説：すべて同じ分岐に入りやすくなります。

すべて合格側では、実装がscore>60でもscore>=60でも結果が同じです。正しそうな例だけでなく、誤った実装と差が出る入力を用意します。

正解：直前、一致、直後を確認できます。

59は境界の下、60は境界そのもの、61は境界の上です。等号を忘れた場合に60の期待値が変わるため、不具合を具体的に検出できます。

解説：同じ条件の繰り返しだけでは境界の両側を確認できません。

60そのものの検査には意味がありますが、59や61への分岐は確認できません。同じ固定条件の反復を、入力の種類の網羅の代わりにはしません。

Q2. 単体テストをしやすくする設計は？
解説：通信状態に依存して不安定になります。

実APIはネットワークや相手の状態で結果が変わります。単体テストでは依存を差し替え、実通信の検査は統合テストなどに分けます。

解説：テスト間の干渉を起こしやすくなります。

staticが常に悪いわけではありませんが、変更可能な共有状態は別のテストから影響を受けます。各テストで状態を独立させる設計が必要です。

解説：画面なしで検証しにくくなります。

計算結果を表示まで一体化すると、結果だけを渡して比べることが難しくなります。入力・計算・表示を分ければ、計算を画面なしで呼び出せます。

正解：固定入力に対する出力を簡単に検証できます。

入力を渡して戻り値を受け取る形なら、期待値との比較が直接できます。外部I/Oは通信やファイルのような環境依存の境界なので、別の検査に分離します。

Q3. テストの期待値をどう決める？
解説：同じ誤りを共有して検出できない場合があります。

実装が境界条件を間違えていたとき、テスト側へ同じ誤りをコピーすると両方一致してしまいます。期待値は仕様を例に当てはめて求めます。

解説：間違いを正解扱いすることになります。

実際の結果へ期待値を合わせ続けると、仕様ではなく実装を追認するだけになります。仕様変更か不具合かを判断してから、どちらを直すか決めます。

解説：検査自体を失います。

比較を削除すると間違った結果でもテストが終わってしまいます。失敗の理由を調べ、期待値・前提・実装のどこが違うかを確かめます。

正解：実装が仕様どおりかを別の基準で確認します。

「3000円以上で送料無料」から3000円の送料は0と決めます。実装に依存しない判定基準があることで、>と>=の取り違えを発見できます。

Q4. 3000以上で無料の境界テストとして有用なのは？
解説：等号の有無を区別できません。

5000は無料側ですが、3000を含むかは確認できません。境界を狙ったテストと、通常値を使うテストを組み合わせます。

解説：同じ条件の反復より分岐点の網羅が重要です。

3001だけでは>3000と>=3000を区別できません。同じ条件を増やす前に、仕様上の境界の両側があるか確認します。

解説：境界条件の誤りを見つけにくい入力です。

100では有料側の一例しか調べていません。送料が切り替わる2999から3001の入力を追加すると、条件式のミスを調べられます。

正解：境界直前・境界・直後を検証できます。

2999は有料、3000と3001は無料という期待値を先に決めます。実装が>3000なら3000だけ失敗するため、修正箇所を絞り込めます。

Q5. 不具合修正のテストは何を確かめる？
解説：誤った実装を拒否できません。

どの実装でも通る検査は、誤った結果を区別していません。意図的に不具合を戻したときに検査が失敗することが、検知能力の確認になります。

解説：失敗を見えなくしてしまいます。

catchして何もせず終えると、本来検出したい例外まで隠れる場合があります。想定する例外は型や条件を明示して検査し、想定外の失敗を残します。

正解：問題を捕まえる回帰テストであることを確認します。

問題を再現する入力と期待値を保存し、修正前後で結果が変わることを確認します。これにより、将来同じ不具合を再導入した場合にも検知できます。

解説：検知能力を確かめられません。

表示されたPASSという文字ではなく、実際に比較が行われたかが重要です。未実行のコードを成功扱いせず、実行環境と検査結果を記録します。

  • 値だけでなく副作用を検証できる
