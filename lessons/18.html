概念と内部の仕組み

LINQはコレクションを操作する共通の語彙です。Whereで選び、Selectで形を変え、OrderByで順序を決めるという各段階の意味を分けて読みます。完成形のチェーンだけでなく、途中の要素数・型・値を表で確認します。

LINQはコレクション処理の共通表現

LINQはデータを検索・変換・集計するための仕組みです。ここではメモリ上の配列やListを対象にしたLINQ to Objectsを学びます。Whereは残す条件、Selectは各要素を何へ変えるか、OrderByは並び順です。SQLに似たクエリ構文もありますが、このコースではメソッド構文を中心に使います。

型がどう変わるか追う

Product[]からWhereで絞っても、要素はProductのままです。Select(p => p.Name)で文字列へ変換すると、要素の型がstringへ変わります。最後のToListは結果を列挙してListへ格納します。途中でどの型の何件の候補を扱っているか、頭の中で図にすると読みやすくなります。

何でも1行にしない

長い連鎖は改行し、変数名を付けて意図を表します。Whereは判定、Selectは変換に使い、途中で元データを書き換える副作用は避けます。データベース向けのIQueryableでは式がSQLなどへ変換される場合があり、任意のC#処理が同じように動くとは限りません。

WhereとSelectを別の操作として読む

Whereは条件がtrueの要素を残します。元がIEnumerable<Product>なら、結果もProductの並びです。Selectは各要素から別の値を作ります。ProductからNameを選ぶとstringの並びへ変わります。Whereは選別、Selectは投影・変換と考えると、どの段階で何の型になっているかを追いやすくなります。

Select(x=>x.Price>100)は高い商品だけを残す処理ではなく、各商品をboolへ変換する処理です。高い商品の名前だけが必要ならWhereで条件を満たすProductを残してから、SelectでNameへ変換します。メソッド名だけでなく戻る要素の型を追う習慣を付けてください。

並べ替えのキーと同点の順序

OrderByは昇順、OrderByDescendingは降順を指定します。価格が同じときは名前順という二段階の順序なら、OrderBy(x=>x.Price).ThenBy(x=>x.Name)と書きます。二回目もOrderByを使うと、主たる並べ替えの基準を新しく作るため「第二キーを足す」という意図とは違います。

文字列順が文化に依存して困るコード値ではStringComparer.Ordinalを明示します。人名など利用者向けの表示順は必要な文化や仕様に合わせます。今回の例では英数字の識別子をOrdinalで比較し、OSや文化設定で検証結果が変わりにくいようにしています。

元のデータの変更と結果の作成

WhereやSelectは、通常それだけで元のListから要素を削除したり書き換えたりする操作ではありません。条件を満たす要素を列挙するクエリや、変換結果を作ります。結果をToArrayで実体化しても、要素が可変の参照型でそのまま選択されていれば実体は共有されます。

更新処理をSelectの副作用として書くと、列挙されるまで更新されない・複数回更新されるなど、意図が伝わりにくくなります。データの変換は新しい値を返すラムダへ、既存要素の更新は明示的なforeachなどへ分けます。LINQの短さより、読んだ人が実行タイミングを予測できるかを優先します。

foreachで書き直して意味を確かめる

LINQの条件と変換は、foreachとifと追加処理に置き換えて考えられます。慣れる前は一度ループで書き、同じ入力から同じ出力になるかを比較します。一つの巨大な式で済ませず、filtered、ordered、labelsのような途中変数へ分けると、デバッガーでも型と要素を確認しやすくなります。

ここで扱うのは主にメモリ内のIEnumerableです。IQueryableを提供するDBライブラリでは式をSQLなどへ変換して実行する場合があります。普通のC#で呼べる任意のメソッドがすべて翻訳できるわけではありません。LINQという同じ構文でも、実行主体とデータの場所を確認してください。

概念をもう一段掘り下げる

LINQはループを消す魔法ではない

LINQは、データの集まりに対して「条件に合うものを取り出す」「別の形へ変換する」「並べ替える」といった操作を、統一した形で記述する仕組みです。このレッスンではメモリ上の配列やListを対象にします。メモリとはプログラムが実行中の値を保持する場所です。LINQを書くだけでデータベースへ接続されるわけではありません。

最初は、既に知っているループと同じ作業を表すところから始めます。何を入力し、何が出力されるかを説明できないままメソッド名をつなげないことが大切です。

① 添字を使うforで抽出する

C# · 独立したコード例
int[] scores = { 40, 80, 65, 90 };
var passing = new List<int>();
for (int i = 0; i < scores.Length; i++)
{
    if (scores[i] >= 70)
    {
        passing.Add(scores[i]);
    }
}
Console.WriteLine(string.Join(", ", passing));

期待出力は80, 90です。string.Joinは複数の値の間に区切り文字を挟んで、一つの文字列へまとめます。最初に空のListを作り、iで各得点を読み、条件を満たしたときだけ追加しています。元のscoresは変わりません。

読む値 条件 passingの変化
40 false []のまま
80 true []→[80]
65 false [80]のまま
90 true [80]→[80,90]

よくある間違いと修正

よくある間違い

Whereは条件に合うものを残すだけです。金額を2倍にする処理はSelectで表します。名前がSQLのSELECTに似ていても、単なる行の絞り込みではありません。

Selectで絞り込んだつもりがTrue/Falseになる

修正箇所: 条件を適用するLINQメソッド

修正前

csharp
int[] scores = { 40, 80, 90 };
var result = scores.Select(x => x >= 60);
Console.WriteLine(string.Join(",", result));

修正後

csharp
int[] scores = { 40, 80, 90 };
var result = scores.Where(x => x >= 60);
Console.WriteLine(string.Join(",", result));
変更理由

必要なのはboolへの変換ではなく、条件を満たす元の数値を残す操作です。Whereへ変えることでIEnumerable<int>を維持し、80,90を得ます。

修正後の確認

  • 40,80,90→80,90
  • 全件未達なら空
  • 60ちょうどを含める

  • まず主キーの点数で順位を作り、同点を名前で確定する。
  • 全体を並べた後のTakeなので上位2件になる。
  • 同点処理を明示しておくと入力順が違っても期待する順位を再現できる。
入力 / 条件期待結果
3人とも80点名前順の先頭2人
1人のみ1人だけ表示
空配列表示なし

処理と結果の読み解き

90点のAmyとBenが先で、同点の名前順はAmy、Ben。上位2人を取り出す前に全ての並べ替え条件を適用する。

よくある別解と選び方

ループと比較関数でも表現できる。条件を比較関数へまとめる場合も主キーと副キーの順序を維持する。

よくある間違いと確認箇所

二回目のOrderByで名前を主条件にしてしまうと点数の優先が失われる。ThenByとTakeの位置を確認する。

実務へのつながり：ランキングや一覧の順序は同点時まで決め、環境による曖昧さを減らす。

確認問題

Q1. 各Productを商品名stringへ変える操作は？
解説：要素を残す条件を指定します。

WhereはProductを残すかをboolで判断し、残したProduct自体を返す列を作ります。商品名へ変えたい処理では入力と出力の型が変わるためSelectを選びます。

解説：OrderByは並び順を変える操作であり、Productをstringへ変換しません。

名前をキーに並べ替えることはできますが、出力の要素はProductのままです。順序を変える操作と、値の形を変える操作を区別します。

正解：各要素を別の値へ投影します。

Select(product=>product.Name)で各ProductからNameを取り出します。元が3件なら通常この変換も3件のstringを生成します。

解説：Countは要素の件数を返します。各要素の型を変える操作ではありません。

Countは集まりから一つの件数を得ます。商品ごとの名前の列ではなくintの集計値になるので、目的に合いません。

Q2. ToList()の役割は？
解説：LINQ to Objectsではメモリ上で処理します。

メモリ上の配列やListに対するLINQでは、列挙結果をメモリへ保存します。データベース提供元によるSQL変換は別の仕組みです。

解説：通常、元配列そのものを並べ替える操作ではありません。

ToListは結果を新しいListへ保存します。元配列を書き換える並べ替えが必要ならArray.Sortなど別の操作を検討します。

解説：型安全性を無効にしません。

作られるListの要素型は元の列の型に従います。ジェネリック型の制約が消えて何でも入る箱になるわけではありません。

正解：遅延した処理を列挙し、結果を具体化します。

この時点で最後まで列挙して具体的な一覧を保存するため、その後に元の列が変わっても一覧の要素構成は自動追随しません。ただし参照先の共有は別です。

Q3. Select(x=>x>=60)が返す要素の型は？
解説：SelectだけでListを生成するとは限りません。

質問は各要素の型であり、Listという入れ物の型ではありません。Selectだけでは一般にListへ保存せず、boolを取り出せる列を返します。

解説：文字列化は指定していません。

ラムダの本体x>=60は真偽値です。文字列表現が必要なら$"{x}点"など、stringを返す変換を明示します。

解説：条件を返す変換なので元の数値を返していません。

このラムダはxそのものを返していません。条件の結果を返しているため、得点の抽出をしたいならWhereを使います。

正解：各要素を条件式の結果true/falseへ変換します。

各入力が60以上ならtrue、そうでなければfalseへ変わります。元が40,80なら結果はfalse,trueで、80だけが残るわけではありません。

Q4. 価格順、同価格なら名前順にしたい場合は？
解説：第二キーの追加ではなく新しい主順序を作ります。

二度目のOrderByは名前を新しい主要な並び順として指定します。価格を第一条件のまま維持したいのでThenByを使います。

解説：Nameへ変換した後は元のPriceをそのまま参照できません。

Selectで名前のstringだけにすると、後の要素にはPriceがありません。必要なプロパティを持つ段階で抽出・整列を行います。

正解：主キーを維持し第二キーを追加します。

まずPriceで並べ、同じ価格の中だけNameで並べます。複数キーの順序をコードのチェーンで明示できます。

解説：全体の順序指定と件数制限の意図が異なります。

Takeで対象を2件に切ってから並べると、残りの商品は順位の候補になりません。全体の価格順と同価格の名前順という契約とは異なります。

Q5. Whereを呼んだ直後の元のListは？
解説：要素や子オブジェクトを深く複製する操作ではありません。

Whereは参照先の子まで複製する操作ではありません。残した参照型要素は同じ実体を使うため、オブジェクト内部の変更は共有され得ます。

解説：列挙対象を空にする処理はしていません。

元ListのClearなどを呼んでいません。クエリの作成と元データの破壊的な変更を分けて考えます。

正解：条件を満たす要素を列挙するクエリを返す操作です。

条件に合う要素を取り出す見方を作ります。元Listから消したいならRemoveAllなどの変更操作を目的に合わせて選びます。

解説：Whereは元Listの削除メソッドではありません。

不一致要素が結果に出ないことと、元Listから削除されることは違います。元のCountを調べればWhereだけでは変わっていないと確認できます。
