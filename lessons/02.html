Program・名前空間・using

型名が解決される範囲。

.NET 10 / C# 14
本文・演習詳細解説
重要usingは名前を省略するための宣言です。メソッドを呼び出す命令ではありません。

同じConsole.WriteLineでも、ファイルの置き方やusingによって書ける場所が変わります。まず実行入口を確認し、次に「型を探す名前」と「ファイルの並び」を分けます。

要点

  • トップレベルステートメントを読める
  • usingとnamespaceの役割を区別する
重要

usingは名前空間内の型名を短く参照するために使います。namespaceは型の論理的な所属を表し、フォルダー構成と一致させることは慣例ですがC#言語の必須条件ではありません。

C#
// トップレベルステートメント
Console.WriteLine("Hello");

どこから実行が始まるか

現在のコンソールテンプレートは数行だけのProgram.csから開始できますが、短い書き方でも実行入口・名前の解決・ファイル分割の規則は存在します。この単元では「コンパイラーが補うもの」と「コード上に明示するもの」を分けて読みます。

Mainが見えなくても実行できる理由

現在のコンソールテンプレートでは、クラスやMainを書かずに処理を置けます。これをトップレベルステートメントと呼び、コンパイラーが入口を生成します。入口がなくなったわけではありません。1つのプロジェクトでトップレベルの処理を書けるファイルは1つです。

トップレベル文から通常のMainへ読み替える

Console.WriteLineを直接書くトップレベルステートメントは、アプリの実行入口をコンパイラーが生成する書き方です。プログラムがクラスや入口を持たずに動くという意味ではありません。短い演習では文法以外の記述を減らせるため利用します。チームの既存コードがProgramクラスとMainを明示していれば、その形も読めることが必要です。

トップレベル文を置けるソースファイルは一つのプロジェクトに一つです。二つの教材のProgram.csを同じプロジェクトへコピーすると、入口の重複として失敗します。教材のサンプルが別プロジェクトになっているのはこのためです。トップレベル文は同じファイル内の型宣言より前に置きます。型を先に宣言し、その下に実行文を置くと有効な並びになりません。

記述順序を確認する

using指示文、トップレベルの実行文、型宣言の順に書きます。教材の1ファイル例でクラスやrecordが下側にあるのはそのためです。実務でファイルが増えたら、型は別ファイルに分け、namespace LearningLab;のようなファイルスコープ名前空間で整理できます。

トップレベル文とMainの対応

入口・名前・ファイルは別々の仕組み

ソースコードが増えると、「どこから動き始めるのか」「この名前はどの型を表すのか」「どのファイルがビルド対象なのか」を区別する必要が出てきます。入口とはプログラム開始時に実行される場所です。名前空間とは型の名前を整理し、同じ短い名前を区別する仕組みです。ファイルは人がコードを分割して保存する単位です。この三つは関連しますが、一対一に一致するものではありません。

C#の型は、値の種類と利用できる操作を定めます。Consoleも.NETが用意した型です。System.ConsoleのSystemは名前空間、Consoleは型の名前、WriteLineはその型が提供するメソッドの名前です。メソッドは名前の付いた処理で、呼び出すとかっこの中の値を渡して処理を依頼します。

型名をフルネームで毎回書けば曖昧さは減りますが、長くなります。using System;は、そのファイルでSystem内の型を短い名前で参照できるようにする宣言です。部品をインストールしたり、すべての型の処理を実行したりする命令ではありません。名前空間を探す範囲をコンパイラーへ知らせています。

トップレベル文とMainの対応

トップレベルステートメントは、外側のProgramクラスやMainメソッドを自分で書かず、入口で行う文を直接書く形式です。コンパイラーが入口を含む構造を生成します。入口が存在しないわけでも、ファイル内のすべての宣言が順番に実行されるわけでもありません。

C# · 独立したコード例
Console.WriteLine("入口");
PrintMessage();
Console.WriteLine("終了");

static void PrintMessage()
{
    Console.WriteLine("呼び出された処理");
}

期待される出力：

想定される出力 / データ
入口
呼び出された処理
終了

PrintMessageの定義は、その場所に到達したから自動実行されるものではありません。二行目の呼び出しでメソッド本体へ移り、Console.WriteLineを行い、終わったら呼び出した場所の次へ戻ります。この定義はトップレベル文から利用できるローカル関数です。staticは周囲のローカル変数へ暗黙に依存しないことを示します。引数や戻り値はLesson 07で拡張します。

同じ内容を明示的な入口で書くと次のようになります。これは上の例と入れ替えて使用する独立した例です。一つのプロジェクトに両方の入口を追加する練習ではありません。

C# · 独立したコード例
using System;

internal class Program
{
    private static void Main()
    {
        Console.WriteLine("入口");
        PrintMessage();
        Console.WriteLine("終了");
    }

    private static void PrintMessage()
    {
        Console.WriteLine("呼び出された処理");
    }
}

classは型を定義し、Mainはこの形式の入口です。voidは結果の値を返さないことを示します。privateは同じ型の内部からの利用に限定し、internalは原則として同じアセンブリ内から型を利用できることを表します。今は外側の構造を読めれば十分で、クラスの設計はLesson 09以降で学びます。

使う型を名前で指定する

名前空間は名前を整理する

namespaceは型名の衝突を避け、関連する型を整理します。using System.Text;はStringBuilderなどの型名を短く書くための指定で、ライブラリをインストールする命令ではありません。テンプレートのImplicitUsingsが有効だと、Systemなどのよく使う名前空間が暗黙に利用できます。

namespaceはフォルダーでもアクセス制御でもない

namespaceは型の名前をまとめる仕組みです。Learning.Models.Bookという完全修飾名なら、Learning.Modelsという名前空間のBookを指します。フォルダーをModelsにしただけで自動的にその名前になるとは限りません。チームではフォルダーと名前空間を揃える規約を設けることがありますが、それは言語の強制ではありません。

using Learning.Models;を書くとBookという短い名前で参照できます。ただしその型が所属するアセンブリへの参照は別に必要です。名前空間を指定しても、未インストールのNuGetパッケージや未参照の別プロジェクトが自動導入されるわけではありません。internalなどのアクセス修飾子は利用できる範囲の規則であり、namespaceの区切りそのものはアクセス権を設定しません。

System.Text.StringBuilderは、型の居場所を含めた名前です。ドットで区切って読みます。

using System.Text;を置くと、曖昧でない範囲でStringBuilderと短く書けます。型そのものをコピーしたり追加インストールしたりする操作ではありません。

同名の型とusingエイリアス

別のライブラリがそれぞれTaskやTimerを定義していると、usingを追加した瞬間に短い名前が曖昧になることがあります。これはコンパイラーがどちらを指すか決められない状態です。完全修飾名で書くか、using Alias = 名前空間.型名;で別名を付けます。型の別名は新しい型を作るものではありません。

C#の識別子は大文字小文字を区別します。Console.WriteLineのようなAPI名も正確に書く必要があります。using staticは型の静的メンバーの名前を短縮しますが、最初から多用するとWriteLineがどこで定義されているか見えにくくなります。読み手が出所を追えることを優先しましょう。

StringBuilderを短い型名で使う

csharp
using System.Text;

var text = new StringBuilder();
text.Append("Hello");
text.Append(" C#");
Console.WriteLine(text.ToString());

この例ではStringBuilderを一つ作り、その中の文字を2回増やしています。

ToStringは組み立てた内容をstringとして取得する処理です。using行は文字列への追加処理には含まれません。

想定出力

Hello C#

処理順

  1. System.Text内の型を短い名前で使えるようにする。
  2. StringBuilderのインスタンスを生成する。
  3. 2回のAppendで文字を追加し、ToStringで文字列にする。

サンプル一式 Program.cs

省略できる記述と省略できない依存関係

ImplicitUsingsと二種類のusing

SDKスタイルのプロジェクトでImplicitUsingsをenableにすると、SDKがよく使う名前空間のglobal usingを生成します。Consoleにusing System;が不要な例はこの設定を利用しています。すべての名前空間が対象ではないため、StringBuilderのSystem.Textなどは明示する場合があります。サンプルだけコピーして別設定のプロジェクトへ移すと、同じコードで名前が見つからないことがあります。

ファイルの先頭に書くusing System.Text;は名前解決の指定です。一方using var reader = ...;はリソースの後始末を予約する構文で、意味が異なります。キーワードが同じという理由で「ライブラリを読み込むもの」と一括りにしないでください。後者のDisposeと例外時の後始末はLesson 16で学びます。

よくある間違いと修正

よくある間違い

using System.Text;とusing var stream = ...;は別の機能です。後者はリソースの後始末で、レッスン16で扱います。

型宣言の後にトップレベル文を置く

修正箇所: Program.cs内のクラス宣言と実行文の順序

修正前

csharp
class Message { }
Console.WriteLine("Hello");

修正後

csharp
Console.WriteLine("Hello");
class Message { }
変更理由

トップレベルの実行文は型宣言より前に置きます。型の定義は実行命令ではないので、ファイル後方の型も文の側から参照できます。大きくなったら型を別ファイルへ移します。

修正後の確認

  • 修正後のプロジェクトがビルドできる
  • Helloが一度だけ表示される
  • MessageをMessage.csへ移しても動く

修正前後で変えているのは、Messageという型の内容ではなく、トップレベル文の位置です。

Messageを別ファイルへ分けても、同じプロジェクトなら型として利用できます。ただし、別ファイルに二つ目のトップレベル実行文を追加してよいわけではありません。

確認問題

Q1. using System.Text;の役割は？
解説：取得する操作はNuGetやdotnet package addです。

usingはパッケージの取得要求ではありません。外部部品が必要なら参照の追加とrestoreを行い、その後に名前を省略するusingが使えます。

解説：この形式は名前空間の指定です。リソース管理のusingとは違います。

using var resource=...という資源管理の構文と、using System.Text;という名前空間の指定を混同しています。後者はDisposeを呼びません。

正解：System.Text.StringBuilderをStringBuilderと書けます。

System.Text.StringBuilderのSystem.Text部分を省略できるようにします。既に参照できる型の名前の解決を助ける指定であり、別の型を作りません。

解説：エントリーポイントを増やす指定ではありません。

Mainはアプリの入口です。名前空間を取り込む指定は入口の個数に影響しないため、二つの処理が自動で始まることもありません。

Q2. トップレベルの実行文とclass宣言を1ファイルに書く順序は？
解説：トップレベルの実行文を型宣言の後に置くとエラーです。

トップレベル文では先に実行文を書き、その後に型の宣言を置きます。classの後で実行文へ戻る構成にせず、入口と型を分けます。

解説：using、実行文、型宣言には順序の制約があります。

たとえばusingを実行文の後へ自由に置くことはできません。省略できる記述が増えた構文でも、配置の規則は残っています。

解説：そのような必須ルールはありません。

namespaceは型を名前で整理する仕組みです。classの内部へnamespaceを入れる構造を要求するルールはなく、そもそも適切な配置ではありません。

正解：教材のクラス付き例もこの順序です。

Console.WriteLine(...);の後にpublic class Productを置く形です。型宣言が後でも、そのファイルより前に作られるわけではなくコンパイラーが宣言を解決します。

Q3. using System.Text;の直接の役割は？
解説：インスタンスの生成はnewなどの実行処理が担当します。

new StringBuilderなどの実行と、usingによる名前の解決は別です。usingだけで文字を入れる実体が作られるわけではありません。

正解：名前空間にある型の名前解決を補助する指定です。

使いたい型の出所がSystem.Textであることを指定します。完全修飾名で書けばusingを省ける場合もあり、両者は名前の書き方の違いです。

解説：外部依存関係の取得はNuGetの復元などが担当します。

ライブラリの存在自体が不足していれば、usingを増やしても直りません。型名の誤記、名前空間、必要な参照を順に切り分けます。

解説：アクセス修飾子はusingとは別の規則です。

publicやprivateは宣言に付けるアクセスの規則です。usingで型名を短く書けても、アクセスできないメンバーが読めるようにはなりません。

Q4. トップレベル文があるファイルを二つ同じプロジェクトへ入れたら？
解説：実行入口がランダムに決まることはありません。

入口は実行のたびに偶然選ばれるものではありません。複数のトップレベル文という構成上の問題はビルド段階で解消する必要があります。

解説：どちらかを自動で採用する仕組みではありません。

後から保存したファイルが勝つ仕組みではありません。別のサンプルを試すときはProgram.csを置き換えるか、別プロジェクトに分けます。

解説：複数ファイルの実行文を自動連結することはありません。

ファイル名順で連結して起動する規則はありません。型の宣言を複数ファイルへ分けることと、トップレベルの入口を複数作ることは違います。

正解：トップレベル文を含められるコンパイル単位は一つです。

複数の.csファイル自体は禁止ではありません。実行文の入口は一つにして、補助の型やメソッドを他のファイルへ置きます。

Q5. using Buffer = System.Text.StringBuilder;について正しい説明は？
正解：コンパイル時の名前解決に使う別名で、対象の型は同じです。

Bufferという名前を使っても対象はSystem.Text.StringBuilderです。別名は同名型の衝突を避けたり長い型名を読みやすくしたりするために使います。

解説：インスタンスの変更可能性は別名と無関係です。

StringBuilderが内容を変更できる性質はそのままです。名前の変更と、オブジェクトの変更可能性を制限する設計は別です。

解説：継承にはclass宣言などが必要で、別名指定では行われません。

派生型なら独自の型の宣言と継承関係が必要です。別名は同じ型を別の表記で呼ぶだけなので、新しい継承階層は生まれません。

解説：別名を作るだけで別のプロジェクトやアセンブリは生まれません。

アセンブリはコンパイルした型や情報をまとめた出力です。別名指定だけで別の出力単位を作ることはありません。
