概念と内部の仕組み

例外処理は「落ちないように全部catchする」ことではありません。正常な失敗と契約違反を分け、回復できる場所で処理し、必要な情報を残しながら資源を確実に片付けます。usingディレクティブとは異なるusingの意味もここで整理します。

例外は失敗の情報

try/catch/finallyは、失敗し得る処理と、その失敗から回復する処理、必ず行う後始末を分ける構文です。C#にはメソッド宣言で特定例外の捕捉を強制する仕組みはありません。それでも例外設計が不要なわけではなく、通信、ファイル、変換など失敗し得る境界を把握します。入力の単純な変換失敗ならTryParse、契約違反ならArgumentExceptionなど、意図に合う手段を選びます。

握りつぶすと調査できない

catch (Exception) { }で何もしないと、不正な状態のまま処理が続き、原因も失われます。ユーザーへ再入力を促す、ログを残して上位へ伝えるなど、回復方法を決めます。同じ例外をそのまま投げ直す場合はthrow;を使うと元のスタック情報を保てます。秘密情報をエラーメッセージへ混ぜないことも重要です。

usingは後始末を保証する

using var reader = new StringReader(...);のように宣言すると、そのスコープを抜けるときにDisposeが呼ばれます。途中で例外やreturnがあっても後始末されます。GCはメモリ管理、Disposeはファイルハンドルや接続などの解放を含む明示的な後始末です。所有するリソースの寿命をスコープへ結び付けるために使います。

例外が発生した後の制御フロー

tryの中で例外が発生すると、その位置より後の通常処理は飛ばされ、型が対応するcatchが探されます。同じtryの続きから自動的に再開するわけではありません。対応するcatchがなければ呼び出し元へ伝わります。処理できる場所で捕捉するため、すべてのメソッドへtry/catchを付ける必要はありません。

FormatExceptionだけ処理できる場所でException全体を捕捉すると、プログラムの欠陥や別種の障害まで同じ入力エラーとして隠してしまいます。一般的なcatchを置く場合は最上位の境界など、役割が説明できる位置へ置きます。通常の入力ミスはTryParse、契約違反はArgumentException系、I/O失敗は対応する例外など、発生の意味で整理します。

catchの順序と再スロー

派生例外を先、基底例外を後に書くのが基本です。Exceptionを先に捕捉すると、後ろの具体例外へ到達できません。catch whenは型だけでなく状態を条件にして捕捉するフィルターです。たとえばキャンセルが自分の要求によるものかを判断する場面で利用します。

捕捉した例外をそのまま上へ伝えるならthrow;を使います。throw ex;ではスタックトレースの起点情報が変わり、元の失敗箇所を追いにくくなります。別の意味の例外へ包み直す必要があるなら、元の例外をInnerExceptionとして保持するなど、調査に必要な文脈を残します。秘密情報はそのまま利用者へ返さないよう、記録と公開メッセージを分けます。

GCとDisposeは役割が違う

ガベージコレクションは到達不能になったマネージドオブジェクトのメモリ回収を担います。一方、開いたファイル、ソケットなどの資源を必要な時点で解放することはDisposeなどの契約で扱います。GCがいつ回収するかを待つと、ファイルロックや接続が長く残ることがあります。

IDisposableを実装するオブジェクトをusingで扱うと、通常のスコープ終了、return、例外で抜ける経路でもDisposeが呼ばれるように構成されます。ただしプロセス強制終了など、すべての終了状況で保証されるという意味ではありません。Disposeは「その変数を使えなくする構文」ではなく、資源の利用を終える操作です。

using宣言のスコープと所有権

using var reader = ...;は宣言したスコープの終わりで後始末します。using (...) { ... }なら指定したブロックで終わります。長いメソッドの先頭でusing宣言をすると、実際には使い終わった後もスコープ終了まで資源を保持する場合があります。解放したい範囲に合わせてブロックを選びます。

自分が作って所有する資源を自分で片付けるのが基本です。他者から借りた列挙処理を勝手にDisposeすると、呼び出し側が続けて使えなくなることがあります。APIの所有権の契約を確認してください。非同期の後始末が必要ならIAsyncDisposableとawait usingという仕組みもあり、同期版と同じ目的を非同期処理で扱います。

概念をもう一段掘り下げる

例外は通常の戻り値とは別の経路で失敗を伝える

メソッドは戻り値を返して呼び出し側へ戻ります。しかし、ファイルが読めない、必要な状態が壊れているなど、通常の結果を作れない場合があります。例外はその異常をオブジェクトとして通知し、通常の次の文ではなく対応する例外処理へ移る仕組みです。

例外オブジェクトには型、メッセージ、呼び出し経路を示すスタックトレースなどがあります。スタックトレースは、どのメソッドからどのメソッドを呼んで問題に至ったかを追う手掛かりです。エラー文の日本語だけを読まず、例外型・発生行・入力・呼び出し経路を合わせて調べます。

すべての失敗を例外にする必要はありません。ユーザーが数字でない文字を入力することが普通に想定されるなら、TryParseのような成功/失敗の戻り値が分かりやすくなります。一方、内部的に保証していた前提が壊れて正常な値を返せないなら、例外が適する場合があります。

try・catch・finallyの処理順

catch (FormatException)
{

finally
{
    Console.WriteLine("後片付け");
}

tryは例外が起こり得る処理の範囲です。catchは対応する型の例外を受け取ります。finallyは通常の終了・例外の伝播・returnなどで対象の範囲を抜ける際の後片付けに使います。プロセスの強制終了やOS障害など、どんな状況でも必ず動くという保証ではありません。

catchで処理した後に、失敗したParseの次へ自動的に戻るわけではありません。やり直しが必要なら、再試行の回数と条件を自分で設計します。無条件に繰り返すと、解決しない失敗を延々と繰り返します。

よくある間違いと修正

よくある間違い

例のParseは例外の流れを見せるためです。日常的なユーザー入力の数値判定にはTryParseを使う方が、失敗を通常の分岐として表現できます。

解析エラーを握りつぶして成功扱いする

修正箇所: catchの内容と捕捉する例外型

修正前

csharp
try { int.Parse("abc"); }
catch (Exception) { }
Console.WriteLine("成功");

修正後

csharp
try
{
    int value = int.Parse("abc");
    Console.WriteLine($"成功: {value}");
}
catch (FormatException)
{
    Console.WriteLine("整数として解析できません");
}
変更理由

回復対象をFormatExceptionへ限定し、成功の表示を成功経路へ移します。元の空catchは失敗を隠していたため、原因も利用者の結果も誤らせます。ユーザー入力ならTryParseによる通常分岐も適しています。

修正後の確認

  • abcで解析できませんと表示
  • 12で成功:12と表示
  • 別種の障害を無条件に成功扱いしない

"\n"という改行表現と、二文字のバックスラッシュnを表す入力を混同しない。実際の内容と行数を確認する。

実務へのつながり：ファイルやストリームを読み、終端と空のデータを区別する処理につながる。

応用

応用：再スローで境界へ伝える

Validateで負数なら例外、Middleでは調査用メッセージを出してthrow;、外側で「入力を確認」と表示します。Middleが成功値へ変えて隠さない形にしてください。

  • Middleのcatchではthrow;を使う
  • 外側も具体的な例外型で捕捉する
  • 表示される順番を予測する
開始コード
csharp
// 応用：再スローで境界へ伝える
// 課題とテストケースを読んで、自分で実装してください。

入力例・前提条件

Validateが負数で失敗し、Middleが調査表示後に再送出する。

考え方のヒント

catch内のthrow;は受け取った例外を引き続き外へ伝える形。

入力するとlocalStorageへ保存実行・自動採点は行いません
解答例と確認ポイント
csharp
try { Middle(-1); }
catch (ArgumentOutOfRangeException) { Console.WriteLine("入力を確認"); }
static void Middle(int value)
{
    try { Validate(value); }
    catch (ArgumentOutOfRangeException)
    {
        Console.WriteLine("中間層で失敗を確認");
        throw;
    }
}
static void Validate(int value)
{
    if (value < 0) throw new ArgumentOutOfRangeException(nameof(value));
}

  • throw;が元の例外を伝え、外側の境界で利用者向けの処理へ変換する。
  • 実務では各層が同じ例外を重複ログにしないよう、記録責任を決める。この二段表示は流れを観察する学習用である。

処理と結果の読み解き

Validate→Middleのcatch→外側のcatchの順に進む。Middleはログ相当の表示を追加しても成功値へ変換せず、外側が入力確認を案内する。

よくある別解と選び方

Middleで追加情報が不要ならcatchせずそのまま伝える方が簡潔である。何のために捕捉するかを明確にする。

よくある間違いと確認箇所

throw ex;で元のスタック情報を扱いにくくしたり、returnで成功へ隠したりしない。原因を追える伝播を保つ。

実務へのつながり：例外を各層で重複記録せず、役割のある境界で文脈を付けて扱う。

確認問題

Q1. using var resource = ...; のDisposeはいつ呼ばれる？
解説：GC待ちで後始末する指定ではありません。

GCがいつ動くかとは独立して、通常のスコープ終了でDisposeするよう構成されます。ファイルを早く閉じる必要をGC任せにしないための仕組みです。

解説：読み取りのたびには破棄しません。

資源を読むたびに破棄したら後続の利用ができなくなります。宣言したスコープの中で使い、最後に後始末するという寿命を表します。

正解：returnや例外による終了でも後始末されます。

通常のreturnや例外でスコープを出るときも後始末の経路を通ります。ただしプロセス強制終了など、コード自体が動けない状況まで保証しません。

解説：対象がIDisposableなどの条件を満たす必要があり、Disposeが呼ばれます。

条件を満たす資源に対して、後始末を忘れにくくする構文です。単に変数名へ印を付けるだけではなく、Disposeを呼ぶ終了処理を生成します。

Q2. catch内で元の例外を再送出してスタック情報を保つ書き方は？
解説：元の詳細情報を失う原因になります。

新しい例外を作ると元の種類・メッセージ・発生位置を捨てる可能性があります。別の意味へ包む必要がある場合も、元の例外を適切に保持します。

解説：失敗を伝えず終了してしまいます。

returnは呼び出し元へ通常の結果として戻る操作です。失敗を上へ伝える契約なら、そのまま終了して成功に見せないようにします。

解説：例外を握りつぶします。

例外を処理したように見えて、原因も結果も残りません。回復できない失敗は適切な情報とともに上へ伝えます。

正解：現在処理中の例外を再送出します。

現在のcatchで扱っている例外を再び伝えます。単なるthrow exとの違いは、元の発生経路を調査しやすく保つことです。

Q3. GCがあるのにusingを使う主な理由は？
正解：Disposeの契約によって必要な時点で資源利用を終えます。

ファイルや通信などのOS資源は、メモリ回収を待たず利用を終えたいことがあります。usingは所有する資源のDisposeを適切な範囲へ結び付けます。

解説：例外を捕捉する機能と後始末は別です。

usingは例外を無視するcatchではありません。後始末をした後でも例外は通常上へ伝わるので、利用側が失敗を別に扱います。

解説：usingはGCを毎回強制実行する構文ではありません。

各行でGCを実行するといった動作ではありません。メモリ管理と資源解放を分け、Disposeが何を終えるのかを型の契約で確認します。

解説：型の分類を変更する構文ではありません。

usingを付けても参照型は参照型のままです。オブジェクトの分類を変えるのではなく、利用後の処理を管理する構文です。

Q4. catch内で元の例外をそのまま上へ伝える基本の書き方は？
正解：元の例外のスタック情報を保って再スローします。

同じ失敗をそのまま伝えるならthrow;を使います。捕捉して記録するだけの場合も、原因の発生位置を失わない形にします。

解説：結果へ置き換えると失敗の契約が変わります。

nullを返すと「対象なし」など別の意味と混同する場合があります。例外から結果へ変換するなら、その意味を呼び出し側との契約として決めます。

解説：空catchは失敗を飲み込み、上へ伝えません。

例外を上へ投げ直していないため、呼び出し側は失敗を知れません。空catchで調査可能性と業務上の整合性を失わないようにします。

解説：throw ex;ではスタックトレースの起点が変わる問題があります。

throw ex;は再スロー位置からの情報へ変わる問題があります。元の例外をそのまま伝える目的ではthrow;を選びます。

Q5. using varを宣言した資源が通常Disposeされる時点は？
正解：using宣言はスコープに後始末を結び付けます。

using宣言があるブロックの終わりまで利用し、その後にDisposeされます。スコープが長すぎるならusingブロックで利用範囲を狭めます。

解説：一行だけの有効期間ではありません。

宣言の次の文だけが対象ではありません。ブロックのどこまで資源が必要かを見て、後始末の時点を配置します。

解説：DisposeのタイミングをGCの実行に依存させる構文ではありません。

GCの実行順序を指定するものではありません。ファイルを閉じる必要がある時点と、オブジェクトのメモリが回収される時点を分けます。

解説：usingディレクティブとは異なる機能です。

using System.IO;の名前空間指定と、using var stream=...の資源管理は別の構文です。同じ単語でも後続の形を見て意味を読み取ります。
