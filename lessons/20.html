enum・タプル・拡張メソッド

注文状態を名前付きの値で表す。

.NET 10 / C# 14
本文・演習詳細解説
重要enumの名前付き定数だけで、外部から来た値が必ず有効になるわけではありません。

この単元では、異なる三つの困りごとを扱います。状態の数字に名前を付けるenum、複数の結果を返すタプル、既存の型を読みやすく使う拡張メソッドを、役割ごとに分けます。

要点

  • 状態をenumで表す
  • 複数の戻り値と拡張メソッドを読める
重要

enumは名前付きの値集合、タプルは一時的な複数値、拡張メソッドは既存型へ呼び出し構文を追加する仕組みです。用途を分けます。

C#
public static bool HasText(this string? text) => ...;

状態の数字へ名前を付ける

enum・タプル・拡張メソッドは、名前のない数値や長い補助コードを整理する道具です。ただし型名を付けただけで不正値が消えるわけではありません。適用範囲と限界を理解し、APIの契約を読みやすくします。

数字に名前を付ける

enumは関連する定数の集合です。TaskState.Todoと書けば、0だけより意図が伝わります。ただし(int)からキャストすると宣言していない値も表せるため、外部入力の検証が不要になるわけではありません。保存形式で番号を使うなら、順序変更による破壊を避けるため値を明示します。

enumは名前付き定数だが未定義値も存在する

enum Status { Unknown=0, Todo=1, Done=2 }は状態を名前で表します。整数をそのまま比較するより意図が明確です。ただし(Status)99のようなキャストで、宣言していない数値を持つことができます。既定値は通常0なので、0の意味を用意するか境界で検証します。

外部から受け取った文字列をEnum.TryParseで変換できても、それが宣言済みの値である保証とは分けて考えます。数値文字列が変換される場合もあるため、通常の単一状態ならEnum.IsDefinedなどで許可する値を確認します。Flags列挙型の複数ビット組み合わせは別の検証規則が必要です。

この例のTaskStateはTodo、Doing、Doneの順で、明示しなければ0、1、2になります。

整数99をキャストできることと、アプリで使える状態であることは別です。外部から受け取る値には、名前付きの状態として有効かの確認が必要です。

enumの状態と値

名前のない数値や複数の戻り値を整理する

enumは関連する定数へ名前を付けた型、タプルは複数の値を一時的にまとめる型、拡張メソッドは既存の型に対してメソッド風に呼べる処理を追加する仕組みです。それぞれ「状態の選択肢」「小さな結果の組」「処理の置き場所」という異なる問題を解決します。

業務コードに0、1、2だけが並ぶと、どれが未着手でどれが完了か読み取りにくくなります。enumを使うと、意味を型と名前で表現できます。ただし、enumを使えば外部入力が自動で正しい値になるわけではありません。

enumの最小例と状態の変化

C# · 独立したコード例
WorkStatus status = WorkStatus.Todo;
Console.WriteLine(status);
status = WorkStatus.Doing;
Console.WriteLine(status);
status = WorkStatus.Done;
Console.WriteLine((int)status);

public enum WorkStatus
{
    Todo = 0,
    Doing = 1,
    Done = 2
}

期待出力はTodo、Doing、2です。enumの基になる整数型は指定しなければintです。(int)statusは名前ではなく対応する数値を取り出します。初期状態TodoからDoing、Doneへ代入で変化しています。enum自身が順序や遷移の可否を判断しているのではありません。

状態 値 この教材での意味 次に許可する状態の例
Todo 0 まだ開始していない Doing
Doing 1 作業中 Done / Todo
Done 2 完了 業務ルール次第

状態遷移とは、現在の状態から別の状態へ移ることです。DoneからTodoへ戻せるかはenum宣言ではなく業務の処理で決めます。

複数の結果をまとめて返す

近い場所で使う複数の戻り値

(int Count, int Total)のようなタプルを返すと、関連する少数の値を簡単にまとめられます。分解代入でvar (count, total) = ...;と受け取れます。公開APIや多くの場所で使うデータに発展したら、名前のあるrecordなどへ切り出すと役割が伝わりやすくなります。

タプルは関連する少数の値を一時的に返す

(int Count,int Total)は二つの値を一つの戻り値として返せます。呼び出し側はresult.Countや分解代入のvar(count,total)で読み取れます。メソッドから集計結果を返すなど、範囲の狭い用途では専用クラスより簡潔です。名前を付けることでItem1やItem2だけより意味が伝わります。

公開APIの中心となるデータや検証・振る舞いが必要な型にはrecordやclassを検討します。タプルの要素名だけに頼って異なる業務概念を同じ形で混ぜると、型の区別が弱くなります。少数の局所的な組なのか、独立した概念として長く利用するものなのかが判断基準です。

件数と合計を返すメソッドでは、同じintでも意味が異なります。

タプルの要素名は、読む人が結果の役割を区別する助けになります。二つのintを逆に入れても型だけでは検出できないため、返す順序とテストも確認します。

既存の型へ呼び出し方を追加する

拡張メソッドは静的メソッド

従来からの拡張メソッドはstatic classのstaticメソッドで、第1引数にthisを付けます。"C#".HasText()のように呼べますが、元のstring型を書き換えているわけではありません。C# 14には拡張メンバーの新構文もあります。従来のthis引数形式は、C# 14でも引き続き利用できます。

拡張メソッドは元の型を変更しない

staticクラス内のstaticメソッドで、第一引数へthisを付ける従来の書き方では、対象.メソッド()という呼び方を提供できます。実際には静的メソッドの呼び出しであり、stringなど既存型のソースを書き換えるわけではありません。利用できるかは名前空間の取り込みにも関係します。

インスタンスメンバーが同じ呼び出しに適合すれば、通常そのメンバーが優先されます。拡張メソッドで既存メソッドをoverrideすることはできません。またprivateフィールドへ特別にアクセスできる権限は得られません。型の公開APIを使った共通操作を、読みやすくまとめる用途に使います。

HasTextを拡張メソッドとして呼ぶ例です。短く書けるようになる仕組みと、型を変更することを分けます。

拡張メソッドは、受け取った値を使う静的なメソッドをインスタンスのような構文で呼べるようにします。stringの内部へ新しいメンバーを保存する操作ではありません。

null受信側と新しい構文の位置付け

拡張メソッドは静的呼び出しなので、string?を受け取るCleanのようにnullを明示的に扱う契約を書けます。null変数に対する通常のインスタンス呼び出しとは異なります。内部でvalue.Trim()を無条件に呼べばやはり失敗するので、拡張構文だから安全ではありません。

C#14には拡張ブロックによる拡張メンバーの書き方が追加されています。this引数形式の拡張メソッドも引き続き利用できます。新構文を導入する場合はチームのSDKと言語バージョンを合わせ、どの型へ何を追加しているかが検索できる配置にします。

C#仕様の整理

観点C#での扱い読み方・設計上の要点
enum整数型を基にした名前付き定数未定義の数値を境界で検証
複数の戻り値名前付きタプルも使用可能長期的なモデルとは分ける
共通の補助関数拡張メソッドで対象.Method()表記元の型を継承・改変しない
nullの受信側nullable引数の拡張メソッドで扱える内部実装のnull契約を明示

実例：注文状態を表示用ラベルへ変換する

内部の状態と日本語の表示文字列を分けます。

よくある間違いと修正

よくある間違い

拡張メソッドは元の型のprivateメンバーにアクセスできません。またインスタンスメソッドを仮想的に上書きする仕組みでもありません。

パースできたenumをすべて有効とみなす

修正箇所: 外部状態値の許可判定

修正前

csharp
string input = "99";
Console.WriteLine(Enum.TryParse<State>(input, out _));
public enum State { Todo = 1, Done = 2 }

修正後

csharp
string input = "99";
bool valid = Enum.TryParse<State>(input, out var state) && Enum.IsDefined(state);
Console.WriteLine(valid);
public enum State { Todo = 1, Done = 2 }
変更理由

変換成功と宣言済み状態であることは別です。通常の単一状態という今回の仕様ではIsDefinedも要求し、不正な99を拒否します。Flagsのビット組み合わせにはこの条件を機械的に流用しません。

修正後の確認

  • Todo→True
  • 99→False
  • 空文字→False

確認問題

Q1. C#のenumへ(int)から未定義の数値をキャストしたら？
解説：明示的なキャストで可能な場合があります。

明示的な変換で基の整数型の値をenumとして扱えるため、宣言名がない値も入り得ます。コンパイル可能性と業務で許す値を分けます。

解説：自動補正はされません。

99をTodoへ戻すような自動補正はしません。定義した選択肢だけ許すなら、変換後にEnum.IsDefinedなどで確認します。

正解：外部入力ではEnum.IsDefinedなどの検証を検討します。

通常の単一選択enumでは、定義済みの値かを追加で調べます。Flagsの組み合わせを許す場合には、単一の定義との一致とは別の検証になります。

解説：enumは値型です。

通常のenumはnullを持たない値型です。未定義整数と欠損nullは同じ状態ではなく、必要ならnullableなenumを別に使います。

Q2. 拡張メソッドについて正しいのは？
解説：元の型定義を変更するわけではありません。

既存のソースファイルを書き換える必要はありません。外側に静的な補助処理を定義して、受け手のメソッドのような記述を提供します。

解説：アクセス制御は守られます。

拡張しても対象型のprivateへ特別に入れるわけではありません。公開された操作など、自分がアクセスできる契約を通して処理します。

解説：overrideの代わりではありません。

拡張メソッドは仮想メソッドの実装差し替えではありません。既存のインスタンスメソッドとの解決規則も異なるので、同名だけで上書きと思わないでください。

正解：第1引数にthisを付ける従来構文が使えます。

従来形式では最初の引数にthisを付け、text.Normalize()を静的メソッドへの呼び出しとして解決します。元の型へ状態を追加するわけではありません。

Q3. Enum.TryParse<State>("99",out var value)がtrueでも追加確認が必要な理由は？
正解：変換可能性と許可する状態は別の条件です。

"99"という数値文字列が解析できても、Stateに99という名前が宣言されているとは限りません。許す集合に入るかを別に判定します。

解説：enumは基になる整数型を持ちます。

enumは整数値に名前を付けた型で、stringそのものではありません。文字列から解析するという入力形式と、結果の型を区別します。

解説：TryParseは通常、変換の成否をboolで返すためのAPIです。

TryParseは成否をboolで表すAPIです。今回trueを返しているので、追加検証の理由は例外回避だけでなく未定義の状態を拒否することです。

解説：通常のenumは値型です。

成功結果が通常のenumなら、その値を保持します。nullを出す仕組みではないため、欠損と未定義値は別に設計します。

Q4. 拡張メソッドについて正しい説明は？
正解：呼び出し構文を提供し、型そのものの実装を変更しません。

外部のstaticクラスなどに補助処理を置けます。既存の型を編集できない場合でも、公開機能を組み合わせた自然な呼び出しを提供できます。

解説：対象型の非公開メンバーへ特別な権限を与えません。

privateのアクセス制御は維持されます。拡張という名前を、元の型の内部へ権限を追加するものとして理解しないでください。

解説：継承によるoverrideとは異なります。

virtual/overrideは実行時の多態性を支える別の機能です。拡張メソッドは受け手のコンパイル時の型や候補解決に依存する静的な呼び出しです。

解説：利用範囲や名前空間の取り込みが解決に関係します。

拡張メソッドの名前空間がスコープ内にあるかなどが関係します。型が存在するだけで、どのファイルからでも常に候補になるわけではありません。

Q5. 公開APIで長く使う複雑な注文モデルに適した判断は？
解説：名前のない位置依存は変更に弱くなります。

Item1やItem2だけでは各値の意味が分かりにくく、並びの変更で誤用しやすくなります。公開して長く使うモデルには明確な名前と契約を持たせます。

正解：局所的な組と長期的な業務モデルを区別します。

Orderという名前、項目名、検証、状態の制約を型へ表現できます。小さな局所的戻り値のタプルと、業務上の独立した概念を分けて選びます。

解説：型情報と検証の境界が失われます。

文字列へ結合すると、数値や日時などの型情報と検証の入口が失われます。後から分解する手間や区切りの曖昧さも増えます。

解説：意味と保守性が分かりにくくなります。

何十項目も位置だけで扱うと、追加や変更の影響を追いにくくなります。専用の型と責務に分け、読める構造を優先します。
