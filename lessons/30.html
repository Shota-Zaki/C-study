概念と内部の仕組み

APIの入力検証は、空白を弾くif文を一つ置くだけでは不十分です。未指定と0の違い、正規化の順番、作成時のLocation、エラー本文の一貫性まで含めて、呼び出し側が扱える契約を設計します。

リクエストも外部入力

POSTのJSONは信頼せず、入力用のDTOとして受け取ります。必須、文字数、数値の範囲を確認し、保存モデルへそのまま流し込まないようにします。C#のstring注釈だけでは業務上の必須チェックになりません。この教材では挙動が見えるように明示的な検証を書きます。

結果をステータスで伝える

取得成功は200、新規作成成功は201、入力不正は400、対象なしは404など、HTTP上の意味に合わせて返します。すべて200で本文だけにerrorを入れると、呼び出し側や監視側が成功と失敗を見分けにくくなります。201では作成した対象のURLをLocationとして返すことができます。

レスポンス契約を決める

Results.Ok、BadRequest、NotFoundなどで分岐を表せます。TypedResultsは戻り値の型をより明確に扱いたいときに利用できます。ここではIResultを返す名前付きの関数を使い、成功と失敗の複数の戻り値を分かりやすくそろえます。エラーには内部のスタックや秘密情報を載せません。

必須・型・範囲・相関を段階的に検証する

POSTでValueが必須なら、int Valueだけでは未指定が0に見える場合があります。int? Valueとして受け取りnullを拒否すると、未指定と明示的な0を区別できます。文字列はnull、空文字、空白のみ、長さ超過を別の入力として考えます。JSON構文の不正は通常ハンドラーへ到達する前の段階で失敗します。

開始日が終了日より後、同じIDを二回使うなど、複数項目の関係も検証対象です。DataAnnotationsや.NET10のMinimal API検証機能を使う場合でも、適切な登録と業務ルールの実装が必要です。この教材のコードは明示的な手動検証を使い、属性を付ければ登録なしでも何でも自動検証されるとは説明しません。

正規化した値を検証してその値を保存する

タイトルの前後空白を除く仕様なら、Trimした値に対して必須と長さを検証し、その同じ値を保存します。元文字列で長さを検査した後、別の加工値を保存すると、判断対象と保存対象がずれます。大小文字を同一視するか、連続空白をまとめるかはデータの意味に応じて決めます。

string.LengthはUTF-16コード単位数です。絵文字などを人が見た文字数と同じに数える仕様ではありません。この教材の上限はこの.Length基準と明示し、利用者にとっての文字数が必要な製品ではStringInfoなどを検討します。正規化は入力を勝手に改変する万能な処理ではなく、合意した規則です。

200・201・204・400・404・409を使い分ける

取得や計算の成功は200、新しいリソースを作った成功は201とその参照先のLocation、本文なしの成功は204が候補です。入力が契約を満たさなければ400、対象が存在しなければ404、現在の状態や重複などとの衝突には409を検討します。エラーでも200を返すと、クライアントや監視がHTTP上の失敗を検出しにくくなります。

ステータスだけで内部の細部を伝えず、必要なエラー情報は一貫した本文にします。ValidationProblemは検証エラーを項目別に表す方法です。例外のスタック、DB接続文字列、秘密情報をそのまま返してはいけません。認証・認可では401や403も関係しますが、この単元に認証の実装は含めません。

作成したものが本当に参照できる契約

Results.Created("/items/1",item)と返すなら、/items/1をGETして作成したデータを取得できるようにすることが自然な契約です。保存していないのに適当なLocationを返すだけでは、HTTPの見た目と実際の動作が一致しません。作成時には新しいID、正規化済み値、保存成功を確認してから応答します。

本単元のメモリ保存はプロセス終了で失われます。ConcurrentDictionaryの個別操作を利用しても、複数操作全体のトランザクションや複数サーバー間の整合性まで得られるわけではありません。学習では一つの作成・取得の契約を確かめ、永続化と競合の要件を次の設計へ分けます。

概念をもう一段掘り下げる

成功・入力不正・対象なしを契約として区別する

APIは呼び出す側へ結果を機械的に伝える必要があります。全て200で返して本文の文字列だけを読ませると、共通の通信処理や監視が成功と失敗を判断しにくくなります。HTTPステータスと応答本文の役割を分け、入力と結果の契約を定義します。

入力検証は少なくとも三段階あります。HTTP本文として読めるか、C#の型へ変換できるか、業務ルールを満たすかです。stringへ変換できても空白の商品名は不適切かもしれません。nullable参照型はコンパイル時の解析を助けますが、外部データの全ての規則を自動で保証するものではありません。

状態 代表的な応答 呼び出し側の行動

新規作成 201とLocation 作成先のURLを把握
成功し本文なし 204 JSON本文を読もうとしない
要求が不正 400 入力や形式を直す

最小例：保存前に検証する

C# · Webプロジェクト用
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapPost("/validate-title", (TitleInput input) =>
{
    if (string.IsNullOrWhiteSpace(input.Title))
    {
        return Results.ValidationProblem(new Dictionary<string, string[]>
        {
            ["title"] = new[] { "タイトルを入力してください。" }
        });
    }
    string title = input.Title.Trim();
    if (title.Length > 100)
    {
        return Results.ValidationProblem(new Dictionary<string, string[]>
        {
            ["title"] = new[] { "タイトルは100以内で入力してください。" }
        });
    }
    return Results.Ok(new { title });
});

app.Run();

public sealed class TitleInput
{
    public string? Title { get; set; }
}

この例の100はstring.Lengthの数え方に基づく上限です。見た目の文字数とは必ずしも一致しません。入力の制約を「100文字」と説明する場合、何を数える仕様なのかも合わせます。

{"title":" Study "}なら200と{"title":"Study"}、{"title":" "}なら400の検証エラーが期待されます。Dictionary<string,string[]>は、項目名ごとに複数のエラーメッセージを持たせています。Results.ValidationProblemは、エラー項目を含む構造化された応答を作る補助です。

文法・実例・処理順

csharp
var builder = WebApplication.CreateBuilder(args);

app.MapPost("/preview", Preview);

static IResult Preview(CreateTaskRequest input)
{
    if (string.IsNullOrWhiteSpace(input.Title) || input.Title.Length > 100)

処理順

  2. 空白や長すぎる入力を拒否し400を返す。

値・状態の変化を追う

タイトルを検証して作成し、GETで参照する

csharp
using System.Collections.Concurrent;
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
var items = new ConcurrentDictionary<Guid, Item>();
app.MapPost("/items", (CreateItem input) =>
{
    string title = input.Title?.Trim() ?? "";
    if (title.Length is < 1 or > 40)
        return Results.ValidationProblem(new Dictionary<string, string[]> { ["title"] = new[] { "1〜40文字で入力してください" } });
    var item = new Item(Guid.NewGuid(), title);
    if (!items.TryAdd(item.Id, item)) return Results.Conflict();
    return Results.Created($"/items/{item.Id}", item);
});
app.MapGet("/items/{id:guid}", (Guid id) => items.TryGetValue(id, out var item) ? Results.Ok(item) : Results.NotFound());
app.Run("http://127.0.0.1:5080");

public record Item(Guid Id, string Title);

よくある間違いと修正

よくある間違い

この例はプレビューなので200です。保存していないのに201 Createdを返して、リソースが作成されたように見せないでください。

未指定valueと0を区別できない

修正箇所: 要求DTOと必須検証

修正前

csharp
public record SquareInput(int Value);
// {}がValue=0になり、必須チェックを通過し得る

修正後

csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
app.MapPost("/square", (SquareInput input) =>
{
    if (input.Value is not int value || value is < 0 or > 100)
        return Results.BadRequest(new { error = "valueは必須、0〜100で指定" });
    return Results.Ok(new { result = value * value });
});
app.Run("http://127.0.0.1:5080");
public record SquareInput(int? Value);
変更理由

nullを持てる入力DTOにして欠損と明示的な0を区別します。基礎演習の範囲検証へ「項目必須」という追加要件を適用するときの修正であり、0を一律に拒否する変更ではありません。

修正後の確認

  • {}→400
  • {"value":0}→200で0
  • {"value":101}→400

基礎・標準・応用演習

基礎

基礎演習

POST /squareへ{"value":5}を渡すと{"result":25}を返し、0〜100の範囲外は400にするAPIを作ってください。

開始コード
csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
// /squareと入力型を定義する。

入力例・前提条件

POST /squareへvalue=5。許可範囲0〜100。

考え方のヒント

受け取る型で欠損を区別し、範囲が正しい場合だけ二乗する。

入力するとlocalStorageへ保存実行・自動採点は行いません
解答例と確認ポイント
csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
app.MapPost("/square", Square);
app.Run("http://127.0.0.1:5080");
static IResult Square(SquareRequest input)
{
    if (input.Value is < 0 or > 100)
        return Results.BadRequest(new { error = "0〜100を指定してください" });
    return Results.Ok(new { result = input.Value * input.Value });
}
public record SquareRequest(int Value);
解答で確認する条件確認方法
value=5で200と25、value=-1で400になる。コードと想定結果を照合
入力不正を500として扱わない。コードと想定結果を照合

処理と結果の読み解き

5なら25を200で返す。範囲外は400にし、計算前に拒否する。0と100は有効で、境界の等号を確認する。

よくある別解と選び方

検証と計算を別メソッドへ分ければ単体検査をしやすい。HTTP上のバインドは別に統合確認する。

よくある間違いと確認箇所

既定値0と未指定を区別する必要がある仕様で、非nullable intだけに任せない。

実務へのつながり：値の存在、値の範囲、計算結果という段階をHTTP契約に反映する。

Nameは必須、Ageは必須で0〜120。両方のエラーをまとめる。

考え方のヒント

エラーの辞書へ項目ごとの理由を集め、空なら正常処理へ進む。

入力するとlocalStorageへ保存実行・自動採点は行いません
解答例と確認ポイント
csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
app.MapPost("/profile", (ProfileInput input) =>
{
    var errors = new Dictionary<string, string[]>();
    string name = input.Name?.Trim() ?? "";
    if (name.Length == 0) errors["name"] = new[] { "名前は必須" };
    if (input.Age is null or < 0 or > 120) errors["age"] = new[] { "年齢は0〜120の必須項目" };
    if (errors.Count > 0) return Results.ValidationProblem(errors);
    return Results.Ok(new { name, age = input.Age });
});
app.Run("http://127.0.0.1:5080");
public record ProfileInput(string? Name, int? Age);

想定出力

POST /profile {} → 400、errorsにnameとage POST /profile {"name":" Aki ","age":0} → 200 {"name":"Aki","age":0} POST /profile {"name":"Aki","age":121} → 400、errorsにage
  • 複数項目を一度に返す方針なので、一つ目のエラーで即returnしない。
  • 数値の0は有効な値、未指定は不正として分ける。
  • 型変換不能なJSON値はハンドラー前に失敗し、この辞書形式の応答にならない場合もある。HTTPエラー全体の統一は別途設計する。

{}name/ageの二項目エラー
age=120名前が有効なら200
age=-1400

処理と結果の読み解き

Nameの空白とAgeの欠損・範囲外を独立して調べる。最初のエラーだけで止めず、利用者がまとめて直せる情報をValidationProblemで返す。

よくある別解と選び方

小さな結果型で検証を分離し、HTTPハンドラーが応答へ変換する設計もできる。

よくある間違いと確認箇所

Age=0を未指定として拒否しない。nullと0を型と条件で分ける。エラー本文に内部情報や秘密を含めない。

実務へのつながり：入力フォームの案内とAPI契約を合わせ、項目名と修正理由を明確にする。

応用

応用：同じコードの二重登録を409にする

POST /codesへCodeを渡し、Trim後の空値は400、同じOrdinal文字列の二回目は409とします。初回は201、GET /codes/{code}で取得できます。

  • ConcurrentDictionary.TryAddで判定と追加を一操作にする
  • 長さ上限も設ける
  • URLに使う値はエスケープする
開始コード

入力例・前提条件

CodeはTrim後の文字列。同じOrdinal文字列の初回と二回目を送る。

考え方のヒント

空値は400、登録済みは409、新規は201へ分け、保存と検索をつなげる。

入力するとlocalStorageへ保存実行・自動採点は行いません
解答例と確認ポイント
csharp
using System.Collections.Concurrent;
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
var codes = new ConcurrentDictionary<string, string>(StringComparer.Ordinal);
app.MapPost("/codes", (CodeInput input) =>
{
    string code = input.Code?.Trim() ?? "";
    if (code.Length is < 1 or > 20 || code.Any(c => !char.IsAsciiLetterOrDigit(c)))
        return Results.BadRequest(new { error = "codeは英数字1〜20文字" });
    if (!codes.TryAdd(code, code)) return Results.Conflict(new { error = "登録済み" });
    return Results.Created($"/codes/{Uri.EscapeDataString(code)}", new { code });
});
app.MapGet("/codes/{code}", (string code) => codes.TryGetValue(code, out var value) ? Results.Ok(new { code = value }) : Results.NotFound());
app.Run("http://127.0.0.1:5080");
public record CodeInput(string? Code);

想定出力

POST /codes {"code":"A1"} → 201 同じPOSTを再送 → 409 GET /codes/A1 → 200 {"code":"A1"}
  • 存在確認の後で追加する二操作ではなくTryAddにまとめる。
  • 今回のコード仕様は英数字で大小文字を区別する。別の仕様なら比較と正規化を合わせて見直す。
  • メモリ内の単一プロセスに限る。永続DBの一意制約や再起動後の重複管理は実装していない。
入力 / 条件期待結果
A1初回201
A1二回目409
記号/空白のみ400

処理と結果の読み解き

最初の作成で一件保存しLocationを返す。同じ値の二回目は状態衝突として拒否し、件数を増やさない。GETで同じコードを参照できることも確認する。

よくある別解と選び方

大文字小文字を同一視したい仕様なら比較方式から変わる。今回のOrdinalという要件を勝手に変更しない。

よくある間違いと確認箇所

共有する集合の存在確認と追加を無保護で分離しない。並行要求でも重複拒否の契約を維持する。

実務へのつながり：一意制約・衝突・作成結果の参照先を、一貫したAPIの契約にする。

確認問題

Q1. リソースを保存していないプレビュー成功の例に適したコードは？
解説：新規リソースを作成したわけではありません。

201は通常、新規リソースを作成したことを表します。保存せず計算やプレビュー結果を返す成功を、作成と同じ意味にしません。

解説：対象なしではありません。

404は要求の対象が見つからない場合に使います。この例ではプレビューが正常に完了しているので、不在を表す理由がありません。

正解：処理が成功して結果を返す例です。

200と結果の本文なら、要求された処理が成功して結果を返したことを示せます。APIの契約では保存の有無と応答内容も併せて説明します。

解説：サーバー内部障害ではありません。

500はサーバーが予期しない問題で処理できなかった場合の分類です。通常のプレビュー成功を障害として返すと、クライアントが誤って再試行する可能性があります。

Q2. 空白タイトルをユーザー入力として拒否する応答は？
解説：不正データを保存しません。

200はHTTP上は成功なので、利用側が保存されたと解釈する恐れがあります。入力を拒否した事実と、保存しなかった状態を応答に一致させます。

解説：通常の入力ミスは内部障害と区別します。

予想できる入力不備を全て500にすると、利用者が直せる問題とサーバー障害を区別できません。秘密情報を隠すことと、役立つ入力エラーを返すことは両立できます。

解説：移転を示す状況ではありません。

301はリソースの恒久的な移転を表す用途です。タイトルが空白という内容の問題を、別のURLへ移すことで表すのは適切ではありません。

正解：クライアントが修正できる情報を返します。

空白を拒否し、どの項目をどう直すべきかを示します。応答を返す前に保存していないことも確認し、再入力で正しくやり直せる契約にします。

Q3. 必須の数値で未指定と0を区別する方法は？
解説：数値の意味と型の検証が不明瞭になります。

文字列に変えれば欠損や空文字は表せますが、数値という契約を曖昧にします。まず数値のまま欠損状態を区別できるnullable型を検討します。

正解：欠損と明示的な0を別の状態で扱えます。

DTOのint?なら未指定などのnullと、明示的な0を区別できます。nullを拒否した後に、0や負数を許すかという業務上の範囲を検証します。

解説：0が有効な仕様を壊します。

在庫数など0が有効な項目で、欠損判定のために0を拒否すると正しい入力を失います。欠損の状態と値の範囲を別々に表します。

解説：設定やDTOによって既定値へなる場合があります。

非nullable値型のプロパティは、構成によって未指定時に既定値の0となる場合があります。requiredやシリアライザー設定などの挙動を確認し、型だけで全て保証されたと考えません。

Q4. Results.CreatedのLocationに求める自然な契約は？
解説：対象を識別できない場合があります。

トップページだけでは作成した一件を識別できません。クライアントが新しいIDを使って対象を取得できる参照先を返します。

解説：作成結果と参照先が食い違います。

Locationが無関係な場所を指すと、作成結果と次の取得操作がつながりません。返した本文のIDとURLの対象が一致するかをテストします。

正解：クライアントが作成した対象を取得できるようにします。

例としてIDが7のTodoを作ったら/todos/7を返します。続けてGETしたときに同じ対象を取得できることまで確認すると、作成と参照の契約を検証できます。

解説：URLへ秘密情報を不用意に含めるべきではありません。

URLは履歴やアクセスログなどへ残ることがあります。リソースの識別に不要な秘密トークンをLocationへ付け足さず、適切な認証方式を別に設計します。

Q5. 既存コードとの重複を表す選択肢は？
正解：現在の状態との衝突として表す候補です。

同じコードを持つデータが既にあるなら、現在の保存状態との衝突として409を返す設計ができます。入力形式が不正な400とは、失敗の原因を区別します。

解説：HTTP上は成功となり、失敗を扱いにくくします。

本文に失敗と書いても、ステータスが200なら成功として扱うクライアントがあります。HTTPの分類と業務結果を一致させます。

解説：新規作成できていない場合には適しません。

重複で作成を拒否したなら新規リソースはできていません。201を返すと利用側が新しいIDやLocationを期待してしまいます。

解説：204は本文なしの成功であり、検証エラー用ではありません。

204は本文なしで完了した成功を表します。検証エラー本文を載せる目的には使わず、失敗の分類と本文を持てる応答を選びます。
