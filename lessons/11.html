継承・virtual・override

共通の型から異なる処理を呼ぶ。

.NET 10 / C# 14
本文・演習詳細解説
重要overrideの呼び出し先は、変数の宣言型ではなく実体の型に応じて決まります。

同じSendの呼び出しで、通常通知とメール通知を切り替えます。コード上の変数の型と、実際に作られたオブジェクトの型を分けることが、overrideを読む手掛かりです。

要点

  • virtualとoverrideの対応を理解する
  • 継承と単なる処理共有を区別する
重要

継承で実行時の上書きを許可するメソッドは基底側でvirtual/abstract、派生側でoverrideを明示します。宣言型と実体型を分けて呼び出しを追います。

C#
class Dog : Animal
{
    public override string Speak() => "ワン";
}

基底型から派生型の処理を呼ぶ

継承では「同名メソッドがある」ことと「基底型として呼び出したときに派生実装へ置き換わる」ことを分けて考えます。C#ではvirtualとoverrideによって意図を明示します。変数の宣言型、実体の型、呼び出される実装の三つを追い、継承を使うべき関係も判断します。

C#は上書きを明示する

class Report : Documentと書いて継承します。C#の通常のインスタンスメソッドは、同名メソッドを派生側に書くだけではポリモーフィックな上書きになりません。基底側でvirtual、派生側でoverrideを指定します。abstractメソッドには実装がなく、具象派生クラスが実装します。abstract class自体はnewできません。

変数の型と実体の型

基底型の変数で派生オブジェクトを扱うとき、仮想メソッドは実体に対応した実装を呼びます。これが多態性です。呼び出し側を「通知を送る」という抽象へ依存させると、送信方法を差し替えられます。new修飾子によるメンバーの隠蔽はoverrideとは異なり、同じ感覚で使うと呼び出し結果が変わります。

Notice notice = new EmailNotice();の左側と右側を別々に読みます。

基底型に存在しない派生型独自のメンバーは、基底型の変数からそのまま使えるわけではありません。呼び出せる範囲とoverrideの選択は別の規則です。

継承は同じコードを共有するだけではない

RectangleはShapeとして使えるという関係なら、利用側はShape.Area()だけを知っていれば異なる図形を扱えます。これが多態性です。派生型は基底型の契約を守る必要があり、基底型として渡されたときにも想定どおりに動かなければなりません。

一部の処理が似ているという理由だけで継承すると、片方の要件変更で不自然な制約を引き継ぐことがあります。たとえば「車はエンジンを持つ」は車がエンジンである関係ではないため、フィールドとして保持する合成が自然です。共通コードを減らすことと、型として代入可能な関係を作ることを分けて判断します。

コードが似ているだけでは、継承を使う理由にはなりません。基底型として扱っても約束を守れるかを考えます。

通知先を切り替えたいだけなら、インターフェイスや部品への委譲で表す方法もあります。どの関係を表したいかが選択の基準です。

virtual・override・newの呼び出し規則

C#の通常のクラスメソッドは、何も指定しなければ仮想メソッドではありません。基底側がvirtualで拡張点を作り、派生側がoverrideで上書きします。基底型の変数に派生インスタンスが入っていても、仮想呼び出しなら実体に対応したoverrideが使われます。

newで同名メンバーを定義するのは隠蔽です。overrideの別表記ではありません。基底型からの呼び出しは基底のメンバー、派生型からは隠した側が選ばれる場合があります。コードが警告だけで動くこともあるため、表示結果だけでなく宣言を確認します。基底型の契約を多態的に置き換えたいならvirtual/overrideを使います。

Notice型の変数からEmailNoticeを呼ぶ

csharp
Notice notice = new EmailNotice();
Console.WriteLine(notice.Send());

public class Notice
{
    public virtual string Send() => "通常の通知";
}
public class EmailNotice : Notice
{
    public override string Send() => "メール通知";
}

noticeの変数の型はNoticeですが、newで作られている実体はEmailNoticeです。

virtualをoverrideした呼び出しなので、実体に対応するEmailNotice.Sendが選ばれます。変数の型だけを見て通常通知になると判断しないでください。

想定出力

メール通知

処理順

  1. 変数noticeの型はNotice、実体はEmailNotice。
  2. Sendはvirtualなので実体の型に応じて呼び先が選ばれる。
  3. EmailNoticeのoverrideされた実装が返される。

同じ基底型から異なるoverrideを呼ぶ

csharp
Notice[] notices = { new Notice(), new MailNotice(), new ScreenNotice() };
foreach (Notice notice in notices) Console.WriteLine(notice.Send());
public class Notice
{
    public virtual string Send() => "標準";
}
public class MailNotice : Notice
{
    public override string Send() => "メール";
}
public class ScreenNotice : Notice
{
    public override string Send() => "画面";
}

出力

標準 メール 画面
段階値・状態読み解き
配列の宣言要素の宣言型はNotice利用側が扱う契約を揃える
一つ目実体はNotice基底のSendを使う
二つ目実体はMailNoticeoverrideされたメールを返す
三つ目実体はScreenNotice同じ呼び出し文で別の実装が選ばれる

共通の通知型を使い、メール通知と画面通知を呼び分けます。実際の通信はしない例です。

virtual・overrideと基底型

継承と基底型・派生型の関係

継承は、あるクラスを基に別のクラスを定義する仕組みです。基になる型を基底クラス、そこから作る型を派生クラスと呼びます。共通実装を再利用できますが、単に同じコードを減らしたいから使うだけでは、変更の影響が広がりやすくなります。派生型が基底型として扱われても期待される契約を守れるかを確認します。

ポリモーフィズムとは、共通の型を通して呼び出しても、実際の型に応じた処理を行う仕組みです。通知を送る処理に対し、具体的には画面表示か、別の方法かを切り替えるような場面で役立ちます。ここではまず、図形の面積を求める例で、変数の型と実体の型を分けます。

最小例：virtualとoverride

C# · 独立したコード例
Shape shape = new Rectangle(3, 4);
Console.WriteLine(shape.Area());

public class Shape
{
    public virtual int Area() => 0;
}

public class Rectangle : Shape
{
    private readonly int _width;
    private readonly int _height;

    public Rectangle(int width, int height)
    {
        _width = width;
        _height = height;
    }

    public override int Area() => _width * _height;
}

期待出力は12です。Rectangle : ShapeはRectangleがShapeを継承する宣言です。virtualは派生型で上書き可能なメソッドを宣言し、overrideはその上書きを実装します。shape変数の宣言型はShape、参照する実体の型はRectangleです。virtual呼び出しでは実体に対応する上書き処理が選ばれます。

型情報と実際のメソッドへの対応によって呼び出しが選ばれます。JITが対象を確定できる場合は最適化も行いますが、言語上の振る舞いはこの対応で理解します。「変数の型だけで常に呼び出す本体が決まる」と覚えるとvirtualの例を説明できません。

よくある間違いと修正

よくある間違い

virtualでない親メソッドを同名で書き直しても、仮想ディスパッチによる上書きにはなりません。警告を無視せず、overrideか別名かを選びます。

newで隠したメソッドが基底型から呼ばれない

修正箇所: 基底側の宣言と派生側の同名メソッド

修正前

csharp
Base value = new Derived();
Console.WriteLine(value.Name());
class Base { public string Name() => "Base"; }
class Derived : Base { public new string Name() => "Derived"; }

修正後

csharp
Base value = new Derived();
Console.WriteLine(value.Name());
class Base { public virtual string Name() => "Base"; }
class Derived : Base { public override string Name() => "Derived"; }
変更理由

多態的に置き換える要件なので、基底をvirtual、派生をoverrideへ変更します。修正前のnewは同名メンバーの隠蔽であり、Base型からの呼び出しを置き換えません。

修正後の確認

  • Base型の変数からDerivedを出力
  • Derived型の変数からもDerivedを出力
  • new Base()はBaseを出力

継承で約束することと設計上の制限

継承を増やしすぎない

C#のクラス継承は基底クラス1つです。sealed classは継承を禁止します。共通コードが少しあるだけで継承にすると、親の変更が子へ広がりやすくなります。「AはBの一種」と自然にいえるかを確認し、そうでなければ必要な機能を別オブジェクトとして持つ構成も検討します。

abstract・sealed・baseの役割

abstract classは直接newできず、抽象メソッドには本体を書きません。具象の派生型が実装を提供します。共通の状態や処理を持たせながら一部を未確定にする設計に向きます。interfaceは操作の契約を中心にするため、基底クラスとどちらが自然かを選びます。

sealed classは継承を禁止し、sealed overrideはそれ以上の上書きを禁止します。拡張を許可する場所を限定することもAPI設計です。base(...)で基底コンストラクターへ初期化値を渡し、base.Method()で基底実装を明示的に呼べます。ただしコンストラクターから仮想メソッドを呼ぶと、派生側が十分に初期化される前に動く危険があるため避ける設計を優先します。

キャストで設計の問題を隠さない

Shapeの変数からRectangle固有のメンバーを使いたいなら、型パターンでRectangleかを確かめて取り出せます。しかし利用側が各派生型へ大量のキャストをして分岐するなら、多態性による共通操作の設計が不足している可能性があります。型を増やすたびに利用側も変更する構造になっていないか確認します。

またoverrideは呼び出し契約を守ります。基底では0以上の入力を受け付けるのに、派生で10以上に限定するなど、受け付ける条件を勝手に狭めると利用側が壊れます。型の共通化で何を保証するのかを文章にし、派生型ごとに同じテスト観点で確認することが実務では重要です。

確認問題

Q1. C#で通常のメソッドを派生クラスから上書きする組み合わせは？
正解：上書きを許可する側と実装する側の両方で明示します。

基底が拡張点を宣言し、派生がその契約に沿う実装へ置き換えます。基底型の変数から呼んでも実体に対応するoverrideを使えます。

解説：この組み合わせではoverrideになりません。

privateの通常メソッドは派生型のoverride用の契約ではありません。staticも型に属するメソッドであり、この仮想呼び出しとは異なります。

解説：sealedは上書きや継承を制限するための指定です。

sealed classは派生を禁じ、sealed overrideはさらに上書きされることを禁じます。newで同名を作ることはoverrideの代わりにはなりません。

解説：単なる同名メンバーは仮想メソッドの上書きと異なります。

同じ名前だけでは、基底型から呼ぶ仮想メソッドの実装を置き換えません。警告を消すためにnewを付ける場合も、意味の違いを確認します。

Q2. Notice n = new EmailNotice(); でvirtualメソッドを呼ぶと？
解説：virtual呼び出しでは実体も関係します。

宣言型Noticeは呼べる契約を決めますが、virtualの実装選択は実体EmailNoticeのoverrideを使います。二つの型の役割を分けます。

正解：基底型を通してもoverrideされた実装を呼べます。

EmailNoticeがoverrideしていれば、その実装が呼ばれます。Noticeとして扱える共通性を保ちながら動作を変える多態性の例です。

解説：base.Send()などを書かない限り両方実行するとは限りません。

派生の実装が基底の処理も必要なら、内部でbase.Send()などを明示します。overrideという指定だけで両方を順に呼ぶ規則はありません。

解説：有効な多態性の利用です。

派生型を基底型の変数へ代入することは通常の継承の利用です。アクセス範囲やメソッド宣言が規則に合っていれば有効です。

Q3. C#の通常のメソッドを派生クラスでoverrideするために必要なことは？
解説：戻り値の種類だけで上書き可能にはなりません。

戻り値がintでもvoidでも、上書き可否は仮想メンバーとしての契約で決まります。stringという型だけでは拡張点になりません。

正解：明示的な拡張点として許可されたメンバーを上書きします。

virtualやabstractなどで公開された拡張点をoverrideします。通常の非仮想メソッドに対して勝手にoverrideを付けてもビルドできません。

解説：名前の大小文字の規約と仮想呼び出しは別です。

命名規約は可読性のための約束です。仮想メソッドの呼び出し規則を、名前の大文字・小文字だけで有効にすることはありません。

解説：通常の非仮想メソッドは同名だけでoverrideできません。

同名の新メンバーを作ることと既存の仮想メンバーを上書きすることは別です。基底側の宣言まで読んで、許される操作を確認します。

Q4. newによるメソッド隠蔽とoverrideは？
解説：newは隠蔽、overrideは仮想メンバーの上書きです。

newは基底の名前を隠す別メンバー、overrideは同じ仮想契約の実装差し替えです。宣言型を変えて呼んだときの結果で違いが現れます。

解説：安全性は意図と契約次第でありnewが常に優れるわけではありません。

newを付けると意図的な隠蔽であることは示せますが、呼び出し側が混乱しない設計かは別です。警告が消えたことを品質保証と考えません。

解説：規則を満たせばどちらも有効な構文です。

どちらもC#にある有効な機能です。ただし基底の宣言や継承条件が合わなければエラーになるため、目的に合う方を選びます。

正解：宣言型から選ばれるメンバーと、実体に基づく仮想呼び出しを区別します。

基底型の変数から呼ぶとnewで隠した派生メンバーは選ばれない場合があります。overrideなら同じ仮想契約として派生実装が選ばれます。

Q5. 「車はエンジンを持つ」を表す設計で自然なのは？
解説：車そのものがエンジンである関係ではないので継承は不自然です。

CarをEngineが必要な場所へそのまま渡せる関係とは言えません。「持っている」関係を「一種である」継承で表さないようにします。

解説：staticにしても部品と所有者の関係は適切に表せません。

staticは共有方法の指定であり、車がエンジンを利用する責務を表すものではありません。個別の部品や差し替えの必要性も考えます。

正解：has-aの関係は依存する部品を保持する合成で表しやすくなります。

CarのフィールドやコンストラクターでEngineを受け取り、必要な操作を委譲します。部品を持つ関係がコード上でも明確になります。

解説：型情報を失うだけで関係を明確化できません。

objectにすると具体的な操作の契約が見えにくくなります。適切なEngine型やinterfaceで、利用できる機能を明示する方が意図を表せます。
