HttpClientでHTTPを扱う

HTTP要求と応答の構成。

.NET 10 / C# 14
本文・演習詳細解説
重要HTTPは、要求を送ったことと、正常なステータスの応答を得たことを分けて扱います。

図解：HTTP要求と応答の構成

要点

  • HTTP成功とデータの妥当性を分ける
  • HttpClientの寿命とキャンセルを考える
重要

HttpClientでは通信成功、HTTPステータス、本文の解析、値の妥当性を別段階として扱います。HttpMessageHandlerを差し替えるとクライアント処理を安定して検証できます。

C#
using var response = await client.GetAsync(url, token);

概念・構文

HTTPでは、接続できたこと・成功ステータスだったこと・本文が期待したJSONだったことは別です。HttpClientの寿命と応答の寿命を分け、通信せず再現できる偽ハンドラーからエラー処理を学びます。

HTTPは成功以外も返す

GetAsyncで応答を受け取り、ステータスコードを確認します。EnsureSuccessStatusCodeは成功範囲外なら例外にしますが、404を「対象なし」と通常分岐にしたい場合は明示的に扱います。JSONとして読めても、必要な項目があるか検証することは別です。タイムアウトやユーザーキャンセルも考慮してCancellationTokenを渡します。

HttpClientを毎回作り捨てない

実際の通信でリクエストごとにHttpClientをnewして破棄すると、接続管理の問題が起こり得ます。長寿命クライアントと接続更新設定、またはIHttpClientFactoryなどを用途に応じて使います。ここでは通信の扱いを確認するため、HTTPハンドラーを差し替えた短い1回限りの例を使います。

外部APIに依存せず学ぶ

下のDemoHandlerは固定JSONをHTTP応答として返すテスト用の実装です。ネットワーク接続は発生しません。JSONの読み取りやステータス確認のC#コードは実際に実行されますが、実サーバーの疎通テストとは区別します。実通信へ進むときは標準ハンドラーを使い、接続先と認証情報を適切に設定します。

通信・ステータス・本文の三段階

GetAsyncが応答を返しても、ステータスが404や500であることがあります。ネットワークへ接続できない失敗と、サーバーがエラー応答を返した状態は別です。業務上よくある404は分岐で扱い、想定しない非成功状態はEnsureSuccessStatusCodeなどで検知する設計ができます。

200でも本文が期待するJSONでない、JSONとして読めても必須値がない場合があります。ステータス確認、本文の読み取り・逆シリアル化、業務データの検証という順番を崩さないようにします。失敗をすべて空Listへ置き換えると「本当に0件だった」と区別できなくなります。

HttpClientと応答の寿命を分ける

HttpClientは内部の接続を再利用するため、要求のたびに大量にnewして破棄する使い方を避けます。長寿命のクライアントとPooledConnectionLifetimeを調整する方式や、IHttpClientFactoryで管理する方式が公式に案内されています。適切な選択はアプリの寿命やDNS更新、Cookieの扱いなどにも依存します。

HttpResponseMessageは各応答に対応するため、usingで本文を使い終えたら破棄する設計が基本です。この単元のコンソール例でusing var clientとするのは、一つの短命アプリ全体で一つのクライアントを使うためです。サーバーの各要求内で毎回作り直す例へ機械的にコピーしないでください。

キャンセル・タイムアウト・再試行

GetAsyncや本文読み取りへCancellationTokenを渡すと、利用者の中止要求や上位操作の停止を伝えられます。タイムアウトもOperationCanceledException系の形で観測される場合があるため、呼び出し元のトークンが要求されたかなどを確認して原因を分けます。HttpRequestExceptionは接続失敗や成功ステータス検査など、発生地点を含めて読む必要があります。

失敗したらすべて自動再試行する設計は危険です。POSTの作成処理では、サーバー側が作成済みなのに応答だけ失われた可能性があります。再試行の安全性は操作の冪等性、冪等性キー、接続先の規約などによります。認証情報や本文全体をログへ出して原因調査する方法も、秘密情報の漏えいにつながります。

偽ハンドラーで通信境界を制御する

HttpClientはHttpMessageHandlerへ要求を渡します。学習用にSendAsyncを実装したハンドラーを与えると、実際の外部サービスへ接続せず、200、404、不正JSON、キャンセルなどを再現できます。テストごとに同じ入力と応答を用意でき、インターネット障害でテストが揺れにくくなります。

これは実際のDNS、TLS、ネットワーク経路、相手サーバーまで検証するテストではありません。HTTPクライアント側の処理を切り出して確認していると区別します。実通信の確認は安全なテスト環境で別に行い、APIキーや実ユーザーデータをサンプルへ埋め込まないでください。

仕組みの補足

HTTPの要求と応答

HTTPは、クライアントが要求を送り、サーバーが応答を返すための通信の約束です。クライアントは要求する側、サーバーは要求を受けて機能を提供する側です。Web APIはHTTPなどを通して、他のプログラムからデータや機能を使えるようにする窓口です。

リクエストには、どこへ送るかというURL、何をしたいかというメソッド、追加情報のヘッダー、必要に応じた本文があります。レスポンスには結果を示すステータスコード、ヘッダー、本文があります。JSONは本文を表現する形式の一つで、HTTPそのものと同じではありません。

DNSは名前から通信先のアドレスを調べる仕組み、TLSは通信を暗号化し相手を確認するための仕組みです。HTTPSはTLSで保護されたHTTPです。本番の秘密情報を平文のHTTPで送らないこと、証明書検証を無効にしてエラーを回避しないことが基本です。

URLとHTTPメソッドを読む

https://example.invalid/items/3?include=detailという例では、httpsが方式、example.invalidがホスト名、/items/3がパス、include=detailがクエリです。example.invalidは説明用で、接続できるサービスとして使いません。フラグメントの#以降は通常HTTPリクエストの対象情報としてサーバーへ送られません。

メソッド 主な意味 選ぶ例 繰り返しの注意
GET 表現を取得 商品一覧を読む 状態変更を目的にしない
POST 資源に処理を依頼 新しい注文を作る 再送で重複し得る
PUT 指定先の表現を置換 ID指定で全項目を更新 同じ要求の意図は冪等
PATCH 部分的な変更を適用 完了状態だけ変更 内容次第で冪等とは限らない
DELETE 対象を削除 指定IDを削除 意図は冪等だが応答は変わり得る

冪等とは、同じ操作を何度行っても、意図した最終状態への効果が一回と同じになる性質です。毎回同じステータスを返すという意味ではありません。再試行を設計するとき、通信失敗でも相手では処理済みの可能性があるため、この性質が重要になります。

文法・実例・処理順

csharp
using System.Net;
using System.Net.Http.Json;

using var client = new HttpClient(new DemoHandler());
using var response = await client.GetAsync("https://example.invalid/score");
response.EnsureSuccessStatusCode();
var score = await response.Content.ReadFromJsonAsync<Score>()
    ?? throw new InvalidOperationException("応答が空です");
Console.WriteLine(score.Value);

public record Score(int Value);
public class DemoHandler : HttpMessageHandler
{
    protected override Task<HttpResponseMessage> SendAsync(HttpRequestMessage request, CancellationToken token)
    {
        token.ThrowIfCancellationRequested();
        return Task.FromResult(new HttpResponseMessage(HttpStatusCode.OK)
        {
            Content = JsonContent.Create(new Score(80))
        });
    }
}

想定出力

80

処理順

  1. HttpClientが差し替えたハンドラーへリクエストを渡す。
  2. ハンドラーが200とJSONを返す。実ネットワークは使わない。
  3. 応答コードを確認し、Scoreへ読み取って80を表示する。

値・状態の変化を追う

HTTP成功後にJSONと必須値を確認する

using System.Net;
using System.Text.Json;
using var client = new HttpClient(new DemoHandler());

response.EnsureSuccessStatusCode();
string body = await response.Content.ReadAsStringAsync();
var score = JsonSerializer.Deserialize<Score>(body);
if (score is null || score.Value is < 0 or > 100) throw new InvalidDataException("得点が不正");
Console.WriteLine($"HTTP: {(int)response.StatusCode}");
Console.WriteLine($"得点: {score.Value}");

public class DemoHandler : HttpMessageHandler
{

        token.ThrowIfCancellationRequested();

        { Content = new StringContent("{\"Value\":80}", System.Text.Encoding.UTF8, "application/json") });
    }
}

よくある間違いと修正

よくある間違い

制作物にAPIキーを直書きしたり、応答や認証ヘッダーを無制限にログ出力したりしないでください。学習用URLexample.invalidは実サービスへの接続先ではありません。

404本文を正常JSONとして処理する

修正箇所: 応答を受け取った直後のステータス判定

修正前

csharp
using var response = await client.GetAsync("https://example.invalid/item");
string body = await response.Content.ReadAsStringAsync();
// ステータスを見ずに正常なDTOへ変換してしまう

修正後

csharp
using System.Net;
using var client = new HttpClient(new MissingHandler());
using var response = await client.GetAsync("https://example.invalid/item");
if (response.StatusCode == HttpStatusCode.NotFound)
{
    Console.WriteLine("見つかりません");
    return;
}
response.EnsureSuccessStatusCode();
Console.WriteLine(await response.Content.ReadAsStringAsync());
public class MissingHandler : HttpMessageHandler
{
    protected override Task<HttpResponseMessage> SendAsync(HttpRequestMessage request, CancellationToken token)
    {
        token.ThrowIfCancellationRequested();
        return Task.FromResult(new HttpResponseMessage(HttpStatusCode.NotFound));
    }
}
変更理由

HTTPの結果を先に判定し、404は契約に沿った分岐として扱います。その他の非成功状態を成功本文と混同せず、本文解析の失敗で本来の原因を隠さない修正です。

修正後の確認

  • 404→見つかりません
  • 500→成功検査で失敗
  • 200→本文処理へ進む
実コード例

実例：HTTP応答の処理を通信なしで確かめる

HttpResponseMessageを直接作り、404の分岐を確認します。実際の外部サーバーへはアクセスしません。

C# · Program.cs
using System.Net;
using System.Net.Http;
using var response = new HttpResponseMessage(HttpStatusCode.NotFound);
if (response.IsSuccessStatusCode)
    Console.WriteLine("取得成功");
else if (response.StatusCode == HttpStatusCode.NotFound)
    Console.WriteLine("対象が見つかりません");
else
    Console.WriteLine($"HTTPエラー: {(int)response.StatusCode}");

想定出力

対象が見つかりません

処理と値の変化

  1. HttpResponseMessage受け取る応答と同じ型を手元で生成する
  2. IsSuccessStatusCode2xxかどうかを確認する
  3. 404の分岐不存在をほかのエラーと分ける
条件を変えた場合

NotFoundをOKへ変えると「取得成功」になります。この例は通信時間やCORSを検証するものではありません。

標準

標準：二つのHTTPステータスを区別する

同じ偽ハンドラーでパス/okなら200、その他なら503を返し、応答コードとIsSuccessStatusCodeを表示します。

  • RequestUri.AbsolutePathを読む
  • 応答ごとにusingを使う
  • 503もHTTP応答自体は得られる

考え方のヒント

要求のRequestUriからパスを読み、返すステータスを切り替える。

入力するとlocalStorageへ保存
解答例と確認ポイント
csharp
using System.Net;
using var client = new HttpClient(new StatusHandler());
foreach (string path in new[] { "ok", "fail" })
{
    using var response = await client.GetAsync("https://example.invalid/" + path);
    Console.WriteLine($"{(int)response.StatusCode}: {response.IsSuccessStatusCode}");
}
public class StatusHandler : HttpMessageHandler
{
    protected override Task<HttpResponseMessage> SendAsync(HttpRequestMessage request, CancellationToken token)
    {
        token.ThrowIfCancellationRequested();
        var code = request.RequestUri?.AbsolutePath == "/ok" ? HttpStatusCode.OK : HttpStatusCode.ServiceUnavailable;
        return Task.FromResult(new HttpResponseMessage(code));
    }
}

想定出力

200: True 503: False
  • 二要求で一つのHttpClientを再利用する。
  • 非成功コードでも応答を取得でき、アプリ側で方針を決める。
  • IsSuccessStatusCodeはステータスの成功範囲を見るだけで、本文の正しさまでは保証しない。

処理と結果の読み解き

よくある間違いと確認箇所

応用

応用：200でもJSONが不正なら失敗する

200を返す偽ハンドラーの本文をnot-jsonにし、JsonExceptionを捕捉して「本文形式が不正」と表示してください。

  • HTTP成功検査の後にJSON変換
  • 通信失敗と本文失敗を分ける
  • 例外メッセージ全文を外部へ返さない
開始コード

考え方のヒント

ReadFromJsonAsyncをawaitする範囲でJsonExceptionを扱う。

解答例と確認ポイント
csharp
using System.Net;
using System.Text.Json;
using var client = new HttpClient(new BrokenBodyHandler());
using var response = await client.GetAsync("https://example.invalid/item");
response.EnsureSuccessStatusCode();
try
{
    _ = JsonSerializer.Deserialize<Item>(await response.Content.ReadAsStringAsync());
}
catch (JsonException)
{
    Console.WriteLine("本文形式が不正");
}
public record Item(string Name);
public class BrokenBodyHandler : HttpMessageHandler
{
    protected override Task<HttpResponseMessage> SendAsync(HttpRequestMessage request, CancellationToken token)
    {
        token.ThrowIfCancellationRequested();

    }
}

想定出力

本文形式が不正

  • JSON nullや必須値の欠損は構文エラーとは限らないため、成功後のデータ検証も別に必要になる。

処理と結果の読み解き

200の確認を通ってもJSON構文として読めず例外になる。呼び出し側は本文形式が不正と表示し、正常データとして使わない。

よくある間違いと確認箇所

全てを見つかりませんと表示すると、相手が不在なのか本文が壊れているのかが分からない。

実務例：外部連携は成功コードだけで信用せず、形式と必要な項目まで検証する。

確認問題

Q1. EnsureSuccessStatusCodeは何を確認する？
解説：本文の業務検証までは行いません。

成功ステータスでも必須項目が欠けたJSONはあり得ます。ステータスの確認、JSONの変換、変換後の業務検証を別の段階として実装します。

解説：保存を行うメソッドではありません。

認証情報の保管先やアクセス権を変更する機能ではありません。HTTP応答を確認するメソッド名から、安全な秘密管理まで保証されると考えないようにします。

正解：成功範囲外なら例外になります。

200〜299の範囲かを確認し、それ以外ならHttpRequestExceptionを発生させます。404を通常の不在として扱いたい場合は、その分岐を先に設ける設計もあります。

解説：このメソッドはHTTP応答のステータスを確認します。ユーザー入力の内容は別途検証します。

ユーザー入力の妥当性は送信前やサーバー側で別途検証します。このメソッドが調べるのは、受け取った応答のStatusCodeです。

Q2. このレッスンのDemoHandlerで確認していないものは？
解説：ReadFromJsonAsyncを実行します。

固定の本文をReadFromJsonAsyncで読み取る処理は確認対象にできます。実ネットワークを省いたからといって、JSON変換まで省かれるわけではありません。

解説：応答コードを扱っています。

ハンドラーが指定のステータスを返せば、成功・404・500などへの分岐を試せます。外部サーバーの実際の状態は確認していません。

解説：非同期呼び出しのコードを実行します。

awaitを含む呼び出し側の処理はコードとして試せます。ただし即座に完了する偽応答では、実通信の遅延や全ての中止動作を再現したことにはなりません。

正解：固定応答なのでネットワークの検証とは異なります。

偽ハンドラーは応答をプログラム内で作るので、DNS、TLS、経路、相手の稼働状況を通りません。確認できた範囲を通信全体へ広げて報告しないことが大切です。

Q3. GetAsyncで404の応答を受けたら？
解説：存在しないデータを自動作成しません。

404は相手が対象を見つけられなかったという応答です。作成には別の契約や操作が必要であり、HttpClientが勝手に新規データを作ることはありません。

解説：エラー本文を正常DTOとして扱うと原因を隠します。

エラー本文がHTMLや別形式のJSONなら、正常DTOへの変換エラーで元の404を見失います。まずステータスに応じた扱いを決めます。

正解：想定する状態を分岐し、必要ならEnsureSuccessStatusCodeを使います。

GetAsyncが返したHttpResponseMessageのStatusCodeを調べます。不在なら利用者へ伝え、予期しない非成功なら例外へ変換するなど方針を決められます。

解説：HTTPの非成功状態と通信自体の失敗は異なります。

HTTP応答を受け取れたことと、その応答が2xxであることは別です。DNS失敗など通信が成立しない場合の例外と、404応答を区別します。

Q4. サーバーで各要求ごとにHttpClientを大量new/disposeする代わりの基本方針は？
解説：接続管理の根本的な問題は解決しません。

作成するスレッドを変えても接続プールの寿命は適切になりません。HttpClientと内部ハンドラーをどの範囲で再利用するかを設計します。

解説：HttpResponseMessageの寿命はクライアントの寿命と別です。

応答やストリームは読み終えたら適切に解放します。HttpClientを長く使うことは、個々のHttpResponseMessageを永久に保持することではありません。

解説：同期化は接続プールの管理方針ではありません。

同期・非同期は待ち方の問題であり、接続資源の再利用とは別です。非同期を保ちつつクライアントとハンドラーの寿命を管理します。

正解：接続再利用やDNS更新の方針に合わせて管理します。

長寿命のクライアントに適切な接続寿命を設定する方式や、ファクトリーでハンドラーを管理する方式があります。DNS更新と資源再利用の両方を考慮します。

Q5. 偽HttpMessageHandlerで確認できないものは？
正解：外部通信を行っていないため実ネットワークを検証したとは言えません。

固定応答は実際の証明書や名前解決を検査しません。本物の相手に届くかを確認するテストを別に実施し、結果を分けて記録します。

解説：任意の本文を返して再現できます。

壊れたJSONを本文として返すハンドラーなら、JsonExceptionなどを扱う処理を再現できます。ネットワークの有無と本文内容の検証可能性は別です。

解説：指定の404応答を返して確認できます。

StatusCodeをNotFoundにした応答を返し、呼び出し側が期待どおり不在へ分岐するかを調べられます。これも相手サーバーの仕様保証とは区別します。

解説：実装したハンドラーと呼び出し側の契約を制御して確認できます。

偽ハンドラーがトークンを確認する実装なら、中止要求を伝える経路の一部を調べられます。実通信の中断や時間条件を全て検証したという意味ではありません。
