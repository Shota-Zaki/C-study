プロジェクトとNuGet

ソース・プロジェクト・依存関係。

.NET 10 / C# 14
本文・演習詳細解説
重要NuGetパッケージを追加すると依存関係が増えます。型を使うusingと、参照を追加する操作は別です。

Program.csをコピーしただけでは、同じアプリを再現できないことがあります。フォルダー内の役割を確認し、ビルドの材料、参照、依存パッケージの復元を順に見ます。

要点

  • .csprojの主要項目を読める
  • 依存パッケージとプロジェクト参照を区別する
重要

プロジェクト設定と依存関係は.csprojへ記録し、NuGetでパッケージを解決します。usingは名前解決の指定であり依存パッケージの追加ではありません。

C#
// .csprojにPackageReferenceやProjectReferenceを宣言

ソースとプロジェクト設定をそろえる

実務ではProgram.csだけでなく、.csproj、参照、依存パッケージ、ビルド結果まで含めてアプリを管理します。コマンドを丸暗記せず、どのファイルへ何が記録され、どの段階で失敗したかを切り分けます。

プロジェクトがビルドの単位

SDK形式の.csprojには、TargetFramework、Nullable、ImplicitUsingsなどを記述します。以下のプロジェクト設定はnet10.0、Nullable=enable、ImplicitUsings=enableです。.csファイルは通常、プロジェクトのディレクトリ配下から自動的にコンパイル対象へ含まれます。別の演習のProgram.csを同じプロジェクトへ増やすと入口や型名が衝突するため、例ごとにフォルダーを分けます。

プロジェクトファイルはビルドの契約

.csprojは対象フレームワーク、出力の種類、nullable解析、依存関係などをMSBuildへ伝えます。TargetFrameworkのnet10.0は対象とする.NETのAPI群を示します。OutputType=Exeなら実行可能なアプリ、通常のclasslibなら再利用するライブラリです。ファイル拡張子が.csであることだけでビルド対象や設定が決まるわけではありません。

SDK形式ではプロジェクト配下の.csが既定で含まれるため、一つのフォルダーへ別々のサンプルを大量に置くと、トップレベル文や型名が衝突します。binやobjはビルドで生成される情報であり、通常はソースの正本として編集しません。

最小の.csprojを読む

ソースコードとプロジェクト設定

C#のソースファイルには処理を書きます。しかし、どの.NET向けに作るか、どのライブラリを使うか、実行するアプリなのか他から参照される部品なのか、といった情報も必要です。それらをまとめる単位がプロジェクトです。通常、設定は拡張子.csprojのファイルに記述します。

ライブラリは、他のプログラムから使えるようにまとめたコードなどの部品です。NuGetは.NETのパッケージを配布・取得・依存関係として管理する仕組みです。パッケージはライブラリ本体だけでなく、関連する設定や資源を含むこともあります。usingを書くこと、プロジェクト参照を追加すること、NuGetパッケージを追加することは別の操作です。

最小構成の.csprojを読む

次はコンソールの独立したサンプルプロジェクトに使う設定です。XMLは、タグで項目と値を囲んで構造を表す記述形式です。

xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>
部分 意味 変える場面
Project Sdk ビルドに使う共通の規則 WebならMicrosoft.NET.Sdk.Webなど
OutputType=Exe 実行するアプリとして出力 部品用プロジェクトはライブラリ
TargetFramework=net10.0 .NET 10のAPIを対象にする 対応環境を変えるとき
ImplicitUsings よく使う名前空間を自動的に取り込む usingを全て明示したい場合
Nullable nullに関する注釈と解析を有効にする 基本は有効のまま設計する

TargetFrameworkはTFMとも呼ばれます。TFMは対象フレームワークを示す短い識別子です。.NET SDKのインストール済みバージョン、対象フレームワーク、C#言語バージョンは関連しますが同一の番号ではありません。対象をnet10.0にするだけで未インストールのSDKが自動的に手に入るわけではありません。

複数ファイルと参照の関係

パッケージと自分のプロジェクト

NuGetは.NET向けのパッケージ管理です。.NET 10のdotnet package add パッケージ名は外部パッケージを追加します。自分の別プロジェクトへ依存する場合はproject referenceを使います。ソリューションは複数プロジェクトをまとめる単位で、.slnや.slnx形式があります。言語の名前空間と、パッケージやプロジェクトの関係を混同しないでください。

using・プロジェクト参照・パッケージ参照の違い

usingは名前空間の型を短い名前で書くための指定です。まだ利用可能になっていない外部ライブラリをダウンロードする命令ではありません。自分の別プロジェクトを使うならProjectReference、NuGetの配布物を利用するならPackageReferenceなどで依存を追加します。

クラスライブラリを作る練習は、空の作業フォルダーでdotnet new classlib -n Study.Core -f net10.0、dotnet new console -n Study.Cli -f net10.0を実行し、dotnet add Study.Cli/Study.Cli.csproj reference Study.Core/Study.Core.csprojで参照を追加できます。依存方向はCLI→Coreにし、Coreから表示側へ逆参照させないことが設計の出発点です。

名前を省略する仕組みと、別のコードをプロジェクトで使えるようにする仕組みを区別します。

usingを書いても、参照していないパッケージを自動で取得するわけではありません。型が見つからないときは、名前と参照の両方を調べます。

パッケージ復元と環境差を調べる

再現できる状態を残す

ソース、設定、必要な依存定義をGitで管理し、bin/objは通常除外します。外部パッケージは公式情報・ライセンス・更新状況を確認し、不要なものは追加しません。新しいパッケージを入れるたび、標準ライブラリで足りない理由を説明できると、保守負担を抑えられます。

restore・build・run・publishを分ける

restoreは依存パッケージを解決してビルドに必要な情報を用意します。buildはコードと設定をコンパイルし、runは対象アプリを実行します。publishは配布・配置用の出力を作る操作です。buildやrunが必要に応じてrestoreを暗黙に行う場合もあるため、毎回すべてを手動実行する必要があるという意味ではありません。

失敗したら段階を読みます。NuGet接続失敗はネットワークやソース設定、名前解決失敗は参照や名前空間、実行時のFileNotFoundはファイル配置など、調べる箇所が異なります。再インストールを繰り返す前に、最初のエラーメッセージ、対象プロジェクト、実行コマンド、SDKの情報を記録してください。

dotnet run一つで進む場面でも、内部では異なる役割の工程があります。

通常のbuildやrunは必要な復元などを暗黙に行うことがあります。失敗時には、どの工程で止まったかをログで区別すると原因を探しやすくなります。

依存追加を再現可能にする

NuGetへ依存すると、そのパッケージがさらに他のパッケージへ依存することがあります。直接依存と推移的依存を確認し、不要なパッケージを増やさないようにします。標準ライブラリにSystem.Text.Jsonがある今回のJSON学習では、それを使うためだけに別のJSONライブラリを追加する必要はありません。

.NET10ではdotnet package add <PACKAGE_NAME>という名詞を先に置く形式が利用できます。具体的なパッケージを追加するときは用途・対象TFM・公式の対応状況を確認し、選んだバージョンをプロジェクトへ記録します。global.jsonによるSDK選択とNuGetのロックファイルは別の再現性の仕組みです。バージョン指定をlatestという可変状態だけに頼らず、更新時に差分とテストを確認します。

自分のPCで偶然動くことと、他の人が必要な材料から再現できることを分けます。

生成物だけでなく、ソース・プロジェクト設定・必要なSDK・依存関係を管理します。バージョン固定やロックファイルの使い方はプロジェクトの運用方針に合わせます。

確認問題

Q1. usingの追加だけではできないことは？
正解：依存関係は別の設定やコマンドで追加します。

usingはコード中の名前を解決するための宣言であり、部品を取得する操作ではありません。PackageReferenceと復元が済んでいなければ、名前だけを短くしても型は利用できません。

解説：usingが行う役割の1つです。

System.Text.Json.JsonSerializerをJsonSerializerと書けるようにするのが名前空間を取り込むusingの働きです。これは選択肢の「できないこと」には当たりません。

解説：名前空間を利用対象にできます。

using System.Text.Json;のように利用する名前空間を指定できます。ただし名前空間そのものを新しく定義するnamespace宣言とは区別します。

解説：完全修飾名を短くできます。

同じ完全修飾名を何度も書かずに済み、コードを読みやすくできます。異なる名前空間に同じ型名がある場合には、別名や完全修飾名で曖昧さを解決します。

Q2. 通常、Gitへ含めず生成し直す対象は？
解説：ビルド設定として必要です。

.csprojには対象フレームワークや参照関係が記録されています。ソースだけを残しても同じ条件でビルドできないため、入力となる設定も管理します。

正解：ビルドから再生成できる出力です。

binとobjはビルドの出力や途中の情報です。再生成できるので通常は除外し、再生成に必要なソース・設定・依存関係を保存します。

解説：アプリ本体のソースです。

Program.csは人が編集するプログラム本体です。ビルドの入力を捨てて成果物だけを残すと、後で修正やレビューを行えません。

解説：利用手順として保存する価値があります。

実行方法や必要な設定はコードだけからは読み取れない場合があります。READMEは使う人が再現するための説明としてソースと一緒に管理できます。

Q3. using System.Text.Jsonの役割は？
正解：型を解決する名前の扱いに関わります。

usingは型名の検索対象を増やします。JsonSerializerという短い名前がどの型なのかを解決しやすくしますが、その型が参照可能であることは別途必要です。

解説：実行コマンドではありません。

ソースにusingを書いてもプロセスは起動しません。アプリを起動する段階はdotnet runなどのコマンドで行います。

解説：TFMは.csproj側の設定です。

net10.0などの対象は通常.csprojのTargetFrameworkに記録します。名前を短縮する宣言と、利用できるAPIを決めるビルド設定は別の層です。

解説：パッケージ参照・復元とは別です。

System.Text.Jsonは .NET 10アプリで利用できる標準APIです。usingが常に通信を起こしたり新しいパッケージを追加したりするわけではありません。

Q4. 自分の別プロジェクトへの依存はどこへ記録する？
解説：表示処理は依存を追加しません。

Console.WriteLineは起動後に出力する処理です。まだビルドできない参照関係を、アプリ実行時の表示処理で解決することはできません。

正解：ビルド順と参照関係を設定として記録します。

ProjectReferenceは参照するプロジェクトをビルドツールへ知らせます。型を参照できるようにすると同時に、関連するビルド順もツールが判断できる情報になります。

解説：同じソース内のプロジェクト参照で対応できる場合があります。

同じ作業ツリーのライブラリならプロジェクト参照を利用できます。配布用のパッケージ化は別の判断であり、部品を分けるたびに公開する必要はありません。

解説：ビルドツールが依存を解決できません。

コメントは人向けの説明です。コンパイラーが参照先を見つけられるようにするには、機械が読むプロジェクト設定として依存関係を残す必要があります。

Q5. binとobjについて基本的に正しいのは？
解説：ビルドで再生成される内容を直接正本にしません。

成果物を直接編集すると再ビルドで変更が失われます。修正の正本を.csファイルや設定ファイルに置けば、変更履歴から意図を追えます。

解説：ファイルの機密性とは別の分類です。

生成物かどうかと機密情報を含むかどうかは別の軸です。生成物にも秘密を含めないように注意しますが、通常はソースと設定から再生成できます。

正解：再生成可能な出力と再現に必要な入力を分けます。

何を入力すれば同じ成果物を作れるかという再現性の観点です。ソース・設定・必要なロックファイルと、そこから生まれる出力を区別します。

解説：通常は.gitignoreで生成物を除外します。

大量の生成物を管理すると本質的な変更をレビューしにくくなります。ただし配布物の保存方針は別途決められ、通常のソース管理と混同しません。
