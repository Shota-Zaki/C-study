概念と内部の仕組み

複数の非同期処理を安全に扱うには、開始順・完了順・結果の順番・キャンセル・失敗を別々に考えます。WhenAllの一行だけで済ませず、処理を所有する側が何を保証するかまで整理します。

開始と待機を分ける

独立した2つの非同期処理は、両方を呼んでTaskを受け取り、その後Task.WhenAllで待てます。await A(); await B();と書くと通常はAが終わってからBを開始します。WhenAllが返す結果の配列は、完了順ではなく渡したタスクの順です。大量の処理を一度に開始すると接続数やAPI制限にぶつかるので、同時実行数の制限も考えます。

キャンセルはお願いを伝える仕組み

CancellationTokenSourceが停止要求を発行し、CancellationTokenが受け取る側へ伝えます。処理側がトークンを非同期APIへ渡すか、ThrowIfCancellationRequestedなどで確認して初めて停止へ進みます。CPUやスレッドを強制停止する機能ではありません。

失敗・キャンセル・成功を分ける

キャンセルはOperationCanceledExceptionなどで表されます。呼び出し側が要求したキャンセルと、別のタイムアウトを区別できるように扱います。WhenAllは渡したタスクすべての完了を待ち、1つ失敗したから他を自動キャンセルするわけではありません。必要なら共有トークンで方針を実装します。

順番に待つ場合と先にすべて開始する場合

await LoadAAsync(); await LoadBAsync();はAの完了後にBを始めます。var a=LoadAAsync(); var b=LoadBAsync(); await Task.WhenAll(a,b);はAとBを開始してから両方の完了を待ちます。独立したI/Oなら待ち時間を重ねられますが、BがAの結果を必要とする場合は順序を保つ必要があります。

WhenAllが渡されたメソッドを魔法のように開始するのではありません。通常はメソッドを呼び出してTaskを得る時点で処理が始まっています。また並行して進むことと、CPU上で同時に並列実行されることは別です。共有Listなどへの同時変更が安全になるわけでもありません。

結果の順番と失敗時の動作

Task.WhenAll<T>から得るT[]の順番は、渡したTaskの順番に対応します。完了の速かった順ではありません。どの結果がどの入力かを対応付けるときに重要です。WhenAnyは最初に完了したTaskを返す別の操作であり、その戻り値のTaskをさらに待って成功・失敗を確認する必要があります。

WhenAllの対象に失敗があれば全体も失敗しますが、一つの失敗が他の処理を自動的にキャンセルするわけではありません。awaitで観測する例外だけで複数の失敗をすべて記録できるとは限らないため、必要ならWhenAllが返すTaskのException.InnerExceptionsなどを確認します。全件成功が必要か部分成功を認めるかを先に決めます。

キャンセルは協調的な中止要求

CancellationTokenSourceが要求を発行し、そのTokenを下位処理へ渡します。受け取る側が非同期APIへさらに渡す、ThrowIfCancellationRequestedで確認するなどして協力する仕組みです。Cancelを呼べば任意の処理を外部から強制終了できるわけではありません。

操作中止と処理の故障を分けるため、対応するOperationCanceledExceptionを別に扱います。複数の原因のトークンを使う場合は、どの要求に対応した中止かも重要です。CancellationTokenSourceにはリソースがあるためusingで寿命を管理します。キャンセル後にも後片付けを行い、中途半端なデータを成功扱いで保存しないようにします。

同時実行数を制限する

大量のURLに対して一度に全件の処理を開始すると、接続先やメモリ、接続数に負荷が集中します。SemaphoreSlimで入場数を制限する、Parallel.ForEachAsyncの並列度を指定するなど、用途に応じた方法を選びます。単にWhenAllへ大量のTaskを渡すこと自体が流量制御ではありません。

SemaphoreSlimではWaitAsyncが成功してからtry/finallyに入り、finallyでReleaseします。取得前にキャンセルされたのにReleaseすると数が崩れます。同時実行上限を決めるだけで、呼び出し先のレート制限や再試行の安全性がすべて解決するわけではありません。上限と失敗時の方針を別の要件として扱います。

概念をもう一段掘り下げる

複数の処理を始める前に依存関係を確認する

処理Bが処理Aの結果を必要とするなら、Aの完了後にBを始めます。一方、別々の資料を読むなど互いに依存しない処理なら、両方を開始してからまとめて待つことができます。並行化の目的は独立した待ち時間を重ねることであり、全てを同時に実行することではありません。

キャンセルは「もう結果が必要ないので、中止してよい場所で止まってほしい」という要求です。外から安全性を無視してスレッドを強制停止する機能ではありません。要求する側、要求を伝えるもの、要求を確認する処理を分けます。

最小例：開始してからWhenAllで待つ

C# · 独立したコード例
Task<int> first = LoadAsync(10);
Task<int> second = LoadAsync(20);
int[] results = await Task.WhenAll(first, second);
Console.WriteLine(string.Join(",", results));

static async Task<int> LoadAsync(int value)
{
    await Task.Delay(10);
    return value;
}

期待出力は10,20です。LoadAsyncを二回呼び出した時点で、それぞれの処理が始まります。WhenAllが各処理を初めて開始するわけではありません。Task.WhenAll<int>の成功結果の配列は、引数で渡したTaskの順序に対応します。どちらが先に完了したかの順ではありません。

await A(); await B(); A完了後にB開始 BがAに依存する
a=A(); b=B(); await WhenAll(a,b); 両方開始後にまとめて待つ 独立した処理
foreach内でawait 一件ずつ進む 順序や負荷制限を優先
件数を制限して同時開始 一定数まで重ねる 外部APIや資源を保護

よくある間違いと修正

よくある間違い

CancellationTokenSourceはusingで管理します。例外をすべて「キャンセル」として扱わず、通信失敗など別原因の調査情報を残しましょう。

中止要求を下位へ渡していない

修正箇所: 非同期待機へ渡すCancellationToken

修正前

csharp
using var cts = new CancellationTokenSource();
cts.Cancel();
await LoadAsync(cts.Token);
static async Task LoadAsync(CancellationToken token) { await Task.Delay(10); }

修正後

csharp
using var cts = new CancellationTokenSource();
cts.Cancel();
try
{
    await LoadAsync(cts.Token);
}
catch (OperationCanceledException) when (cts.IsCancellationRequested)
{
    Console.WriteLine("キャンセル済み");
}
static async Task LoadAsync(CancellationToken token)
{
    await Task.Delay(10, token);
}
変更理由

引数として受け取るだけでは中止されません。待機を行うAPIまでトークンを渡し、要求に対応した中止を呼び出し側で観測します。

修正後の確認

  • 事前Cancel→中止表示
  • Cancelしない→正常完了
  • catchで成功値へ置換しない

よくある別解と選び方

各結果を順にawaitしても合計は得られるが、開始を先に揃える今回の学習目的を満たす形にする。

よくある間違いと確認箇所

Taskの生成と結果の取得を同じ意味で扱わない。全体が完了する前に未確定の値を使わない。

実務へのつながり：独立した問い合わせをまとめて待つ際、依存関係と資源上限を確認する。

標準

標準：失敗しても他の処理は自動キャンセルされない

成功Taskと失敗TaskをWhenAllで待ち、失敗を捕捉した後に成功Taskの完了結果を表示します。今回は完了済みTaskを使ってタイミングに依存しない確認をします。

  • Task.FromResultとFromExceptionで状態を作る
  • WhenAllが成功結果を返さないことを確認
  • 成功したTaskの状態は失われない

WhenAll全体は失敗になるが、成功側の結果は失われず、自動で取消にもならない。完了済みのTaskを使うので通信やタイマーの順序に依存しない。

よくある別解と選び方

実I/Oで試すのは別の統合確認。まず制御されたTaskで完了・失敗の契約を検査する。

よくある間違いと確認箇所

一つの失敗で他の処理が必ず中断されたと報告しない。中止したいならトークンなど別の協調処理が必要。

実務へのつながり：複数処理の一部成功をどう扱うか、業務の整合性や再試行の方針を決める。

応用

応用：同時入場を2件に制限する

1〜4を非同期に2倍し、SemaphoreSlim(2)で入場数を制限します。結果は入力順で2,4,6,8を表示します。

  • WaitAsync成功後にtryへ入る
  • finallyでReleaseする
  • SelectでTaskを作った後WhenAllする

考え方のヒント

WaitAsyncに成功した後のtry/finallyで、必ずReleaseする。

入力するとlocalStorageへ保存実行・自動採点は行いません
解答例と確認ポイント
csharp
using var gate = new SemaphoreSlim(2);
Task<int>[] tasks = Enumerable.Range(1, 4).Select(ProcessAsync).ToArray();
int[] values = await Task.WhenAll(tasks);
Console.WriteLine(string.Join(",", values));
async Task<int> ProcessAsync(int value)
{
    await gate.WaitAsync();
    try
    {
        await Task.Delay(10);
        return value * 2;
    }
    finally
    {
        gate.Release();
    }
}

想定出力

2,4,6,8
  • セマフォへ入れる処理を最大2件にするが、結果配列の順番はTaskの入力順である。
  • finallyによって入場後の成功・失敗のどちらでも枠を返す。
  • これは小規模な同時実行制限の例で、無制限な件数のTaskをすべて生成しない設計やキャンセル伝播は別途追加する。
入力 / 条件期待結果
1〜42,4,6,8
上限1へ変更結果は同じ、待機は直列化
処理中に例外枠をfinallyで返し、WhenAllは失敗

処理と結果の読み解き

ゲートを通れた処理だけが実作業へ進む。WhenAllの結果は渡したTaskの順なので2、4、6、8。ゲートは作業の同時数を制限し、全Taskの生成数を自動で減らすわけではない。

よくある別解と選び方

大きな入力ではチャネルなど生産側も制御する設計を検討する。ここでは四件で制御範囲を把握する。

よくある間違いと確認箇所

取得前に中止された場合までReleaseすると、許可数を壊す。取得の成功後から解放責任を持つ。

実務へのつながり：外部サービスやファイル資源へ過大な同時要求を送らない設計につながる。

確認問題

Q1. WhenAllに1つの失敗が含まれると、他のタスクは？
解説：自動停止の保証はありません。

WhenAllは全ての完了をまとめて観察する仕組みです。一つが失敗しても、他の処理へ自動的に中止要求を送る契約ではありません。

解説：タスクは追跡可能な処理として残ります。

既に開始した処理はそのTaskで追えます。失敗した仲間があることを理由に、実行や保持している情報が消えるわけではありません。

正解：停止も必要ならトークンなどで方針を実装します。

残りも止めたいなら共有Tokenなどへ中止を要求し、各処理が協力する設計にします。要求後も終了と例外を最後まで観察します。

解説：すでに発生した副作用も取り消されません。

途中でファイルへ書いたなどの副作用は、WhenAllの失敗で自動的に巻き戻りません。取り消しや整合性は業務と保存の仕組みで設計します。

Q2. CancellationTokenの停止要求は？
解説：強制的なスレッド終了の仕組みではありません。

キャンセルは協調的な要求で、任意のOSスレッドを強制終了する命令ではありません。途中の状態を壊さず止められる位置を処理側で作ります。

解説：トークンを渡す・確認する対応が必要です。

同期の長いループなら定期的にTokenを確認する必要があります。引数にTokenが存在するだけで全命令へ自動挿入されるわけではありません。

解説：そのような命令ではありません。

ネットワーク機器の接続を切る操作ではありません。対応する通信APIへTokenを渡し、その処理が提供する中止の契約を使います。

正解：対応する非同期APIへの伝播も重要です。

ThrowIfCancellationRequestedや対応APIへの引き渡しで要求を観察します。受け取ったTokenを下位処理へ渡し忘れないことが重要です。

Q3. WhenAll<T>の結果配列の順番は？
解説：値を並べ替える操作ではありません。

WhenAllはソート操作ではありません。結果が20,10となるTaskをその順で渡せば、成功結果も20,10の対応になります。

正解：各入力Taskに対応した順番で結果を返します。

入力の配列や引数の順と結果の位置が対応します。どのTaskが先に終わったかとは独立なので、結果を元の要求と結び付けられます。

解説：完了順とは限りません。

後に渡したTaskが先に完了しても、その結果が配列の先頭へ移るわけではありません。完了順で処理したい場合は別の構成を考えます。

解説：順番の契約があります。

順序の契約があるので偶然ではありません。開始順・完了順・入力Taskの並びという三つを分けて説明します。

Q4. CancellationTokenSource.Cancelは何をする？
正解：トークンを渡し、受け取る側が中止へ協力する設計です。

Sourceが要求を出し、Tokenを持つ処理が状態を確認します。Cancelの後に処理がいつ止まるかは、確認位置と対応APIの動作に依存します。

解説：下位処理がトークンを確認しなければ止まらない場合があります。

要求を無視する処理は動き続ける場合があります。強制終了で状態が壊れる方式ではなく、後始末できる協調的な停止を設計します。

解説：例外処理の代わりではありません。

キャンセル自体もOperationCanceledExceptionなどで観察する場合があります。例外を消す操作ではなく、完了の意味を中止として区別します。

解説：キャンセルと成功は異なる完了状態です。

成功、失敗、キャンセルは異なる状態です。利用者が中止した処理を保存成功などと表示しないよう、呼び出し側で区別します。

Q5. SemaphoreSlimのReleaseを置く基本位置は？
解説：取得していない枠を増やしてしまいます。

入場前にReleaseすると、まだ取得していない枠を返すことになります。同時数を守る仕組みを壊さないよう、取得と返却を対応させます。

正解：入場後の成功・失敗のどちらでも返却します。

WaitAsyncが成功してからtryへ入り、finallyで返せば内部の例外でも枠が戻ります。資源の取得に成功したかを構造で表すことが大切です。

解説：失敗時に枠が返らず後続が止まるおそれがあります。

内部処理が例外になると返却されず、後続が枠を待ち続ける可能性があります。成功時だけでなく失敗時にも必ず後始末するfinallyを使います。

解説：取得できなかった場合にReleaseしてはいけません。

WaitAsync自体がキャンセルされた場合は枠を取れていません。無条件に外側でReleaseすると過剰返却になるため、取得後だけfinallyの対象にします。

理解チェックと公式資料

  • 開始順と結果順を説明できる
  • WhenAllの失敗と個別Taskを区別できる
  • トークンを末端へ伝播できる
  • 取得成功時だけ枠を返せる
