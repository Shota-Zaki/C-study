Lesson 29 · Chapter 8

ASP.NET Coreの最小API

Minimal APIの要求経路。

.NET 10 / C# 14
本文・演習詳細解説
重要エンドポイントはHTTPメソッドとパスの組み合わせで、どの処理を呼ぶかを決めます。

ここからはHTTPを受け取る側を作ります。アプリ起動時に登録する処理と、要求が届くたびに実行される処理を分け、URLの値が引数へ渡るまでを追います。

要点

  • ルートとハンドラーの関係を説明する
  • ローカルでJSONを返すAPIを起動する
重要

Minimal APIはBuilder→Build→Map→Runの起動処理と、要求ごとに実行されるハンドラーを分けて読みます。HTTPメソッドとルートを契約として扱います。

C#
app.MapGet("/hello", () => new { message = "Hello" });

アプリを起動して処理を登録する

Web APIは、HTTP要求をC#の処理へ結び付け、その結果をステータス・ヘッダー・本文として返す入口です。MapGetを登録する時点と、ブラウザから要求が来てハンドラーが実行される時点を分けて理解します。

コンソールからWebへ

ASP.NET Coreは.NETのWebアプリ基盤です。Minimal APIでは小さなAPIを少ない記述で作れます。新しいフォルダーでdotnet new web -n StudyApi -f net10.0を実行し、そのProgram.csを例に置き換えます。コンソール用とは異なり、.csprojのSDKはMicrosoft.NET.Sdk.Webです。

起動時と要求時の二つの時間軸

WebApplication.CreateBuilderは設定やサービス登録の準備、Buildはアプリの構築、MapGetなどは経路と処理の対応付けです。app.Runを呼ぶとサーバーとして待ち受けます。MapGet("/health",()=>...)のラムダは、登録した瞬間に毎回のレスポンスを作るのではなく、対応する要求が来たときに実行されます。

コンソールアプリのように上から一回だけ流れて終了するモデルから、起動後に多数の要求を処理するモデルへ変わります。起動時に一つ作ったオブジェクトが全要求で共有されることもあるため、メソッドの中だけでなく変数をどこで作ったかを確認します。停止はターミナルのCtrl+Cで行います。

起動時にはURLと処理を結び付けます。ハンドラーの中身は、対応する要求が来たときに実行されます。

MapGetの行が実行された時点で、全てのリクエスト処理を実行するわけではありません。起動時に一度だけ行う準備と、要求ごとに行う処理を区別します。

最小APIへGETを送る

csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/hello", () => new { message = "Hello CSharp" });
app.MapGet("/lessons/{id:int}", (int id) => new { id, title = $"Lesson {id}" });

app.Run("http://127.0.0.1:5080");

GET /lessons/3が来たとき、/lessons/{id:int}という経路と対応させます。

この経路のint制約はルーティングの条件です。整数であることと、アプリが許可するIDであることは別なので、必要な範囲や存在の確認は処理側で行います。

想定出力

GET /hello → 200、{"message":"Hello CSharp"} GET /lessons/3 → 200、{"id":3,"title":"Lesson 3"}

処理順

  1. CreateBuilderとBuildでWebアプリを準備する。
  2. MapGetはその時点で応答を返すのではなく、リクエスト時の処理を登録する。
  3. Runで待ち受け、該当URLへのGETでJSONを返す。

起動するAPIと要求の入口

HTTPリクエストを受け取るAPI

前のレッスンではHttpClientから要求を送りました。ASP.NET Coreは、HTTP要求を受け取り、経路を選び、入力を型へ変換し、結果を応答へ変えるWebアプリケーションの仕組みを提供します。Minimal APIは、必要な経路と処理を比較的少ない構造から記述できる方式です。少ないコードで書けることと、入力検証や運用の設計が不要になることは別です。

エンドポイントは、ある経路とHTTPメソッドに対応する処理の窓口です。ルーティングは要求を適切なエンドポイントへ対応付ける処理、ハンドラーは選ばれた後に実行する処理です。ミドルウェアは要求・応答の途中に挟まる共通処理です。例外処理、認証、ログなどを流れの途中へ配置できます。

最小APIの完全なProgram.cs

このコードはコンソール用ではなく、Microsoft.NET.Sdk.Webを使うWebプロジェクトへ置きます。起動中はHTTP要求を待つため、自動で終了するコンソール例とは違います。

C# · Webプロジェクト用
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/hello", () => Results.Ok(new { message = "Hello, C#" }));

app.Run();

匿名型new { message = ... }は、名前付きの専用classを宣言せず、その場で読み取り用のプロパティをまとめる構文です。この例では応答用の小さなデータを表しています。繰り返し使う契約なら名前付きの型にすると管理しやすくなります。

ターミナルで入力するコマンド
dotnet new web -n HelloApi -f net10.0
cd HelloApi

生成されたProgram.csを上のコードへ置き換え、保存してから次を使います。

ターミナルで入力するコマンド
dotnet build
dotnet run --no-launch-profile -- --urls http://127.0.0.1:5080

127.0.0.1は同じ端末を表すループバックアドレスです。5080はポート番号で、同じ端末のどの待受先へ送るかを区別します。この練習は端末内のHTTPに限定し、秘密情報を送らず、外部公開しません。公開環境ではHTTPS、認証、権限、ネットワーク構成などを別途整備します。

URLと引数を対応させる

URLと処理を結び付ける

MapGet("/hello", ...)はGET /helloへの処理を登録します。ルートの{id:int}は整数の経路パラメーターです。戻り値のオブジェクトはJSONとして応答できます。CreateBuilderで構成を準備し、Buildでアプリを作り、ルートを登録した後にRunで待ち受けを開始します。

HTTPメソッド・パス・データの位置

GET /items/3ではGETが操作の種類、/items/3が対象を表すパスです。ルート値、?page=2のようなクエリ、JSON本文、ヘッダーには別の役割があります。Minimal APIはハンドラー引数をこれらやDIサービスへ結び付けますが、どこから値が来るかを型とルート定義から読み取れることが重要です。

GETは取得を目的にし、データ作成はPOSTなど、HTTPの意味に合う設計にします。ブラウザのURL欄で開くと通常はGETになるため、POST本文の検証にはcurl.exeやHTTPクライアントが必要です。ルートパラメーター名と引数名の対応も確認し、値が取れない問題を型変換の問題と混同しないようにします。

GETでもアクセスログや観測メトリクスなどの付随処理はあり得ます。ただしタスク完了や購入のように、利用者が要求する業務上の更新をGETへ割り当てないという区別が必要です。

URLの経路、クエリ文字列、JSON本文は、別々の入力元です。

呼び出し側と受け取り側で位置をそろえます。/lessons/3を想定するAPIへ?id=3を付けるだけでは、同じ経路を呼んだことにはなりません。

バインドと業務検証は別

/items/{id:int}のint制約は、ルートが一致するかを決める制約です。abcはこのルートへ一致しないため通常404になります。一方/int/{id}のルート値をint引数へバインドする場合、パスが一致してから型変換に失敗し400となるケースがあります。404と400の違いを意図せず混ぜないようにします。

intへ変換できてもidが0や負数なら、業務的には許さない場合があります。これはハンドラーやサービスの検証です。フレームワークのバインド機能が商品の存在や所有権まで確認するわけではありません。技術的な型変換と業務上の有効性を別の段階に置きます。

実コード例

実例：稼働確認APIと商品取得API

ASP.NET Core WebプロジェクトのProgram.csに置くコードです。サーバー起動が必要です。

C# · Webプロジェクト
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
app.MapGet("/health", () => Results.Ok(new { status = "ok" }));
app.MapGet("/products/{id:int}", (int id) =>
    id == 1
        ? Results.Ok(new { id = 1, name = "Notebook" })
        : Results.NotFound());
app.Run();

このコードの図解：Minimal APIの要求経路

想定出力・HTTP応答

GET /health → 200 / {"status":"ok"}
GET /products/1 → 200 / {"id":1,"name":"Notebook"}
GET /products/9 → 404

  1. MapGetGETとパスに対応する処理を登録する
  2. {id:int}ルートの値をintとして扱う制約
  3. Resultsステータスと本文を含むHTTP応答を作る
条件を変えた場合

よくある間違いと修正

よくある間違い

ASP.NET CoreのAPIは、HTTP要求を受け付けるサーバーアプリです。静的HTMLの配信とは異なり、APIの処理を実行する.NETのプロセスが必要です。

取得用ルートで状態を変更する

修正箇所: HTTPメソッドの登録

修正前

csharp
int count = 0;
app.MapGet("/increment", () => ++count);

修正後

csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
int count = 0;
app.MapGet("/count", () => Results.Ok(new { count = Volatile.Read(ref count) }));
app.MapPost("/increment", () => Results.Ok(new { count = Interlocked.Increment(ref count) }));
app.Run("http://127.0.0.1:5080");
変更理由

GETは取得として扱い、状態を変える操作をPOSTへ分けます。共有カウンターは単純なcount++では競合するため、この整数加算だけをInterlockedで保護します。永続化も認証もなく、本番公開用のカウンターではありません。

修正後の確認

  • GET /countは値を変えない
  • POST /incrementで1増加
  • GET /incrementはPOST専用のため405

複数の要求で共有される状態

教材ではローカル限定で動かす

dotnet runで起動したら、ブラウザでhttp://127.0.0.1:5080/helloを開きます。停止はターミナルでCtrl+Cです。起動しただけではWebサイトのような画面は出ず、APIのJSONが返ります。教材は127.0.0.1にバインドし、他の端末へ公開しません。外部公開にはHTTPS、認証、権限、監視など別の設計が必要です。

ミドルウェア・レスポンス・待ち受け範囲

ミドルウェアは要求の前後を処理するパイプラインです。例外処理、認証、ログなどを順に組み合わせます。Useで登録した処理はnextを呼ぶことで後続へ進み、戻ってきた後に応答側の処理を行えます。順序によってどの処理を包むかが変わるため、登録順が動作の一部です。

Results.OkなどはHTTPレスポンスの意図を表します。学習コードはhttp://127.0.0.1:5080で自分のPCだけに待ち受け、別の端末へ公開しない前提です。0.0.0.0へ変えるだけで安全な公開APIになるわけではありません。認証、TLS、入力制限、運用設定は公開前に別途必要です。

よくある別解と選び方

よくある間違いと確認箇所

コンソール用プロジェクトへ部分だけ貼り、ASP.NET Coreの参照があると考えない。SDKと待ち受けURLを確認する。

実務例：簡単な状態確認用の入口から、HTTPサーバーとしての接続を学ぶ。

標準

標準：ルート値とクエリ値を分ける

GET /greet/{name}?repeat=2でnameを2回並べた配列を返します。repeatは省略時1、1〜3以外は400とします。

  • nameはルート、repeatはクエリ
  • int?で省略を表す
  • 検証後にEnumerable.Repeat
開始コード
csharp
// 標準：ルート値とクエリ値を分ける
// 課題とテストケースを読んで、自分で実装してください。
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
// ここにエンドポイントを実装
app.Run("http://127.0.0.1:5080");

入力例・前提条件

パスのnameとクエリrepeat。省略時1、許可範囲1〜3。

考え方のヒント

入力位置の違いを分け、repeatの変換後に範囲を検証する。

入力するとlocalStorageへ保存
解答例と確認ポイント
csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
app.MapGet("/greet/{name}", (string name, int? repeat) =>
{
    int count = repeat ?? 1;
    if (count is < 1 or > 3) return Results.BadRequest(new { error = "repeatは1〜3" });
    return Results.Ok(Enumerable.Repeat($"Hello, {name}", count).ToArray());
});
app.Run("http://127.0.0.1:5080");

想定出力

GET /greet/Aki?repeat=2 → 200 ["Hello, Aki","Hello, Aki"] GET /greet/Aki → 200 ["Hello, Aki"] GET /greet/Aki?repeat=0 → 400
  • パスのnameとクエリのrepeatは別の場所から取得する。
  • repeat省略をnullで受け、アプリ側の既定値1を適用する。
  • repeat=abcはintへのバインドに失敗し、今回のハンドラー内の範囲検証より前の失敗になる。
入力 / 条件期待結果
repeat省略1件
repeat=33件
repeat=4400

処理と結果の読み解き

nameを必要回数だけ並べるが、0や4なら400へ分岐し生成しない。クエリ自体が整数に変換できない場合は、独自の範囲判定より前に失敗し得る。

よくある別解と選び方

ループで配列を作っても、Enumerable.Repeatを使ってもよい。要求の契約と範囲が一致するかを確認する。

よくある間違いと確認箇所

文字列のrepeatを数値として受け取れたことだけで巨大な回数を許さない。範囲制限には資源利用を抑える意味もある。

実務例：パス・クエリ・本文の入力源を区別し、型変換と業務条件を分ける。

応用

応用：同じパスでもHTTPメソッドを区別する

/messageへGETなら固定のメッセージ、POSTなら本文TextをTrimして返します。空白は400とします。保存はしません。

  • GETとPOSTを別のMapへ登録
  • 本文用DTOはstring?
  • POSTの成功は変換結果を返すだけなので200
開始コード
csharp
// 応用：同じパスでもHTTPメソッドを区別する
// 課題とテストケースを読んで、自分で実装してください。
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
// ここにエンドポイントを実装
app.Run("http://127.0.0.1:5080");

入力例・前提条件

/messageへGETとPOST。POSTの本文TextはTrimし、空白を拒否。

考え方のヒント

同じパスでもHTTPメソッドで別の処理を登録する。

入力するとlocalStorageへ保存
解答例と確認ポイント
csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();
app.MapGet("/message", () => Results.Ok(new { text = "read" }));
app.MapPost("/message", (MessageInput input) =>
{
    string text = input.Text?.Trim() ?? "";
    return text.Length == 0
        ? Results.BadRequest(new { error = "textは必須" })
        : Results.Ok(new { text });
});
app.Run("http://127.0.0.1:5080");
public record MessageInput(string? Text);

想定出力

GET /message → 200 {"text":"read"} POST /message 本文{"text":" C# "} → 200 {"text":"C#"} POST /message 本文{"text":" "} → 400
  • パスだけでなくメソッドもルーティングの入力である。
  • 既存リソースを新規作成していないので、201やLocationを返す理由はない。
  • ブラウザURL欄だけではPOST本文を送れないため、HTTPクライアントで検証する。
入力 / 条件期待結果
GET固定応答
POST Text空白400
PUT /message今回未登録なので405

処理と結果の読み解き

GETは固定メッセージを返し、POSTは入力を加工して返す。POSTが必ず永続保存を意味するわけではなく、この課題の契約では保存しない。

よくある別解と選び方

DTOの検証を別メソッドへ分けてもよいが、正常値と空白値で同じ応答になることを確認する。

よくある間違いと確認箇所

GETで本文入力を前提にしたり、保存しない処理を201作成として返したりしない。

実務例：HTTPのメソッドと、個々のエンドポイントの処理契約を合わせて設計する。

確認問題

Q1. MapGetの主な役割は？
正解：外から届くリクエストを処理する側の登録です。

MapGetは指定したパスへのGET要求と、その要求を処理するデリゲートを結び付けます。登録時と、後で要求を受けて呼び出す時を区別します。

解説：外部へ送る側はHttpClientなどです。

要求を外へ送るのはクライアント側の仕事です。MapGetはサーバー側で要求を受け取るための登録なので、通信の向きが逆です。

解説：保存基盤の作成ではありません。

ルート登録だけではテーブルや保存ファイルは作られません。返すデータをどこに保存するかは、メモリ・ファイル・DBなど別の設計です。

解説：ブラウザの起動を保証する操作ではありません。

待ち受けを開始しても、必ずブラウザーが起動するわけではありません。開発ツールの起動設定と、サーバーのルート登録を分けて考えます。

Q2. この例の127.0.0.1での待ち受けは？
解説：外部へ公開する設定ではありません。

127.0.0.1はそのコンピューター自身を指すループバックアドレスです。これだけで外部端末から利用できる公開状態にはなりません。

正解：学習時に公開範囲を抑えるための設定です。

同じPCの別ターミナルやブラウザーからlocalhost側のAPIを確認できます。ローカル学習用と、外部へ公開するサーバー設定を区別します。

解説：Steamとは関係しません。

待ち受けアドレスはネットワーク上でどこから要求を受けるかの設定です。アプリの販売先や特定の配布サービスを指定する設定ではありません。

解説：別端末にとって127.0.0.1はその端末自身です。

スマートフォンで127.0.0.1を開くと、そのスマートフォン自身へ向かいます。PC側のローカルアドレスを指す共通の名前ではありません。

Q3. MapGetへ渡したラムダが主に実行されるのは？
解説：プロジェクト設定の保存だけで要求は発生しません。

.csprojの保存はビルド条件の変更であり、クライアントからのHTTP要求ではありません。起動・登録・要求処理の各段階を分けて追います。

解説：登録処理と要求処理は別の時間軸です。

MapGetという登録の呼び出し自体は起動時に行いますが、渡したラムダの本体は通常その場では処理しません。後から呼べる処理を渡しています。

正解：ルートに一致した要求に対して呼び出されます。

メソッドとパスが一致し、必要な引数が用意されるとハンドラーが呼び出されます。1回の登録を、多数の要求に対して利用できます。

解説：依存の復元はHTTP要求処理ではありません。

復元は必要な依存関係を利用できる状態にするビルド準備です。サーバーが要求を処理する段階とは異なります。

Q4. /items/{id:int}へ/items/abcを要求した場合の基本動作は？
解説：変換不能な値を勝手に0へ置き換える例ではありません。

int制約に一致しない文字列を自動的に0として処理する契約ではありません。制約は候補のルートに一致するかどうかを選ぶために使われます。

解説：リソース作成の応答ではありません。

201は新しいリソースを作った成功応答です。ルートに一致しない要求であり、この例では作成処理は行いません。

解説：パスの制約とJSON本文は別です。

URL中のパス要素とJSON本文は別の入力位置です。ルート制約の失敗を、本文のシリアル化で修復することはありません。

正解：int制約はルート一致の判定に使われます。

このルートだけなら、abcはint制約に一致せず通常404になります。クエリ引数の型変換失敗で400になる例とは処理段階が違います。

Q5. GETに状態更新を入れない主な理由は？
正解：自動取得や再読み込み等で意図せぬ変更を起こさない設計にします。

GETは取得の意図を示すため、再読み込みや自動取得が業務データの変更にならない設計にします。アクセス記録などの付随処理と、要求した業務更新は区別します。

解説：HTTPメソッドを変えただけでは認証は追加されません。

POSTを選んだだけでは本人確認や操作権限のチェックは行われません。HTTPメソッドの意味と認証・認可の仕組みを別々に実装します。

解説：暗号化はHTTPS等の通信設定に関係します。

GETもPOSTもHTTPだけなら通信は暗号化されません。HTTPSによる経路保護と、URLやログへ秘密を出さない設計が必要です。

解説：実装は可能でもHTTPの意味に反します。

C#では更新処理を書けますが、書けることとHTTPの契約に合うことは別です。自動クライアントが取得と解釈する操作へ更新を混ぜないようにします。
