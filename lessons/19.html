遅延実行と集計

クエリ定義と列挙の時点。

.NET 10 / C# 14
本文・演習詳細解説
重要遅延実行のクエリは、作った時点ではなく列挙した時点のデータを読むことがあります。

Whereを書いた時点と、結果を表示した時点の間で元データが変わるとどうなるでしょうか。時間の順番に沿って、クエリの定義・列挙・ToListによる保存を分けます。

要点

  • 遅延実行とToListの差を確認する
  • Any・Sum・GroupByを使い分ける
重要

IEnumerable<T>のクエリは列挙時に処理されるものがあります。再列挙のコスト、元データの変化、集計APIの空シーケンス時契約を確認します。

C#
// IEnumerableは再列挙できる場合があるが、コストと副作用を確認

クエリを作る時点と結果を読む時点

クエリを書いた時点とデータを読む時点は一致するとは限りません。この単元では、遅延実行・実体化・集計を分けて扱い、「同じ式なのに二回目の結果が違う」理由を説明できるようにします。

クエリは結果ではなく手順の場合がある

WhereやSelectは、多くの場合その場で全結果を保存しません。foreachなどで列挙されると実際に処理します。クエリを作った後に元のListへ要素を追加すると、後から列挙した結果に追加分が含まれることがあります。今の結果を保持したいならToListやToArrayで具体化します。

定義・列挙・実体化という三段階

Whereなどは列挙の規則を保持し、foreachやToArrayなどで実際に列挙されると要素を読みます。ListへWhereをかけた後、列挙前に要素を追加すれば、その要素も条件判定の対象になります。クエリの変数へ代入したから、その時点の結果を保存したとは限りません。

ToListやToArrayはその場で列挙して結果をコレクションへ保存します。以降元Listへ要素を追加しても、既存の結果配列の件数は増えません。ただし要素自体が可変の参照型なら参照先は共有されることがあります。実体化と深いスナップショットは別の要求です。

元データの追加前後で結果を比べる

csharp
var values = new List<int> { 1, 2, 3 };
var query = values.Where(x => x >= 2);
var snapshot = query.ToList();
values.Add(4);
Console.WriteLine(string.Join(",", query));
Console.WriteLine(string.Join(",", snapshot));
Console.WriteLine(query.Sum());

queryを作る操作とsnapshotを作る操作は、同じ時点の同じ処理ではありません。

追加後にqueryを列挙すると2,3,4ですが、すでに作ったsnapshotは2,3です。この例の要素はintです。ToListが一般に要素オブジェクトまで深く複製するという意味ではありません。

想定出力

2,3,4 2,3 9

処理順

  1. queryは2以上を選ぶ手順。snapshotはこの時点の2,3を保持する。
  2. 元のListに4を追加する。
  3. 後からqueryを列挙すると4が含まれ、Sumも9になる。

クエリと保存済み配列の違い

csharp
var values = new List<int> { 1, 2, 3 };
var query = values.Where(x => x >= 2);
int[] snapshot = query.ToArray();
values.Add(4);
Console.WriteLine(string.Join(",", query));
Console.WriteLine(string.Join(",", snapshot));
Console.WriteLine(query.Sum());

出力

2,3,4 2,3 9
段階値・状態読み解き
Where定義条件x>=2を保持まだ結果を配列へ保存しない
ToArray2,3を配列化この時点の数値を保存
Add(4)元Listが1,2,3,4既存配列は変化しない
query列挙2,3,4変更後の元Listを読む
Sum2+3+4=9queryを集計のため再列挙

IEnumerableとyield return

IEnumerableと列挙時の処理

IEnumerable<T>は、T型の値を順に取り出せるという約束です。配列のように既に存在する値を読むことも、必要になるたびに値を計算することもできます。foreachは列挙子と呼ばれる進行役を使って、次の要素へ進み、現在の要素を読みます。一般的にはGetEnumeratorで列挙子を取得し、MoveNextで次へ進み、Currentで値を読みます。配列などではコンパイラーが別の効率的な形へ変換する場合もあります。

列挙子は「今どこまで読んだか」という状態を持ちます。IEnumerableとIEnumeratorを同じものと考えないでください。前者は読み進める仕組みを提供する側、後者は一回の読み進めを管理する側です。

yield returnで一つずつ値を渡す

C# · 独立したコード例
Console.WriteLine("A:列を取得");
IEnumerable<int> numbers = CreateNumbers();
Console.WriteLine("B:列挙を開始");
foreach (int number in numbers)
{
    Console.WriteLine($"受取:{number}");
}

static IEnumerable<int> CreateNumbers()
{
    Console.WriteLine("C:生成開始");
    yield return 10;
    Console.WriteLine("D:次へ進む");
    yield return 20;
}

期待出力は次の順です。

想定される出力 / データ
A:列を取得
B:列挙を開始
C:生成開始
受取:10
D:次へ進む
受取:20

yield returnは、列挙している側へ一つ値を渡し、次に要求されたときに続きから進める構文です。通常のreturnのように処理全体を終了するわけではありません。コンパイラーは途中の位置や必要なローカル変数を保持できる形へ変換します。こうした「状態と、次にする処理を保持する仕組み」を状態機械と呼びます。asyncでも別の目的で似た発想が使われますが、yield自体が非同期になるわけではありません。

実コード例

実例：検索条件と検索結果を分ける

偶数を取るクエリと、先に取得した結果の違いを確認します。

var snapshot = query.ToList();

Console.WriteLine($"再評価: {string.Join(", ", query)}");
Console.WriteLine($"保存済み: {string.Join(", ", snapshot)}");

想定出力

再評価: 2, 4
保存済み: 2

処理と値の変化

  1. query条件付きの列挙を定義する
  2. snapshot追加前に列挙して2だけを保存する

条件を変えた場合

もう一度query.ToList()すると、変更後の結果2, 4を持つ別のListができます。

サンプル一式 Program.cs

列挙の回数と必要なデータ量

何回列挙しているかを見る

同じクエリにCount、Sum、foreachを続けると、同じ処理が繰り返される場合があります。要素が存在するかだけならAnyが意図を表します。空の列にFirstを呼ぶと失敗します。FirstOrDefaultは既定値を返しますが、intの0が本物の0なのか「なかった」のか区別できるかも考えます。

IEnumerableのクエリをAny、Count、foreachなどで繰り返し読む場面を考えます。

実際のコストは元の型や最適化によって変わりますが、毎回の列挙で処理や外部アクセスが再び起き得る点が重要です。一度固定する必要があるときにToListなどを検討します。

遅延実行でも全件が必要な演算がある

Whereは条件を確認しながら順次要素を返せます。一方OrderByは全体の順序を決めるため、列挙を始めた後に元の要素を集めて並べ替える必要があります。遅延実行だから常に一件ずつ・メモリ不要という意味ではありません。GroupByもグループを作るための保持が必要になります。

大量データでTake(10)を付ければ常に先頭10件だけを読むと考えるのも誤りです。OrderBy(...).Take(10)なら全体を比較する必要があります。どの演算が全体を必要とするか、実行先がメモリかDBかを確認し、必要なら件数と時間を測定します。

複数回の列挙と副作用

同じIEnumerableにCount、Sum、foreachを順に呼ぶと、元の処理を複数回実行する場合があります。元データがDB、ファイル、生成器ならコストや結果が変わる可能性があります。クエリ内で表示やカウントをする副作用があると、予想外に何度も実行されます。

何度も同じ集合を読む必要があり、件数が適切なら一度ToArrayして共有する方法があります。ただし全部をメモリへ載せるコストとの交換です。一回のループで必要な集計を済ませる選択肢もあります。何でもToListするのではなく、いつのデータを何回読むかという要件を先に確認します。

よくある間違いと修正

よくある間違い

ToListによる固定化も要素オブジェクトの深いコピーではありません。List<Product>の各Productが可変なら、その中身の変更は結果へ見えることがあります。

空の平均を計算して例外になる

修正箇所: 集計前の空集合の扱い

修正前

csharp
int[] scores = Array.Empty<int>();
Console.WriteLine(scores.Average());

修正後

csharp
using System.Globalization;
int[] scores = Array.Empty<int>();
double? average = scores.Length == 0 ? null : scores.Average();
Console.WriteLine(average?.ToString("0.##", CultureInfo.InvariantCulture) ?? "データなし");
変更理由

平均が定義できない空集合を欠損のnullとして表現し、表示時に区別します。0点の平均とデータがない状態を同じ0にしてしまわない修正です。

修正後の確認

  • 空→データなし
  • 0だけ→0
  • 60,80→70

集計と空のデータ

GroupByはグループを作る

GroupBy(x => x.Category)はカテゴリごとに要素をまとめます。それぞれのKeyと、そのグループ内の要素を使って集計します。この例は小規模なメモリ上のデータを集計します。大量データやDBでは、いつ何件を読み込むのかを別途測定し、無条件のToListを増やしすぎないようにします。

集計と空データの契約

Countは件数、Anyは一件でも条件を満たすか、Sumは合計を返します。存在確認だけならAnyの方が意図が明確です。AverageやFirstなどは対象が空の場合の動作を考える必要があります。intの空列にAverageを呼ぶと例外になり、FirstOrDefaultなら既定値を返すため0が「なかった」と「実際に0だった」を混同させることがあります。

Singleは一件だけであることを期待し、0件や複数件を拒否します。Firstは最初の一件を選ぶだけです。ユーザーIDの一意性を検査したい場面と、新着一覧から最初を取る場面を同じ扱いにしないでください。空の平均を0とするか欠損とするかは業務仕様として決めます。

ここではLINQ to Objectsの空のint列を対象にします。0件の場合に返る値と、そもそも求められない値を区別します。

「0なら正常な結果」か「0件なので計算できない」かは別の意味です。Averageなどを呼ぶ前に、空のときのアプリの振る舞いを決めます。

確認問題

Q1. Whereでクエリを作った後、列挙前に元のListへ条件に合う要素を追加すると？
正解：遅延実行なので実際の列挙時に元データが読まれます。

Whereは結果をその場で固定保存しません。foreachやToListなどで列挙するときに追加後のListを読むため、一致する追加要素も現れます。

解説：結果が固定されているとは限りません。

作成時の一覧を保存したいなら、変更より前にToListなどを呼びます。クエリを変数に入れただけで古い結果が固定されると思わないでください。

解説：Whereが自動的に結果を保存するわけではありません。

キャッシュは結果を保持して再利用する仕組みです。通常のWhereは自動キャッシュではなく、再列挙時には現在の入力を読む場合があります。

解説：通常は有効なコードです。

Listへ追加してから列挙する順序自体は有効です。列挙中に同じListを変更するケースとは分けて判断します。

Q2. 条件に合う要素が1件でもあるかだけ確認するには？
解説：並び替えは不要です。

存在だけなら順位を付ける必要はありません。全体を並べ替える作業を増やさず、目的が伝わるAnyを使います。

正解：存在確認の意図を直接表せます。

条件に合うものを見つけた時点でtrueと判断できます。件数全てや最初の要素そのものが不要な場面の意図を直接表します。

解説：複数の列を平坦化する必要はありません。

SelectManyは入れ子の複数の列を平坦化する操作です。この質問では存在を調べるだけなので、データの形を変える必要がありません。

解説：通常の存在確認を例外に頼る必要はありません。

Firstは対象がないと例外になります。存在しないことが通常の分岐なら、Anyでboolを受け取る方が目的に合います。

Q3. Where定義後、列挙前に元Listへ一致要素を追加すると？
解説：LINQ to Objectsが自動的に並列化されるわけではありません。

通常のLINQ to ObjectsのWhereは自動で別スレッドへ処理を送るものではありません。列挙する時点と並列化を混同しています。

正解：メモリ内Listの現在の内容を列挙すると追加分も見えます。

クエリが参照するListへ列挙前に追加したので、現在の内容として読めます。実行時点をToListの前後で変えると結果の違いを観察できます。

解説：Whereだけでは通常結果を保存しません。

Whereだけの宣言は、過去の結果を凍結する指示ではありません。同じクエリでも入力を変えた後の再列挙で結果が変わり得ます。

解説：列挙中の変更とは区別が必要です。

列挙を始める前の変更と、foreachが進行している途中の変更は別です。後者ではListの列挙子が変更を検出して失敗する場合があります。

Q4. 件数が必ず一件であることまで要求する取得は？
解説：存在のboolだけで対象を返しません。

Anyは存在の有無だけを返し、一件か複数件かを区別しません。呼び出し側が欲しいのが要素そのものか、性質のboolかを分けます。

正解：0件と複数件を拒否し、一件のみを要求します。

一件ならその要素を返し、0件や複数件なら制約違反として失敗します。データが必ず一意という仕様を確認したいときに使います。

解説：最大一件に制限して重複を隠す場合があります。

二件以上あっても先頭一件だけに切るため、重複という問題を隠します。一件だけ存在することを要求する操作ではありません。

解説：複数あっても最初だけを返すため一件性を保証しません。

Firstは二件以上でも先頭を返して正常終了します。最初を欲しいのか、必ず唯一の一件を欲しいのかという要件が違います。

Q5. OrderBy(...).Take(10)について正しいのは？
解説：内部の保持や処理コストがなくなるわけではありません。

返す件数が10でも、順位を決めるための入力確認や内部保持は必要です。出力サイズと処理に必要な資源を同じに見積もりません。

解説：通常は元Listそのものを更新する操作ではありません。

OrderByは並べ替えた列を提供し、通常のList.Sortのように元List自体を変更しません。結果をどう保存するかも別に選びます。

正解：遅延実行と、全体を必要とする処理かは別の性質です。

後ろに最小の値がある可能性があるので、先頭10件だけでは全体の上位を決められません。遅延で始める性質と、入力全体を必要とする性質は両立します。

解説：最後の結果が10件でも並べ替えの入力は別です。

例えば最後の11件目が最安なら、それも上位10件へ入る候補です。Takeの出力件数から元データの読み取り件数を推測しないでください。
